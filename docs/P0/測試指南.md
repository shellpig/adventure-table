# P0 — 測試指南

> Phase：**P0 — Character Core + SRD / Rules Foundation**  
> 本文件定義 P0 如何驗收。測試要證明 `實作規格.md` 的 AC-P0-01 ～ AC-P0-10，而不是只證明「頁面打得開」。

最後更新：2026-08-29

---

## 1. 測試原則

P0 測試分五層：

1. **SRD Content Validation** — reference data 是否完整、合法、可引用。
2. **Rules Unit Tests** — D&D 角色衍生計算是否正確。
3. **Persistence / API Tests** — Character Build / State 是否正確保存與讀回。
4. **Frontend Tests** — 三頁 Character Sheet 是否正確呈現 Server DTO。
5. **Playwright E2E** — 真實瀏覽器操作、保存、重載是否成立。

測試 fixture 必須固定、可重現，不依賴人工先去 DB 改資料。

標準 fixture 保持**無 Numeric Override**；Override 測試一律由標準 fixture 建立固定 variant，避免把正常規則與非標準數值混在同一份基準資料。

## 2. P0 標準驗證角色

P0 使用固定 fixture：

> **Human Fighter 5 / Wizard 5，Character Level 10**  
> Class order：Fighter 1→5，再 Wizard 1→5。

### 2.1 Ability Scores

固定 Build Ability Scores：

| Ability | Build Score | Modifier |
|---|---:|---:|
| STR | 16 | +3 |
| DEX | 14 | +2 |
| CON | 14 | +2 |
| INT | 16 | +3 |
| WIS | 10 | +0 |
| CHA | 8 | -1 |

這些是**永久 Build 效果已解析後、Numeric Override 前**的值。Human racial ability increase 已包含在上表；Rules Engine 不得再因 `race_ref = human` 額外加一次 +1。

Starting Class：Fighter。

至少包含：

- Saving Throw proficiency：STR、CON。
- Skill proficiency：Athletics、Arcana、Perception。
- Fighter / Wizard features references。
- Wizard Spellbook entries 存於 Build。
- 至少數個 Wizard Prepared Spells 存於 Current State，且必須指向可準備的 Build spell access entry。
- Spell Slot current state。
- Build starting equipment 初始化資料。
- Live Inventory State：Chain Mail、Shield、Longsword、Healing Potion ×2。
- Current HP 初始設為 Max HP。
- Temporary HP 初始 0。
- 初始無 Condition。

### 2.2 Hit Dice

Build total：

```text
d10 × 5  # Fighter 5
d6  × 5  # Wizard 5
```

Initial Current State：

```text
d10 available 5 / total 5
d6  available 5 / total 5
```

Character Sheet 必須依骰型分列，不能合成模糊的「10 Hit Dice」。

### 2.3 HP Progression

這隻 fixture 明確使用 5e fixed value 作為各級實際採用的 base HP gain：

```text
Character Lv1  Fighter: 10
Character Lv2  Fighter: 6
Character Lv3  Fighter: 6
Character Lv4  Fighter: 6
Character Lv5  Fighter: 6
Character Lv6  Wizard:  4
Character Lv7  Wizard:  4
Character Lv8  Wizard:  4
Character Lv9  Wizard:  4
Character Lv10 Wizard:  4
```

這是**fixture choice**，不是「Adventure Table 所有角色都只能 fixed HP」的產品規則。未來 rolled HP 只要把實際採用的 base HP gain 保存進 Build 即可。

固定 Max HP expectation：

```text
Base HP:
10 + 6 + 6 + 6 + 6 + 4 + 4 + 4 + 4 + 4 = 54

CON contribution:
+2 × Character Level 10 = 20

Max HP = 54 + 20 = 74
```

因此標準 fixture 的 Max HP 預期為 **74**。

### 2.4 固定 Derived Expectations

依上面 fixture，至少驗證：

| 項目 | 預期 |
|---|---:|
| Total Character Level | 10 |
| Fighter Level | 5 |
| Wizard Level | 5 |
| Proficiency Bonus | +4 |
| STR Save | +7 |
| CON Save | +6 |
| Athletics | +7 |
| Arcana | +7 |
| Perception | +4 |
| Passive Perception | 14 |
| AC（Chain Mail + Shield） | 18 |
| Wizard Spell Save DC | 15 |
| Wizard Spell Attack | +7 |
| Max HP | 74 |

### 2.5 P0 Multiclass Spellcasting 邊界

Fighter（非 Eldritch Knight）5 對 multiclass caster level 貢獻 0，因此這隻角色的 slots 不會測到「多個 caster class 合併 caster level」的規則。

P0 刻意只驗：

- Multiclass data representation。
- Class acquisition order。
- Spell source / access representation。
- Build Spellbook 與 Current State Prepared selection 分離。

**Multiclass caster-level / combined spell-slot progression 明確留 P1，不得把 AC-P0-08 解讀成已驗過這條規則。**

## 3. SRD Content Validation

對應：AC-P0-01、AC-P0-02。

### 3.1 Manifest / Required Categories

測試必須確認 P0 規格要求的主要 category 都存在並可載入：

- races
- classes
- subclasses
- backgrounds
- feats（若 SRD source 有）
- skills / abilities / saves reference
- equipment / weapons / armor / adventuring gear
- spells
- conditions
- monsters
- damage types
- languages

不要只測「檔案存在」；至少要 parse 成對應 Pydantic model。

### 3.2 Stable Key Uniqueness

每個 reference category：

- key 不可重複。
- key 不可空白。
- Character fixture 使用的 key 必須存在。

### 3.3 Cross-reference Validation

至少驗證：

- Class / Subclass reference 可解析。
- Spell source / class reference 可解析。
- Equipment property / damage type 等必要 reference 可解析。
- Monster 使用的 damage type / condition 等 reference 不出現 dangling key（若 schema 有此引用）。

### 3.4 Negative Cases

測試故意注入：

- duplicate key
- missing required field
- dangling content reference
- invalid enum / malformed value

預期：ContentRegistry validation fail，不能靜默略過。

## 4. Rules Unit Tests — pytest

對應：AC-P0-05、AC-P0-08。

### 4.1 Ability Modifier

至少測：

```text
8  -> -1
10 -> 0
14 -> +2
16 -> +3
18 -> +4
```

另外必須驗證 fixture 的 Human racial bonus **不會在 Rules Engine 再套一次**。

### 4.2 Proficiency Bonus

每個區間的下界與上界成對測，避免 off-by-one：

```text
Lv1  -> +2
Lv4  -> +2

Lv5  -> +3
Lv8  -> +3

Lv9  -> +4
Lv12 -> +4

Lv13 -> +5
Lv16 -> +5

Lv17 -> +6
Lv20 -> +6
```

標準 fixture Lv10 必須是 +4。

### 4.3 Skill / Save

標準 fixture：

- Athletics = STR + PB = +7。
- Arcana = INT + PB = +7。
- Perception = WIS + PB = +4。
- STR Save = +7。
- CON Save = +6。
- 未 proficiency 的 DEX Save = +2。

### 4.4 Passive Perception

標準 fixture：

```text
10 + Perception modifier 4 = 14
```

### 4.5 Armor Class

標準 fixture live Inventory：

```text
Chain Mail equipped 16
+ Shield equipped 2
= AC 18
```

確認：

- Heavy Armor 不錯誤加入 DEX modifier。
- AC 計算讀 Current State 中的 equipped Inventory，不讀 Build starting equipment。
- 若 Shield `equipped: true → false`，正常 calculated AC 應變成 16，Build Version 不變。

### 4.6 Spellcasting

標準 fixture Wizard INT 16、PB +4：

```text
Spell Save DC = 8 + 4 + 3 = 15
Spell Attack = 4 + 3 = +7
```

Prepared selection 不得影響 Spell Save DC / Spell Attack 的基礎公式。

### 4.7 Max HP

標準 fixture固定 expected = 74。

至少再測一次 CON 相關重算，證明不是把 74 當常數寫死。例如建立 rules-only variant，讓 effective CON modifier 從 +2 變 +3，若無 Max HP override：

```text
Base HP 54 + (3 × 10) = 84
```

### 4.8 Numeric Override Variant

由標準 fixture 建立固定 variant：

```text
ability:strength = 18
ac = 19
max_hp = 80
```

固定 expectation：

| 項目 | 預期 |
|---|---:|
| Effective STR | 18 |
| STR Modifier | +4 |
| Athletics | +8 |
| STR Save | +8 |
| AC | 19 |
| Max HP | 80 |

另外驗證：

- 標準 fixture 無 override 時仍使用正常 derived value。
- AC override 在正常 Armor calculation 後成為 authoritative AC。
- Max HP override 後，Current HP validation 使用 80 作為 Max HP。
- Current HP = 80 合法；超過規格允許範圍的值應依 CharacterState validation 明確拒絕或依正式 HP state 規則處理，不可因底層 calculated 74 而誤判。
- Override 不應改動 Race / Class / Feature / Spell access / Starting Equipment 等結構資料。

## 5. Character Schema / Multiclass Tests

對應：AC-P0-03、AC-P0-04、AC-P0-08。

### 5.1 Class Order

標準 fixture 必須保存：

```text
Fighter
Fighter
Fighter
Fighter
Fighter
Wizard
Wizard
Wizard
Wizard
Wizard
```

測試 derive：

- starting class = Fighter
- Fighter level = 5
- Wizard level = 5
- total = 10

### 5.2 Ability Score Round-trip

標準 fixture Save / Reload 後 Ability Scores 必須仍是：

```text
16 / 14 / 14 / 16 / 10 / 8
```

不得因 Reload、Sheet calculation 或重新解析 `race_ref` 而變成 17 / 15 / 15 / 17 / 11 / 9。

### 5.3 Spell Access vs Prepared State

Build spell access entry 至少能辨識：

- logical `entry_id`
- spell key
- source class / feature
- Build access type，例如 `spellbook`

Current State 另外保存 prepared spell entry ids。

至少測：

1. Wizard spellbook entry 存於 Build。
2. 該 spell 可出現在 State `prepared_spell_entry_ids`。
3. 把某個 spell prepared → unprepared、另一個 unprepared → prepared，只改 State。
4. Build payload 與 Build Version id 完全不變。
5. State 引用不存在或不可準備的 Build spell entry 時，validation 明確失敗。

P0 不要求驗證完整 Wizard progression legality，也不驗證 multiclass caster aggregation，但 schema 不能丟掉 spell source 資訊。

### 5.4 Hit Dice Structure

標準 fixture derive：

```text
Fighter 5 -> d10 total 5
Wizard 5  -> d6 total 5
```

State initial available：

```text
d10 = 5
d6 = 5
```

修改 `d10 available 5 → 4` 後：

- Sheet 顯示 `d10 4/5`、`d6 5/5`。
- Build class progression 不變。
- Reload 後狀態保留。

### 5.5 Optional Roleplay

Roleplay profile 全空時：

- schema 合法。
- Character Sheet 可正常 render。

有資料時可正確 round-trip。

## 6. Persistence Tests — pytest

對應：AC-P0-03、AC-P0-04、AC-P0-07。

### 6.1 Save / Reload

流程：

```text
Seed fixture
↓
Read character
↓
Serialize Build + State
↓
Close transaction/session
↓
Read again
↓
Compare
```

結果：

- Build 完整相同。
- State 完整相同。
- Derived result 相同。

### 6.2 Build / State Isolation

先記錄 current Build Version id 與 canonical build payload。

依序修改：

- current HP
- temporary HP
- Prepared Spells
- Condition
- spell resource usage
- available Hit Dice
- Healing Potion quantity
- Shield equipped state
- 新增一個合法 live Inventory entry
- 移除一個 live Inventory entry

每次或整組操作後再讀回 Build。

預期：

- Build Version id 不變。
- Build payload byte-for-byte / canonical-object equivalent 不變。
- State 正確改變。
- 需要 derived recalculation 的項目，例如 Shield equipped state，Sheet 反映新的 authoritative result。

### 6.3 Starting Equipment 不覆寫 Live Inventory

流程：

```text
Seed from Build starting equipment
↓
Live Inventory 產生
↓
修改／新增／移除 live Inventory
↓
Save + Reload + new application session
```

預期：Reload 後仍以最後保存的 Inventory State 為準，不可再次從 Build starting equipment 初始化並把玩家後來取得／丟失的物品洗掉。

### 6.4 Server Restart Persistence

Integration test 至少模擬新的 application / DB session，不能只測同一 ORM object 還在 memory。

## 7. API Tests — pytest / FastAPI Test Client

### 7.1 Reference Content

測：

```text
GET /api/rules/content/spells
GET /api/rules/content/spells/{fireball-key}
GET /api/rules/content/classes/{fighter-key}
```

預期：

- known key → 200 + valid DTO
- unknown key → 404 + machine-readable error code

### 7.2 Character Sheet

```text
GET /api/characters/{fixture-id}/sheet
```

驗證 Header 與三頁所需欄位完整，包括：

- Hit Dice `d10 5/5`、`d6 5/5`。
- Spellbook / Prepared 狀態可區分。
- Inventory 來自 Current State。

### 7.3 State Patch

至少測：

```text
PATCH HP
PATCH temporary HP
PATCH prepared spells
PATCH condition list
PATCH resource usage
PATCH available hit dice
PATCH inventory quantity
PATCH inventory equipped state
PATCH inventory add/remove entry
```

每次 patch：

- request validation 正常。
- DB state 改變。
- Build Version / payload 不變。
- 後續 GET sheet 反映新值。

### 7.4 Invalid State

至少測：

- negative inventory quantity
- malformed condition key
- prepared spell 指向不存在／不合法的 Build spell entry
- available Hit Dice 超出該骰型 Build total
- malformed inventory item reference
- wrong data type

預期 4xx，且資料庫不得留下半套更新。

## 9. Playwright E2E

對應：AC-P0-06、AC-P0-07、AC-P0-09、AC-P0-10。

### E2E-P0-01 — Character Sheet 基本流程

```text
啟動 app
↓
開啟 Fighter 5 / Wizard 5 fixture
↓
看到 Header
↓
切換 Attributes / Skills
↓
看到 d10 5/5、d6 5/5
↓
切換 Spells
↓
可區分 Spellbook / Prepared
↓
切換 Inventory
```

驗證預期主要數值。

### E2E-P0-02 — Current HP Persistence

```text
HP 74 → 50
↓
保存成功
↓
reload browser
↓
仍為 50
```

### E2E-P0-03 — Temporary HP / Condition

```text
Temp HP 0 → 8
加入 Poisoned
↓
reload
↓
Header / Page 1 仍正確顯示
```

### E2E-P0-04 — Spell Resource

改變 spell slot 使用狀態，reload 後保持。

Prepared Spells 的 Build/State isolation 主要由 schema / persistence / API tests 驗證；P0 不為了這條測試額外要求完整「準備法術」互動流程。

### E2E-P0-05 — Inventory Quantity

Healing Potion ×2 → ×1，reload 後保持；Character Build Version 與 starting equipment 不變。

### E2E-P0-06 — Optional Roleplay

使用一名 Roleplay profile 全空的 fixture 或變體；Page 1 不報錯、不顯示強制填寫訊息。

### E2E-P0-07 — P0 Independence

P0 UI 在沒有 Room / Campaign / Session / Combat / AI 連線的情況下可完整操作 Character Sheet。

## 11. 人工驗收

自動測試全綠後，人工快速檢查：

1. Character Sheet 三頁閱讀性。
2. 繁體中文 UI 文案正常；Action / Spell Slot 等規則關鍵字保留英文。
3. Fighter / Wizard features 與 spells 沒有明顯被混在錯誤頁面。
4. HP / Conditions 在 Header 一眼可見。
5. Hit Dice 能清楚分辨 `d10 available/total` 與 `d6 available/total`。
6. Spellbook / Prepared 狀態不會被顯示成同一概念。
7. Inventory 顯示 live state，不會因 reload 回到 starting equipment。
8. Roleplay 空白不造成大片空洞或必填提示。
9. 重新整理後沒有短暫顯示錯誤 authoritative state 再跳回正確值的明顯 UX 問題。

P0 不需要人工驗收 Room、AI、Combat、Map。

## 13. P0 關門條件

P0 可以標記完成前：

- SRD validation 全綠。
- pytest 全綠。
- Vitest 全綠。
- Playwright P0 suite 全綠。
