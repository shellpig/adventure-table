## 3. SRD 5.1 Content Layer

### 3.1 Source of Truth

P0 採：

> **Version-controlled normalized data files = SRD reference content 的 Source of Truth。**

P0 不需要為了 static SRD reference data 額外做一份可手動編輯的 DB truth。

資料放在：

```text
data/srd5.1/
```

建議依類別拆檔或拆資料夾，例如：

```text
data/srd5.1/
├─ manifest.json
├─ races.json
├─ classes.json
├─ subclasses.json
├─ backgrounds.json
├─ feats.json
├─ skills.json
├─ equipment.json
├─ spells.json
├─ conditions.json
├─ monsters.json
├─ damage-types.json
├─ languages.json
└─ ...
```

如果某類資料太大，可再拆成多檔，但不要為了形式一致硬塞單檔。

### 3.2 Stable Content Key

每個 reference entry 必須有不依賴顯示名稱的 stable key。

建議形式：

```text
srd5.1:spell:fireball
srd5.1:class:fighter
srd5.1:equipment:chain-mail
```

Character 只保存 stable content key，不複製整份 SRD definition。

顯示名稱可改，stable key 不應因此改變。

### 3.3 Content Schema

各類 reference content 使用 Pydantic model 驗證。

共同欄位至少包含：

```text
key
name
source
ruleset
```

其他欄位依資料類型定義。

不要設計一個「萬能巨大 SRD schema」硬吃所有類別。

### 3.4 Content Registry

Server 啟動時：

```text
Read manifest
↓
Load data files
↓
Pydantic validation
↓
Cross-reference validation
↓
Build ContentRegistry
↓
Application ready
```

若 mandatory content schema / reference 錯誤：

> **啟動失敗。**

不要靜默 skip。

P0 先讓 static reference data 由 `ContentRegistry` 提供查詢即可；若未來真的需要 DB indexing，再在需要的 Phase 增加，不在 P0 多做一份同步系統。

## 4. Character Persistence Model

P0 要支援下一個 Phase 的 Builder，因此直接把「角色 identity」「immutable Build Version」「mutable Current State」分開。

### 4.1 `characters`

負責角色 identity 與目前 Build Version 指標。

概念欄位：

```text
id
name
ruleset
current_version_id
created_at
updated_at
```

P0 使用 UUID 作為 DB entity id，避免之後 import / copy 時依賴自增流水號。

這只是 DB entity id；SRD reference 仍使用 stable content key。

### 4.2 `character_versions`

保存角色 **Build snapshot**。

概念欄位：

```text
id
character_id
version_no
build_payload JSONB
created_at
```

原則：

- Character Version 就是 Build Version；**不包含 live Current State**。
- 一旦建立，舊 version 不原地修改。
- P0 只需要 version 1 與讀取 current version。
- P1 才實作正式 Level Up / Version History workflow。
- Current HP、Prepared Spells、Spell Slot 使用量、Available Hit Dice、live Inventory、Conditions 等不因建立新 Build Version 而被凍進 snapshot。

`build_payload` 必須通過 Pydantic `CharacterBuild` schema。

P0 採 JSONB snapshot 的理由：

- Build choice 結構會在 P1 快速演進。
- Immutable version 天然適合 snapshot。
- 避免 P0 先拆出大量尚未證明必要的 join tables。

如果 P1 後證明某些欄位需要 relational query，再針對真正需求 migration。

### 4.3 `character_states`

保存 mutable Current State。

概念欄位：

```text
character_id
state_payload JSONB
updated_at
```

`state_payload` 必須通過 Pydantic `CharacterState` schema。

至少表示：

- current_hp
- temporary_hp
- conditions / temporary_effects
- prepared_spell_entry_ids
- resource_usage
- hit_dice_state
- inventory_state

Build 與 State 不可共用同一 payload。

### 4.4 Character DTO

API 對外不要直接 serialize SQLAlchemy model。

至少區分：

```text
CharacterBuild
CharacterState
CharacterSheetDTO
```

`CharacterSheetDTO` 是 Server 計算後給前端顯示的 read model。

## 5. CharacterBuild P0 Schema 原則

P0 不必完整實作 P1 progression validator，但 schema 必須能表示：

```text
identity/basic profile
race_ref
class_progression[]
ability_scores
proficiencies
saving_throw_proficiencies
skill_choices
feature_refs[]
feat_refs[]
spell_access_entries[]
hp_progression[]
starting_equipment[]
roleplay_profile
numeric_overrides
```

`starting_equipment[]` 只記錄 Build 的起始裝備選擇／初始化來源。角色建立後，真正目前持有什麼 Item 只看 `CharacterState.inventory_state`，不可拿 starting equipment 反覆覆蓋 live Inventory。

### 5.1 Class Progression

不要只存：

```text
fighter = 5
wizard = 5
```

至少能保留 level acquisition order，例如：

```text
[
  fighter,
  fighter,
  fighter,
  fighter,
  fighter,
  wizard,
  wizard,
  wizard,
  wizard,
  wizard
]
```

Server 可由此 derive：

- total character level
- per-class level
- starting class

這是 P1 立即需要的資料，不屬於過度預留。

### 5.2 Ability Score Semantics

`CharacterBuild.ability_scores` 保存的是：

> **永久 Build 選擇全部解析後、但尚未套用 Numeric Override 的 resolved Build Score。**

因此 Human racial bonus、ASI、Feat 等若已屬於這個 Build，必須已反映在保存值中；Rules Engine 不可讀到 `race_ref = human` 後又額外再加一次 +1。

例如標準 fixture：

```text
STR = 16
DEX = 14
CON = 14
INT = 16
WIS = 10
CHA = 8
```

這些就是 Character Sheet 正常計算前的 Build Score，不是「套種族前」的 raw allocation。

計算時：

```text
Build Score
↓
Ability Numeric Override（optional）
↓
Effective Score
↓
Modifier / Skill / Save / Spell / HP calculation
```

### 5.3 Spell Access

Build 的 spell entry 保存角色**長期擁有的 spell access**，不保存每天可改的 Prepared selection。

P0 建議每個 spell access entry 至少有：

```text
entry_id
spell_key
source_type
source_key
access_type
```

`entry_id` 是 Character Build 內的 logical stable id；P1 建立新 Build Version 時，未改變的既有 spell access entry 應保留或可被 reconcile，避免 Current State 無法對應。

P0 已知的 Build `access_type` 可包含：

```text
known
spellbook
always_prepared
granted
```

**不得使用 `prepared` 作為 Build access type。**

一般 Prepared Spells 屬於 `CharacterState.prepared_spell_entry_ids[]`，指向目前 Build 中可被準備的 spell access entry。Always-prepared / Granted 若規則上永遠準備，不需要塞進每日 prepared selection 才生效。

P0 標準 fixture 只需要完整支援 Wizard spellbook + prepared state。Cleric / Druid 類「從整份 class spell list 準備」的完整資料表示與 progression validation 可在 P1 按實際 Builder 需求擴充，不在 P0 預先做大型 abstraction。

### 5.4 HP Progression

Max HP 必須能從 Build deterministic 重算，而不是只把測試答案 74 硬存成一般值。

P0 `hp_progression[]` 至少保存每個 Character Level 實際採用的 **base HP gain**，順序與 `class_progression[]` 對齊。

標準 fixture：

```text
class_progression:
Fighter, Fighter, Fighter, Fighter, Fighter,
Wizard, Wizard, Wizard, Wizard, Wizard

hp_progression:
10, 6, 6, 6, 6,
4, 4, 4, 4, 4
```

這代表該 fixture 選擇 5e fixed value；不是全產品限制。P1 若允許 rolled HP，只保存該級實際 roll 後採用的 base HP gain 即可。

P0 Max HP 基本計算：

```text
sum(base_hp_gain)
+ effective CON modifier × total character level
↓
其他已支援的 structured modifier（若有）
↓
Max HP Numeric Override（若有，最後套用）
```

永久 CON 改變後要能對所有既有 Character Levels 正確反映 Max HP 變化。

### 5.5 Numeric Override

Numeric override 放在 Build，Server calculation pipeline 最後依目標值套用。

例如：

```text
ability:<ability-key>
ac
max_hp
skill_modifier:<skill-key>
spell_save_dc:<source-key>
```

實際 key 集合由 P0 規則層明確定義；不要允許任意 raw DB field override。

## 6. CharacterState P0 Schema 原則

### 6.1 HP

至少：

```text
current_hp
temporary_hp
```

Max HP 由 Build + Rules 計算，若有 Numeric Override 使用 override 結果。

### 6.2 Conditions / Temporary Effects

至少保存：

```text
condition_ref
display/source note（optional）
```

P0 只需要保存與顯示；完整 condition gameplay automation 屬 P4。

### 6.3 Prepared Spells / Resource Usage

Prepared Spells 與消耗型資源都屬 Current State。

至少能表示：

```text
prepared_spell_entry_ids[]
spell_slots_used / remaining
class-specific resource usage（若 fixture 需要）
hit_dice usage
```

Prepared selection 改變時只更新 State，不建立 Character Version。

P0 不必把所有 class resource 都自動化；schema 可有 typed generic resource state，實際引用必須有 stable source key。

### 6.4 Hit Dice State

Build 可由 class progression 得到 Hit Dice 的**總數與骰型**；State 保存每種骰型目前可用數量。

標準 fixture：

```text
d10: available 5 / total 5
d6:  available 5 / total 5
```

State 不需要複製 total 作為另一份 truth；`CharacterSheetDTO` 可把 Build total 與 State available 組合成顯示資料。若實作為方便同時回傳 total，也必須以 Build derive 結果為 authoritative。

### 6.5 Inventory State

**整份 live Inventory 都住 Current State。**

每個 live inventory entry 至少能表示：

```text
entry_id
item_ref
quantity
equipped
```

需要時可再有 P0 真正使用到的 carried / note 等欄位，但不要先做 Shop / Loot / Container subsystem。

關鍵規則：

- `item_ref` 只需要存在於 live inventory entry；不需要在 Build 再維護一份「目前持有物品」清單。
- Character 建立／seed 時可由 Build `starting_equipment[]` 產生第一次 `inventory_state`。
- 初始化完成後，Starting Equipment 不再自動同步 live Inventory。
- 撿到新劍、丟掉物品、消耗 Potion、Equip / Unequip 都只修改 State。
- 這些動作不得產生新的 Build Version。

Armor Class 等需要裝備狀態的規則計算，應讀取 `CharacterState.inventory_state` 中目前 equipped 的 Armor / Shield，而不是讀 Build starting equipment。

## 7. Rules / Calculation Layer

Rules Engine 必須是純 Python domain logic，不依賴 FastAPI request object、SQLAlchemy session 或 React。

建議：

```text
app/domain/rules/
├─ abilities.py
├─ proficiency.py
├─ skills.py
├─ saves.py
├─ armor_class.py
├─ hit_points.py
├─ spellcasting.py
└─ character_sheet.py
```

P0 計算流程：

```text
CharacterBuild
+ CharacterState
+ ContentRegistry
↓
Resolve effective Ability Scores
↓
Rules Calculation
↓
Apply remaining Numeric Overrides
↓
CharacterSheetDTO
```

其中至少遵守：

- Ability / Skill / Save / Spell calculation 使用 override 後的 effective Ability Score。
- AC 使用 live Inventory 中目前 equipped Armor / Shield，再套 AC override。
- Max HP 使用 `hp_progression[]` + effective CON modifier，再套 Max HP override。
- Hit Dice total 由 Build / class progression derive；available 由 State 取得。
- Prepared 狀態由 State 取得，不把 Build Spellbook entry 自動當成 prepared。

Server 是 authoritative calculation source。

Frontend 不重新實作同一套 D&D 計算。

## 8. P0 API

P0 只做 Character / Reference Content 所需 API。

### 8.1 Reference Content

建議：

```text
GET /api/rules/content/{category}
GET /api/rules/content/{category}/{key}
```

第一個 endpoint 可提供基礎 filter / search query，但不要在 P0 做大型 search service。

### 8.2 Character

建議：

```text
GET   /api/characters/{character_id}
GET   /api/characters/{character_id}/sheet
PATCH /api/characters/{character_id}/state
```

`PATCH /state` 至少能承載 P0 驗收需要的 Current State 變化：HP、Temp HP、Prepared Spells、Conditions、resource usage、Available Hit Dice、live Inventory entries / quantity / equipped state。

P0 不做正式 Builder API。

測試 fixture / seed 角色透過 developer seed command 建立，不需要暴露 production `POST /characters` workflow。

例如：

```text
python -m app.scripts.seed_p0_fighter_wizard
```

### 8.3 Error Contract

Backend 回傳 machine-readable error code + readable message。

不要讓 frontend 依英文 error string 判斷流程。

P0 不需要先導入完整 i18n framework。

## 9. Frontend Character Sheet

### 9.1 Route

P0 至少提供：

```text
/characters/:characterId
```

### 9.2 Layout

固定：

```text
Character Header
├─ Name
├─ Level
├─ HP
├─ AC
└─ Conditions

Tabs / Pages
├─ Attributes / Skills
│  └─ Hit Dice by die type
├─ Spells
└─ Inventory
```

Page 2 要能分辨 Build spell access（Known / Spellbook / Always-prepared）與 Current State Prepared selection。

Page 3 顯示 `CharacterState.inventory_state` 的 live Inventory，不從 Build starting equipment 重新產生畫面。

### 9.3 Data Flow

```text
React page
↓
TanStack Query
↓
GET /api/characters/{id}/sheet
↓
CharacterSheetDTO
```

修改 current state：

```text
UI action
↓
PATCH state
↓
Server validates + persists
↓
refetch / invalidate
↓
UI 顯示 authoritative result
```

不要做 optimistic mutation 來假裝正式 HP / resource / inventory state 已成功；P0 先採 server-confirmed update。

P0 不要求做完整「準備法術 Wizard」或「Short Rest 花 Hit Die」UX；Prepared Spells 與 Hit Dice state 的資料模型、API persistence、Sheet display 必須正確即可。完整 workflow 可在對應後續 Phase 補上。

## 10. P0 Seed / Fixture

P0 必須有一隻固定的複雜驗證角色：

> **Human Fighter 5 / Wizard 5，Character Level 10**

標準 fixture 必須保持**無 Numeric Override**，方便先證明正常規則計算。

Fixture 必須包含：

- Resolved Build Ability Scores：STR 16 / DEX 14 / CON 14 / INT 16 / WIS 10 / CHA 8；Human racial ability increase 已包含在這些值中，Rules Engine 不可再加一次。
- Fighter → Wizard 的 class acquisition order。
- HP progression：`10, 6, 6, 6, 6, 4, 4, 4, 4, 4`。
- Fighter / Wizard features references。
- Wizard Spellbook access entries 放 Build。
- 至少數個 Wizard prepared entries 放 Current State。
- Spell Slot current state。
- Hit Dice total：5d10 + 5d6；initial available：5d10 + 5d6。
- Build starting equipment 初始化資料。
- Live Inventory State：至少 Chain Mail、Shield、Longsword、Healing Potion ×2。
- 至少一個 Condition 測試案例可由測試套用。

不要要求使用者在 P0 UI 手動建立這隻角色。

Fixture 是 P0 / P1 contract test 的共同基準。

### 10.1 Numeric Override Variant

不要污染標準 fixture；測試時由標準 fixture 建立固定 override variant，例如：

```text
ability:strength = 18
ac = 19
max_hp = 80
```

至少驗證：

- Effective STR = 18，STR modifier = +4。
- Athletics = +8。
- STR Save = +8。
- AC = 19。
- Max HP = 80。
- Race / Class / Feature / Spell access 等 Build structure 不因 override 改變。

### 10.2 P0 Multiclass Spellcasting 邊界

Fighter（非 Eldritch Knight）5 / Wizard 5 的 spell slot progression 等同 Wizard 5，**不會觸發多個 caster class 的 caster-level aggregation**。

因此 P0 fixture 只證明：

- Multiclass data 可表示。
- Class order 可保留。
- Spell source / access / prepared state 可分離。

不把「multiclass caster-level / combined spell-slot progression」視為 P0 已驗證能力；完整規則留 P1。

## 13. P0 Implementation Order

