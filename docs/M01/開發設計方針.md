> Phase：**M01 — Multi-Source Character Content Expansion**  
> 類型：**M Phase（Modification / Maintenance Phase）**  
> 本文件是 M01 的具體實作契約。M01 必須建立在 P0/P1 已完成的 Content / Character / Builder / Rules / Inventory / Versioning 上，不能為非 SRD 內容另做第二套角色系統。

最後更新：2026-08-30


## 2. 現有地基與不可破壞契約

M01 開工時應以當下 `main` 實際 codebase 為準重新核對 API 簽名，但目前已知核心地基包括：

```text
data/srd5.1/
data/rules/dnd5e-2014/character-builder.json

apps/server/app/content/
├─ registry.py
└─ schemas.py

apps/server/app/domain/character/
├─ schemas.py
└─ ...

apps/server/app/domain/character_builder/
├─ schemas.py
├─ compiler / resolver / validation...
└─ ...

apps/server/app/domain/rules/
apps/server/app/persistence/
apps/server/app/api/

apps/web/src/features/character-builder/
apps/web/src/features/character-sheet/
```

現有重要契約：

- `CharacterBuild` 是 immutable versioned snapshot。
- `CharacterState` 是 mutable live state。
- Builder Draft 保存輸入／選擇，不是假 `CharacterBuild`。
- Builder choices 由 server authoritative logic 產生。
- Frontend 不複製 D&D progression engine。
- Starting Equipment 只在 Create Confirm 初始化一次 live Inventory。
- Level Up 不重建 live Inventory。
- Prepared spell eligibility 屬 Build；daily prepared selection 屬 State。
- Version History 必須保留舊 Build，不做 in-place rewrite。

M01 的所有修改都要延續這些邊界。

# M01-A — Multi-Source Content Pack Foundation

## 目標架構

目前 `ContentRegistry` 與 `ContentEntry` envelope 的 `source` / key regex / manifest metadata 偏向 `srd5.1` 專用。M01-A 將它泛化為：

```text
ContentRegistry
├─ ContentPack: srd5.1
├─ ContentPack: phb2014
├─ ContentPack: scag
├─ ContentPack: vgm
├─ ContentPack: vrgr
├─ ContentPack: tce
└─ ContentPack: gos
```

Registry 對外仍提供單一 lookup / search surface，不讓 caller 自己遍歷資料夾。

## Content Pack directory

建議正式資料：

```text
data/
├─ srd5.1/
│  ├─ manifest.json
│  └─ ...
├─ phb2014/
│  ├─ manifest.json
│  └─ ...
├─ scag/
├─ vgm/
├─ vrgr/
├─ tce/
└─ gos/
```

不要把非 SRD 內容塞進 `data/srd5.1/`。

若現有 loader 以單一 `DEFAULT_CONTENT_ROOT` 為起點，M01-A 應升級為「content roots / pack discovery」概念。可採：

```text
DEFAULT_CONTENT_ROOT = data/
↓
scan known child pack manifests
↓
validate manifest
↓
register pack
↓
load declared categories
```

或等價且更符合現有 codebase 的 explicit pack list。重點是：caller 不再假設只有一個 `manifest.json`。

## StableKey schema

正式格式：

```text
<pack_id>:<kind>:<index>
```

建議 validator：

```text
pack_id: [a-z0-9][a-z0-9.-]*
kind:    [a-z0-9][a-z0-9-]*
index:   [a-z0-9][a-z0-9-]*
```

`require_stable_key()` 不再檢查第一段等於 `srd5.1`，而是：

1. syntax 合法。
2. 需要 registry context 時，pack 存在。
3. 需要 content lookup 時，完整 key 存在。

Schema-level syntax validation 與 registry-level existence validation要分開，避免 Pydantic model 依賴 global registry singleton。

## ContentEntry envelope

將原本類似：

```text
source: Literal["srd5.1"]
ruleset: Literal["dnd5e-2014"]
license: Literal["CC-BY-4.0"]
```

泛化成 pack-driven metadata。

概念：

```text
ContentEntry
├─ key
├─ source            # pack id
├─ ruleset
├─ kind
├─ index
├─ name
├─ data
└─ provenance?       # optional entry-level override/reference
```

`license` 建議以 manifest 為 pack-level default；若某 entry 需要 override 再允許 entry metadata，避免每個 item 複製相同字串。

## Manifest

建議最小 manifest：

```json
{
  "id": "phb2014",
  "ruleset": "dnd5e-2014",
  "display_name": "Player's Handbook 2014",
  "version": "local-1",
  "provenance": {
    "source_type": "user-provided-reference"
  },
  "usage": {
    "visibility": "private-project"
  },
  "categories": [
    {"kind": "background", "file": "backgrounds.json"}
  ]
}
```

實際欄位依現有 manifest model 最小修改，不為 M01 建 publisher/dependency manager。

## Registry indexes

Registry 建議至少維護：

```text
by_key: dict[StableKey, ContentEntry]
by_kind: dict[kind, list[ContentEntry]]
by_pack: dict[pack_id, ContentPack]
```

Search/filter 可組合 `pack_ids` + `kind`。

Duplicate rule：

- 完整 StableKey duplicate：fatal。
- 同 `kind:index` 不同 pack：合法。
- 同 display name：合法。

## Cross-reference validation

新 pack JSON 內所有正式關聯直接寫 StableKey：

```json
{"feature_ref": "phb2014:feature:variant-human-feat"}
```

不要新增 `/api/2014/...` compatibility URL。

SRD importer 若現有資料仍用 legacy URL：

- 允許既有 adapter 繼續轉換。
- adapter 只屬 SRD compatibility layer。
- registry core 不把 URL 當 identity。

## CharacterBuild / Builder source validation

現有 `content_sources` 應由 compiler 產生／驗證。

建議 canonical semantics：

- `content_sources` = Build 中實際引用到的 pack id 集合，排序 deterministic。
- 不要求使用者手填。
- Draft 可有 `enabled_content_sources` 或由 server policy 決定可選 pack。
- compile 時每一個 stable ref 必須屬於允許 pack。
- candidate Build 重新 derive actual `content_sources`，不信任 client 傳回的結果。

如果現有 Draft 已有等價欄位，沿用；不要重複兩個 source lists。

## API / frontend

Reference API 需要支援：

- 多 pack search。
- stable key lookup。
- optional source filter。
- 回傳 source display metadata，供 UI badge 使用。

Frontend selector value 使用 stable key，不使用 display name 或 bare index。

## Migration

若 DB 裡沒有 source enum constraint，可能不需要 schema migration；若有：

- migration 只做必要 constraint generalization。
- 不 rewrite 舊 `build_payload`。
- 不改舊 stable keys。

## M01-A 禁止事項

- 不新增 `lineage_ref`，除非 M01-F 才需要。
- 不做 replacement graph。
- 不做 infusion schema。
- 不做 magic-item effect interpreter。

# M01-B — PHB Character Origins & Background Expansion

## Content pack

建立／擴充：

```text
data/phb2014/
├─ manifest.json
├─ backgrounds.json
├─ subraces.json
├─ race-variants.json      # 若採 kind=race-variant
├─ features.json
└─ ...只放真正需要的 categories
```

不要為了形式建立空 category files。

## Background data model

優先重用 P1 已有 structural choice primitive。

Background entry 應描述 mechanical grants，而不是把自然語言塞進 compiler：

```text
Background
├─ skill_grants[]
├─ tool_grants[] / choices[]
├─ language_grants[] / choices[]
├─ equipment_grants / equipment_choices
├─ feature_refs[]
├─ variant_of? / replacement?  # 只有來源真的需要時
└─ roleplay_tables?             # optional UI data
```

如果目前 SRD background schema 已有類似欄位，M01-B 應擴充該 schema，而不是建立 `PhbBackgroundData` 平行模型。

### Roleplay tables

traits / ideals / bonds / flaws：

- 可存在 content data。
- UI 可提供選擇／隨機參考。
- 不納入 structural validity。
- 未填不 blocking。

## PHB subrace

Wood Elf / Drow / Mountain Dwarf / Stout Halfling / Forest Gnome 應延續現有 base race + subrace composition。

Compiler 不複製母種族全部 grants 到每個 subrace；應：

```text
base race grants
+
selected subrace grants
=
resolved Build grants
```

這能避免 SRD base race 修正時 PHB subrace 漂移。

## Variant Human representation

Variant Human 與普通 subrace 不同。建議建成 `race-variant` 或等價 explicit identity，而不是假裝 `subrace=variant-human`，前提是這不迫使 CharacterBuild 大改。

最小需求：

```text
base race: srd5.1:race:human
variant: phb2014:race-variant:variant-human
```

Variant compile 行為：

1. 以 Human 為 base identity。
2. 替換標準 Human ability package。
3. 建立 two-distinct-ability choice。
4. 建立 one-skill choice。
5. 建立 one-feat choice。
6. 保留未被 variant 取代的 Human grants。

### Two distinct ability choice

不要在 frontend 寫：

```text
if variantHuman then disable selected ability
```

Server choice schema 要能表達：

```text
choose 2 distinct references from ability category
quantity/effect = +1 each
```

如果 P1 `counted_reference` 已能達成，延伸它；若不能，只補最小 distinct-selection constraint。

### Feat choice

Variant Human feat 必須走 P1 現有 feat eligibility / prerequisite resolver。

流程：

```text
Variant grants feat-choice source
↓
Builder emits generic feat choice
↓
existing feat validation
↓
selected feat_ref enters Build
```

不得有第二套 Variant-Human feat validation。

## Background starting equipment

Background equipment 仍走 P1 equipment resolver。

Create Confirm：

```text
starting class equipment
+
background equipment
↓
Build provenance
↓
initial live Inventory once
```

Level Up / reload 不得重建。

## UI

Origin step 建議顯示來源 badge：

```text
Wood Elf     PHB
High Elf     SRD
```

但 selector value 一律 stable key。

Variant Human 的能力／skill／feat choices 應使用現有 generic choice renderer；缺 renderer type 才新增 generic renderer，不建立一整頁特製 UI。

## 真人創角修正 policy

M01-B manual gate 若發現：

- selector 難用。
- choice reload 失效。
- Review 不清楚。
- feature / background grants 錯。
- Variant Human 無法完成。

只要屬 A/B scope，直接在 M01-B 修完並補 regression。

如果發現真正新的大型產品需求，再記錄至後續 Roadmap；不得用「真人測試」當理由無限擴張 M01-B。

# M01-C — SCAG / GoS Background Expansion

## Data packs

建立：

```text
data/scag/
data/gos/
```

只加入此 Subphase 已提供的 Background / supporting feature categories。

## Background reuse

M01-C 的首要工程判準：**能否用 M01-B 同一套 Background schema / choice compiler 表示。**

遇到來源差異時依序：

1. 先看 existing grant / branch / nested choice 是否足夠。
2. 不足時加最小 generic capability。
3. 禁止 `if source == scag` 或 `if background == sailor-variant-x` scattered hardcode。

## Variant background

如果 variant 是：

```text
Base background
- feature A
+ feature B
```

可先採 data-driven replacement metadata：

```text
variant_of
replace_grants[]
add_grants[]
```

但只支援 Background 需要的粒度，不在 M01-C 宣告它就是 M01-E 所有 replacement 的最終抽象。

## Collision

例如來源出現相同 index/name：

```text
phb2014:background:x
scag:background:x
```

兩者可共存。UI 可額外顯示 source；API / Draft / Build 不可只存 `x`。

# M01-D — VGM Race Expansion

## Data

建立：

```text
data/vgm/
├─ manifest.json
├─ races.json
├─ features.json
└─ ...
```

目標 race：Goblin、Hobgoblin、Aasimar。

## Race schema

優先沿用現有 race `data` schema。若 VGM feature 需要：

- level gate。
- limited use capacity。
- ability-based formula。

應在 **feature data** 加通用 metadata，而不是擴一個 `VgmRaceData`。

概念：

```text
FeatureGrant
├─ feature_ref
├─ min_character_level?
├─ resource?
│  ├─ capacity_formula
│  └─ refresh
└─ effect_metadata?
```

具體字段名稱要對齊現有 schemas，不要求照此命名。

## Level-dependent racial grant

Create high-level / Level Up compiler 必須根據 Character Level 重新 resolve eligibility。

如果 racial spell / feature 在 level N 解鎖：

- Build v1 若 target level >= N 應包含該 access。
- Level Up 跨過 N 時 Build vN+1 新增。
- Current State reconciliation 只增加 capacity，不自動恢復既有其他資源。

## Runtime deferred

Combat trigger 只保留 feature identity / mechanical metadata。不要新增 attack pipeline。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## 資料表示

建立 SCAG variant entries，例如概念：

```text
scag:race-variant:half-elf-wood-descent
scag:race-variant:half-elf-drow-descent
...
```

每個 variant 指向：

```text
base_race_ref = srd5.1:race:half-elf
replacement_set_ref / inline replacement declaration
```

## Replacement primitive

M01-E 要正式抽出可重用的最小 primitive。

概念 schema：

```text
GrantReplacement
├─ id
├─ removes[]          # stable grant identities, not display labels
├─ branch
│  ├─ choice_id
│  ├─ min/max
│  └─ options[]
└─ provenance
```

重要：被替換的 target 不能靠 `"Skill Versatility"` 字串比對。需要 deterministic grant identity，例如：

```text
srd5.1:race:half-elf#grant:skill-versatility
```

或現有系統可提供的等價 stable choice/grant id。

## Compiler order

建議：

```text
resolve base race grants
↓
resolve subrace/variant applicability
↓
apply explicit replacement removals
↓
emit replacement choices
↓
resolve selected replacement grants
↓
compile final Build
```

不能先 materialize 最終 feature_refs 再用 name 去刪。

## Draft stale selection

當使用者：

```text
選 Wood descent → Fleet of Foot
↓
改成 Drow descent
```

舊 Wood selection：

- 不得進 Build。
- 可以被清除或留下 inactive warning，依既有 P1 stale branch policy。
- server 必須 deterministic 判斷 active path。

## Frontend

沿用 branch / nested choice renderer。UI 顯示「你將放棄 X，取得 Y」可以由 server view model 提供 resolved summary；frontend 不自己推算 replacement。

# M01-F — VRGR Lineage & Dhampir

## CharacterBuild schema

M01-F 才正式決定 lineage 欄位。建議最小：

```text
lineage_ref: StableKey | null
ancestral_origin_ref: StableKey | null
ancestral_legacy_selections: ...
```

但開工時需先檢查 P1-G 是否已有 lineage metadata 欄位；若已有可直接延伸，禁止重複欄位。

`race_ref` 的語意需要清楚：

方案偏好：

- `race_ref` 保留角色 original/base racial origin（若有）。
- `lineage_ref` 表示 active lineage。
- compiler 的 effective origin grants 由 lineage 規則決定。

如果現有 CharacterBuild 更適合其他方式，仍必須保留「original origin」與「active lineage」可追溯性。

## New-create Dhampir

Direct create：

```text
select Dhampir lineage
↓
no ancestral race required
↓
lineage emits its own fallback skill choice / other grants
```

不要建立假的 ancestral race 只為滿足 schema。

## Transform existing character

透過 P1-G versioned Build Edit / Correction：

```text
Build vN: original race
↓
create edit draft based on vN
↓
select Dhampir lineage
↓
server derives eligible legacy traits
↓
user selects/accepts valid legacy retention
↓
review diff
↓
confirm Build vN+1
```

舊 vN 永不改寫。

## Ancestral Legacy allowlist

Dhampir 只能保留規則允許類別，例如 skill proficiencies / specified movement modes（依正式來源資料）。實作要用 category-aware extraction：

```text
eligible_legacy = filter(original_origin_grants, allowed_legacy_kinds)
```

禁止：

```text
copy all original feature_refs
remove known forbidden names
```

## Movement model

若現有 CharacterBuild 只有單一 `speed`，而 lineage 需要 walk/climb 等多 movement modes，M01-F 應建立最小通用 movement representation，並向後兼容既有 walk speed。

例如 derived model：

```text
movement.walk
movement.climb
movement.swim
movement.fly
```

是否直接改 Build schema 或由 feature derive，開工時依現有 code 決定；不可把 climb speed 塞進文字描述後聲稱支援 Ancestral Legacy。

## Lineage resources

Vampiric Bite 等 limited-use capacity：

- Build：feature + capacity derivation。
- State：used / remaining。
- runtime attack/heal execution若依賴未來 Combat Engine，先不自動執行。

# M01-G — TCE Artificer Core

## Rule config

Artificer class progression應進正式 content / rules config，不散落 Python 常數。

建議：

```text
data/tce/classes.json
\data/tce/subclasses.json
\data/tce/features.json
\data/rules/dnd5e-2014/character-builder.json   # 只有真正跨來源的 class spellcasting/progression config
```

避免把 source-book content 全塞進 `character-builder.json`。

## Slot contribution generalization

現有：

```text
full
half
none
```

不足以表達 Artificer multiclass「half with ceil」。建議泛化：

```json
"slot_contribution": {
  "formula": "half",
  "rounding": "ceil"
}
```

其他 half caster：

```json
"slot_contribution": {
  "formula": "half",
  "rounding": "floor"
}
```

full caster：

```json
"slot_contribution": {
  "formula": "full",
  "rounding": "floor"
}
```

如果需向後兼容舊字串，loader 可 normalize legacy form 成 canonical object，逐步 migration；不要讓 rules engine 同時維護多條計算路徑。

## Prepared formula

將 prepared formula 表示成既有 generic formula schema；如果目前只有 enum：

```text
class_level_plus_ability
half_class_level_plus_ability
```

Artificer 需要的 rounding semantics應顯式化：

```text
level_component = floor(class_level / 2)
+
ability_modifier
minimum = 1
```

不要把 multiclass slot contribution 的 ceil 與 prepared-count 的 floor 混在同一 rounding setting。

## Spell focus requirement

Artificer 施法 focus 的 tool / infused item requirement可先作：

- Character Sheet / spellcasting profile metadata。
- structural data identity。

若真正 cast transaction 尚未存在，不需要 M01-G 建 cast permission runtime。

## Specialist

Subclass identity使用 `tce:subclass:*` stable keys。Subclass selection由 class-level progression data emit，走 P1 existing subclass choice。

## Tool proficiency

Artificer 的 artisan tool choice必須使用 generic tool choice；不存 display string。

## Multiclass tests implication

Rules service 必須能從 ordered class progression compute：

```text
artificer contribution
+
other caster contribution
→ multiclass caster level
→ existing combined slot table
```

Pact Magic繼續獨立 pool。

# M01-H — TCE Artificer Advanced Features & Infusions

## Infusion domain boundary

建議拆：

```text
Build
├─ known_infusions[]
└─ infusion_capacity

Current State / Inventory
└─ active_infusions[]
   ├─ infusion_ref
   └─ inventory_item_id
```

已知 infusion 是角色 build choice；目前灌注哪件物品是 live state。

## Inventory integration

Active infusion assignment必須引用 stable inventory entry id，不複製一份 item。

對 assignment 至少驗證：

- inventory item存在。
- infusion eligibility / item category合適。
- capacity未超過。
- uniqueness restriction正確。

取消 infusion 只改 Current State，不新增 Build version。

## Replicate Magic Item

若 Infusion 可以選 magic item option：

- known infusion choice應引用正式 item / infusion option identity。
- 不把整個 magic item JSON copy 進 Build。

## Feature resource model

建議抽出通用：

```text
FeatureResourceCapacity
├─ source_ref
├─ resource_key
├─ capacity_formula
└─ refresh_period
```

Current State沿用既有 resource counter representation；若目前只服務 spell resources，需要擴成 feature resources，但不要破壞 spell slot invariant。

## Level-up reconciliation

容量 old/new：

```text
used_before = old_capacity - remaining_before
new_remaining = max(new_capacity - used_before, 0)
```

不因 Level Up 自動 full restore。

如果 resource semantics是 tracked `used` 而非 `remaining`，等價保持消耗量。

## Attunement capacity

角色 derived attunement capacity應由：

```text
base capacity
+
class feature override / replacement
```

Artificer 高等 feature若是「capacity becomes N」就不要錯建成 `+N`。

Inventory validation讀 derived result，不查 class name。

## Advanced subclass effects

分類：

1. **Structural**：必須 M01-H 自動化，例如選擇、capacity、proficiency、resource。
2. **Derived numeric**：現有 Rules Layer能自然承接者應接。
3. **Runtime combat/world action**：保存 metadata / description，defer到對應 Phase。

每一個未自動化 feature需在資料或開發註記標明 `manual_runtime` / 等價狀態，避免未來誤認已執行。

# M01-I — TCE Magic Items

## Magic item schema

不要建立第二套 TCE-only item model。擴現有 item/magic item schema。

概念：

```text
MagicItemData
├─ item_type
├─ rarity
├─ attunement
│  ├─ required
│  └─ restrictions[]
├─ charges?
├─ bonuses?
├─ effects[]?
└─ manual_effects[]?
```

## Restriction model

最小可結構化 restriction：

```text
class_ref / class_tag
spellcaster requirement
other feature prerequisite（只有資料真正需要時）
```

不做 arbitrary expression language。

## Effect model

M01-I 只建立現有系統真正會 consume 的 effect types，例如：

- spell attack bonus。
- spell save DC bonus。
- attunement capacity interaction（來源在角色，不是 item）。
- charge capacity。

其餘保留：

```text
manual_effect
```

包含清楚 description / trigger / source identity；不把自然語言 parser 當 engine。

## Inventory item identity

Live Inventory entry應引用 content StableKey：

```text
content_ref = tce:item:...
```

角色自訂 item若現有系統支持，繼續可並存。

## Attunement state

若現有 Inventory 尚無明確 attuned flag/list，M01-I加最小 live state：

```text
attuned: bool
```

或角色 state上的 attuned item IDs。選擇要符合現有 inventory mutation API。

Server mutation時驗證：

- item requires/permits attunement。
- restriction。
- character capacity。

Frontend只顯示 server結果。

## 3. Coding 原則摘要

1. **Stable identity 永遠是完整 StableKey，不是 display name。**
2. **來源差異優先資料化，不優先 class/race name hardcode。**
3. **Build 選擇與 Current State 使用狀態分離。**
4. **新 primitive 在真正需要的 Subphase 才加入。**
5. **Frontend 不計算規則。**
6. **所有新增資料都先 schema / cross-reference validation，再進 Builder。**
7. **舊 SRD Character compatibility 是 hard requirement。**
8. **未自動化 runtime effect 要明確標示 manual/deferred，不假裝完整。**
9. **不為 M01 提前建立 P2/P3/P4 infrastructure。**
10. **每一 Subphase 關門時都必須可執行、可測試、可 commit。**
