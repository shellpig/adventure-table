# M01 — 開發設計方針

> Phase：**M01 — D&D 5e 2014 Private Content Expansion**  
> 本文件定義 M01 的具體實作契約：Content Pack、StableKey、Builder / Character 接線、資料 layout、必要 schema 變更與各 Subphase 的技術邊界。  
> 「完成後必須為真」以 `實作規格.md` 為準；測試證據以 `測試指南.md` 為準。

最後更新：2026-08-30

---

## 1. 現況基線與 M01 必須沿用的架構

M01 開工時，P1 已 closeout。不得重做 Character / Builder core。

目前已存在並必須沿用：

- `data/srd5.1/`：P0 normalized SRD content。
- `apps/server/app/content/schemas.py`：Content envelope / typed data schemas。
- `apps/server/app/content/registry.py`：啟動時載入、validation、query。
- `apps/server/app/domain/character/schemas.py`：immutable `CharacterBuild`、mutable `CharacterState`。
- `apps/server/app/domain/character_builder/`：Draft、choice、compiler、structural rules、progression、spellcasting、equipment、review / confirm、reconciliation。
- `data/rules/dnd5e-2014/character-builder.json`：Builder rules configuration。
- P1-G immutable Build Version / Level Up / Build Edit / Correction workflow。

M01 的責任是**泛化既有基礎並增加內容能力**，不是建立 `content_v2`、`builder_v2` 或第二套 Character model。

## 2. 目前已知的硬耦合

M01-A 必須先解除以下現況耦合，後續資料才可安全進來。

### 2.1 Content envelope 寫死 SRD

目前 `ContentEntry` 類似：

```text
key     = ^srd5.1:...
source  = Literal["srd5.1"]
ruleset = Literal["dnd5e-2014"]
license = Literal["CC-BY-4.0"]
```

`ContentManifest` 也把 `id = srd5.1`、CC BY 4.0、MIT extraction 與 P4-A scope guard 綁在同一 schema。

這些 SRD-specific metadata 必須拆成：

- generic pack contract
- SRD pack 自己的 metadata / scope guard

不得要求非 SRD pack 偽裝成 `CC-BY-4.0`。

### 2.2 Registry 只載入一個 directory

目前：

```text
DEFAULT_CONTENT_ROOT = data/srd5.1
ContentRegistry.from_directory(root)
```

且 `expected_key`、`resolve()`、cross-reference normalization 都硬寫 `srd5.1`。

M01-A 改為多 pack registry。

### 2.3 Character StableKey validator 寫死 `srd5.1`

目前 `require_stable_key()` 要求：

```text
srd5.1:<kind>:<index>
```

這會讓 Build 無法保存 `phb2014:*` / `vgm:*` / `tce:*`。

M01-A 必須把 validator 泛化。

### 2.4 Builder 內重複解析 SRD API URL

目前至少 `basics.py`、`structural.py` 等存在類似：

```text
/api/2014/<route>/<index>
→ srd5.1:<kind>:<index>
```

M01-A 必須集中成一個 reference normalization helper；後續 domain code 不得再自行拼 `srd5.1:`。

### 2.5 Class level / spellcasting config 有 source hardcode

目前 progression / structural / spellcasting 路徑中，class level lookup 與 spellcasting config key 都以 SRD class identity 為主。

Artificer 會是第一個 `tce:class:*`，因此 class level lookup 必須依 class stable key / pack identity，而不是固定找 `srd5.1:level:*`。

## 3. Content Pack 正式模型

### 3.1 Directory layout

M01 使用：

```text
data/
├── srd5.1/
│   ├── manifest.json
│   └── ...
├── phb2014/
│   ├── manifest.json
│   └── ...
├── scag/
│   ├── manifest.json
│   └── ...
├── vgm/
├── vrgr/
├── tce/
└── gos/
```

`data/rules/dnd5e-2014/` 仍放 ruleset-level computation config；不要把所有 class / race content 混進 rules config。

### 3.2 Pack ID

Pack ID 要穩定、machine-readable、不可依 UI 名稱。

M01 固定使用：

```text
srd5.1
phb2014
scag
vgm
vrgr
tce
gos
```

建議 validation：

```text
^[a-z0-9][a-z0-9.-]*$
```

禁止 `:`，因為 StableKey 使用 colon 分隔。

### 3.3 Generic manifest

Manifest 需要表達 generic pack metadata，而不是每個來源都複製 SRD extraction shape。

建議核心欄位：

```json
{
  "id": "phb2014",
  "name": "Player's Handbook 2014 — Private Supplement",
  "ruleset": "dnd5e-2014",
  "provenance": {
    "type": "user-supplied-private-reference",
    "reference_documents": ["docs/暫用規則資訊/背景_PHB.md"]
  },
  "categories": [
    {
      "name": "backgrounds",
      "kind": "background",
      "file": "backgrounds.json",
      "count": 13
    }
  ],
  "total_entries": 13
}
```

實際 count 以轉換後資料為準，文件不要手抄死數字。

### 3.4 License / provenance

Generic pack schema 不應把 license 設成必填 `CC-BY-4.0`。

建議：

```text
provenance.type
provenance.reference_documents[]
optional license
optional attribution
optional source_url
```

SRD pack 可以保留完整 CC BY 4.0 / extraction metadata；private supplied pack 可記 `user-supplied-private-reference`。

### 3.5 SRD-specific scope guard

P0 的 Monster / Beast → P4-A guard 只屬 `srd5.1` pack。

不要讓所有 pack 的 generic manifest 都被迫具有：

```text
scope_guard.deferred_to = P4-A
```

M01-A 應把它變成 SRD manifest-specific optional metadata / validator。

## 4. StableKey 與 Reference Contract

### 4.1 StableKey 格式

正式格式：

```text
<pack-id>:<kind>:<index>
```

三段都必須非空；`index` 保持既有 kebab-case 原則。

### 4.2 StableKey 不代表顯示名稱

例如：

```text
vgm:race:goblin
```

即使 UI 中文名稱之後修正，key 不變。

### 4.3 新 pack 使用 explicit stable reference

新的 normalized non-SRD data 不應偽造 D&D API URL。

建議 reference shape：

```json
{
  "key": "srd5.1:skill:stealth",
  "name": "Stealth"
}
```

或：

```json
{
  "key": "phb2014:subrace:wood-elf",
  "name": "Wood Elf"
}
```

### 4.4 SRD legacy reference compatibility

現有 SRD 仍大量使用：

```json
{
  "index": "stealth",
  "name": "Stealth",
  "url": "/api/2014/skills/stealth"
}
```

M01-A 不要求一次 rewrite 全 SRD dataset。

建立一個共用 helper，例如概念上：

```text
reference_to_stable_key(reference, default_source?)
```

規則：

1. 有 explicit `key` → validate 並使用。
2. 沒有 key，但符合 legacy SRD `index + /api/2014/...` → normalize 為 `srd5.1:*`。
3. 其他 reference shape → fail validation；不要猜來源。

`basics.py`、`structural.py`、`equipment.py`、`spellcasting.py` 等需要 stable key 時全部用同一 helper。

### 4.5 Reference validation

Registry validation 必須檢查：

- target pack 已載入。
- target key 存在。
- expected kind 符合使用位置。
- explicit key 與 optional display/index metadata 不矛盾。

Cross-pack reference 是合法且必要的，例如 PHB Wood Elf 可以引用 SRD Elf base traits / languages / proficiencies。

## 5. ContentRegistry 泛化

### 5.1 Registry identity

M01-A 後 registry 概念上持有：

```text
packs: dict[pack_id, ContentManifest]
entries: dict[StableKey, ContentEntry]
by_kind: dict[kind, tuple[ContentEntry, ...]]
by_source_and_kind: optional index
```

禁止使用 `(kind, index)` 作 globally unique identity。

### 5.2 Loader

建議提供：

```text
ContentRegistry.from_directories([...])
```

或等效的 multi-pack factory。

`load_default_content_registry()` 可以從一個明確設定的 installed pack list 載入：

```text
srd5.1
phb2014
scag
vgm
vrgr
tce
gos
```

若某 pack 尚未在對應 Subphase 建立，不可讓 M01-A 預設啟用不存在 directory；M01-A 可先只載 `srd5.1 + test fixture pack`，之後各 Subphase把正式 pack 加到 installed list。

### 5.3 Query API

保留：

```text
get(stable_key)
get_optional(stable_key)
list_kind(kind)
```

`resolve(kind, index)` 目前隱含 SRD，應改成不模糊的 API，例如：

```text
resolve(source, kind, index)
```

或只鼓勵 caller 直接用 stable key。

不要讓新 code 呼叫 bare `resolve("race", "goblin")`，因為 VGM / future source 可以同時存在 Goblin。

### 5.4 Duplicate policy

以下是錯誤：

```text
tce:item:x  // pack A
 tce:item:x // 同一 key 第二筆
```

以下合法：

```text
vgm:race:goblin
future-pack:race:goblin
```

### 5.5 Startup fail-fast

維持 P0 原則：pack manifest、schema、duplicate、dangling reference、wrong kind、count mismatch 都在 Server startup fail-fast。

## 6. CharacterBuild / Builder Content Provenance

### 6.1 `require_stable_key()`

改為只驗證：

- 三段 stable-key shape。
- source / kind / index lexical validity。
- caller 傳入 `kinds={...}` 時驗 kind。

是否真的存在於 installed registry 屬 compile / service validation，不應由 Pydantic schema 在沒有 registry context 時硬判。

### 6.2 `content_sources`

現有：

```python
content_sources = ("srd5.1",)
```

M01 後其語意定義為：

> 此 immutable Build snapshot 直接或間接依賴的 Content Pack provenance。

Compiler 在產生 `CharacterBuild candidate` 時，從 persisted Build references 與必要 rule sources 收集 prefix，排序 deterministic 後保存。

不要讓 frontend 傳一個任意 `content_sources` list 並被直接相信。

### 6.3 Existing Characters

現有 SRD-only Character 不做 destructive migration。

舊 Build 的：

```text
content_sources = [srd5.1]
```

仍合法。

只有新的 Build Version / Create 使用新的 multi-source compiler semantics。

### 6.4 Builder option merging

Origin / Class / Background / Spell / Feat selector 應從 registry 聚合已 installed pack。

同名 option 顯示來源 badge 或 secondary text，例如：

```text
Goblin · VGM
```

Stable identity 永遠用 key，不用 label。

## 7. Normalized rule data 原則

M01 不應把 Markdown 敘述直接塞進各 domain 的 if/else。

建議每個 content entry 分成：

```text
identity / display
mechanical fields
builder choice rules
feature / description metadata
source provenance
```

P1 已能讀取既有 D&D API canonical option shape；M01 可以沿用該 shape，但新資料不需要假造 upstream URL。

### 7.1 Grant

可直接加入 Build 的東西，例如：

```text
proficiency
language
feature
spell access
speed / ability bonus 等 resolved permanent rule input
```

### 7.2 Choice

使用既有 `BuilderChoice` / `BuilderChoiceOption`：

- reference
- counted_reference
- nested_choice
- category_filter
- branch

新需求優先擴充資料轉譯層，不新增另一套 choice DTO。

### 7.3 Replacement

M01-E 新增最小通用 representation，概念例如：

```json
{
  "replace": ["srd5.1:feature:skill-versatility"],
  "grant": ["phb2014-or-scag:feature:..."]
}
```

實際 schema 可依當時 codebase 調整，但必須是 explicit、可 validation、可 trace provenance。

### 7.4 Conditional / progression grant

level-gated spell / feature 應由 character/class level 決定，不在 UI 寫：

```text
if level >= 3 and race == ...
```

資料至少需要：

```text
minimum_character_level / minimum_class_level
source
feature/spell grant
```

只建立 supplied content 需要的條件，不做 general expression engine。

# M01-A — Multi-Source Content Pack Foundation

## 實作範圍

優先修改：

```text
apps/server/app/content/schemas.py
apps/server/app/content/registry.py
apps/server/app/domain/character/schemas.py
apps/server/app/domain/character_builder/*  // 移除 source hardcode 的必要檔案
data/... manifests / fixture
```

### Required changes

1. generic `ContentEntry.source` / key validation。
2. generic `ContentManifest`，SRD-only metadata optional / specialized。
3. multi-directory registry。
4. central reference normalization。
5. cross-pack reference validation。
6. generic StableKey validator。
7. source-aware class level lookup foundation。
8. Build `content_sources` derivation。
9. Builder selectors merge multi-pack entries。
10. UI 能顯示 source metadata，至少在 ambiguity 時辨識。

### 不在 M01-A 加的 kind

`lineage`、`race-variant` 可以等 M01-E/F 真正需要時加入 `StableKind` / typed schema，避免 foundation 階段先猜完整模型。

### Compatibility

M01-A 必須保證原本：

```text
srd5.1:<kind>:<index>
```

完全不變。

不得 rename 現有 stable keys。

# M01-B — PHB Background & Core Race Completion

## Pack

建立 / 啟用：

```text
data/phb2014/
```

### Background normalization

Background data 優先對齊現有 P1 能力：

- `starting_proficiencies`
- structural choice fields
- `starting_equipment`
- `starting_equipment_options`
- `feature`
- optional roleplay suggestion tables

若 supplied PHB background 有固定 skill + 任選 tool/language，轉成 canonical Builder choice，不在 `background == X` 時分支。

### Roleplay suggestions

可新增 normalized optional fields：

```text
personality_traits[]
ideals[]
bonds[]
flaws[]
```

Builder UI 把它們當 suggestion：

- 點選填入 existing `roleplay_profile`
- 允許手動修改
- 允許空白

不要讓 roleplay tables 直接成為 immutable rule grants。

### PHB subraces

Wood Elf / Drow / Mountain Dwarf / Stout Halfling / Forest Gnome 使用：

```text
phb2014:subrace:<index>
```

其 `race` parent reference 可 cross-pack 指向 `srd5.1:race:*`。

### Variant Human

M01-B 採務實模型：

```text
phb2014:race:variant-human
```

把它視為完整 selectable race，而不是先建立 `race-variant` schema。

原因：

- 它在創角 UI 中本來就是 Human 的替代選項。
- 其規則是完整 race package 的差異，不需要保留「remove Skill Versatility」式 provenance。
- 可以讓 M01-B 先驗證任意 ability / skill / feat choice，而不把 M01-E 的 replacement model 提前耦合進來。

需要資料驅動 choices：

```text
choose 2 distinct abilities → +1 each
choose 1 skill
choose 1 feat
```

Feat option 必須重用 existing `feat_failure_reason()` / structural prerequisite logic。

### Racial spell grants

Drow / Forest Gnome 等 supplied racial spell access 不應塞到 Current State prepared list。

使用 `SpellAccessEntry` / source-aware grant 語意，source_type 可延伸／沿用 race；若 current enum 已有 `race`，直接使用。

level-gated spell access 在 Build compiler 依 target level / level-up 產生。

# M01-D — VGM Race Expansion

## Pack

```text
data/vgm/
```

### Race identity

使用：

```text
vgm:race:goblin
vgm:race:hobgoblin
vgm:race:aasimar
```

Aasimar 的 variant / subrace shape 以 supplied document實際內容為準；如果 supplied data 分成 parent + subrace，使用 `race` + `subrace`，不要為方便全部 flatten 成單一 race。

### Limited-use racial features

P1 `CharacterState.resources` 已能保存 generic `dict[str, ResourceCounter]`。

若 feature 的 capacity / recharge 能由 Build deterministic derive，可新增 deterministic resource key，例如概念：

```text
feature:<stable-feature-key>
```

但 M01-D 不需要建立 formal short-rest / long-rest automation；後續 Rest Phase 可正式接 recovery。現在至少要做到 capacity / current state 可保存與手動調整（若 UI 已有 generic resource 操作）。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## 新增 `race-variant` identity

M01-E 才正式新增 StableKind：

```text
race-variant
```

建議資料：

```text
key
base_race_ref
label / ancestry
replacement_rules[]
additional_choices[]
```

### Builder persistence

在 `BuilderDraftPayload` 加入明確的 optional：

```text
race_variant_selection
```

或等價 typed field。

正式 `CharacterBuild` 也加入：

```text
race_variant_ref: StableKey | None
```

不要把 variant 只藏在 generic `choice_selections`，否則 Version History / Character Sheet 無法明確回答角色使用哪個 ancestry variant。

### Replacement compile order

固定順序：

```text
base race grants
→ subrace grants（若有）
→ selected variant replacement removes
→ variant grants / choices
→ dedupe / validation
→ final Build
```

Replacement target 必須以 stable identity / grant identity 對應，不以 display string `"Skill Versatility"` 做 brittle match。

### UI

Origin step 在 Race = Half-Elf 時顯示 optional Variant / Ancestry selector。

不選時：標準 SRD Half-Elf。

選時：Server 回傳 replacement choice / grant summary。

# M01-F — VRGR Lineage & Dhampir

## 新增 kind

M01-F 新增：

```text
lineage
```

Pack：

```text
data/vrgr/
```

### CharacterBuild

建議新增 typed lineage provenance，而不是只加一個 string：

```text
lineage_ref: StableKey | None
ancestral_origin_ref: StableKey | None
ancestral_legacy: ...
```

實際 `ancestral_legacy` shape 以當時 compiler 所需最小資料為準，但必須能重建「保留了哪些技能／特殊速度」的來源。

### Race semantics

Lineage active 時，不應把 `race_ref` 的所有 grants 與 lineage 全部疊加。

兩種合理 persistence 方案擇一，以較少破壞既有 P1 為優先：

A. `race_ref` 保留 ancestral origin identity，但 compiler / Sheet 以 `lineage_ref` 宣告 race-package replacement，並只透過 `ancestral_legacy` 帶回允許內容。

B. `race_ref` 改成 lineage-compatible base identity，另以 `ancestral_origin_ref` 保存舊 race。

M01-F 開工時依當時 codebase選擇；無論哪種方案，**不得同時把 old race full grants + Dhampir full grants 相加。**

### Existing Character transformation

重用 P1-G Build Edit：

```text
current version
→ edit draft seeded from Build
→ choose lineage / ancestral legacy
→ review
→ reconcile
→ new immutable version
```

不新增「Transform Character」獨立 persistence path；UI 可以日後用 specialized入口包同一 Builder mode。

# M01-G — TCE Artificer Core

## Pack

```text
data/tce/
```

先加入：

- class
- class levels
- subclasses
- class features required for progression display
- Artificer spell list / spell access references（必要時引用 SRD spell + supplied non-SRD spell data；若 supplied M01 source沒有某 spell 完整資料，不可自行捏造）

### Class level lookup

現有 `_class_level_entry()` 不能固定：

```text
srd5.1:level:<class-index>-<n>
```

改成由 class source 或 explicit level index 查找：

```text
tce:class:artificer
→ tce:level:artificer-1
```

### Spellcasting config

現有：

```json
"slot_contribution": "half"
```

不足以區分：

- Paladin / Ranger：half floor
- Artificer：half ceil

M01-G 將 contribution 改為可表達 rounding 的資料結構，例如：

```json
"slot_contribution": {
  "formula": "half",
  "rounding": "floor"
}
```

Artificer：

```json
"slot_contribution": {
  "formula": "half",
  "rounding": "ceil"
}
```

Full caster 可用：

```json
{"formula": "full"}
```

Pact Magic 仍是獨立 pool，不參與此 combined contribution。

### Prepared spell formula

Prepared formula 另外表示，例如 Artificer：

```text
INT modifier + floor(Artificer level / 2)
minimum 1
```

不得因 slot contribution 是 ceil 就把 prepared formula 也 ceil。

### Subclasses

四個 specialist 使用既有 `subclass` identity / timing；specialist-specific complex runtime effects延後 M01-H 或未來 Combat。

# M01-H — TCE Artificer Advanced Rules & Infusions

## Infusion content kind

若現有 `feature` 無法清楚區分可選 Infusion，可以在 M01-H 增加：

```text
infusion
```

或使用 `feature` + subtype。

選擇原則：

- 若 Builder 需要 `list_kind("infusion")`、level prerequisite、item applicability 等獨立 query，新增 kind 比塞成普通 feature 清楚。
- 若 supplied data 很少且所有行為都能由 feature metadata完成，可先不新增 kind。

不要先在 M01-A 決定。

### Known vs active infusion

Persistence：

```text
Known Infusions = Build
Currently Infused Items = Current State / inventory relationship
```

可對 `InventoryEntry` 增加 minimal metadata，例如：

```text
infusion_ref: StableKey | None
```

或建立獨立 Current State mapping：

```text
infused_items[entry_id] = infusion_ref
```

依當時 Inventory API 修改成本選擇，避免同一狀態重複保存兩份。

### Class resources

使用既有 `CharacterState.resources`，resource id deterministic 並由 Build capacity derive。

例如 Flash of Genius capacity 若由 INT modifier 決定，Review / reconciliation 必須能更新 capacity而保留已使用量的合理語意。

### Attunement capacity

建立一個 Rules Layer helper：

```text
attunement_capacity(build) -> int
```

一般基線與 Artificer level override 由資料／feature progression決定；不要把 `if artificer_level >= ...` 寫在 React。

# M01-I — TCE Magic Items

## Item schema

現有 `ItemData` 至少有：

```text
equipment_category
rarity
variant
desc
```

M01-I 視 supplied data擴充 optional typed fields：

```text
item_type / category
requires_attunement
attunement_requirements
charges / recharge metadata（若適用）
common modifiers（若 existing rules layer可承載）
```

保持 `extra="allow"` 的來源資料彈性時，也應對 M01 真正依賴的欄位建立 typed validation，不要全部藏在 untyped dict。

### Inventory state

現有 `InventoryEntry` 已有：

```text
quantity
equipped
carried
```

M01-I 加入：

```text
attuned: bool = false
```

必要時再增加 minimal instance metadata；不要把物品 description 複製進 Character State，State 只保存 item_ref + live state。

### Attunement validation

Inventory API / Character rules 至少檢查：

- item 是否需要 attunement。
- class restriction / requirement 是否滿足（若已結構化）。
- current attuned count 是否超過 character capacity。

第一版可以 warning / blocking 依操作語意決定：

- `attune` action 本身超 capacity → blocking。
- 讀取 legacy/imported abnormal state → 顯示 warning，不讓資料無法載入。

### Simple modifiers

只有 existing Character Rules Layer 能明確安全接入的 simple modifier 才自動化。

任何需要：

- Combat trigger
- reaction timing
- target selection
- recharge roll
- custom script

的 item effect，先保留 structured description / metadata，未來對應 Phase 再接。

# M01-J — Full M01 Integration & Closeout

## Integration cleanup

M01-J 不應再大量新增功能；主要做：

- consolidate duplicated helpers
- remove temporary compatibility hacks introduced during M01
- verify manifest counts / provenance
- ensure source badges / display names consistent
- ensure Build Version history可辨識 multi-source identity
- update docs / PROJECT_BRIEF status
- full regression / restart persistence / E2E

### Migration policy

若 M01 中 Character schema新增 optional fields（如 `race_variant_ref`、`lineage_ref`、`InventoryEntry.attuned`）：

- JSONB schema以 backward-compatible default處理舊資料。
- DB relational migration只在真正需要 column/table 時新增。
- 不 rewrite existing CharacterBuild JSONB 只為填 null/default。

### Closeout cleanup rule

不得留下：

```text
TODO use real pack later
if source == "tce" and index == "artificer"  // 可資料驅動卻硬寫
frontend-only legality
silent ignored replacement
unvalidated dangling stable key
```

若某效果刻意 manual，文件／metadata要明確標成 manual，而不是留曖昧 TODO。

## 8. API / UI 設計邊界

M01 不是 API redesign Phase。

優先維持既有 endpoints / DTO，僅擴充必要欄位：

- reference source metadata

## 9. Data conversion 規則

每個 supplied Markdown 轉資料時固定：

```text
Read source reference
→ identify mechanical records
→ normalize stable identities
→ map cross references
→ schema validate
→ add builder/rules metadata
→ automated fixture tests
→ UI / Review / Confirm test
```

禁止只用 bulk text transformation 後看到 JSON parse成功就算完成。

每筆正式資料至少確認：

- canonical identity
- parent / source relationship
- grants
- choices
- level gates
- prerequisites
- equipment quantities
- spell source identity
- roleplay-only fields與mechanical fields沒有混用

## 10. M01 的 anti-patterns

以下一律視為設計錯誤：

1. 把非 SRD data 放進 `data/srd5.1/`。
2. 把所有新資料的 `source` 偽裝成 `srd5.1`。
3. 以 name 做 foreign key。
4. 同名 content 後載入者覆蓋前者。
5. 在 frontend `if race === "Variant Human"` 計算 rule。
6. 在 Artificer code path 寫死 multiclass ceil，而 rules config仍宣稱普通 `half`。
7. Dhampir 直接疊加 old race + lineage 全部 grants。
8. Half-Elf variant 只隱藏 UI 選項但 Build仍保留 Skill Versatility。
9. TCE magic item為了完整自動化引入 generic script engine。
10. 為 M02 / future books 預先設計一堆尚未有 supplied content 驗證的 schema。
