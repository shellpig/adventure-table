## 2. 現有地基與不可破壞契約

M01 開工時應以當下 `main` 真正 codebase 為準再次核對 API 簽名。目前已確認的重要地基：

```text
data/srd5.1/
data/rules/dnd5e-2014/character-builder.json

apps/server/app/content/
├── registry.py
└── schemas.py

apps/server/app/domain/character/
├── schemas.py
└── ...

apps/server/app/domain/character_builder/
├── basics.py
├── choices.py
├── compiler.py
├── equipment.py
├── progression.py
├── schemas.py
├── spellcasting.py
├── structural.py
└── ...

apps/server/app/domain/rules/
apps/server/app/persistence/
apps/server/app/api/

apps/web/src/features/character-builder/
apps/web/src/features/character-sheet/
```

現有重要契約：

- `CharacterBuild` 是 immutable versioned snapshot。
- `CharacterState` 是 mutable live state。
- Builder Draft 保存未完成輸入／選擇，不是假 `CharacterBuild`。
- Builder choices 由 Server authoritative logic 產生。
- Frontend 不複製 D&D progression engine。
- Starting Equipment 只在 Create Confirm 初始化一次 live Inventory。
- Level Up / Build Edit 不重新建立 live Inventory。
- Spell Access / Spellbook / Known / Always Prepared 等長期取得屬 Build。
- Daily Prepared selection 與 resource usage屬 State。
- Version History 必須保留舊 Build，不做 in-place rewrite。
- Numeric Override 仍只覆 numeric value，不繞過 Structural Validation。

M01 的所有修改都必須延續這些邊界。

## 3. 已知 SRD-only 耦合：M01-A 必須先解除

目前 codebase 已確認至少存在以下硬耦合：

### 3.1 `ContentEntry` envelope

`apps/server/app/content/schemas.py` 目前有類似：

```text
key regex -> ^srd5.1:...
source    -> Literal["srd5.1"]
ruleset   -> Literal["dnd5e-2014"]
license   -> Literal["CC-BY-4.0"]
```

`ContentManifest` 同時把：

- id = `srd5.1`
- CC BY metadata
- extraction source / MIT metadata
- P4-A Monster / Beast scope guard

綁在同一個 SRD-specific model。

### 3.2 `ContentRegistry`

目前：

```text
DEFAULT_CONTENT_ROOT = data/srd5.1
ContentRegistry.from_directory(root)
```

並且：

- expected key 寫死 `srd5.1:<kind>:<index>`。
- `resolve(kind, index)` 隱含 `srd5.1`。
- cross-reference 從 `/api/2014/...` 推導 `srd5.1:*`。

### 3.3 Character StableKey validator

`apps/server/app/domain/character/schemas.py` 的 `require_stable_key()` 目前要求第一段必須是 `srd5.1`。

### 3.4 Builder reference normalization

`basics.py`、`structural.py` 等目前各自存在 `_stable_key()` 類邏輯：

```text
/api/2014/<route>/<index>
→ srd5.1:<kind>:<index>
```

這會讓新 pack 只能靠 fake URL 才能運作。

### 3.5 Class lookup / multiclass path

目前部分 Builder code使用：

```text
entry.key.startswith("srd5.1:class:")
```

或：

```text
srd5.1:level:<class-index>-<n>
```

Artificer 是 `tce:class:artificer`，因此這些 source assumptions 必須消失。

### 3.6 Build provenance

`CharacterBuild.content_sources` 已存在，預設：

```text
("srd5.1",)
```

但目前 compiler 建 candidate 時沒有真正 derive 多來源 provenance。

### 3.7 Spellcasting contribution

`data/rules/dnd5e-2014/character-builder.json` 目前用：

```text
slot_contribution = full | half | none
```

無法區分：

```text
Paladin / Ranger half → floor
Artificer half → ceil
```

此項在 M01-G 才正式泛化；M01-A 不提前做 Artificer規則。

## 4. 全 M01 共通 Content Pack 契約

### 4.1 Directory layout

正式方向：

```text
data/
├── srd5.1/
├── phb2014/
├── scag/
├── gos/
├── vgm/
├── vrgr/
├── xge/
├── tce/
└── rules/
    └── dnd5e-2014/
```

`data/rules/dnd5e-2014/` 是 ruleset-level computation config；它不是某本書的 Content Pack。

### 4.2 Pack IDs

M01 固定使用：

```text
srd5.1
phb2014
scag
gos
vgm
vrgr
xge
tce
```

Pack ID lexical contract：

```regex
^[a-z0-9][a-z0-9.-]*$
```

禁止 `:`，因 StableKey 使用 colon 分隔。

### 4.3 StableKey

正式格式：

```text
<pack-id>:<kind>:<index>
```

建議集中 parser，而不是各 module 自己 `split(":", 2)`：

```python
@dataclass(frozen=True)
class ParsedStableKey:
    source: str
    kind: str
    index: str
```

Schema-level：

- 驗三段 syntax。
- 驗 caller 要求的 kind。

Registry/service-level：

- 驗 pack 是否 installed。
- 驗完整 key 是否存在。
- 驗 cross-reference target kind。

Pydantic schema本身不要依賴 global registry singleton。

### 4.4 新 Content Reference shape

新的 non-SRD normalized data優先使用 explicit stable ref：

```json
{
  "key": "srd5.1:skill:stealth",
  "name": "Stealth"
}
```

可選擇附：

```json
{
  "key": "srd5.1:skill:stealth",
  "index": "stealth",
  "name": "Stealth"
}
```

identity以 `key` 為準。

### 4.5 Legacy SRD Reference compatibility

現有 SRD仍可能是：

```json
{
  "index": "stealth",
  "name": "Stealth",
  "url": "/api/2014/skills/stealth"
}
```

建立一個共用 helper，例如：

```text
reference_to_stable_key(reference)
```

行為：

1. 有 explicit `key` → parse + validate。
2. 沒有 key，但符合 legacy SRD `index + /api/2014/...` → normalize成原 `srd5.1:*`。
3. 其他 shape → invalid；不要猜來源。

`basics.py`、`structural.py`、`equipment.py`、`progression.py`、`spellcasting.py` 等全部共用；不能每個 module各寫一套 URL parser。

### 4.6 Generic `ContentEntry`

M01-A後至少：

```text
key
index
name
source
ruleset
data
license?       # backward-compatible / entry override only
provenance?    # only when entry-level override is actually needed
```

具體修改：

- `key` regex不再寫死 `srd5.1`。
- `source`從 `Literal["srd5.1"]`改成 generic pack id。
- `ruleset` M01仍可限定 `dnd5e-2014`，但不得因 source不同失敗。
- `license`不再每筆要求 `CC-BY-4.0`；既有 SRD entry若仍帶該欄位必須可原樣載入。

來源／license / extraction主要住 pack manifest；entry-level metadata只在真正需要 override時存在。

### 4.7 Generic Manifest — 現有 model 的明確 migration 契約

M01-A 不得只新增新 manifest 範例後寫「依現有 model 最小修改」。現行 `ContentManifest` / supporting models 的 SRD-only欄位要按以下方式泛化。

#### `ContentManifest.id`

現有：

```text
Literal["srd5.1"]
```

改成 generic Pack ID string，套 4.2 的 lexical validator。

#### `ContentManifest.license` / `ManifestLicense`

現有 `license.spdx` 鎖死 `CC-BY-4.0`。

改成：

```text
license: ManifestLicense | None = None
```

有 `license` object 時仍要求 object內欄位完整；但 `spdx` / identifier改為 generic non-empty string，不鎖死 CC-BY-4.0。手動整理的 private pack可以整個省略 `license`，不得偽造授權資料。

既有 SRD manifest完整 CC-BY metadata必須原樣通過。

#### `ContentManifest.extraction` / `ExtractionSource`

現有 `extraction` required，`commit`要求 40-hex，`license`鎖死 MIT。這是 P0 SRD extraction provenance，不是 generic pack requirement。

改成：

```text
extraction: ExtractionSource | None = None
```

手工整理的 PHB/SCAG/GoS/VGM/VRGR/XGE/TCE pack不提供 extraction也合法。若某 pack真的由 Git repository extraction產生，`commit`可繼續要求 40-hex；但 `ExtractionSource.license`改為 generic non-empty string，不鎖死 MIT。

Generic manifest另保留／新增 `provenance`（或等價欄位），讓手工 pack可以誠實表示：

```text
source_type = user-supplied-private-reference
reference_documents = [...]
```

#### `ContentManifest.scope_guard` / `ScopeGuard`

現有 model強制：

```text
excluded_categories包含 monsters + beasts
deferred_to = P4-A
```

這是 P0 SRD scope-cut，不是 generic pack contract。

改成：

```text
scope_guard: ScopeGuard | None = None
```

並把 monsters/beasts + P4-A 的驗證限制在 `srd5.1` 的 SRD-specific compatibility validator／metadata；非 SRD pack沒有 `scope_guard` 必須合法。

#### `ManifestCategory.upstream_file`

現有 required，改成：

```text
upstream_file: str | None = None
```

只有真有 upstream file provenance才填；手工 pack不偽造。

#### `ManifestCategory.count` / `ContentManifest.total_entries`

維持 required與 strict consistency：

```text
count >= 0
total_entries == sum(categories.count)
```

M01仍要 deterministic completeness / fail-fast。

#### Generic manifest shape

優先沿用現有 `name`，不要為了範例同時維護 `name` + `display_name` 兩個重複欄位：

```json
{
  "id": "phb2014",
  "name": "Player's Handbook 2014",
  "ruleset": "dnd5e-2014",
  "version": "local-1",
  "provenance": {
    "source_type": "user-supplied-private-reference",
    "reference_documents": [
      "docs/暫用規則資訊/背景_PHB.md"
    ]
  },
  "usage": {
    "visibility": "private-project"
  },
  "categories": [
    {
      "name": "backgrounds",
      "kind": "background",
      "file": "backgrounds.json",
      "count": 18
    }
  ],
  "total_entries": 18
}
```

SRD-specific CC BY / extraction / scope guard可以繼續存在，但只能是 optional/SRD-specific metadata，不能逼 private pack偽裝成 SRD。

### 4.8 Registry indexes

至少維護：

```text
by_key: dict[StableKey, ContentEntry]
by_kind: dict[kind, tuple[ContentEntry, ...]]
by_source: dict[source, ContentPack]
by_source_kind: dict[(source, kind), tuple[ContentEntry, ...]]
```

Duplicate policy：

```text
same full StableKey → fatal
same kind:index but different source → legal
same display name → legal
```

### 4.9 Installed pack / fixture isolation policy

Private project不做 pack manager UI。

**正式定案：production/dev 使用 explicit deterministic enabled pack list，不掃描 `data/` 所有 child directories自動啟用。**

例如：

```text
DEFAULT_CONTENT_PACKS = (...)
```

或等價 config。

Registry / loader同時必須可注入：

```text
content_root
enabled_pack_ids
```

或等價 dependencies。測試用 `testpack` / `pack-a` / `pack-b` / `future` 放 tests專用 fixture root，由測試明確 enable；不得放 production `data/`後依賴命名規則或掃描排除。

每個 Subphase只有在 pack正式資料完成後才加入 default enabled list。M01-A不可先把不存在或未完成的 `tce/`等資料夾當 mandatory startup dependency。

### 4.10 `content_sources` canonical semantics

`CharacterBuild.content_sources` = **Build實際引用到的 pack集合**。

Compiler完成 candidate後收集：

- race / subrace。
- race variant / lineage（後續有時）。
- background。
- class progression / subclasses。
- features / feats。
- spell access sources。
- starting equipment references。
- 其他 persisted Build refs。

然後：

```text
dedupe
→ deterministic sort
→ CharacterBuild.content_sources
```

如果 Builder要控制「此 Draft可選哪些來源」，用獨立：

```text
enabled_content_sources
```

或 server policy。

**`content_sources` 絕不可作為 selection allowlist / permission gate。** 正確順序是：

```text
allowed-source policy
→ emit / validate selectable refs
→ compile final refs
→ derive content_sources provenance
```

actual provenance不能反過來決定自己是否允許。

### 4.11 Existing JSONB compatibility

新 optional fields一律有 backward-safe default。

原則：

- 不因新增 optional JSON field bulk rewrite所有舊 Build。
- old `content_sources=["srd5.1"]`合法。
- old Build沒有 variant / lineage / optional feature selection時使用 backward-safe default。

### 4.12 規則參考文件與 Runtime Content

`docs/`、`docs/暫用規則資訊/` 與其他人工規則文件只作為開發／維護時 reference，**不得由 server / Content Registry 在 runtime 解析成規則資料**。

Reference 內的規則描述文字可以在 authoring/materialization 階段直接複製到正式 `data/<pack>/` 或 localization；禁止的是 runtime parsing，不是文字搬用。

Materialization 時必須把 mechanics 與 provenance拆清楚。Reference 若彙整了後來來源新增的 access/選項，不能因為出現在同一 Markdown 就把後來來源的規則錯標成原書 canonical provenance。

正式流程：

```text
reference Markdown
→ authoring / normalization
→ checked-in data/<pack>/ and locale data
→ runtime Content Registry
```

Server / Docker 在沒有 `docs/` 的情況下也必須可以正常載入 content 並啟動。

# M01-A — Multi-Source Content Pack Foundation

## A.1 主要修改面

開工時先 grep並核對最新 signatures：

```text
srd5.1:
DEFAULT_CONTENT_ROOT
/api/2014/
resolve(
startswith("srd5.1:class:")
level:
```

優先涉及：

```text
apps/server/app/content/schemas.py
apps/server/app/content/registry.py
apps/server/app/domain/character/schemas.py
apps/server/app/domain/character_builder/basics.py
apps/server/app/domain/character_builder/structural.py
apps/server/app/domain/character_builder/progression.py
apps/server/app/domain/character_builder/equipment.py
apps/server/app/domain/character_builder/spellcasting.py
apps/server/app/domain/character_builder/compiler.py
reference APIs / frontend reference DTOs
```

Known SRD anomaly corrections可保留 `srd5.1:*` hardcode，因為它們真的只針對特定 SRD source anomaly；要移除的是 generic runtime假設。

## A.2 StableKind策略

A只泛化現有 kinds。

新 kinds在真正需要時加入：

```text
M01-E → race-variant
M01-F → lineage
M01-H → infusion（若 feature subtype不足）
M01-I → fighting-style（若 generic feature subtype不足）
```

Variant Human在 M01-B 使用完整 `race` identity；`race-variant` 直到 M01-E 的 SCAG Half-Elf grant replacement才首次引入。

## A.3 Multi-pack loader

採 explicit enabled packs + injectable root；具體 class/function名稱可按現有 code調整，例如：

```text
ContentRegistry.from_directories([...])
```

或：

```text
ContentPackLoader(content_root, enabled_pack_ids)
→ ContentRegistry
```

重點：

- 只載 explicit enabled packs。
- 每個 manifest各自 validation。
- 合併 entries後做 global StableKey uniqueness。
- cross-pack reference validation要在所有指定 packs load完成後執行。
- tests可注入 fixture root與fixture pack list。

不要逐 pack load時就因 target pack還沒讀到而錯判 dangling，也不要掃描所有子資料夾自動 enable。

## A.4 Cross-reference validation

Reference walker只處理明確 reference shape：

- explicit `key` reference。
- legacy SRD `index + url` reference。

不要看到任意 dict有 `key`字串就當 content ref。

必要時建立 typed `ContentReference` model。

## A.5 Source-aware class level lookup foundation

將：

```text
srd5.1:class:fighter
→ srd5.1:level:fighter-5
```

泛化成：

```text
<class source>:level:<class index>-<n>
```

或由 class data提供 explicit level refs。

A不要求重寫 SRD levels格式，只要求 helper不再固定 `srd5.1`。

## A.6 Multiclass option path

目前 compiler / progression中的：

```text
entry.key.startswith("srd5.1:class:")
```

應改成 StableKey kind判断：

```text
parsed.kind == "class"
```

是否為可用 class由 Registry / content policy判斷，不由 source prefix判斷。

## A.7 Registry query API

保留：

```text
get(full_key)
get_optional(full_key)
list_kind(kind)
```

把模糊：

```text
resolve(kind, index)
```

改成：

```text
resolve(source, kind, index)
```

或要求 caller直接用 full key。

新 code不得用 bare `kind:index`做 lookup。

## A.8 Source-aware reference API / UI

ReferenceDTO至少增加：

```text
source_id
source_label
```

Selector：

```text
Wood Elf · PHB
Goblin · VGM
```

不需要建立 Book tab。

## A.9 Fixture packs

A的 foundation tests用 tiny fixture packs，不用正式 PHB當唯一驗證。

所有 fixture packs放 tests專用 content root，透過 injected `content_root + enabled_pack_ids`載入。

需涵蓋：

- same index different source。
- cross-pack ref。
- wrong-kind ref。
- duplicate full key。
- invalid manifest。
- unlisted fixture directory不會自行進 registry。

## A.10 M01-A migration policy

如果 DB沒有 source enum constraint，A可能完全不需要 Alembic。

若有 relational constraint：只做必要 generalization。

不 rewrite舊 JSONB StableKeys。

# M01-B — PHB Character Origins & Background Expansion

## B.1 Pack layout

建議：

```text
data/phb2014/
├── manifest.json
├── backgrounds.json
├── races.json           # Variant Human 等完整 race identity
├── subraces.json
├── traits.json          # 需要 reusable racial traits時
├── features.json        # background / racial feature需要時
└── ...
```

不要為形式建立空 category files。

M01-B 不新增 `race-variant` StableKind；Variant Human 是 `race` entry。`race-variant` 留到 M01-E。

## B.2 Background schema

現有 `BackgroundData`至少已有：

```text
starting_proficiencies
starting_equipment
```

B要把 Builder實際會用的欄位正式 typed / normalized：

```text
starting_proficiency_options
language_options
tool_options
starting_equipment_options
feature / feature_refs
variant_of optional
roleplay_suggestions optional
```

能沿用 P1 canonical option shape就沿用，不建立 `PhbBackgroundChoice`第二套 engine。

## B.3 Roleplay suggestions

建議：

```json
"roleplay_suggestions": {
  "personality_traits": ["..."],
  "ideals": ["..."],
  "bonds": ["..."],
  "flaws": ["..."]
}
```

Frontend把點選結果寫入 existing `roleplay_profile`；仍可手動修改或留空。

## B.4 PHB subrace parent refs

例如：

```json
{
  "key": "phb2014:subrace:wood-elf",
  "race": {"key": "srd5.1:race:elf"}
}
```

Builder subrace filtering依 parent full key；不能要求 subrace與 race同 source。

## B.5 Base + subrace composition

不要把 SRD Elf / Dwarf / Halfling / Gnome全部 grants複製到 PHB subrace entry。

Compiler仍做：

```text
base race grants
+
selected subrace grants
→ resolved origin grants
```

避免 base source日後修正時兩份漂移。

## B.6 Variant Human representation — 正式定案

Variant Human不假裝成 subrace，也不使用 `race-variant`。

Content / Build identity：

```text
phb2014:race:variant-human
```

Final Build：

```text
race_ref    = phb2014:race:variant-human
subrace_ref = None
```

Data可保存：

```text
variant_of = srd5.1:race:human
```

但 `variant_of` 只做 provenance / UI relation / maintainer readability，**不能觸發 mechanical inheritance**。也就是：

```text
variant_of != base_race_ref
variant_of != compile parent
```

Compiler不得看到 `variant_of` 就自動：

```text
load normal Human grants
→ apply Variant Human changes
```

Variant Human entry必須 mechanically complete；所有實際 ability / skill / feat / language / size / speed等規則，必須由該 Race entry自身或它明確引用的 reusable feature/trait data決定。

M01-B不修改 `CharacterBuild` schema，不新增 `race_variant_ref`；BuilderDraft也不新增 `race_variant_selection`。這是刻意保護真人創角 Gate的 scope。

## B.7 Variant Human choices

Server-generated choices：

```text
Ability Bonus: choose 2 distinct abilities, +1 each
Skill: choose exactly 1 skill
Feat: choose exactly 1 eligible feat
```

Ability choices要：

```text
choose_count=2
```

不要為形式建立空檔案；如果現有 generic `feature` / choice-option model已足夠，Fighting Style可用 subtype，但必須能依 parent class / source / level做可靠 query。

## I.2 Optional Class Feature typed semantics

```text
parent_class_ref
minimum_class_level

replaces_feature_ref optional
choice_pool_extension optional
resource metadata optional
spell_access metadata optional
```

不要在 compiler散落：

```python
if class == "ranger" and feature == "deft-explorer": ...
```

## I.3 Build persistence

永久採用的 Optional Feature / Fighting Style / retraining結果屬 Build。

如果現有 `feature_refs`無法分辨：

```text

optional replacement
user-selected optional feature
```

或等價 `feature` subtype identity。

```text

```

Builder option由：

```text
class_ref
+ class_level
+ enabled sources
```

server-side derive。

## I.5 Nested Fighting Style choices

### Druidic Warrior

## I.6 Addition resolver

新增 feature只在指定 class level以上生效：

```text

+ selected/available optional additions
→ grants
```

Direct High-Level Create與 sequential Level Up共享 resolver。

## I.7 Replacement resolver

沿用 M01-E 的 stable grant replacement概念，泛化 target scope：

```text

```

如果某 feature replacement不是單一一對一，而是多 level progression group，使用 deterministic group identity，不做 arbitrary JSON patch language。

## I.8 Expanded option pools

```text
Fighting Styles
Battle Master Maneuvers
Metamagic
Eldritch Invocations / Pact options

```

## I.9 Retraining / Versatility

```text

→ Level Up / Build Edit Draft
→ emit eligible retraining choice
→ Review
→ Confirm
→ Version N+1
```

Eligibility由 feature data + class level + current Build derive。

不得 in-place edit Version N。

## I.10 State reconciliation

如果 Optional Feature replacement / retraining造成：

- prepared spell不再合法。
- resource capacity改變。
- active selection依賴被移除。

沿用 P1 reconciliation pattern：preserve legal state、列 conflict、禁止 silent destructive cleanup。

## I.11 Localization

所有新 feature/style names、descriptions、choice labels、manual-effect labels在同一 Subphase補齊 `zh-TW` / `en`，StableKey不因 locale改變。

# M01-K — PHB Feat & Spell Catalog Expansion

## K.1 Scope / authoring inputs

K 的 supplied authoring inputs：

```text
docs/暫用規則資訊/專長_PHB_非SRD內容.md
docs/暫用規則資訊/法術_PHB_非SRD內容.md
```

Expected scope：

```text
41 phb2014 non-SRD feats
42 phb2014 non-SRD spells
```

兩份 Markdown 可直接提供規則描述文字、中文 presentation 與 authoring facts，但 runtime 絕不依賴它們。

K 開工時先產生 machine-verifiable expected inventories；不要靠「檔案大概有 41 / 42 段」人工判定 closeout。

## K.2 PHB Feat data layout

正式資料進：

```text
data/phb2014/
├── feats.json                # 或 deterministic shards
├── manifest.json
└── locales/
    └── ...
```

Stable identity：

```text
phb2014:feat:<index>
```

SRD Grappler保持：

```text
srd5.1:feat:grappler
```

不要複製 Grappler成 `phb2014:feat:grappler`，除非未來有明確 canonical/reprint policy；M01-K 的 41 inventory只代表 PHB 相對 SRD的缺口。

## K.3 Feat schema / structural grants

現有 SRD `FeatData` 主要只有：

```text
prerequisites
desc
```

K 必須在不建立 universal effect DSL的前提下，補目前 41 Feats實際需要、且 Builder/Build能安全表達的有限 typed primitives。

優先沿用既有 generic choice / grant / proficiency / ability-score machinery；只有現有 contract真的不足才擴充。

需要支援的典型形狀：

```text
ability_increase fixed/chosen
skill/tool/armor/weapon proficiency grant
saving_throw proficiency grant
language grant/choice
choose N distinct
spellcasting-source choice
spell/cantrip choice
maneuver choice
persistent feat option
repeatable / non-repeatable acquisition rule
per-acquisition uniqueness constraint where supplied
static derived modifier over a closed target whitelist
```

不要建：

```text
FeatEffectScript
arbitrary expression evaluator
generic trigger DSL
```

### Feat acquisition persistence

現有以 unique `feat_refs` 表示結果的方式不足以承載 repeatable Feat。K 必須建立 backward-safe 的 **acquisition-level** 表示，名稱可依現有 model 調整，但語意至少包含：

```text
feat_ref
acquisition identity / source opportunity
nested selections for this acquisition
```

要求：

- 同一 Feat StableKey 可在規則允許時出現多個 acquisition instance。
- acquisition identity 必須 deterministic，且足以讓每次 nested choice 的 choice id 不互相碰撞。
- `feat_refs` 若為相容性保留，可作 unique identity summary / derived view，但不得再是 repeatable Feat 的唯一 source of truth。
- compiler 不得再用 set / `dict.fromkeys` 等 identity-only dedupe 把合法的 repeatable acquisitions 靜默壓成一筆。
- 舊 Build 沒有 acquisition-level資料時必須有 backward-safe讀法，不 bulk rewrite舊 immutable Build。

### Static derived modifiers

Tough 與 Observant 的效果是無條件的 derived value 修正。目前 Rules Layer 沒有任何 feat 修正入口：`calculate_max_hp()` 只取 `hp_progression` 與 CON，`passive_perception()` 是 `10 + skill_modifier(...)`，而 passive Investigation 根本還不存在。因此「已被 Rules Layer 支援」在 K 開工時對這批效果一個都不成立，必須補一個**最小且封閉**的入口。

Build 側新增 acquisition-derived 的 typed modifier 集合，欄位名可依現有 model 命名慣例調整，語意至少包含：

```text
target        closed Literal，K 只開放 max_hp / passive_perception / passive_investigation
value         int
per_level     bool，true 時以角色等級縮放
source_ref    來源 feat acquisition
```

要求：

- `target` 是 closed enum。要多一個 target 就必須改這個 enum，讓擴張是規格決定而非資料驅動——這是本節與 effect DSL 的分界線。
- 三個 Rules Layer 計算點各加一個加總點，順序固定 `base → derived modifiers → numeric_override`。Numeric Override 仍是最終絕對值覆寫，語意不變。
- `passive_investigation` 是本節新增的 derived field，需一併補進 Character Sheet DTO 與兩語 presentation。
- `per_level` 的縮放在 Level Up 後由既有 recompute path 自然更新，不另開快取或寫死數值。
- repeatable Feat 的多次 acquisition 各自貢獻，依 K.3 的 acquisition-level 表示計入。
- 存於 Build 的是 modifier 資料本身，不是計算結果；舊 Build 沒有這個欄位時視為空集合，不 bulk rewrite。

不要建：

```text
條件式 modifier（需要判斷裝備 / 戰鬥狀態才成立者）
expression / predicate 欄位
target 由資料任意指定的開放式修正
```

Medium Armor Master 與 Dual Wielder 需要看角色當下裝備才成立，屬 K.6 的 `deferred_equipment_conditional`，不進本節。

## K.4 Feat prerequisite normalization

把 reference prerequisites materialize 成 server-authoritative typed data。

至少支援本 inventory實際需要的：

```text
ability minimum
armor proficiency
can cast at least one spell
AND / OR composition where actually required
repeatable / non-repeatable acquisition legality
```

現有 P1 `feat_failure_reason()` / prerequisite resolver優先泛化，不建立 PHB-only validator。

Numeric Override只沿 P1已定義的 effective numeric prerequisite語意運作；不能 bypass：

```text
ASI timing
feat count
armor proficiency
spellcasting structural prerequisite
repeatability rule
```

已取得的 non-repeatable Feat 在後續 Feat opportunity 必須由 server option generation排除或 disabled，final validation仍需阻擋 forged duplicate payload。

### Prerequisite evaluation context

現有 `feat_failure_detail()` 只收 effective abilities，且只認 `ability_score` + `minimum_score`；其餘形狀一律落到 `unsupported_feat_prerequisite`，結果是該 Feat 被永久 disabled。K 需要的四種形狀有兩種不在這個簽名的視野內：

```text
ability minimum      effective abilities
armor proficiency    已取得的 proficiencies
can cast a spell     spellcasting 來源
AND / OR             以上任意組合
```

所以 resolver 的輸入必須擴成一份統一的 evaluation context，而不是再加參數疊上去。要求：

- 單一 resolver 同時服務 option generation（disabled reason）與 final validation（blocking issue），不得為兩條路徑各寫一份判定。
- Variant Human 與 ASI → Feat 共用同一個 resolver 與同一份 context 組法。
- `unsupported_feat_prerequisite` 保留為真正未知形狀的最後防線，但 K 完成後 41 個 Feat 都不該再命中它。

### Prerequisite failure reporting

沿用 M02-H 已拍板的語言中立 `code + params`，**不為每種前置條件新增 code**。`feat_prerequisite_not_met` 的 `requirements[]` 升級成可辨別型別的清單，概念上：

```text
{"type": "ability",           "ability": ..., "minimum_score": ...}
{"type": "armor_proficiency", "proficiency_ref": ...}
{"type": "spellcasting"}
{"type": "any_of",            "options": [ ...上述任一... ]}
```

理由：複合 AND 時能一次列出全部未達項；每種前置條件各給一個 code 的話只能挑一個回報，使用者看不到完整缺口，code 數量也會隨規則來源持續膨脹。

前端只擴充既有的 requirement 格式化函式：多認三種 type、`any_of` 以「或 / or」連接、`proficiency_ref` 走既有 content localization 取名稱。canonical identity 仍走 StableKey，不把在地化字串塞進 params。

## K.5 Feat nested choices / source-granted option entitlement

需要選擇的 Feats 使用 generic deterministic choice IDs。對 repeatable Feat，choice identity 必須包含 acquisition/opportunity identity，而不能只有 Feat StableKey，例如概念上：

```text
feat:<acquisition-id>:ability
feat:<acquisition-id>:proficiencies
feat:<acquisition-id>:spell-source
feat:<acquisition-id>:cantrips
feat:<acquisition-id>:spell
feat:<acquisition-id>:maneuver
```

具體 prefix可沿現有 Builder convention，但必須：

- Draft reload deterministic。
- Direct Create與 Level Up一致。
- 切換 Feat後 stale child values不進 Build。
- Variant Human與 ASI/Feat共用同一 child-choice compiler。
- repeatable Feat不同 acquisition 的 child selections彼此隔離。

代表：

### Resilient

```text
choose one ability
→ ability +1
→ corresponding saving throw proficiency
```

### Skilled

```text
choose exactly 3 legal skill/tool proficiencies
```

### Weapon Master

```text
choose STR or DEX +1
+ choose reference-defined legal weapon proficiencies
```

### Magic Initiate

```text
choose legal source class
→ derive that class spell list
→ choose required cantrips
→ choose required level-1 spell
→ persist casting-source choice / spell refs
```

不要 hardcode spell names到 frontend。

### Elemental Adept

- Feat data明確標成 repeatable。
- 每次 acquisition 產生自己獨立的 feat-specific choice。
- 不同 acquisition 的 choice distinctness 由 materialized Feat data 驗證；不能因 `feat_ref` 相同而合併。

### Martial Adept

重用 M01-I / M01-J 已存在的 canonical Maneuver identities；不得再建第二批 maneuver StableKeys。

目前 Maneuver content 的 `eligible_class_refs` 是 **class-native entitlement**，不能為了 Martial Adept 直接刪掉或全域放寬。K 要把 option-pool legality泛化成：

```text
native class eligibility
OR
explicit source-granted entitlement
```

其中 feat-granted entitlement 需保留 granting source，例如 `source_ref=<Martial Adept acquisition/feat>` 或等價 provenance。Choice generation與 final validation都必須理解這個來源；不能只在 UI 放行，最後又被 M01-I final validator擋掉。

Martial Adept 本身還必須 materialize supplied reference 定義的：

- maneuver choice count / distinctness。
- superiority-die resource contribution。
- 與既有 superiority-die pool 的 stacking / aggregation semantics。
- 沒有既有 pool 時的 standalone die metadata。
- recharge metadata。

若實際花費 / Rest recovery仍需要未來 runtime，K只要求正確 Build-derived capacity / State resource representation與 recharge metadata，不提前做 Combat / Rest Engine。

## K.6 Feat automation classification

每個 Feat runtime data需有可驗證的 automation classification，形式可依現有 metadata convention，例如：

```text
automation = full
automation = static_derived
runtime_execution = deferred_roll
runtime_execution = deferred_combat
runtime_execution = deferred_reaction
runtime_execution = deferred_rest
runtime_execution = deferred_equipment_conditional
```

或等價 typed enum/flags。

`static_derived` 對應 K.3 的 whitelisted derived modifier；`deferred_equipment_conditional` 對應「規則靜態但需先判斷裝備」的效果。兩者都是 K 新增的格子，缺了它們 Tough / Observant 與 Medium Armor Master / Dual Wielder 會被迫錯誤歸類。

目的是讓 UI / maintainer知道哪些效果目前只是正式描述 + structured metadata，不是要求建立通用 effect interpreter。

涉及下列 runtime context的效果可 deferred：

```text
attack roll / damage roll
advantage / disadvantage execution
reaction / opportunity attack
reroll transaction
shove / forced movement
target / range / cover execution
concentration check transaction
turn/action economy
```

但 prerequisite、永久 choice、ability/proficiency grant不能因另有 deferred combat效果就整個 Feat都只留 description。

## K.7 Spell inventory reconciliation

K 不從空白建立 42 個 spell。

```text
EXPECTED_42
∩ current phb2014 spell identities
→ existing entries to enrich

EXPECTED_42
- current identities
→ missing entries to create
```

Closeout assertion：

```text
expected 42 keys == installed 42-scope keys
```

不能 duplicate StableKey，也不能因舊 shard裡已有空 `desc` 就視為 catalog完整。

## K.8 Spell canonical data / shard normalization

```text
canonical English name
level
school
casting_time
range
components / material metadata where supplied
duration
ritual
concentration
PHB class access
description
provenance
```

現有：

```text

spells-m01j.json
```

可以合併為：

```text
spells.json
```

或 deterministic shards；是否 rename不是核心 requirement。核心是：

- 每個 StableKey只載一次。
- 沒有 phase-specific雙主資料。
- existing Build spell refs不改 key。

## K.9 Spell access provenance model

Spell identity與「某來源讓某 class可選它」分開。

對 PHB spell：

```text
identity = phb2014:spell:<index>
```

Canonical spell entry的 PHB class access只放 PHB來源本身的 access。

若 reference table因後來規則已列 Artificer等 access：

- 不把 Artificer寫成 PHB原始 access。
- 由 `tce` Optional Class Feature / class-spell relation / expanded access overlay提供。
- 同一 spell identity仍被 TCE relation引用，不複製成 `tce:spell:<same-spell>`。

若現有 spell schema將 `classes[]`直接當唯一 access source，K需把它泛化成能保留 source-aware access relation，或至少確保 base PHB access與既有 TCE overlay不互相污染；不能用一個無 provenance的 classes list把來源混掉。

## K.10 Spell Builder integration

沿用 P1 spellcasting engine。


```text

+ enabled source expansions / grants
→ eligible access pool
→ known/spellbook/prepared rules
```

Expanded access本身仍不代表 Known / Prepared。

## K.12 Localization policy / completeness

Supplied reference中文規則文字可以直接作 `zh-TW` presentation source。英文 presentation依 M02 policy補齊；不要求使用與中文 reference相同來源或逐字對照，但語意要與 canonical mechanics一致。

K 必須**擴充既有 localization field policy SSOT**，不能另寫 K-only completeness checker。具體以 `data/localization/localizable-fields.json`（或開工時已正式取代它的同一 SSOT）加入 K 真正 user-visible 的 required field coverage：

```text
pack=phb2014, kind=feat,  data.desc.*
pack=phb2014, kind=spell, data.desc.*
```

並將 K 新增／首次 expose 的 prerequisite、choice、manual/deferred presentation field 納入同一 policy（若這些文字以獨立 localizable field存在）。既有 wildcard `name` rule繼續沿用。

要求：

- `zh-TW` / `en` 都是 required supported locales。
- 缺任一 required description translation時，既有 completeness gate必須 fail。
- policy coverage本身要可 machine-check，避免資料存在但 policy漏列。
- **在上述 policy擴充尚未生效前，任何只驗到 name 的 completeness green 都不能算 M01-K closeout evidence。**

Canonical `name` / StableKey / mechanical field仍 locale-neutral，不能把中文塞 canonical identity再靠 en locale覆蓋。

## K.13 Build / persistence compatibility

Feat permanent selection沿 P1 Build semantics；Spell Known / Spellbook / access沿 P1 Build semantics；Daily Prepared仍在 State。

K不得：

- rename `srd5.1:feat:grappler`。
- rename既有 `phb2014:spell:*`。
- bulk rewrite舊 immutable Build。
- 把 daily prepared selection搬回 Build。
- 把 repeatable Feat acquisitions壓回 unique `feat_refs` 後遺失 acquisition-specific choices。

Version N已有 feat/spell refs時，Level Up / Build Edit seed要維持 deterministic round-trip。舊 Build若只有 unique feat summary，載入時按 legacy語意建立兼容 view；新 K acquisition records則是 repeatable Feat 的 canonical persistence。

## K.14 UI

不新增 PHB Feat Library頁或 PHB Spell Library管理系統。

沿用既有 Builder：

```text
Variant Human / ASI opportunity
→ Feat selector
→ nested choices

Spell step
→ searchable eligible spells
→ Known / Spellbook selections
→ Review
```

Feat / Spell selector顯示 source label；description可直接顯示由 reference materialized 的正式 locale text。

對 Feat：

- non-repeatable Feat再次遇到 Feat opportunity時不應呈現為可合法重選；若顯示 disabled，理由由 server提供。
- repeatable Feat每次 acquisition 的 nested choice UI使用 acquisition-specific identity，不覆寫前一次 selection。

UI不得把 `runtime_execution=deferred_*` 的效果標成「自動套用」。

## 7. M01 Anti-patterns

以下一律視為設計錯誤：

1. 非 SRD data寫入 `data/srd5.1/`。
2. 新 data偽裝 `source=srd5.1`。
3. 用 display name當 foreign key。
4. 同名後載內容覆蓋先載內容。
5. Frontend hardcode Variant Human / Dhampir / Artificer / Optional Feature / Subclass / PHB Feat legality。
6. 每個 Builder module各自解析 `/api/2014/...`。
7. `content_sources`同時被當 allowlist與actual provenance，語意混用。
8. 掃描 `data/`所有子資料夾並自動 enable pack，導致fixture/未完成pack污染 production registry。
9. Variant Human在 M01-B被拆成 `srd5.1:race:human + race_variant_ref`，或讓 `variant_of`觸發 ordinary Human mechanical inheritance。
10. Half-Elf replacement只 hide UI、不移除 final Build grants。
11. Dhampir old race + lineage完整疊加。
12. Artificer用 scattered `if artificer: ceil`而 rules config仍只寫 `half`。
13. Known Infusions與Active Infusions都放 Build。
14. Active Infusion在 Inventory與State mapping各存一份。
15. 為完整 Magic Items提前建立 generic Attunement / charges subsystem。
16. TCE Optional Class Feature replacement只 hide UI、不移除 final Build grants。
17. Fighting Style / Maneuver / Metamagic / Invocation擴充由 Frontend hardcode option list。
18. Expanded spell access被誤寫成 Known / Prepared spell。
19. Versatility直接 in-place改 immutable Build Version。
20. Subclass gate使用 total Character Level而不是 target Class Level。
21. 跨書 reprint以 display name去重或因 load order決定 canonical identity。
22. 建 schema-incomplete fake spells / dangling refs只為讓 Artificer或Subclass spell list看起來完整。
23. Flavor table變 mandatory Builder choice。
24. Full closeout才發明前面 Subphase本來就該完成的 major schema。
25. 為 future books / 2024 ruleset先設計沒有 supplied content驗證的機制。
26. 把 `docs/` 或其他人工規則文件當成 runtime content source。
27. 因為 reference text可以搬用，就讓 runtime直接 parse Markdown。
28. 把 reference中後來 TCE 增加的 Artificer spell access寫成 PHB canonical class access。
29. 對 M01-I/J已存在的 `phb2014:spell:*` 在 K再建立第二份相同 StableKey。
30. 41 個 PHB Feats只放 description，不結構化現有 substrate明明能表達的 ability/proficiency/nested choices。
31. 為 Sentinel / Lucky / War Caster 等效果在 K提前建立 generic Combat/Roll trigger engine。
32. 把 Spell完整描述資料誤解成 K必須實作完整 Spell execution engine。
33. 用 set / `dict.fromkeys` 等 identity-only dedupe 把合法 repeatable Feat acquisitions靜默壓成一筆。
34. 為了讓 Martial Adept 工作而刪除／全域放寬 Maneuver 的 class-native eligibility，讓沒有 feat/source entitlement 的 non-Fighter 也能使用該 pool。
35. Martial Adept只存 maneuver refs，卻遺失其 feat-granted resource / stacking / recharge semantics。
36. `phb2014` Feat / Spell descriptions沒有進 localization policy required coverage，卻因 name-only completeness gate green 就宣告 K localization完成。
