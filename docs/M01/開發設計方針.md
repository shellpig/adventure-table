# M01 — 開發設計方針

> Phase：**M01 — D&D 5e 2014 Private Content Expansion**  
> 本文件定義 M01-A～M01-J 的具體實作契約：Content Pack、StableKey、Builder / Character / Inventory 接線、資料 layout、compile order、Build / State 邊界、migration 與相容策略。  
> 「完成後必須為真」以 `實作規格.md` 為準；測試證據以 `測試指南.md` 為準。

最後更新：2026-08-30

## 1. M01 開工基線

M01 直接建立在已 closeout 的 P0 / P1 上；禁止重做第二套 Character / Builder core。

必須沿用：

```text
data/srd5.1/
apps/server/app/content/schemas.py
apps/server/app/content/registry.py
apps/server/app/domain/character/schemas.py
apps/server/app/domain/character_builder/
data/rules/dnd5e-2014/character-builder.json
P1-G immutable Build Version / Level Up / Build Edit / Correction
P0/P1 Character Sheet + Current State APIs
```

目前已知硬耦合：

1. `ContentEntry.key` regex 寫死 `srd5.1`。
2. `ContentEntry.source` 寫死 `Literal["srd5.1"]`。
3. `ContentManifest.id/license/extraction/scope_guard` 是 SRD-specific。
4. `ContentRegistry.DEFAULT_CONTENT_ROOT` 只指向 `data/srd5.1`。
5. Registry `expected_key` / `resolve()` / URL ref normalize寫死 `srd5.1`。
6. `CharacterBuild.require_stable_key()` 第一段寫死 `srd5.1`。
7. Builder `basics.py` / `structural.py` 等重複把 `/api/2014/...` 解析成 `srd5.1:*`。
8. class-level lookup有 `srd5.1:level:<class>-<level>` 假設。
9. spellcasting rules config目前 `slot_contribution = full|half|none` 無法表達 Artificer half-ceil。

M01-A 先解除 1～8；G 再補 9。

## 2. 全 M01 共通架構

### 2.1 Content Pack directory

正式 layout：

```text
data/
├── srd5.1/
├── phb2014/
├── scag/
├── gos/
├── vgm/
├── vrgr/
├── tce/
└── rules/
    └── dnd5e-2014/
```

`data/rules/dnd5e-2014/` 是 ruleset computation config，不等同來源內容 Pack。

### 2.2 Pack IDs

M01 固定：

```text
srd5.1
phb2014
scag
gos
vgm
vrgr
tce
```

Pack ID lexical contract建議：

```regex
^[a-z0-9][a-z0-9.-]*$
```

禁止 `:`。

### 2.3 StableKey

```text
<pack-id>:<kind>:<index>
```

建議 central parser：

```python
@dataclass(frozen=True)
class ParsedStableKey:
    source: str
    kind: str
    index: str
```

所有 domain validator / registry / builder helper共用 parser；不要各自 `split(":", 2)` 後再寫不同規則。

StableKey parser只處理 lexical shape / kind；「key是否真的存在」需有 Registry context，在 compiler/service validation做。

### 2.4 Reference representation

新 non-SRD normalized data優先使用 explicit ref：

```json
{
  "key": "srd5.1:skill:stealth",
  "name": "Stealth"
}
```

允許 optional：

```json
{
  "key": "srd5.1:skill:stealth",
  "index": "stealth",
  "name": "Stealth"
}
```

但 identity以 `key` 為準。

舊 SRD legacy ref仍可能是：

```json
{
  "index": "stealth",
  "name": "Stealth",
  "url": "/api/2014/skills/stealth"
}
```

建立 single helper：

```text
reference_to_stable_key(reference)
```

規則：

1. explicit `key` → parse / validate。
2. 沒 key、符合 legacy SRD URL → normalize到原 `srd5.1:*`。
3. 其他 → invalid；不要猜 source。

### 2.5 ContentEntry envelope

M01-A後 concept：

```text
key
index
name
source
ruleset
data
```

`license` 不再是每筆必須 `CC-BY-4.0` 的 Literal；provenance / license以 Pack manifest為主。

可保留 entry-level optional provenance override，但不必要就不要每筆重複。

### 2.6 Generic Manifest

建議：

```json
{
  "id": "phb2014",
  "name": "Player's Handbook 2014 — Private Content",
  "ruleset": "dnd5e-2014",
  "provenance": {
    "type": "user-supplied-private-reference",
    "reference_documents": [
      "docs/暫用規則資訊/背景_PHB.md",
      "docs/暫用規則資訊/種族_PHB_非SRD內容.md"
    ]
  },
  "license": null,
  "categories": [],
  "total_entries": 0,
  "extensions": {}
}
```

SRD-specific：

- CC-BY metadata。
- extraction repo / commit。
- P4-A Monster/Beast scope guard。

這些放在 SRD manifest的 optional / extension schema，不強迫所有 pack都有。

### 2.7 Registry indexes

M01-A後：

```text
manifests_by_source: dict[source, ContentManifest]
entries_by_key: dict[StableKey, ContentEntry]
entries_by_kind: dict[kind, tuple[ContentEntry, ...]]
entries_by_source_kind: dict[(source, kind), tuple[...]]
```

Global uniqueness只看 full StableKey。

### 2.8 Installed pack config

Private project不做內容管理 UI。

先使用 repository-side deterministic config，例如：

```python
DEFAULT_CONTENT_PACKS = (
    REPOSITORY_ROOT / "data" / "srd5.1",
    ...existing completed packs...
)
```

各 Subphase完成時才把 pack加入 default installed list；A不能預設不存在的未來資料夾。

### 2.9 Content source display

API reference DTO需要能返回：

```text
key
name
kind
source_id
source_name
```

Frontend selector：

```text
Wood Elf · PHB
Goblin · VGM
```

source只作辨識，不強迫「先選書」。

### 2.10 Build provenance

Compiler完成 candidate後收集所有正式 Build refs的 source prefix。

至少包含：

- race / subrace / variant / lineage。
- background。
- class / subclass progression。
- feature / feat。
- spell access sources。
- starting equipment source references（若 Build保留）。

再：

```text
dedupe
→ deterministic sort
→ CharacterBuild.content_sources
```

Frontend不可直接指定。

### 2.11 Existing JSONB相容

新 optional Build/State fields一律有 backward-compatible defaults。

原則：

- 不因新增 field而 rewrite全部舊 JSONB。
- old `content_sources=["srd5.1"]` 合法。
- old Inventory沒有 `attuned` → default false。
- old Build沒有 variant / lineage → null / absent semantics。

# M01-A — Multi-Source Content Pack Foundation

## A.1 主要修改面

優先檔案：

```text
apps/server/app/content/schemas.py
apps/server/app/content/registry.py
apps/server/app/domain/character/schemas.py
apps/server/app/domain/character_builder/basics.py
apps/server/app/domain/character_builder/structural.py
apps/server/app/domain/character_builder/equipment.py
apps/server/app/domain/character_builder/spellcasting.py
apps/server/app/domain/character_builder/progression.py
apps/server/app/domain/character_builder/compiler.py
apps/server/app/api/... reference endpoints（實際名稱依 codebase）
apps/web/... selectors / reference labels（必要最小修改）
```

實作前先 grep：

```text
srd5.1:
DEFAULT_CONTENT_ROOT
/api/2014/
resolve(
level:
```

把 runtime hardcode列成 checklist逐一消除；source-specific test fixture / known SRD correction可以保留，因為它真的只屬 SRD。

## A.2 StableKind策略

M01-A只保留當下已有 kinds。

不要現在加入：

```text
race-variant
lineage
infusion
```

分別等 E/F/H真正需要再加。

## A.3 Cross-reference validator

新的 recursive reference walker只把「符合 explicit ref contract或 legacy SRD ref」視為 content reference。

不要把普通 dict裡碰巧有 `key` 字串都當 reference。

建議 typed `ContentReference` model或 recognizable shape：

```text
key + optional name/index
```

validator要能確認 expected kind；例如 `race.parent`不得指 spell。

## A.4 Source-aware class level lookup foundation

把：

```text
srd5.1:class:fighter
→ srd5.1:level:fighter-5
```

改為 source-aware：

```text
<class source>:level:<class index>-<n>
```

或更穩：ClassData / progression config explicit `level_refs`。

A階段不需要改現有 SRD data格式，只要 helper不再固定 `srd5.1`。

## A.5 Builder option queries

禁止：

```text
registry.resolve(kind, index)
```

若 caller有 full key就直接 `get(key)`。

真的需要 source+kind+index時：

```text
registry.resolve(source, kind, index)
```

## A.6 Test fixture packs

不要用正式 PHB作 A的唯一驗證；建立 tiny fixture pack能精準測：

- source identity。
- cross-pack ref。
- duplicate key。
- wrong kind。
- same index different source。

# M01-B — PHB Background & Core Race Completion

## B.1 Pack layout

```text
data/phb2014/
├── manifest.json
├── backgrounds.json
├── races.json          // Variant Human，如採完整 race
├── subraces.json
├── traits.json         // 若需要獨立 reusable feature
├── features.json       // background / racial feature需要時
└── NOTICE/REFERENCE.md // optional maintainer provenance
```

不要求每個 category一定存在；manifest列實際存在者。

## B.2 Background schema extension

現有 `BackgroundData`至少有：

```text
starting_proficiencies
starting_equipment
```

M01-B需 typed support existing Builder真正會讀的欄位：

```text
starting_proficiency_options
language_options
starting_equipment_options
feature
roleplay_suggestions
variant_of / variant_label（若 supplied variant需要）
```

若沿用 upstream D&D API canonical option shape，優先共用 P1 existing choice parser；不要另造 `phb_background_choice`格式。

## B.3 Roleplay suggestion model

建議：

```json
"roleplay_suggestions": {
  "personality_traits": ["..."],
  "ideals": ["..."],
  "bonds": ["..."],
  "flaws": ["..."]
}
```

Frontend只把選項寫入 existing `roleplay_profile`。

若 SCAG後續要 reuse PHB table，可在 C增加：

```text
roleplay_suggestion_source_ref
```

B不必過早實作 reuse，除非做了也很自然。

## B.4 Parent race cross-pack refs

PHB subrace：

```json
{
  "key": "phb2014:subrace:wood-elf",
  "race": {"key": "srd5.1:race:elf"}
}
```

Builder subrace filter不能用「source必須跟 parent相同」；要以 `subrace.data.race.key == selected_race.key`。

## B.5 Variant Human data

以 full race entry實作：

```text
phb2014:race:variant-human
```

Data應包含三個 structural choices：

```text
ability choice: choose 2 distinct from six, each +1
skill choice: choose 1 from all skills
feat choice: choose 1 from eligible feats
```

### Ability choice

不要用 generic `reference count=+1` 造成同 ability可選兩次。

Choice resolver要支援：

```text
choose_count=2
allow_duplicates=false
category=ability_bonus
count=1
```

### Feat choice

Option generation來自：

```text
registry.list_kind("feat")
```

每個 option套 existing `feat_failure_reason()`；disabled reason回到 UI。

## B.6 Racial spell source

Existing `SourceType`已有 `race`，可直接用。

對 racial cantrip / leveled spell：

```text
SpellAccessEntry.source_type = race
source_key = race/subrace feature identity
access_type = granted / always_prepared（依真正語意）
```

若是「每天可施展一次、不用 spell slot」不要假裝成 prepared spell；需要 feature-specific resource metadata。

## B.7 Background equipment

沿用 P1 `starting_equipment_choices` namespace。

不把 Background equipment choice塞回 generic choice namespace。

Confirm只在 Version 1建立 initial Inventory一次。

# M01-C — SCAG / GoS Background Expansion

## C.1 Pack layout

```text
data/scag/backgrounds.json
data/gos/backgrounds.json
```

必要 reusable features / tables可拆：

```text
features.json
roleplay-tables.json
```

但不要為了資料漂亮過度拆檔。

## C.2 PHB roleplay table reuse

SCAG supplied資料常出現：

```text
使用 PHB Soldier / Guild Artisan / Sage 等表格作為基礎
```

建議 normalized representation：

```json
"roleplay_suggestions": {
  "inherits_from": "phb2014:background:soldier",
  "guidance": "..."
}
```

Builder resolution：

```text
selected background own tables
else inherits_from target tables
+ optional guidance text
```

這只是 suggestion reuse，不能讓 SCAG Background mechanical grants繼承 PHB Background mechanical grants。

也就是：

```text
roleplay inheritance != rule inheritance
```

必須在 code/model分開。

## C.3 Background variant identity

若 supplied background是某背景 variant：

方案優先：保持它是一個完整 `background` entry，另加：

```text
variant_of: StableKey | None
```

原因：Builder目前 top-level只選一個 `background_ref`；讓 variant擁有自己的 background stable key最簡單，也最適合 Version History。

除非資料本質只是同 entry內 branch，才用 nested choice。

## C.4 Mechanical table vs flavor table

Converter要分類：

**mechanical：** skill/tool/language/equipment/feature。  
**roleplay：** personality/ideal/bond/flaw、story table、hardship table、specialty flavor。

例如 GoS Fisher的 Fishing Tale不應變成 required builder choice；可作 optional roleplay suggestion/custom field。

## C.5 Currency / special objects

若 source equipment含「裝有 X gp 的囊袋」而現有 P1 inventory尚未把 currency當item，沿用當時既有 P1 policy；不可在 C私自新增 economy subsystem。

至少要在 normalized data保留 amount/provenance，若現有 initial State已有 currency field則接入；沒有就以已定義的 minimal representation處理並在文件註明。

## C.6 Source badge

Reference DTO不要靠前端把 `scag`硬翻成文字；registry manifest提供 display name / short label。

# M01-D — VGM Race Expansion

## D.1 Pack layout

```text
data/vgm/
├── manifest.json
├── races.json
├── subraces.json
├── traits.json
└── features.json // 若 limited-use feature需要獨立 identity
```

## D.2 Race schema fields

現有 `RaceData`只有：

```text
speed
ability_bonuses
languages
traits
subraces
```

M01-D supplied rules需要額外 typed / normalized能力：

```text
size_options / size
movement_modes
resistances
racial_spellcasting
level_gated_features
resource_features
```

不一定全部直接塞 RaceData；也可放 Trait/Feature資料，再由 Race refs組合。

優先 reusable feature entry，避免 RaceData變萬用垃圾桶。

## D.3 Limited-use resource descriptor

建議 feature data有：

```json
"resource": {
  "capacity": {"type": "fixed", "value": 1},
  "recharge": ["short_rest", "long_rest"]
}
```

或：

```json
"capacity": {"type": "proficiency_bonus"}
```

M01-D不需要 recovery engine；但 Build compiler可產生 resource capacity descriptor，initial Current State可初始化 counter。

Resource key deterministic：

```text
feature:<feature stable key>
```

不要用 translated display name當 key。

## D.4 Hobgoblin weapon choice

Martial Training的 2 weapons choice需要 filter：

```text
registry equipment / proficiency entries
where category == martial weapon
choose_count=2
allow_duplicates=false
```

不要 hardcode四五把武器。

## D.5 Aasimar parent/subrace

Parent：

```text
vgm:race:aasimar
```

Subrace：

```text
vgm:subrace:protector-aasimar
vgm:subrace:scourge-aasimar
vgm:subrace:fallen-aasimar
```

Parent `subraces` refs指向三者。

Builder subrace selector必須 exactly one；不能允許母種族無 subrace Confirm。

## D.6 Aasimar level-gated feature

Feature representation建議：

```json
{
  "key": "vgm:feature:radiant-soul",
  "minimum_character_level": 3,
  "resource": {"capacity": 1, "recharge": ["long_rest"]}
}
```

Compiler在 target level / level-up candidate中決定是否加入 `feature_refs`。

注意是 **Character Level**，不是 class level。

## D.7 Aasimar Light cantrip

Spell access source可用 parent race feature：

```text
source_type=race
source_key=vgm:feature:light-bearer
```

CHA casting ability需能顯示；不建立 fake class spell profile。

## D.8 Transform between Aasimar subraces

不用新 workflow；P1 Build Edit seed existing build，replace `subrace_ref`與對應 grants，產生新 version。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## E.1 新 StableKind

E才新增：

```text
race-variant
```

更新：

- `StableKind`
- manifest category validation
- generic reference validation
- reference API kinds（若有 allowlist）

## E.2 Data schema

建議：

```text
RaceVariantData
  index
  name
  base_race_ref
  replacements[]
  choices[]
  optional level_gated_grants[]
```

Replacement entry：

```text
target_grant_id / target_feature_ref
action = remove
replacement_choice_id
```

不要用 label string比對 `"Skill Versatility"`。

若現有 SRD Half-Elf把 Skill Versatility只表示為 `starting_proficiency_options` 而沒有 feature stable key，M01-E要先給該 grant一個 deterministic internal grant identity，例如：

```text
grant:srd5.1:race:half-elf:skill-versatility
```

不必修改 external stable content key，但 compiler內要能定位要移除的 grant。

## E.3 BuilderDraft

新增：

```python
race_variant_selection: BuilderReferenceSelection | None
```

Patch DTO也同步。

Seed existing Build Edit時要從 current Build填回。

## E.4 CharacterBuild

新增：

```python
race_variant_ref: StableKey | None = None
```

validator：kind=`race-variant`。

Build Version舊 JSON缺欄位時default null。

## E.5 Compile order

固定：

```text
base race grants
→ subrace grants
→ variant selection validation
→ apply variant removals
→ activate replacement branch
→ compile selected replacement option
→ level-gated variant grants
→ dedupe
→ structural validation
```

不能先compile Skill Versatility兩個skill再「最後只是藏掉feature」。

## E.6 Half-Elf variant option definitions

### Moon/Sun

- wizard cantrip choice：resource list filter spells where Wizard + level 0。
- Elf Weapon Training。
- Keen Senses。

### Wood

- Fleet of Foot。
- Mask of the Wild。
- Elf Weapon Training。
- Keen Senses。

### Aquatic

- Swim Speed 30。
- Keen Senses。

### Drow

- Drow Magic。
- Keen Senses。

另保留 `keep_skill_versatility` branch。

## E.7 Movement modes

Character rules目前若只有單一 `speed`，E需要最小擴充：

```text
walking_speed
optional swim_speed
optional climb_speed
optional fly_speed
```

不要把所有 movement mode塞 Numeric Override string而沒有結構。

若 CharacterSheetDTO目前只顯示 Speed，至少加 secondary movement display。

## E.8 Racial magic

Drow Magic使用 source-specific spell access + feature resource。

Faerie Fire / Darkness若 spell content存在，ref正式 spell；不存在則這 Subphase必須先補可合法 reference的 spell content或明確 content blocker，不可 dangling。

# M01-F — VRGR Lineage & Dhampir

## F.1 新 StableKind

```text
lineage
```

Data pack：

```text
data/vrgr/lineages.json
features.json
```

## F.2 Builder schema

Draft新增：

```text
lineage_selection
ancestral_origin_ref / selection
ancestral_legacy_selection
lineage_ability_choice
lineage_size_choice
```

不一定要每個做 top-level field；但 lineage identity必須是 typed top-level selection，不能全藏 generic map。

Generic choices可保存 ability / skill selection。

## F.3 CharacterBuild schema

建議最小：

```python
lineage_ref: StableKey | None = None
ancestral_origin_ref: StableKey | None = None
ancestral_legacy: AncestralLegacySelection | None = None
```

`AncestralLegacySelection`至少可保存：

```text
retained_skill_refs
retained_movement_modes
```

不要保存完整 old race serialized copy。

## F.4 Race vs lineage authoritative package

推薦方案：

- `race_ref`保留 ancestral origin（對 existing P1 model改動最小）。
- `lineage_ref != None` 時，compiler / rules計算把 lineage視為 active race package。
- `race_ref`的 grants不直接全部套用，只從 `ancestral_legacy`帶回 whitelist。

因此語意：

```text
race_ref = ancestry/provenance
lineage_ref = active race-package replacement
```

Character Sheet顯示：

```text
Dhampir
Origin: <old race>（如有）
```

而不是顯示 old race當 active mechanical race。

## F.5 Direct Create

若選 Dhampir而沒有 inherited race：

- `ancestral_origin_ref`可 null。
- `ancestral_legacy`保存 two skill choices。
- languages按照 direct-create規則。

## F.6 Existing Build Edit

Seed Draft：

```text
base_version_id
old race_ref
old permanent race-derived grants
```

Compiler不應靠「目前 Build裡有哪些 skill」猜哪些來自 race，因為 skill也可能來自 class/background。

要使用 provenance：

- P1 selected grant source_ref。
- Build若沒有 per-grant provenance，M01-F需要在 compiler seed階段依 old race data + Build交集 reconstruct only race-origin eligible grants。

不得把所有 `skill_choices`都當 racial skills保留。

## F.7 Movement retention

只保留 old race的：

```text
climb
fly
swim
```

不保留 walking speed。

Dhampir自己提供 walk 35 / climb 35；若 ancestral fly/swim存在，合併 secondary modes。

## F.8 Ability choice

需要 generic choice表達：

```text
branch A: +2 one + +1 different one
branch B: +1 three distinct
```

所有 ability targets不得重複。

## F.9 Vampiric Bite

Data model不必現在創 `AttackAction`，但 FeatureData可以有 future-runtime metadata：

```text
natural_weapon
attack_ability = constitution
damage = 1d4 piercing
conditional_advantage = hp <= half max
resource_capacity = proficiency_bonus
recharge = long_rest
empowerment modes
```

P4接入時讀此 metadata。

## F.10 Reconciliation

New Build的 resource capacities重新derive；State reconciliation沿 P1：

- damage delta。
- Temp HP。
- Conditions。
- Inventory。
- prepared legality。

新增 lineage不能重建 Inventory。

# M01-G — TCE Artificer Core

## G.1 Pack layout

```text
data/tce/
├── manifest.json
├── classes.json
├── levels.json
├── subclasses.json
├── features.json
├── spells.json        // 只有真正 supplied且足以成為正式 spell entries者
└── ...
```

Magic Items在 I再啟用對應 category；同一 `tce` manifest可在 Subphase增量新增 categories，記得更新 count / validation。

## G.2 ClassData

Artificer entry需具備 existing Class Builder要用的：

```text
hit_die
saving_throws
starting_proficiencies
starting_proficiency_options
starting_equipment
multi_classing
subclasses
spellcasting identity
```

若 generic ClassData現在只驗少數欄位，可保留 `extra=allow`但對 M01 code實際讀取欄位補 typed validation。

## G.3 LevelData

建立：

```text
tce:level:artificer-1
...
tce:level:artificer-20
```

每級至少：

- `level`
- `prof_bonus`
- `features`
- `class` explicit ref → `tce:class:artificer`
- spell slots / cantrips / infusion progression所需數值
- ASI cumulative marker或 equivalent progression field

不要假造 `/api/2014/classes/artificer/levels/...`。

## G.4 ASI detection

現有 P1 structural可能用 `ability_score_bonuses` cumulative counter。

Artificer levels需提供與現有 generic ASI resolver相容的資料；若 resolver目前高度依賴 SRD oddities / marker names，G要抽成 source-independent helper，而不是寫：

```python
if class_ref == "tce:class:artificer": ...
```

## G.5 Spellcasting config schema

把：

```json
"slot_contribution": "half"
```

泛化成：

```json
"slot_contribution": {
  "formula": "full|half|none",
  "rounding": "floor|ceil|none"
}
```

Backward loader可以 normalize舊 string config：

```text
full -> full/none
half -> half/floor
none -> none/none
```

這樣不用一次人工重寫所有 class config也可相容。

Artificer：

```json
{
  "access_model": "prepared",
  "slot_contribution": {"formula": "half", "rounding": "ceil"},
  "resource_pool_type": "normal_multiclass_slots",
  "prepared_formula": "half_class_level_floor_plus_ability",
  "prepared_minimum": 1
}
```

## G.6 Contribution calculation

建立 pure function：

```text
caster_level_contribution(class_ref, class_level, config)
```

不得在 combined slot aggregator裡用 class name分支。

## G.7 Prepared formula

Prepared limit function獨立於 slot contribution：

```text
prepared_limit(profile, class_level, effective_ability_mod)
```

Artificer odd level要 floor；multiclass contribution odd level要 ceil。

## G.8 Spell list / missing content

`registry.list_kind("spell")`後依 spell.classes explicit refs / dedicated class spell list關聯過濾。

若 class reference來自 TCE，legacy SpellData `classes`若只接受 APIReference，需要 M01-A的 explicit ref support。

Source不足以建立某 spell時：

- 不建立 dangling ref。
- 不建立 schema-incomplete fake spell。
- closeout report列 gap。

## G.9 Subclass data

```text
tce:subclass:alchemist
tce:subclass:armorer
tce:subclass:artillerist
tce:subclass:battle-smith
```

Class parent → `tce:class:artificer`。

Subclass selection timing可由 class levels feature marker或 explicit class rule config決定；不要 UI hardcode level 3。

## G.10 Specialist spells

若 supplied doc只列代表 spell而非完整 progression，不能假裝完整。

有完整可 reference資料者，表示為 `always_prepared` / granted spell access，source_type=`subclass`。

## G.11 UI

Level rail不需要 Artificer special page。

沿用 generic：

```text
Class
Subclass
Choices
Spells
Review
```

source badge顯示 TCE。

# M01-H — TCE Artificer Advanced Rules & Infusions

## H.1 Infusion identity策略

開工時先評估：是否需要 independent kind。

推薦新增：

```text
infusion
```

理由：

- Builder需要列出所有 infusions。
- 有 minimum level。
- 有 acceptable item filters。
- 有 attunement metadata。
- Replicate Magic Item有特殊 target item關係。

若確認 `feature` subtype已足夠並不會造成 API混亂，可不增 kind；但三份文件與 test需一致。

## H.2 InfusionData建議

```text
index
name
minimum_artificer_level
requires_attunement
item_filter
modifiers
charges/resource metadata
replicates_item_ref optional
description
```

Item filter不要 free-text only；至少支持 supplied常見：

```text
armor
shield
simple_or_martial_weapon
thrown_weapon
ammunition_weapon
rod_staff_wand
boots
ring
helmet
```

## H.3 Build persistence

新增 Build field方案：

```python
infusion_refs: tuple[StableKey, ...] = ()
```

因「已知注法」是永久 Build choice，放明確 field比塞 `feature_refs`更可讀。

若不想新增 field，至少需有 typed `feature_refs` subtype provenance；但 Version History應能清楚顯示 Known Infusions。

## H.4 Draft choices

每個 Artificer class level依 progression生成 deterministic choice id：

```text
artificer:infusions-known:<acquisition-level>
```

Level Up只要求新增的差額，不重問整份既有已知注法；Build Edit則可調整到規則允許狀態。

## H.5 Current active infusion state

推薦放 CharacterState：

```python
class ActiveInfusion(FrozenModel):
    inventory_entry_id: str
    infusion_ref: StableKey

active_infusions: list[ActiveInfusion] = []
```

比在 `InventoryEntry`內加 `infusion_ref`更容易 validation與未來一對一約束；但若 Inventory API改動成本顯著，以單一 Source of Truth為原則擇一。

禁止同時兩邊各存一份。

## H.6 Active infusion validation

Mutation service檢查：

- actor owns selected inventory entry（現階段Character service scope）。
- infusion在Build Known。
- Artificer level prerequisite。
- item filter符合。
- same item not already infused。
- same infusion active count符合 supplied限制。
- active count < capacity。

拒絕必須 zero side effect。

## H.7 Resource capacity expressions

只支援 supplied需要的有限 expression types：

```text
fixed
proficiency_bonus
ability_modifier(intelligence, minimum=N)
ability_modifier_x2(intelligence, minimum=N?)
class_level
```

不要 generic formula parser。

## H.8 Reconciliation

Artificer Level Up：

- known infusion capacity增加 → new Builder choice。
- active infusion capacity增加 → 不自動新增 active infusion。
- ability mod改變導致 resource capacity變化 → preserve used amount / clamp only if invariant要求。

Build Edit若刪除 Known Infusion但 Current State仍 active：Review必須 blocking，要求先 resolve或由 reconciliation preview明確移除；不得 silent delete。

## H.9 Armorer model

Current State可新增：

```text
class_feature_modes: dict[feature_key, mode_key]
```

或 typed Artificer state extension；優先 generic minimal field可給未來其他 toggle feature使用，但不要萬用 JSON垃圾袋。

Guardian / Infiltrator切換屬 Current State，不產生 Build Version。

## H.10 Spell-Storing Item

State建議：

```text
spell_storing_item:
  inventory_entry_id
  spell_key
  remaining_uses
```

只有 Artificer有該 feature且 inventory entry存在才合法。

M01-H不做 cast action，只做設定／清除／使用次數 state contract若 UI需要。

## H.11 Subclass runtime boundaries

- Steel Defender：只保存 future stat-generation metadata；P4再建 combatant。
- Eldritch Cannon：同上。
- Experimental Elixir：可保存 resource / known options，random roll / consume effect可 manual。
- Armor Model：可做 state toggle，因不需要 Combat Engine也能持久化。

# M01-I — TCE Magic Items

## I.1 Manifest增量

在 existing `data/tce/manifest.json` 新增：

```text
kind=item
file=magic-items.json
count=<actual>
```

總數以 converter output驗證；supplied source應為 84。

## I.2 Item schema

現有 `ItemData`需擴充 typed optional fields：

```text
rarity
item_type
requires_attunement
attunement_requirements
charges
recharge
modifiers
manual_effects
```

建議：

```python
class AttunementRequirement:
    required: bool
    allowed_class_refs: tuple[StableKey, ...]
    allowed_race_refs: tuple[StableKey, ...]
    spellcaster_required: bool | None
    other_text: str | None
```

不要把「奇械師 / 法師 / 牧師」只存中文 free text，否則 validator無法用。

## I.3 Magic item variants

+1/+2/+3每件都是獨立 item entry：

```text
tce:item:all-purpose-tool-plus-1
tce:item:all-purpose-tool-plus-2
tce:item:all-purpose-tool-plus-3
```

可加：

```text
family_id=all-purpose-tool
bonus=1/2/3
```

供 UI grouping，但 stable identity獨立。

## I.4 InventoryEntry

新增：

```python
attuned: bool = False
```

若 item effect需 instance charges且現有 generic resource不適合，可增加：

```text
item_resources: dict[inventory_entry_id, ...]
```

不要把 charges寫回 shared content item definition。

## I.5 Attunement service

建議 domain service：

```text
attune_item(character, inventory_entry_id)
unattune_item(...)
```

Mutation順序：

```text
load Character/State
→ resolve item content
→ verify carried/exists
→ verify requires_attunement
→ calculate capacity
→ check restrictions / bypass flags
→ update State atomically
```

不要讓 frontend直接 PATCH `attuned=true` 跳過 validation。

## I.6 Capacity helper

放 Character Rules Layer / domain helper：

```text
attunement_capacity(build) -> int
```

再搭配：

```text
attunement_requirement_is_satisfied(build, item)
```

Artificer Magic Item Savant提供 bypass flags，而不是 item service硬判 `if artificer_level >= 14`。

## I.7 Simple modifiers

建立有限、typed modifiers，例如：

```text
spell_attack_bonus
spell_save_dc_bonus
weapon_attack_bonus
weapon_damage_bonus
armor_class_bonus
saving_throw_bonus
```

只把 existing Rules Layer可安全計算的 modifier接入。

Modifier要帶 scope：

```text
class_ref / spell_source / weapon item / all saves
```

例如 All-Purpose Tool只影響 Artificer spells，不是全角色所有 spell attacks。

## I.8 Manual effects

Content可有：

```json
"manual_effects": [
  {
    "summary": "...",
    "reason": "requires per-dawn trigger / target selection"
  }
]
```

Character Sheet item detail顯示「需手動裁定／尚未自動化」。

## I.9 TCE 84-item converter

建議建立 maintainer script：

```text
scripts/vendor_private_tce_items.py
```

或 generic private content conversion script。

要求 deterministic：

- same input → same JSON order / keys。
- generated stable index deterministic。
- duplicate canonical name需要 explicit disambiguation。
- conversion完成後 schema validate。

Runtime不執行 converter。

## I.10 Soul of Artifice integration

若 H已提供 rule flag，I在 attuned count改變後 Character Sheet calculation可derive save bonus。

不保存 duplicated `soul_of_artifice_bonus` state；它應從 Build + attuned count derive。

## 4. Data conversion固定流程

每份 supplied Markdown：

```text
讀 reference
→ 列機械 records
→ 定 StableKey
→ 建 cross refs
→ 分 mechanical / roleplay text
→ 建 choices / prerequisites / level gates
→ schema validate
→ focused domain tests
→ Builder Review / Confirm test
→ human / E2E
```

不接受：

```text
Markdown → bulk JSON → json.loads成功 → 宣告完成
```

每筆 mechanical record至少核對：

- source / identity。
- parent relationship。
- ability bonuses。
- proficiencies。
- choices + counts + distinctness。
- movement modes。
- level gates。
- spell sources。
- resource capacity / recharge metadata。
- equipment quantities。
- Build vs Current State ownership。

## 5. M01 Anti-patterns

以下一律視為設計錯誤：

1. 非 SRD data寫進 `data/srd5.1/`。
2. 新 data source偽裝 `srd5.1`。
3. 以 display name作 foreign key。
4. 同名 content後載覆蓋先載。
5. Frontend hardcode Variant Human / Dhampir / Artificer legality。
6. Builder每個模組各自解析 `/api/2014/...`。
7. Half-Elf replacement只隱藏 UI、不移除 Build grant。
8. Dhampir把 old race + lineage全疊加。
9. Artificer用 `if class == artificer: ceil`，rules config仍宣稱普通 half。
10. Known Infusions與active infused items都放 Build。
11. Attunement直接任意 PATCH boolean、不走 server validation。
12. 為了 TCE items建立 generic scripting DSL。
13. 建 incomplete fake spell / dangling refs只為讓 Artificer列表看起來完整。
14. 把 flavor tables變 mandatory builder choices。
15. M01-J才發明前面應該已完成的大型 schema。
16. 為 M02 / future books預先設計沒有實際 supplied content驗證的機制。
