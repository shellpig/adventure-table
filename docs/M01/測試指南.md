# M01 — 測試指南

> Phase：**M01 — D&D 5e 2014 Private Content Expansion**  
> 本文件定義 M01-A～M01-J 的自動測試、real-backend E2E、人工檢視與 closeout 證據。  
> Subphase 名稱與順序必須與 `實作規格.md`、`開發設計方針.md` 完全一致。

最後更新：2026-08-30

---

## 1. 共通驗證原則

M01 是建立在已 closeout 的 P0 / P1 上，因此每個 Subphase 除了自己的測試外，都必須遵守：

1. **Backend tests green**。
2. **Frontend build / typecheck / unit tests green**。
3. 任何有 DB schema / migration 變更的 Subphase，都要驗 fresh database + migration path。
4. 不得破壞 existing SRD-only Character load / Character Sheet。
5. 不得破壞 P1 Builder Create / High-level Create / Multiclass / Spellcasting / Level Up / Version History。
6. StableKey / content validation 的錯誤應 fail-fast，不接受 silent fallback。
7. UI 有新增選擇流程時，至少補 real-backend browser coverage；不要只靠 mocked frontend unit test。
8. 文件提供的 supplied rules 必須以 deterministic fixtures驗證關鍵數值／選擇，不只 snapshot 大段 JSON。

每個 Subphase closeout 前都要回答：

```text
新增內容真的能進 Builder / Character / Inventory 嗎？
既有 SRD flow 還正常嗎？
reload / restart 後還一樣嗎？
錯誤資料會被擋下來嗎？
```

# M01-A — Multi-Source Content Pack Foundation

## Automated tests

至少建立 tiny test packs，例如：

```text
test-pack-a
  race:test-race

test-pack-b
  feature:test-feature
  cross-ref → test-pack-a:race:test-race
```

### Positive cases

- 一次載入 SRD + test pack。
- `registry.get("test-pack-a:race:test-race")` 成功。
- `list_kind("race")` 同時包含 SRD 與 test pack race。
- cross-pack explicit key reference 成功。
- legacy SRD `/api/2014/...` reference仍 normalize 成原 key。
- Character schema接受非 SRD stable key shape。
- Build compiler可推導 multi-source `content_sources`。
- `content_sources` order deterministic。

### Negative cases

必須 fail：

- malformed pack id。
- malformed stable key。
- envelope source與 key prefix不同。
- duplicate stable key。
- missing manifest category file。
- manifest count mismatch。
- explicit cross-pack dangling key。
- reference expected `race` 卻指向 `spell`。
- 同一 pack同一 key重複。

必須成功：

- 不同 pack都有 `race:goblin`，兩者同時存在。

### Regression

- 原 `srd5.1:*` stable key一筆都不改名。
- SRD manifest / 1,944 existing entries仍可載入。
- P0/P1 tests不需要把 stable key fixture全部改成新格式。

# M01-B — PHB Background & Core Race Completion

M01-B 是 M01 第一個 user-facing gate，測試要求高於一般 content import。

## Content tests

對每個 PHB background至少驗證：

- stable key source = `phb2014`。
- fixed skill proficiencies。
- tool / language choice count。
- starting equipment quantities / branch。
- background feature存在。
- roleplay suggestion fields可讀。

對每個新增 race/subrace至少驗證：

- parent race reference。
- ability bonus / choice。
- speed。
- proficiencies / features。
- level-gated spell / feature（有的話）。

不要用「每檔 JSON 可 parse」取代逐項 mechanical assertions。

## Variant Human unit tests

必測：

1. 可選兩個不同 abilities，各 +1。
2. 同一 ability選兩次 → blocking error。
3. 少選一個 ability → blocking error。
4. 多選 ability → blocking error。
5. skill exactly one。
6. feat exactly one。
7. 無 prerequisite feat可選。
8. prerequisite滿足時可選。
9. prerequisite不滿足時 option disabled / confirm blocked。
10. Numeric Override若依既有 P1規則使 prerequisite達標，eligibility行為與既有 Feat規則一致。
11. Review顯示 resolved ability bonuses、skill、feat。
12. Confirm後 `feat_refs` / `skill_choices` / ability scores正確。
13. reload後完全一致。

## PHB subrace tests

至少各有 focused fixture：

- Wood Elf：base Elf + subrace grants合併且不重複。
- Drow：level-gated racial spell access正確。
- Mountain Dwarf：armor / ability grants正確。
- Stout Halfling：subrace feature存在。
- Forest Gnome：Minor Illusion / feature source identity正確。

## Background pipeline integration

至少挑：

- 一個全 fixed grants background。
- 一個有 language choice background。
- 一個有 tool choice background。
- 一個有 starting equipment branch / quantity background。

走：

```text
Draft
→ select Background
→ structural choices
→ equipment choices
→ Review
→ Confirm
```

## Mandatory First Real Character-Creation Gate

此 Gate **不能只由 Playwright取代**。

真人至少建立六個 flow：

### Flow 1 — SRD Regression Character

目的：確認 M01-A/B 沒把舊流程弄壞。

檢查：

- Race / Background / Class selector可用。
- Review正常。
- Confirm正常。
- Character Sheet正常。
- reload正常。

### Flow 2 — PHB New Subrace

選 Wood Elf / Drow / Mountain Dwarf / Stout Halfling / Forest Gnome 任一。

檢查 inherited + subrace grants顯示是否清楚。

### Flow 3 — Variant Human

強制實際操作：

```text
+1 Ability A
+1 Ability B
Skill
Feat
```

檢查 UI 是否容易理解「不可選同一 Ability兩次」。

### Flow 4 — PHB Background with Choices

至少一個有 tool / language choice 的背景。

檢查 choice label、搜尋、選擇數量、Review summary。

### Flow 5 — Martial

例如 Fighter / Barbarian 等。

目的：驗 Race + Background + Class grants不衝突。

### Flow 6 — Caster

例如 Wizard / Cleric 等。

目的：驗新增 Origin content不破壞 Spellcasting step / prepared / spellbook flow。

### Human Gate 必查 UX

人工紀錄：

- Race / Background選項量增加後 selector 是否仍好找。
- source badge 是否太吵或不夠清楚。
- inherited trait / new grant是否能分辨。
- Background的 tool / language選擇是否會不知道在選什麼。
- roleplay suggestions是否 optional，不會卡住 Confirm。
- Variant Human選 ability / feat是否自然。
- 回上一步修改 Race / Background後 stale choices是否被正確清理或標示。

### Gate 處理規則

M01-A/B 導致或暴露出的 blocker / major UX confusion：

```text
發現
→ 修正
→ rerun affected tests
→ rerun human flow
→ 才可 close M01-B
```

不把明顯 M01-A/B 問題留到 M01-J。

# M01-D — VGM Race Expansion

- ability bonuses。
- size / speed。
- language。
- darkvision / proficiency / feature grants。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## Replacement unit tests

### Base Half-Elf

不選 variant：

- Skill Versatility仍存在。
- 原本 two-skill choice正常。

### Variant replacing Skill Versatility

選 replacement：

- Skill Versatility從 compiled grants移除。
- 原 Skill Versatility selection不再 counted。
- replacement grant加入。
- Review不顯示已移除 grant。
- Build不殘留相關 proficiency。

### Switch branch

```text
select Variant A
→ fill nested choice
→ switch to Variant B
```

驗 stale child selection：

- 不可偷偷污染 Build。
- 可被清理或 warning，但 Confirm結果只含 active branch。

### Round-trip

- Draft save / reload保留 `race_variant_selection`。
- Confirm後 Build保存 variant identity。
- Version History可辨識 variant Build。

## E2E

至少一隻 Half-Elf：

```text
Race = Half-Elf
→ Variant / Ancestry
→ replacement
→ Review
→ Confirm
→ Sheet
```

# M01-F — VRGR Lineage & Dhampir

## Direct Create tests

- Lineage = Dhampir。
- ability choice合法。
- size choice合法。
- speed / darkvision等 grants正確。
- no-breathing / Spider Climb / Bite feature存在。
- level threshold前後 Spider Climb能力表示正確。
- initial Ancestral Legacy skill choice數量正確。

## Transformation tests

Fixture：先建立普通 existing Character。

```text
Version 1 = original race
→ Build Edit
→ select Dhampir lineage
→ choose retained legacy
→ Review
→ Confirm
→ Version 2
```

必驗：

- Version 1 immutable。
- Version 2有 lineage provenance。
- old race不允許保留的 grants被移除。
- retained skill / special movement only按 supplied rules保留。
- ability / feature不 double-apply。
- Current HP damage delta合理延續。
- Temp HP / Conditions / Inventory原樣延續。

## Negative cases

- lineage key kind錯誤。
- ancestral origin dangling。
- retention選到不允許的 trait → blocking。
- old race full grants + lineage full grants雙重存在 → test必須抓到。

# M01-G — TCE Artificer Core

## Class progression tests

每個 class level 1–20至少驗 progression資料連續、parent正確、feature reference可解析。

focused assertions：

- hit die d8。
- saving throws。
- starting class proficiencies。
- multiclass proficiencies。
- skill choice count / pool。
- subclass timing。
- cantrip progression。
- spell slot access / max spell level。

## Spellcasting rounding matrix

Artificer最重要 regression必須用 table-driven tests。

至少：

```text
Artificer 1 → contribution 1
Artificer 2 → 1
Artificer 3 → 2
Artificer 4 → 2
Artificer 5 → 3
```

再與其他 caster組合：

```text
Artificer 1 + Wizard 1
Artificer 3 + Wizard 2
Artificer 3 + Paladin 2
Artificer + Ranger
Artificer + Warlock
```

Warlock Pact Magic仍獨立，不可被 combined slot table吞掉。

## Prepared formula tests

Artificer prepared count以 supplied公式驗 boundary：

- odd/even class level。
- low INT modifier。
- minimum 1。

確認 prepared rounding與 multiclass contribution rounding互不影響。

## Subclass tests

Alchemist / Armorer / Artillerist / Battle Smith：

- correct subclass stable key。
- correct class parent。
- selection timing。
- granted spell / feature metadata（若本 Subphase納入）。

## E2E

至少四條：

1. Artificer Lv1 Create。
2. Artificer Lv3 + subclass。
3. High-level Artificer direct Create。
4. Existing Artificer Level Up。

至少一條 multiclass real-backend flow驗 Review上的 spell slots。

# M01-H — TCE Artificer Advanced Rules & Infusions

## Infusion tests

- known infusion count by class level。
- level prerequisite。
- duplicate selection policy。
- capacity by class level。
- Build只保存 Known，不把 active infused item當 permanent Build choice。

## Current State tests

若實作 active infused item：

- inventory entry可綁 infusion。
- 超過 capacity → blocking / clear error。
- remove infusion後 state一致。
- item被移除時不留下 dangling active infusion。
- reload / restart後仍一致。

## Resource tests

對 limited-use Artificer feature：

- capacity derive。
- consume/update。
- Level Up capacity增加時 reconciliation不自動把已消耗部分全部補滿，除非 supplied rule明確如此。

## Manual-boundary tests

對未 fully automated 的 feature，要能在 DTO / Sheet看到：

- feature存在。
- description / rule metadata存在。

但測試不應期待不存在的 Combat resolution。

# M01-I — TCE Magic Items

## Content validation

對完整 supplied item set：

- unique stable key。
- source `tce`。
- rarity可解析。
- attunement requirement shape合法。
- description存在。

針對代表性種類做 focused fixtures：

- Artificer-only focus item。
- spellcaster focus item。
- no-attunement item。
- attunement-required item。
- class-restricted item。

## Inventory state

必測：

```text
add item
→ carried
→ equip
→ attune
→ reload
→ unattune
→ remove
```

### Attunement capacity

- normal capacity baseline。
- 超 capacity的 attune action被拒。
- Artificer capacity override在對應 level生效。
- Level Up改 capacity後現有 attuned state reconciliation合理。

### Legacy inventory

舊 `InventoryEntry` 沒有 `attuned` field時應以 false/default安全載入，不做 destructive rewrite。

## Effects

若實作 simple modifier，必須有 isolated calculation test。

未實作的 complex effect只驗 metadata / description，不可有 misleading「已自動生效」UI。

- multiclass

若 M01新增 migration：

2. P1 closeout schema → M01 head。

## Frontend regression

至少：

```bash
npm test -- --run

```

以及 project當時正式 typecheck / lint command。

### E2E 1 — Variant Human + PHB Background

驗 +1/+1 / Skill / Feat / equipment / Confirm。

### E2E 2 — PHB Subrace Caster

### E2E 3 — SCAG / GoS Background

### E2E 10 — TCE Magic Item

驗 add / equip / attune / reload。

Docker / real DB restart前建立至少：

- multi-pack normal Character。
- Variant Human。
- Dhampir versioned Character。
- Artificer。

restart後逐一讀回，比對：

- current version id / version no
- stable refs
- content_sources
- Current HP / Temp HP / Conditions
- spell state

## Final human smoke

M01-J 再做一次人工瀏覽：

- Character Workshop
- Origin selectors with source badges
- Background choices
- Variant Human
- Half-Elf Variant
- Dhampir
- Artificer level rail / spells
- Review summary
- Character Sheet
- Inventory attunement

人工檢查不是逐字 proofread所有 sourcebook文字；重點是：

M01-J closeout回報至少要列：

```text
Backend test result
Frontend test/build result
Migration result
Playwright result
```

## 4. M01-B 真人 Gate 與 M01-J closeout 的差異

兩者都需要人工測試，但目的不同：

### M01-B Gate

目的是**提早使用**。

重點：

- PHB背景量夠不夠實際創角。
- Variant Human是否自然。
- Origin / Background UX是否在選項增加後仍可用。

有問題立即修。

### M01-J Closeout

目的是**整體封版**。

重點：

- 所有 M01新增 rule shapes彼此相容。
- regression / migration / persistence完整。
- 可以安全回到 P2。

因此不能因 M01-B已真人測過，就省略 M01-J完整 smoke。
