# M01 — 測試指南

> Phase：**M01 — Multi-Source Character Content Expansion**  
> 類型：**M Phase（Modification / Maintenance Phase）**  
> 本文件定義 M01-A～M01-J 的自動與人工驗收流程。M01 不能只證明「JSON 可以 load」，而要證明多來源內容真的能進入 Character Builder、Build Version、Current State、Inventory 與既有 P0/P1 流程。  
> Subphase 名稱與順序必須與 `實作規格.md`、`開發設計方針.md` 完全一致。

最後更新：2026-08-30

## 1. M01 共通驗證原則

每個 Subphase closeout都要同時證明：

```text
新 content / 新 rule shape 正確
AND
已完成 P0/P1 功能沒有 regression
```

最低要求：

1. Backend pytest green。
2. Frontend unit tests / build / typecheck依 repository當時正式 command green。
3. 有 DB schema migration時，fresh DB與既有 P1 schema upgrade都要測。
4. Existing SRD-only Character可以讀、可以開 Character Sheet。
5. Existing P1 Create / High-Level / Multiclass / Spellcasting / Equipment / Review / Confirm / Level Up / Version History主要 flow維持 green。
6. 新 StableKey / source identity在 Draft reload、Character reload、server restart後不變。
7. malformed content要 fail-fast，不能 silent skip。
8. structural choice新增時要有 server domain test；影響 UI時要有 real-backend browser test。
9. 重要 D&D規則用 focused assertions驗算，不只做大 JSON snapshot。
10. 拒絕操作要 zero side effect。
11. Subphase closeout要列出 intentionally manual / deferred的 runtime效果。

# M01-A — Multi-Source Content Pack Foundation

## A.1 Tiny fixture packs / fixture isolation

不要只用正式 PHB資料驗 foundation。

所有 foundation test packs放 **tests專用 content root**，不得放 production `data/`。

建立 test fixture：

```text
pack-a
├── race:test-race
└── feature:test-a

pack-b
├── background:test-background
├── feature:test-b
└── cross-ref → pack-a:feature:test-a
```

再建立：

```text
pack-a:race:goblin
pack-b:race:goblin
```

驗 same `kind:index` different source。

Registry由測試明確注入：

```text
content_root=<fixture root>
enabled_pack_ids=(...)
```

或等價 dependencies。

必測：fixture root中另放一個**未列入 enabled pack list**的合法 pack，Registry不得自動載入它。這條用來證明 production不會因掃描資料夾而污染。

## A.2 Manifest compatibility matrix

至少準備以下 manifest：

### Legacy SRD manifest

使用現行 `data/srd5.1/manifest.json` shape，包含：

- `id=srd5.1`。
- CC-BY license object。
- extraction repository / 40-hex commit / MIT。
- P4-A scope guard。
- categories `upstream_file`。

預期：**原樣仍可 load**。

### Minimal private/manual manifest

至少：

- generic id，例如 `pack-a`。
- ruleset。
- name。
- provenance。
- categories with `name/kind/file/count`。
- total_entries。

刻意不提供：

```text
license
extraction
scope_guard
categories[].upstream_file
```

預期：合法。不得要求測試 fixture偽造 Git repo SHA、MIT、CC-BY 或 P4-A metadata。

### Generic optional license/extraction

若提供非 SRD `license` / `extraction`：

- `license.spdx` 不是 CC-BY-4.0也能通過 generic schema（只要格式/required fields合法）。
- `ExtractionSource.license`不是 MIT也能通過 generic schema。
- extraction存在時 malformed/non-40-hex commit仍按該 object的 strict contract拒絕。

### Scope guard isolation

- `srd5.1` 的既有 P4-A scope guard仍按 SRD compatibility validator驗證。
- non-SRD pack省略 scope guard合法。
- non-SRD pack不能因未排除 monsters/beasts而被 generic manifest拒絕。

## A.3 Positive Registry tests

必測：

- SRD單獨 load。
- SRD + pack-a。
- SRD + pack-a + pack-b。
- `get(full_key)`。
- `get_optional(full_key)`。
- `list_kind("race")`跨 pack聚合。
- source filter（若有）。
- explicit cross-pack StableKey ref。
- legacy SRD `/api/2014/...`仍 normalize成原 `srd5.1:*`。
- same index different source可同時存在。
- manifest source label / provenance可讀。

## A.4 Negative Registry tests

以下必須 fail-fast：

- pack id含 `:`。
- StableKey少段、多段、空段。
- key prefix與 `source`矛盾。
- duplicate full StableKey。
- manifest category file不存在。
- category count mismatch。
- manifest total mismatch。
- explicit dangling key。
- expected `race`卻引用 `spell`。
- legacy URL與 index不一致。
- unknown legacy API route被誤認為合法 ref。

## A.5 Character StableKey tests

- `phb2014:background:test`通過 generic syntax。
- `vgm:race:goblin`可進 race_ref syntax validator。
- `vgm:spell:x`填進 race_ref被 kind validator拒絕。
- malformed source被拒。
- existing `srd5.1:*` fixtures不需要改 key。

## A.6 `content_sources` / allowlist separation tests

Candidate引用：

```text
srd5.1 race
phb2014 background
```

預期：

```text
content_sources = deterministic [phb2014, srd5.1] 或專案定義排序
```

重點：

- dedupe。
- deterministic。
- 不受 selection insertion order影響。
- client傳假的 `content_sources`不能污染 final Build。
- `enabled_content_sources`若存在，不等於 final provenance。

另做真正 gate test：

```text
enabled_content_sources = [srd5.1]
client/draft硬塞 phb2014:background:test
```

預期：在 Builder choice/validation 階段 blocking；不能先編譯成功再因 derived `content_sources`「剛好包含 phb2014」而視為合法。

反向：

```text
enabled_content_sources = [srd5.1, phb2014]
final Build只實際引用srd5.1
```

預期 `content_sources`仍只有 `srd5.1`，不得把 allowlist整份抄進 Build provenance。

## A.7 Class / progression source regression

針對移除 `startswith("srd5.1:class:")`後：

- existing SRD Fighter / Wizard class options仍可用。
- multiclass prerequisite logic仍正常。
- level lookup仍找到 SRD level entries。

## A.8 Existing P1 regression

至少跑：

- Lv1 SRD Create。
- Fighter 5 / Wizard 5 high-level Create。
- multiclass slots。
- Starting Equipment。
- Level Up。
- Version History。

## A.9 UI sanity

如果 source badge已加：

- SRD option仍可搜尋。
- same name different source都顯示。
- keyboard navigation正常。
- selector value使用 full StableKey。

## M01-A Closeout Evidence

回報：

```text
Loaded pack count
Entry count per fixture pack
SRD entry count unchanged
Legacy SRD manifest compatibility
Minimal private manifest compatibility
Fixture isolation / explicit enabled-pack result
Cross-pack tests result
Duplicate/wrong-kind negative tests result
P0/P1 regression result
```

## B.9 Variant Human identity / provenance

正式 Build identity：

```text

subrace_ref = None
```

Content entry：

```text
kind = race
variant_of = srd5.1:race:human
```

必測：

- `phb2014:race:variant-human`作為 `race_ref`合法。
- entry kind不是 `race-variant`。
- `variant_of`指向 existing Human race；指向 spell/subrace等 wrong kind時 content validation fail-fast。
- `variant_of`只做 provenance：compiler不因此自動套用 `srd5.1:race:human` mechanical grants。
- 標準 Human ability package不會與 Variant Human +1/+1疊加。
- M01-B Build沒有 `race_variant_ref` requirement；舊 P0/P1 Build schema不因 Variant Human改動。
- Review / Character Sheet能辨識 Variant Human來源為 PHB。
