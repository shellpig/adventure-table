# M01 — 測試指南

> Phase：**M01 — Multi-Source Character Content Expansion**  
> 類型：**M Phase（Modification / Maintenance Phase）**  
> 本文件定義 M01-A～M01-J 的自動與人工驗收流程。M01 不能只證明「JSON 可以 load」，而要證明多來源內容真的能進入 Character Builder、Build Version、Current State、Inventory 與既有 P0/P1 流程。

最後更新：2026-08-30

---

## 1. 測試總原則

M01 的測試證據至少分為：

- Content Pack / Manifest schema tests。
- StableKey / Registry / cross-reference unit tests。
- Character / Builder schema regression。
- Builder choice / compiler / validation tests。
- Rules Layer tests。
- Persistence / immutable Build Version tests。
- API tests。
- Frontend Vitest。
- Real-backend Playwright E2E。
- Restart persistence。
- M01-B 真人創角 Gate。
- M01-J Full Regression / Manual Smoke。

每一 Subphase 必須先通過自己的驗收，不得把 M01-A～I 的錯誤全部留到 M01-J。

所有規則 fixture 需 deterministic；不能依賴人工先在 UI 建角色再拿 DB 當 fixture。

測試 assertion 要分清：

```text
content data是否合法
↓
Builder choice是否正確生成
↓
Build compile結果是否正確
↓
Current State seed / reconciliation是否正確
↓
UI是否正確呈現
```

不能只 assert `HTTP 200`、`entry count > 0`、`can_confirm=true`。

# M01-A — Multi-Source Content Pack Foundation

## Manifest / Pack tests

至少建立：

1. valid `srd5.1` pack。
2. valid test pack，例如 `testpack`。
3. invalid manifest pack。
4. duplicate pack id。
5. incompatible ruleset pack。

測試：

- 多 pack 同時 load。
- invalid manifest fail fast。
- duplicate pack id fail。
- error message含 pack identity。

## StableKey syntax tests

合法：

```text
srd5.1:race:elf
phb2014:background:acolyte
vgm:race:goblin
```

非法至少包含：

```text
race:elf
:race:elf
PHB:race:human
phb2014::human
phb2014:race:
```

若 pack id 規則允許 `.`，必須有對應 coverage。

## Same index cross-pack collision

Fixture：

```text
pack-a:race:goblin
pack-b:race:goblin
```

預期：

- registry 兩筆都存在。
- bare `race:goblin` 不被當成唯一 identity。
- full key lookup各自正確。

完整 StableKey duplicate：fatal。

## Cross-reference tests

至少：

- same-pack valid ref。
- cross-pack valid ref。
- unknown pack ref。
- known pack / unknown entry ref。
- wrong kind ref（若 schema要求 kind）。

新 pack測試不得依賴 `/api/2014/...` URL。

## Character stable key regression

舊：

```text
srd5.1:race:elf
```

仍可通過 Character schema。

新：

```text
phb2014:subrace:wood-elf
```

不應被 regex擋掉。

unknown content是否 blocking，應在 registry / builder validation層測。

## `content_sources`

至少測：

- pure SRD Build → `("srd5.1",)`。
- SRD base race + PHB subrace → 同時包含兩 pack。
- client偽造少一個 source → server compile結果修正／validation fail，不能信任 client。
- Version reload後 sources不變。

## P0/P1 regression

M01-A關門必跑：

- P0 content tests。
- P0 Character schema / API tests。
- P1 Builder schema / compile tests。
- P1 Create / Level Up核心 regression。

## M01-A 關門證據

- Multi-pack registry unit suite全綠。
- 至少一個 non-SRD test entry可由 reference API查到。
- 舊 SRD full regression無 stable key migration。

# M01-B — PHB Character Origins & Background Expansion

## PHB pack data validation

所有本 Subphase導入 entry 必須：

- manifest category count與實際一致或有明確可驗證清單。
- stable key唯一。
- refs全部存在。
- base race refs正確。
- Background feature / equipment refs正確。

不得 silent skip malformed entry。

## PHB subrace compile tests

至少各一個：

- Wood Elf。
- Drow。
- Mountain Dwarf。
- Stout Halfling。
- Forest Gnome。

每例至少 assert：

- base race grants仍存在。
- subrace新增 grants正確。
- 不重複套用 base ASI / proficiency。
- Build references保留來源。

Drow / Forest Gnome等有 racial spell時，另測 spell source identity不是 class spell。

## Variant Human choice tests

### Two distinct abilities

至少：

- Str + Dex：合法。
- Str + Str：blocking。
- 少選1項：blocking。
- 多選3項：blocking。
- reload draft後選擇仍一致。

最終 resolved ability只套用一次。

### Skill choice

- 任一合法 skill可選。
- 非 skill ref被拒絕。
- 未選 blocking。

### Feat choice

- 合法 feat可選。
- 不符合 prerequisite feat被既有 P1 validation阻擋。
- feat stable key進 `feat_refs`。
- 不產生 Variant-Human 專用平行 feat state。

## Background mechanical tests

至少涵蓋不同 shape：

1. 固定兩個 skill grants。
2. tool choice。
3. language choice。
4. starting equipment nested choice。
5. feature ref。
6. roleplay tables缺省不影響 Confirm。
7. PHB variant background（若提供資料中有）。

## Starting Equipment regression

Create Confirm：

- background equipment加入 initial Inventory。
- quantity正確。
- reload後存在。

Level Up：

- 不再次加入 background equipment。

## Builder API tests

Origin / Background choices需驗證：

- source metadata存在。
- value使用 StableKey。
- search不因相同 display name collision選錯來源。
- draft reload保留 PHB choice。
- Review summary包含最終 grants。

## Frontend Vitest

至少覆蓋：

- source badge顯示。
- Variant Human generic choices renderer。
- background searchable selector。
- required choice error呈現。
- Review來源呈現。

## Real-backend E2E

至少自動跑：

### Flow B1 — Variant Human

```text
Workshop
→ Create
→ Human / Variant Human
→ 選兩個不同 ability
→ 選 skill
→ 選 feat
→ PHB Background
→ Class
→ Review
→ Confirm
→ Character Sheet
→ reload
```

assert Build / State / source refs。

### Flow B2 — PHB subrace caster

選一個含 racial spell的 PHB subrace，確認 spell access來源與 class spell來源不混淆。

### Flow B3 — PHB background equipment

確認 nested equipment與live Inventory初始化。

## 真人創角 Gate（M01-B 必做）

這不是可選 smoke；M01-B closeout前必須實際由真人使用 UI 建角色。

至少建立：

1. **純 SRD martial**：確認舊流程。
2. **純 SRD caster**：確認舊 spell flow。
3. **PHB 新 subrace martial 或 caster**。
4. **Variant Human**：必須實際完成 ability + skill + feat。
5. **含 tool / language choice 的 PHB Background**。
6. **含 starting equipment choice 的 PHB Background**。

每個角色至少檢查：

```text
建立 Draft
→ 各步驟操作
→ Review
→ Confirm
→ Character Sheet
→ 回 Workshop
→ 再開角色
→ browser reload
```

人工觀察項目：

- 選項是否找得到。
- 中文 label / source badge是否足夠辨識。
- choice順序是否自然。
- required / blocking error是否能理解。
- Review是否能看出最終結果。
- reload是否遺失選擇。
- Character Sheet是否與 Review一致。

### 真人測試 issue policy

屬 M01-A/B 的 blocker：

- 當場記錄。
- 修正。
- 補 automated regression。
- 重新走受影響流程。

不得只在文件寫 known issue後就關 M01-B。

## M01-B 關門證據

- automated suite全綠。
- Playwright B1～B3全綠。
- 真人創角 Gate完成。
- Gate blocker全部關閉。

# M01-C — SCAG / GoS Background Expansion

## Data validation

SCAG、GoS各自：

- manifest valid。
- Background refs完整。
- feature refs完整。
- equipment refs完整。
- duplicate full key不存在。

## Cross-pack selector tests

同一 Background selector同時有：

```text
SRD
PHB
SCAG
GoS
```

assert：

- search結果都能出現。
- source label正確。
- StableKey選值正確。
- 同名內容不collision。

## Variant tests

若來源含 base/variant：

- base feature只出現一次。
- replacement後被替換 feature不在 final Build。
- replacement feature存在。
- stale choice不進 final Build。

## Equipment tests

至少選 SCAG與GoS各一個含 equipment的 Background進 Create Confirm，驗證 initial Inventory與P1 isolation contract。

## E2E

至少：

- SCAG Background Create。
- GoS Background Create。
- reload / reopen。

## 關門

所有已提供 Background均有「導入成功」或「明確資料缺失／規格原因未導入」記錄，不允許 silent omission。

# M01-D — VGM Race Expansion

## Race compile tests

Goblin、Hobgoblin、Aasimar各至少：

- Lv1 Create compile。
- ability / size / speed / language。
- feature refs。
- proficiency / sensory traits（若有）。

## Level-dependent feature

選一個有 level gate的 racial feature：

- target level在門檻前：沒有 grant。
- target level達門檻：有 grant。
- Level Up跨門檻：新 Build取得。
- 舊 Build version不變。

## Limited-use resource

若 race有 PB / level-based uses：

- capacity derive正確。
- Current State counter初始化正確。
- Level Up capacity增加時保留已消耗量。

若該 feature尚未接正式 resource model，至少驗證 metadata與manual/deferred標記；不能測成假自動化。

## E2E

至少建立一隻 Goblin與另一隻 VGM race角色，Confirm後重開。

## Future-version collision fixture

加入測試 pack fixture：

```text
vgm:race:goblin
future:race:goblin
```

確保 registry / selector不以裸 index覆寫。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## Base Half-Elf regression

先證明原 SRD Half-Elf：

- 未選 SCAG variant時完全維持原行為。
- Skill Versatility /既有 grants不消失。

## Replacement unit tests

至少：

1. 指定 target grant可被精準移除。
2. 未列為 target的 base grants保留。
3. replacement branch只能選合法 option。
4. mutually exclusive option不可同時存在。
5. final Build沒有 removed grant。
6. provenance可追到 SCAG variant。

## Stable grant identity

用測試證明 replacement不是 name match：

- 兩個不同 grant display name相同或相近時，只移除指定 stable grant id。

## Stale branch test

```text
選 Wood descent
→ 選 Fleet of Foot
→ 改 Drow descent
→ Review
```

assert：

- Wood choice不進 candidate Build。
- Drow branch要求正確。
- `can_confirm`符合 active branch completeness。

## UI / E2E

至少跑：

- baseline Half-Elf。
- Wood ancestry variant。
- Drow ancestry variant。

Review要能看出「放棄 X / 取得 Y」或等價 resolved outcome。

# M01-F — VRGR Lineage & Dhampir

## Schema tests

- 普通舊 Character沒有 lineage仍合法。
- direct Dhampir可沒有 ancestral origin。
- transformed Dhampir可保存 ancestral origin。
- invalid lineage ref被拒絕。

## Direct Create test

```text
Create
→ Dhampir
→ fallback ancestral legacy choices
→ Class / Background
→ Review
→ Confirm
```

assert：

- active lineage正確。
- 不建立假的 race inheritance。
- lineage grants完整。

## Transformation / Version test

Fixture：一個既有 PHB/SRD race Character Build v1。

```text
Open Edit/Correction Draft
→ choose Dhampir lineage
→ derive eligible Ancestral Legacy
→ Review diff
→ Confirm
```

assert：

- Build v1 immutable。
- Build v2 active lineage = Dhampir。
- parent/version lineage metadata正確。
- only allowed legacy traits retained。
- Current State依既有 P1 reconciliation保留不相關 live data。

## Allowlist negative tests

原 race具有：

- skill proficiency。
- movement mode。
- darkvision。
- weapon proficiency。
- spell。

依正式 Dhampir規則，只允許類別才可保留；其餘即使 client塞入 selection也被 blocking。

## Movement tests

若實作 multi-mode movement：

- walk/climb獨立。
- inherited climb/swim不覆寫walk。
- old Character只有walk仍可derive。

## Resource tests

Vampiric Bite limited uses若納入 state counter：

- initial capacity。
- reload。
- level/PB change reconciliation。

真正 attack/heal效果若deferred，測資料標記，不做虛假的 combat assertion。

## E2E

- direct Dhampir Create。
- existing Character → Dhampir version transition。
- Version History可看到前後版本。

# M01-G — TCE Artificer Core

## Class progression data tests

對每個 class level 1～20至少做 table-driven validation：

- feature grants不缺 level。
- ASI/subclass timing合法。
- spell slot/progression資料 shape合法。
- cantrip / prepared profile metadata存在。

不要求在測試文件重抄數值；expected values由受控 fixture或正式規則資料斷言。

## Lv1 Create

驗證：

- HP。
- proficiency。
- saves。
- skill choice。
- tool choice。
- spellcasting profile。
- prepared eligibility。

## High-level Create

直接建高等 Artificer，仍需 ordered Lv1→target progression，不可只填 class level。

assert：

- subclass choice出現在正確 class level。
- ASI choices出現在正確 level。
- class features完整。

## Multiclass slot rounding

這是 M01-G 必測核心。

至少 table-driven cases：

- Artificer 1 單獨 contribution。
- Artificer 2。
- Artificer 3。
- Artificer odd level與 full caster混合。
- Artificer odd level與另一個 floor-half caster混合。
- Artificer + Pact Magic class，Pact pool仍分離。

測試目標是證明：

```text
Artificer half contribution uses ceil
other half caster keeps floor
prepared-count rounding remains its own rule
```

不能只有一個 happy path。

## Prepared formula tests

至少測：

- low INT minimum floor/minimum rule。
- odd/even Artificer class level。
- ability modifier change後 eligibility recalculated。
- prepared live selection不寫回 Build access。

## Specialist tests

每個本 Phase導入的 Specialist至少：

- 過早選擇 → blocking。
- 正確 level → choice出現。
- 保存／reload identity。

## Level Up

Lv1→Lv2→Lv3至少走一次：

- progression choices。
- spell/resources。
- Specialist timing。
- immutable versions。

## E2E

至少：

- Lv1 Artificer Create。
- 高等 Artificer Create。
- Existing Artificer Level Up。
- Artificer multiclass代表流程。

# M01-H — TCE Artificer Advanced Features & Infusions

## Known Infusions tests

- level未達不可選。
- known count不超量。
- known selection reload穩定。
- duplicate限制按規則。
- Level Up新增 known capacity時可新增，不重置舊 choices。

## Active Infusion state tests

```text
Character knows infusion
+ Inventory item exists
→ assign infusion
```

assert：

- assignment在 live state / inventory side。
- immutable Build version不變。
- invalid item category拒絕。
- capacity超限拒絕。
- remove assignment後 Build仍不變。

## Replicate item tests

若有 Replicate Magic Item：

- option stable ref正確。
- 不copy整份 item JSON進Build。
- 不合法 prerequisite / level拒絕。

## Feature resource reconciliation

建立已消耗資源的Artificer：

```text
old capacity N
remaining R
→ level up
→ new capacity M
```

assert消耗量保留，不自動回滿。

## Attunement capacity tests

至少測門檻前後：

- base capacity。
- Artificer feature提高後capacity。
- crossing level threshold via Level Up。
- downgrade/correction若可能，超額attunement需有明確 blocking/reconciliation規則，不silent detach。

## Manual/deferred effects audit

對本 Subphase每個 advanced feature分類：

```text
structural automated
derived automated
manual_runtime / deferred
```

測試可用 schema validation保證每個複雜 feature都有狀態，不留 ambiguous「好像支援」。

## E2E

至少：

- Artificer選Infusion。
- 給Inventory item套Infusion。
- reload仍在。
- Level Up capacity增加且已用資源不回滿。

# M01-I — TCE Magic Items

## Import completeness test

以受控 expected key list / count驗證本 Phase預計導入資料：

- 每筆唯一 stable key。
- 無 silent skip。
- schema-invalid item使CI失敗。

如果來源資料本身缺欄位而明確不導入，需有 exclusion list與原因，不能單純少一筆。

## Metadata tests

代表性 items至少涵蓋：

- 無 attunement item。
- requires attunement item。
- class-restricted item。
- charged item。
- spell attack / DC bonus item。
- Artificer-related item。

assert rarity / restrictions / charges / effect classification。

## Inventory tests

```text
add item
→ persist
→ reload
```

content ref仍是 `tce:item:*`。

移除／數量修改不影響 content registry entry。

## Attunement tests

至少：

- attune valid item成功。
- non-attunable item不能被錯誤attune（若產品語意如此）。
- class restriction不符 → fail。
- capacity full → fail。
- Artificer enhanced capacity → success。
- unattune → live state更新。

## Effect tests

只對已正式自動化 effect做 numeric assertion。

例如 spell save DC bonus若接 Rules Layer：

- unattuned：不生效。
- attuned：生效一次。
- remove/unattune：撤銷。

manual effect只驗證 metadata可讀，不假裝 server已執行。

## E2E

至少從 Character Sheet / inventory UI：

- 加入代表性 TCE item。
- attune。
- 查看 derived bonus或manual effect資訊。
- reload。

## 2. 測試資料維護原則

- 規則 expected values盡量來自小型、可讀的專用 test fixtures；不要複製整本來源文字。
- 對大量 imported entries，以 schema + key list + representative semantic tests組合驗證。
- 每修一個真人創角 bug，都要補最小 automated regression。
- source pack tests必須能單獨指出是哪個 pack / entry壞掉。
- CI不得因某個 pack invalid而悄悄跳過該 pack繼續啟動。

M01 的測試成功標準不是「資料很多」，而是：**多來源資料能被可靠識別、正確編譯、保存、重載，且複雜來源規則不破壞既有 Character architecture。**
