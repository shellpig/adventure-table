# M01 — 實作規格

> Phase：**M01 — D&D 5e 2014 Private Content Expansion**  
> 類型：**Modification / Maintenance Phase**  
> 本文件定義 M01-A～M01-J 每個 Subphase 完成後「什麼必須成立」。具體資料模型、檔案結構、API / module 接線與 migration 決策放在同目錄 `開發設計方針.md`；自動／人工驗收流程與測試證據放在 `測試指南.md`。

最後更新：2026-08-30

---

## 1. M01 的定位

M01 不取代 P2，也不改寫既有 P0 → P8 產品 Roadmap。

M01 是插入在 P1 closeout 與 P2 規劃之間的 **Modification / Maintenance Phase**，目的有四個：

1. 把目前只真正承載 SRD 5.1 的角色內容基礎擴充成可承載多來源規則資料的 Content Pack 架構。
2. 把 `docs/暫用規則資訊/` 中使用者已提供的非 SRD D&D 5e 2014 規則資料逐步轉為 Builder / Character / Inventory 真正可使用的正式 runtime data。
3. 在進入 Room / Campaign / Session 前，先把 Character Builder 的內容量補到足以進行真實創角，並以真人操作找出 UX / rule representation 缺口。
4. 對 Variant、Lineage、Artificer、Magic Item 等已明確出現的新規則形狀，只補「目前資料確實需要」的通用能力，不趁機建立萬用規則 DSL。

M01 完成後，正常產品 Roadmap 回到：

```text
P2 — Room / Campaign / Session / Seat
```

---

## 2. M Phase 共通規則

M Phase 與正常 P Phase 使用不同編號軸：

```text
產品 Roadmap：P0 → P1 → P2 → P3 → ...
                    ↑
                  M01
```

M Phase 適用於：

- 補資料／補規則內容。
- 強化已完成系統的可擴充性。
- 為新提供的規則資料增加必要表示能力。
- migration / normalization / technical hardening。
- 已完成 Phase 在真實使用時暴露出的既有系統缺口。

M Phase **不是**偷跑下一個正常產品 Phase 的方式。Room、Session、Roll、Combat、Adventure、Timeline 等若本質屬未開工 P Phase，仍要回到對應 P Phase。

所有 M Phase 與 P Phase 一樣：

- coding 前必須拆 Subphase。
- 每個 Subphase 必須可獨立實作、驗證、commit。
- `實作規格.md`、`開發設計方針.md`、`測試指南.md` 的 Subphase 名稱與順序必須一字不差。
- 只拆目前準備開工的 M Phase；不得現在預拆 M02 / M03。
- 每個 Subphase closeout 時 repository 必須可 build、可 test，且既有完成 Phase 的 regression 不能被破壞。

命名固定為：

```text
M01-A
M01-B
M01-C
...
```

M01 以目前 repository 中已存在的私人參考資料為輸入：

```text
docs/暫用規則資訊/

├── 背景_PHB.md
├── 背景_SCAG.md

├── 大地精_VGM.md

├── 半血裔_VRGR.md
├── 奇械師_TCE.md
└── 魔法物品_TCE.md
```

這些 Markdown 的角色是：

```text
human / maintainer reference
```

不是 runtime Source of Truth。

## 4. M01 共通硬原則

### 4.1 SRD 5.1 是 baseline，不再是唯一來源

M01 後 ruleset 仍是：

```text
dnd5e-2014
```

但 Builder / Character 可以依賴多個 installed content packs。

M01 至少會出現：

```text
srd5.1
phb2014
scag
vgm
vrgr
tce
gos
```

來源 ID 是 identity 的一部分，不是單純 UI badge。

### 4.2 StableKey 固定為三段

```text
<pack-id>:<kind>:<index>
```

例如：

```text
srd5.1:race:elf
phb2014:subrace:wood-elf
phb2014:race:variant-human
vgm:race:goblin
vgm:race:aasimar
vgm:subrace:protector-aasimar
scag:race-variant:half-elf-wood-descent
vrgr:lineage:dhampir
tce:class:artificer
tce:item:all-purpose-tool-plus-1
```

不同來源可以有相同 `kind:index`；不得以 bare `index` 或 display name 當 global identity。

### 4.3 非 SRD 資料不得污染 `data/srd5.1/`

`data/srd5.1/` 永遠代表 SRD 5.1 normalized source。

不得：

- 把 PHB missing subrace 塞進 SRD pack。
- 把 VGM Goblin 偽裝成 SRD race。
- 為了少改 code 把所有 `source` 寫成 `srd5.1`。

### 4.4 Builder 仍是 Server authoritative

新規則必須透過既有 Builder domain：

```text
Draft
→ server choices / rules
→ validation
→ Review
→ Confirm
→ immutable CharacterBuild
```

禁止 React hardcode eligibility / rule arithmetic。

### 4.5 Build / Current State 邊界不因 M01 改寫

沿用 P0/P1：

**Build：**永久取得、角色建構、來源、選擇、長期 spell access、class/race/lineage identity。  
**Current State：**目前 HP、Temp HP、prepared、resource usage、Inventory、equipped / attuned、目前 active infusion 等 live state。

M01 新能力若跨兩邊，必須明確拆開，不可把使用次數或目前 infused item 塞進 immutable Build。

### 4.6 只做有來源需求的 primitive

允許增加：

- grant
- choice
- replacement
- conditional / level-gated grant
- lineage replacement
- resource capacity metadata
- attunement metadata

不做：

- generic expression language
- user-authored rules scripts
- combat trigger DSL
- arbitrary effect interpreter

### 4.7 「有資料」不等於「所有效果都自動化」

優先順序：

1. identity / source 正確。
2. Builder legality 正確。
3. Build / State persistence 正確。
4. Character Sheet / Review 顯示正確。
5. 既有 substrate 能安全支援的 runtime automation 才自動化。
6. 需要未來 Combat / Rest / Roll / Adventure substrate 的效果，先保存 structured metadata + description + manual adjudication marker。

不得假裝未實作效果已自動生效。

# M01-A — Multi-Source Content Pack Foundation

## 目標

解除 P0/P1 對 `srd5.1` 的硬耦合，建立後續全部 M01 Subphase 共用的 multi-source content foundation。

## 必須交付

### A1. Generic Content Pack

Registry 可以一次載入多個 pack；每個 pack 有獨立 manifest / provenance / categories / counts。

### A2. Generic StableKey

所有 Character / Builder stable refs 可以接受：

```text
<pack>:<kind>:<index>
```

不再要求第一段必須是 `srd5.1`。

### A3. Legacy SRD compatibility

現有 SRD 1,944 entries 與既有 Character JSONB 不改 key、不大量重寫。

舊 SRD reference shape：

```text
index + /api/2014/... URL
```

仍可 normalize 成原 `srd5.1:*`。

### A4. Explicit new-pack references

非 SRD pack 必須能直接 reference stable key；不得偽造 `/api/2014/...` URL 來騙現有 parser。

### A5. Cross-pack references

例如：

```text
phb2014:subrace:wood-elf
→ parent race srd5.1:race:elf
```

必須可 schema validate、load、compile。

### A6. Multi-pack Builder options

Race / Subrace / Background / Class / Feat / Spell / Item 等已有 selector 的 kind，應能聚合 installed pack；source 可在 UI secondary label / badge 顯示。

### A7. Build provenance

`CharacterBuild.content_sources` 不再永遠是 `("srd5.1",)`；Confirm 時由 server 根據 Build 所引用的內容來源 deterministic derive。

### A8. Fail-fast validation

Server startup 仍需阻擋：

- malformed manifest
- malformed StableKey
- key/source mismatch
- duplicate global key
- dangling reference
- wrong-kind reference
- category count mismatch

## 明確不做

- 不在 A 新增正式 PHB / SCAG / VGM / TCE content。
- 不新增 `race-variant` / `lineage` 行為。
- 不做 Artificer rounding。
- 不做 Magic Item effect engine。
- 不做 pack marketplace / dependency manager / enable-disable UI。

## Closeout

M01-A 完成時必須有至少一個 tiny fixture pack 證明：

```text
SRD + Pack A + Pack B
```

可以同時載入、cross-reference、同名不同來源共存，並保持 P0/P1 regression green。

# M01-B — PHB Background & Core Race Completion

## 目標

把第一輪真人創角最直接缺少的 PHB 內容補足，完成後立即進行真人 Character Builder 測試。

## 資料輸入

- `背景_PHB.md`：13 個 PHB 核心背景 + 5 個官方內建變體。
- `種族_PHB_非SRD內容.md`：SRD 缺失的 PHB race/subrace/variant 資料。

## B1. PHB Background

每個 Background 至少完整承載：

- fixed skill proficiencies
- tool proficiency / choice
- language grant / choice
- starting equipment / quantity / branch
- background feature
- optional personality traits
- optional ideals
- optional bonds
- optional flaws
- variant identity（ supplied source 有時）

Background 不得只做到「下拉選得到名字」。必須走完整：

```text
select background
→ server choices
→ equipment choices
→ Review
→ Confirm
→ Build + initial Inventory
```

### Roleplay tables

Personality / Ideal / Bond / Flaw：

- 可點選 suggested value。
- 可自行輸入。
- 可完全留空。
- 不得成為 blocking validation。

## B2. PHB missing subraces

至少加入 supplied source 中：

- Wood Elf
- Drow
- Mountain Dwarf
- Stout Halfling
- Forest Gnome

這些必須正確繼承既有 SRD parent race，並加入各自：

- ability bonus
- speed change
- proficiency
- racial feature
- racial spell grant
- level gate

## B3. Variant Human

Variant Human **在 M01-B 完成，不延後到 M01-E**。

第一版把它視為 selectable complete race identity：

```text
phb2014:race:variant-human
```

必須支援：

- 選兩個**不同** Ability，各 +1。
- 選一個 Skill proficiency。
- 選一個 Feat。
- Feat prerequisite 仍走 P1 Structural Validation。
- Numeric Override 與 prerequisite 的互動沿用 P1既有規則。
- Review 可清楚看到三類選擇。
- Confirm 後 ability / skill / feat 正確進 Build。

## B4. Racial spell access

Drow / Forest Gnome 等 racial spell 必須保留 source identity；不能混進 class spell profile，也不能把日常 prepared state寫進 Build。

level-gated racial spell在 high-level Create / Level Up 時依 Character Level取得。

## B5. 真人創角 Gate

M01-B closeout 前 mandatory human browser test，至少包含：

1. 純 SRD 角色。
2. PHB 新 subrace。
3. Variant Human。
4. 有 tool / language choice 的 PHB Background。
5. martial。
6. caster。

全都走：

```text
Draft
→ Origin
→ Abilities
→ Class / progression
→ Spells（如有）
→ Equipment
→ Review
→ Confirm
→ Sheet
→ reload
```

凡 M01-A/B 引入或揭露的 Builder blocker /重大 UX confusion，必須在 M01-B closeout 前修掉。

## 明確不做

- 不在 B 支援 SCAG Half-Elf replacement。
- 不在 B 建立 generic race variant system。
- 不在 B 做 Dhampir lineage。

## Closeout

M01-B closeout 的成功標準是「真人可以用 PHB 級別內容量正常完成創角」，不是只看 JSON count。

# M01-C — SCAG / GoS Background Expansion

## 目標

在 M01-B 已經證明 Background pipeline 可用後，將 SCAG 與 GoS 背景完整納入正式 Content Packs，驗證背景系統可以承載不同來源、不同 choice 結構與 roleplay template reuse。

## 資料輸入

- `背景_SCAG.md`：13 個 SCAG 寶劍海岸背景。
- `背景_GoS.md`：4 個 GoS 航海／海岸背景。

## C1. Content Pack

建立並正式啟用：

```text
data/scag/
data/gos/
```

每筆 Background identity 使用來源 pack，不覆蓋 PHB/SRD 同名內容。

## C2. Mechanical completeness

每個背景逐筆確認並資料化：

- skill proficiencies
- tool proficiencies
- language grants / choices
- starting equipment
- money / quantity（若 inventory model已有 currency representation則正確接入；若尚未，至少保留 source data與既有 starting-equipment policy一致）
- background feature
- special choice tables中會影響 Build 的機械選擇

不得把 purely flavor table 誤當 structural rule。

## C3. Roleplay suggestion reuse

SCAG 有些背景會指定「沿用 PHB 某背景的 Personality / Ideal / Bond / Flaw 表格，再依身份調整」。這不能靠複製大量文字才能運作。

產品行為必須允許：

- 背景有自己的 roleplay tables；或
- 背景 reference 一組既有 suggestion tables；或
- 沒有完整表格，只顯示 supplied guidance。

無論哪種，roleplay 仍 optional。

## C4. Variants / special background choices

若 SCAG / GoS supplied background 有 variant 或特殊 branch：

- identity 必須可追溯。
- selected variant / branch 必須在 Draft / Review 中可見。
- mechanical grants 必須由 server compile。
- inactive branch choices 不得污染 Build。

本 Subphase 只補背景所需最小 replacement / branch 能力；不得提前建立 M01-E 的 Half-Elf race-variant top-level model。

## C5. Source-aware UI

Background selector 在來源增加後至少做到：

- 可搜尋 canonical / display name。
- 同名可辨認 source。
- 不要求先選書再選背景。
- source badge 是輔助，不增加 mandatory workflow。

## C6. Build / Inventory correctness

Background grants 必須同時正確反映：

```text
CharacterBuild proficiencies / choices
Starting Equipment provenance
Initial Current State inventory
```

Level Up 不可再次從 Background 重建 Inventory，沿用 P1 boundary。

## 明確不做

- 不把 SCAG 世界觀介紹做成 Campaign Fact。
- 不因航海背景建立 ship system。
- 不因 Faction Agent 等背景建立 faction subsystem。
- 不把背景 feature 做成 adventure automation。

## Closeout

至少完成：

- 一隻 SCAG Background Character。
- 一隻 GoS Background Character。
- 一個同名／近似背景來源辨識案例。
- Confirm + reload 後 Build / Inventory / roleplay profile一致。

# M01-D — VGM Race Expansion

## 目標

將使用者提供的 VGM Goblin、Hobgoblin、Aasimar 正式加入 Builder，並驗證 race/subrace、level-gated racial feature、limited-use racial resource 都能在既有 Character 架構下被正確表示。

## 資料輸入

- `地精_VGM.md` — Goblin。
- `大地精_VGM.md` — Hobgoblin。
- `阿斯莫_VGM.md` — Aasimar 母種族 + Protector / Scourge / Fallen 三亞種。

## D1. Goblin

至少正確表示：

- DEX +2 / CON +1。
- Small。
- walking speed 30。
- Darkvision 60。
- Common + Goblin。
- Fury of the Small。
- Nimble Escape。

### Fury of the Small

Build 保存 feature identity與規則 metadata；Current State若使用 generic resource承載，capacity = 1。

短休／長休自動 recovery 若尚無正式 Rest substrate，不在 M01-D 假做；但 Sheet 必須能看見能力與目前可追蹤使用狀態（若已接 resource）。

## D2. Hobgoblin

至少正確表示：

- CON +2 / INT +1。
- Medium。
- speed 30。
- Darkvision 60。
- Light Armor proficiency。
- 任選 2 種 Martial Weapons proficiency。
- Saving Face。
- Common + Goblin。

Saving Face 的 ally-count dynamic bonus 屬未來 Roll/runtime rule，不在 M01-D 自動判斷 30 ft ally；但 feature / max +5 / recharge metadata 必須保存。

## D3. Aasimar parent race

Aasimar 必須建模為：

```text
vgm:race:aasimar
+ exactly one vgm:subrace:...
```

不是三個互不相關的平行 races。

母種族至少正確表示：

- CHA +2。
- Medium。
- speed 30。
- Darkvision 60。
- Necrotic / Radiant resistance metadata。
- Healing Hands：heal = Character Level，1 / Long Rest。
- Light cantrip，CHA casting ability。
- Common + Celestial。

## D4. Aasimar subraces

### Protector Aasimar

- WIS +1。
- Radiant Soul，Character Level 3 取得。
- fly speed 30 during transformation metadata。
- once / long rest。

### Scourge Aasimar

- CON +1。
- Radiant Consumption，Character Level 3 取得。
- self / area / bonus damage metadata保留。
- once / long rest。

### Fallen Aasimar

- STR +1。
- Necrotic Shroud，Character Level 3 取得。
- fear DC formula metadata保留。
- once / long rest。

## D5. High-level Create / Level Up

角色若直接建立 Lv3+ Aasimar，必須已具有 subrace Lv3 feature；Lv2 → Lv3 Level Up時新 Build Version才新增該 feature。

不得用「創角時選的 target level」之外的 UI hack判斷。

## D6. Optional transformation note

VGM 文件提到 Aasimar 在 DM同意下墮落／救贖可換 subrace。M01-D 不新增獨立 transformation subsystem；可使用既有 Build Edit / Correction 建新 immutable version，並由 DM / user自行發起。

## 明確不做

- 不自動解算 Bonus Action / Reaction / AoE / Fear target。
- 不做 Rest Engine。
- 不做 spatial ally count。
- 不建立 angelic guide NPC system。

## Closeout

必須能成功：

- Goblin Create。
- Hobgoblin Create + two martial weapon choices。
- Aasimar + each of 3 subraces。
- Lv2 → Lv3 Aasimar Level Up。
- reload / Version History後來源與 feature一致。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## 目標

正式支援 SCAG Half-Elf ancestry variants，並建立第一個必要的、資料驅動的 **grant replacement** primitive。

## 資料輸入

`半精靈變體_SCAG.md`，包含：

- Moon Elf or Sun Elf Descent。
- Wood Elf Descent。
- Aquatic Elf Descent。
- Drow Descent。

## E1. Base Half-Elf 不重建

Base Race 沿用：

```text
srd5.1:race:half-elf
```

Variant 是額外 identity / selection，不複製一份整套 Half-Elf data。

## E2. Variant identity

每個 ancestry variant 必須有 stable identity，例如：

```text
scag:race-variant:half-elf-moon-sun-descent
scag:race-variant:half-elf-wood-descent
scag:race-variant:half-elf-aquatic-descent
scag:race-variant:half-elf-drow-descent
```

Build / Version History 能回答「這隻 Half-Elf 用了哪個 SCAG ancestry」。

## E3. 保留 Skill Versatility 是合法 branch

玩家可：

```text
不使用 replacement
→ 保留標準 Skill Versatility
```

即使選擇 ancestry identity，也必須依 supplied rule允許保留標準能力的情況正確處理；UI不得強迫 replacement。

## E4. Replacement semantics

若選 ancestry replacement：

```text
remove Skill Versatility grant / its two-skill choice
→ add exactly one ancestry option
```

Server compiler負責 remove；不能只把原 choice藏起來。

原已填的 Skill Versatility selection若 branch失效：

- 不得進 Build。
- Draft可保留 stale selection供使用者切回，也可清理；但 Review / Confirm只看 active branch。

## E5. Moon / Sun Elf Descent options

replacement後選 exactly 1：

- Wizard cantrip；INT casting ability。
- Elf Weapon Training。
- Keen Senses。

Cantrip選擇必須由 spell data / class-list filter驅動，不 hardcode spell names。

## E6. Wood Elf Descent options

replacement後選 exactly 1：

- Fleet of Foot → walking speed 35。
- Mask of the Wild。
- Elf Weapon Training。
- Keen Senses。

Speed replacement必須反映在 resolved Sheet，不只是 feature text。

## E7. Aquatic Elf Descent options

replacement後選 exactly 1：

- swim speed 30。
- Keen Senses。

必須能表示 secondary movement speed，不可把 swim speed硬改成 walking speed。

## E8. Drow Descent options

replacement後選 exactly 1：

- Drow Magic。
- Keen Senses。

Drow Magic：

- Dancing Lights immediately。
- Faerie Fire at Character Level 3，1 / Long Rest。
- Darkness at Character Level 5，1 / Long Rest。
- CHA casting ability。

Build要保存 spell source / level gate / use metadata；Current State若 resource化不得與 class spell slots混用。

## E9. Generic replacement boundary

M01-E 新增的 replacement primitive至少能：

- 指定要移除的 grant identity。
- 指定 replacement branch / choice。
- 在 compile後驗證 removed grant不殘留。
- 保留 provenance。

但不擴張成 arbitrary patch language。

## 明確不做

- Temp HP延續。
- Conditions延續。
- Inventory延續。
- resources只依新 Build capacity做必要 reconciliation。

## 明確不做

- 不建立故事層「吸血飢渴」系統。
- 不自動把 Hunger / Origin flavor table變成 gameplay constraint。
- 不做 Vampiric Bite combat resolution。

## Closeout

# M01-H — TCE Artificer Advanced Rules & Infusions

## 目標

在 Artificer Core 已能正確建角後，補 Artificer 真正會影響 Build choices、Inventory / resources、attunement capacity與 subclass persistent state的進階能力。

## 資料輸入

`奇械師_TCE.md` 中：

- Infuse Item。
- 常用 Infusions表。
- Magical Tinkering。
- The Right Tool for the Job。
- Tool Expertise。
- Flash of Genius。
- Magic Item Adept / Savant / Master。
- Spell-Storing Item。
- Soul of Artifice。
- Alchemist / Armorer / Artillerist / Battle Smith進階 features。

## H1. Known Infusions = Build

Build必須能回答：

- 角色知道哪些 Infusions。
- 每個 Infusion取得時是否合法。
- level prerequisite。
- selection count / progression。

不能只把所有 Infusion當 feature description列出。

## H2. Active Infusions = Current State

目前哪些 Inventory items被 infused是 live state。

必須支援：

- item instance reference。
- infusion reference。
- active infusion count。
- 同一 infusion同一時間只能 active於一件物品（依 supplied rule）。
- 同一 item不得同時承受多個 infusion。
- item移除 / infusion取消時不留下 dangling state。

## H3. Infused item capacity

依 Artificer class level derive `infused items max`。

超過 capacity的 mutation必須 blocking；Level Up增加 capacity時可多出可用空間，不自動新增 infusion。

## H4. Infusion prerequisites / item applicability

Supplied infusion至少資料化：

- minimum Artificer level。
- acceptable item category / property。
- requires attunement。
- common modifier metadata。

例如 Enhanced Defense / Enhanced Weapon / Returning Weapon / Repeating Shot / Mind Sharpener / Replicate Magic Item等，不可只剩 name。

複雜 combat trigger可 manual，但 eligibility必須正確。

## H5. Replicate Magic Item

若 supplied table列出可複製 item：

- Infusion identity與 replicated item identity分開。
- Builder選的是 Infusion / recipe knowledge。
- Current State active infusion指向實際 Inventory item instance。
- 未安裝的 referenced magic item不得用文字名稱假裝可執行；至少要有 valid content ref或明確 manual placeholder policy。

## H6. Generic class resources

至少為可由現有 State承載的 limited-use features建立 deterministic resource identity / capacity，例如：

- Flash of Genius uses = INT modifier。
- Armorer Defensive Field uses = PB（supplied version）。
- Battle Smith Arcane Jolt uses = INT modifier。
- Alchemist free restorative feature uses（supplied data可確定時）。

Recovery timing可記 metadata；正式 Rest auto-recovery等待 Rest substrate。

## H7. Attunement capacity

Artificer capacity progression：

- default baseline。
- Lv10 = 4。
- Lv14 = 5。
- Lv18 = 6。

Rules Layer能 derive `attunement_capacity(build)`；frontend不得 hardcode level checks。

Magic Item Savant「忽略使用／同調的 class/race/spell/level requirement」若 M01-I attunement validator已存在時必須能尊重；若 I尚未實作，H至少提供可查詢 rule flag，I正式接線。

## H8. Spell-Storing Item

M01-H至少表示：

- selected stored spell identity。
- eligible spell restriction metadata。
- current stored item instance。
- use capacity = INT modifier × 2。

如果現有 Inventory / State不足以自然承載，可先建立 minimal Current State record；不做 spell cast resolution。

## H9. Subclass persistent choices

### Alchemist

Experimental Elixir count progression與feature metadata；不需要在H做完整隨機表 runtime。

### Armorer

Armor Model = Guardian / Infiltrator是角色可切換的 live/persistent choice；若 supplied rule允許短／長休切換，Build只保存可用能力，Current State保存目前 model。

Armor Modifications對 infusion capacity / item slots的例外需能表示。

### Artillerist

Eldritch Cannon type / active cannon屬未來 combat/runtime；Build保存 feature與available types，不建立 Monster Instance。

### Battle Smith

Steel Defender屬 combat/runtime entity；Build保存 feature grant與必要 stat-generation metadata，不在 H建立 P4 combatant persistence。

## H10. Soul of Artifice

至少保存：

- saving throw bonus與current attuned item count關係。
- emergency infusion-drop reaction metadata。

若 Character Sheet已有 save calculation可安全納入 static「每 attuned item +1」部分，M01-H/I整合時可接；reaction仍等待 Combat。

## 明確不做

- 不做正式 Rest workflow。
- 不做 combat Reaction / Bonus Action timing engine。
- 不把 cannon / defender建成 P4 combat entities。
- 不做 generic magic item crafting system。

## Closeout

Artificer Review / Sheet至少能清楚回答：

- Known Infusions。
- active infused items / capacity。
- advanced feature access。
- tracked resources。
- attunement capacity。
- 哪些效果目前 manual。

# M01-I — TCE Magic Items

## 目標

把 supplied `魔法物品_TCE.md` 全套 84 項 TCE magic items轉成正式 `tce` content，並補足 Character Inventory 對 attunement與必要 item instance state的支援。

## 資料輸入

`魔法物品_TCE.md`：84 項，包括但不限於：

- class-specific spell focuses / relics。
- magic tattoos。
- arcane grimoires / school books。
- sorcerous shards。
- artifacts / prostheses / specialized items。

M01-I 是**完整資料轉換 Subphase**；不是只挑 5 件示範。

## I1. Item identity

每件 item必須有：

- `tce:item:<index>` stable key。
- canonical name / display name。
- source = `tce`。
- rarity。
- type / category（source可判定時）。
- description。
- attunement requirement。
- class / race / spell / other requirement（若 supplied data有）。

+1 / +2 / +3 variants是不同 stable identities，不用 runtime tier參數把它們混成同一筆。

## I2. Attunement state

Inventory instance至少能表示：

```text
carried
equipped
attuned
quantity
```

Attunement屬 Current State，不屬 Build。

## I3. Attunement legality

正式 `attune` mutation至少檢查：

- item是否 requires attunement。
- character是否符合 class / other structured requirement。
- current attuned count < derived capacity。
- Artificer Magic Item Savant等 ignore-restriction規則。

讀取舊資料不因新 validator直接 crash；legacy abnormal state顯示 warning / invalid-state提示，mutation則不可繼續製造非法狀態。

## I4. Source item categories

### Class focus items

例如 All-Purpose Tool、Amulet of the Devout、Arcane Grimoire、Bloodwell Vial、Moon Sickle、Rhythm-Maker's Drum等：

- class restriction / attunement structured。
- +1/+2/+3 spell attack / DC bonus若現有 Rules Layer可安全計算，可自動化。
- once-per-dawn額外功能可保留 resource/effect metadata，不需立即做 day clock。

### Magic tattoos

至少能保存：

- tattoo item identity。
- attunement requirement。
- body/needle activation description。
- effect metadata。

不做 body-slot visualizer。

### Grimoires / shards / specialized items

建立可查詢 type / attunement / class metadata；複雜 trigger保持 manual。

## I5. Item effects分級

### Level 1 — Identity / display

全部 84件都必須有。

### Level 2 — Structural metadata

rarity / attunement / restriction / charges / common numeric bonus等 source有提供者應資料化。

### Level 3 — Existing-engine simple automation

只有 existing Rules Layer已能清楚處理者才自動生效，例如：

- static AC bonus。
- static spell attack / spell save DC bonus。
- static ability / save modifier（若有明確 substrate）。

### Level 4 — Manual effect

涉及：

- reaction timing
- target selection
- per-turn trigger
- random table
- summon/entity
- combat geometry
- dawn/day clock

可先 manual / descriptive。

UI必須可辨識 manual，不得顯示成「已套用」卻沒真的算。

## I6. Artificer interaction

M01-I必須與 H的 attunement capacity整合：

- normal character capacity。
- Artificer 10 / 14 / 18 capacity。
- Magic Item Savant restriction bypass。
- Soul of Artifice若 static save bonus已接 Rules Layer，attuned count改變時結果同步。

## I7. Persistence

Add / equip / attune / unattune / remove後：

- browser reload一致。
- server restart一致。
- Character Build Version不因 Inventory live change而新增。

## 明確不做

- 不做完整 magic item crafting。
- 不做 item marketplace。
- 不做 generic effect scripting DSL。
- 不要求 84 件全部 fully automated。

## Closeout

- 84件全部 schema-valid / unique / source-correct。
- 代表性不同類型 items可正常加入 Inventory。
- attunement rules可操作。
- simple automation有測試證據。
- complex manual effects明確標示。
