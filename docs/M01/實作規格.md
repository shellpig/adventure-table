## 1. M01 定位

P0 / P1 已完成 Character Core、SRD 5.1 Content Foundation、Character Builder、Level Up、immutable Build Versions 與 Current State。M01 不重做這些地基；M01 要解決的是：

1. **SRD 5.1 角色內容量不足。**
2. **Content Registry / StableKey / Builder 仍有 `srd5.1` 單一來源假設。**
3. 使用者已提供一批 PHB / SCAG / GoS / VGM / VRGR / XGE / TCE / MTF 私人規則資料，需要正式轉成 runtime content。
4. Variant / Lineage / Artificer / Optional Class Features / Fighting Styles / Subclasses / PHB Feats / expanded races 會帶來幾種現有 P1 尚未正式表示的規則形狀，需要補最小通用能力。
5. PHB 相對 SRD 缺少的 Feats / Spells 已在 M01-K 補成正式 runtime catalog，而不是只停留在 reference Markdown。
6. M01-L / M01-M 進一步補齊目前已拍板的 VGM / SCAG / MTF 種族範圍，並補上 Race/Subrace movement、negative racial modifier compatibility、Natural Armor、Tiefling replacement composition、conditional movement 與 live ancestry mode 等最小通用能力。
7. **Magic Items 延後。** `魔法物品_TCE.md` 保留為 reference，但完整 Magic Item / Attunement / item live-state 擴充不再是 M01 closeout blocker。

M01 的目標不是「一次做完整 D&D」，而是把角色建立與角色成長目前確定需要的內容做成可靠的 Multi-Source Character Content，並確保既有 Character Builder 真正可用。

M01 執行期間已確定一個正式插入點：

```text
M01-A → M01-B → M01-C
→ 暫停 M01
→ M02 — Traditional Chinese / English Localization
→ 回到 M01-D → ... → M01-K → M01-L → M01-M
→ Full M01 Integration & Closeout — Subphase ID TBD
```

被暫停的 M01 不改編號；M02 closeout 後直接從 M01-D 接續。

**原 `M01-K — Full M01 Integration & Closeout` 已取消固定編號。** M01-L / M01-M 現已正式拍板並固定接在 K 後；Full M01 Integration & Closeout 的實際 Subphase ID 仍暫不決定，避免未來又有已拍板內容插入時重複改號。

M01 最終 closeout 後：

```text
回到 P2 — Room / Campaign / Session / Seat
```

M01 不改寫 P2～P8 的產品 Roadmap。

## 2. M Phase 全專案規則

M Phase 使用：

```text
M01
M02
M03
...
```

適用於：

- 補資料／補設定。
- 加強已完成系統。
- 為新資料補必要 schema / validation / migration。
- 修正既有完成 Phase 在實際使用中暴露的設計缺口。
- 做 technical hardening / normalization。

M Phase 與 P Phase 相同：

- coding 前必須先拆 Subphase。
- Subphase 必須可獨立實作、驗證、commit。
- 三份 Phase 文件使用完全一致的 Subphase 名稱與順序。
- 原則上只拆現在要做的 M Phase，不提前拆尚未確定的未來 M Phase。
- **唯一例外：使用者已明確決定要插入、且插入點已確定的 M Phase，可以在插入點到達前先完成拆分與三份文件；M02 即為此例。**
- 上述例外不適用「將來可能會做」但尚未拍板的 M03 / M04 等 Phase。
- M Phase 不重新編號正常 P Phase；插入另一個 M Phase 時，被暫停的 M Phase 也保留原 Subphase 編號與順序。

M Phase 不得拿來偷跑未來產品系統。例如 M01 遇到 Combat feature 時，可以保存 metadata，但不得因此提前建立 P4 Combat Engine。

## 3. M01 資料來源與正式資料原則

### 3.1 supplied reference documents

本 Phase 已提供的 reference 包含：

```text
docs/暫用規則資訊/
├── 種族_PHB_非SRD內容.md
├── 背景_PHB.md
├── 背景_SCAG.md
├── 背景_GoS.md
├── 專長_PHB_非SRD內容.md
├── 法術_PHB_非SRD內容.md
├── 半精靈變體_SCAG.md
├── 種族_SCAG.md
├── 種族_VGM.md
├── 種族_MTF.md
├── 地精_VGM.md
├── 大地精_VGM.md
├── 阿斯莫_VGM.md
├── 半血裔_VRGR.md
├── 奇械師_TCE.md
├── 子職業_*.md
└── 魔法物品_TCE.md
```

這些檔案是：

```text
human / maintainer reference
```

不是 runtime source。

**Reference Markdown 內的規則描述文字可以在 authoring / materialization 階段直接搬進正式 runtime data / localization。** 禁止的是 runtime 將 Markdown 本身當作規則資料源，不是禁止複製 reference text。

Reference 中的 mechanics / metadata 仍必須在 materialization 時依正式 source identity 正規化。例如 `法術_PHB_非SRD內容.md` 的「適用職業」若同時包含後來 TCE 才新增的 Artificer access，不能因此把該 access 寫成 PHB canonical spell origin；PHB spell identity、PHB 原始 class access 與其他來源的 expanded access 必須保持 provenance 分離。

`魔法物品_TCE.md` 在本次重排後仍保留，但**不再代表目前已拍板的 M01 runtime scope**。不得靠 UI hardcode 或模型記憶補規則。

### 3.2 Runtime Source of Truth

某項內容正式導入後：

```text
data/<pack>/...
```

才是程式 Source of Truth。

禁止 runtime：

- parse Markdown。
- 依 Markdown 標題判規則。
- 從 Markdown 即時生成 Builder choices。
- 透過檔案路徑、URL、import、startup hook 或 lazy loader 回頭讀取 `docs/暫用規則資訊/`。
- 因 reference Markdown 缺失而無法啟動 server、載入 Registry、產生 Builder choices 或開 Character Sheet。

Markdown 可以保留 provenance / reference，也可以作為 authoring-time 規則文字來源，但不與正式 JSON 形成雙主來源。正式 runtime data 與 reference 若日後出現差異，runtime 一律以 `data/<pack>/...` 與既有 localization SSOT 為準。**正式 runtime image / package 即使完全不包含 `docs/`，M01-L / M01-M 功能也必須完整成立。**

### 3.3 Pack identities

M01 預期正式使用：

```text
srd5.1
phb2014
scag
gos
vgm
vrgr
xge
tce
mtf
```

Stable identity 不因中文翻譯、UI 顯示名稱或檔名變動。

### 3.4 Private project boundary

Repository 為 private，專案為朋友間私人使用。M01 不建立：

- Marketplace。
- Publisher backend。
- 公開 Content Pack distribution。
- 商業 license workflow。

但來源／provenance仍要明確，因為它直接影響資料 identity 與未來維護。

## 4. M01 共通硬原則

### 4.1 StableKey

正式格式：

```text
<pack-id>:<kind>:<index>
```

例如：

```text
srd5.1:race:elf
phb2014:subrace:wood-elf
phb2014:race:variant-human
phb2014:feat:alert
phb2014:spell:hex
scag:race-variant:half-elf-wood-descent
vgm:race:goblin
vgm:race:aasimar
vgm:subrace:protector-aasimar
vrgr:lineage:dhampir
tce:class:artificer
tce:fighting-style:blind-fighting
xge:subclass:samurai
```

同 `kind:index` 不同 pack 可共存。Display Name 永遠不是 foreign key。

### 4.2 `content_sources`

`CharacterBuild.content_sources` 的 canonical semantics：

> **該 Build 實際引用到的 Content Pack 集合。**

由 server compiler 依 candidate Build refs derive；不信任 client 手填。

如果 Builder 需要控制「目前允許選哪些 pack」，使用 Draft / server policy 的 `enabled_content_sources` 或等價概念，與 Build 最終 provenance 分離。

**`CharacterBuild.content_sources` 絕不可被拿來當 Builder allowlist / permission gate。** 它是 compile 後的 provenance summary；允許哪些來源必須在選項產生／validation 前由獨立 policy 決定。

### 4.3 Server authoritative

M01 所有新規則仍走：

```text
Builder Draft
→ server choices / compile / validation
→ Review
→ Confirm
→ immutable CharacterBuild
```

Frontend 不 hardcode D&D legality。

### 4.4 Build vs Current State

延續 P0/P1：

**Build：**永久角色選擇與來源，例如 race / subrace / M01-E 起的 race variant / lineage / class / subclass / feat / fighting style / optional class feature choices / known infusions / known or spellbook spell acquisition。  
**Current State：**目前 HP、resources、prepared、Inventory、目前 active infusion、目前 Armor Model等 live state。

不得因 M01 新功能把這條邊界打亂。

### 4.5 不做 Universal Rules DSL

M01 可以增加目前資料真正需要的 primitive：

- choice
- grant
- replacement
- level-gated grant
- lineage replacement
- optional feature addition
- expanded option pool
- retraining / versatility
- subclass progression
- feat prerequisite / permanent grant / nested choice
- resource capacity metadata
- attunement-related metadata（僅 Artificer H 所需，不代表完整 Magic Item subsystem）

但不做：

- arbitrary expression language
- user-authored scripts
- combat trigger DSL
- generic effect interpreter

### 4.6 Automation 等級

優先：

1. identity / source 正確。
2. Builder legality正確。
3. Build / State persistence正確。
4. Character Sheet / Review顯示正確。
5. 已有 Rules / State substrate能安全支援的效果才自動化。
6. 需要未來 Combat / Rest / Roll / day-clock的效果可先 structured + manual。

UI 不得把 manual effect誤表示為已自動套用。

### 4.7 M02 closeout 後的 Localization 承接

M01-D 是 M02 closeout 後第一個恢復的 Subphase，因此 **M01-D 起所有後續 M01 Subphase** 都必須遵守 M02 已建立的永久 localization rule：

- 新增或修改 user-visible UI / rules presentation，同一 Subphase 同步提供 `zh-TW` / `en`。
- 新增畫面使既有 content field 首次變成 user-visible，同一 Subphase 同步補齊該 field 的兩語 translation。
- StableKey / mechanics identity 不因翻譯改變。
- 缺 required locale 視為該 M01 Subphase 未完成。

具體 localization model / field policy / completeness contract 以已 closeout 的 `docs/M02/` 為準；M01 不建立第二套翻譯規則。

# M01-A — Multi-Source Content Pack Foundation

## 目標

把 P0/P1 的「單一 `srd5.1` registry」泛化成真正 Multi-Source Content Pack foundation，同時保持所有舊 SRD Character / Builder compatibility。

## A1. Generic Content Pack

Registry 可以同時載入多個 pack。每個 pack至少有：

- stable pack id。
- display metadata。
- ruleset identity。
- provenance。
- category declarations。
- entry counts。
- optional usage / license metadata。

SRD-specific extraction / CC BY / P4-A scope guard不能被硬塞成所有 pack的必填欄位。

M01-A 必須把目前 `ContentManifest` 的 SRD-only 限制明確拆開：

- `id`：從 `Literal["srd5.1"]` 改為 generic pack id。
- `license`：generic manifest 可省略；存在時不得鎖死 CC-BY-4.0。
- `extraction`：改為 optional；只在有實際 upstream extraction provenance 的 pack 使用，手動整理的 private pack 不需偽造 repository / 40-hex commit / MIT license。
- `scope_guard`：改為 optional 或 SRD-specific metadata；不得要求所有 pack 排除 monsters / beasts，也不得要求所有 pack `deferred_to=P4-A`。
- `categories[].upstream_file`：改為 optional；手工整理 pack 不需偽造 upstream filename。
- `categories[].count` 與 manifest `total_entries`：仍需可驗證，並維持 count consistency fail-fast。

既有 SRD manifest 必須仍可原樣載入；這是 schema generalization，不是要求先重寫 `data/srd5.1/manifest.json`。

## A2. Generic StableKey

`require_stable_key()`、ContentEntry envelope、Builder DTO、CharacterBuild validators不再限制第一段只能 `srd5.1`。

Schema-level驗 syntax；Registry/service-level驗存在與 kind。

## A3. Legacy SRD compatibility

現有：

```text
srd5.1:<kind>:<index>
```

全部維持不變。

現有 SRD 仍可能透過：

```text
index + /api/2014/... URL
```

表示 reference。M01-A保留 compatibility adapter，不要求一次 rewrite全部 SRD data。

## A4. Explicit new-pack references

新的 non-SRD normalized data直接用 StableKey reference。

不得為了讓舊 parser接受而偽造 `/api/2014/...` URL。

## A5. Cross-pack refs

必須合法支援：

```text
phb2014:subrace:wood-elf
→ srd5.1:race:elf
```

以及其他 pack → SRD / pack → pack references。

## A6. Multi-pack lookup / search

Registry至少能：

- full StableKey lookup。
- list/search by kind across packs。
- optional source filtering。
- source metadata lookup。

同名／同 index不同 source不得互相覆蓋。

Production/dev 啟用哪些 pack 必須是 **explicit enabled pack list**；不得因 `data/` 下多一個資料夾就自動成為正式可用 pack。Registry 必須允許測試注入替代 content root / enabled pack list，使 `testpack`、`pack-a`、`pack-b`、`future` 等 fixture 不污染 production registry。

## A7. Builder source policy

Builder options可以來自多 pack。

Draft / server policy如果需要限制 allowed packs，必須與 Build final `content_sources`分離。

Build final `content_sources`由實際 refs derive、deterministic sort、dedupe。

## A8. Source-aware UI

Reference DTO至少能給 UI：

- stable key。
- display name。
- source id。
- source display label。

UI value用 StableKey，不用 display name / bare index。

## A9. Fail-fast

Server startup仍要阻擋：

- malformed manifest。
- malformed StableKey。
- key/source mismatch。
- duplicate full key。
- category count mismatch。
- dangling reference。
- wrong-kind reference。

## A10. 明確不做

- 不新增 PHB正式資料。
- 不做 Half-Elf replacement。
- 不做 Dhampir lineage。
- 不做 Artificer rounding。
- 不做 Infusion / Attunement。
- 不做 Content Pack marketplace / downloader / dependency manager。

## M01-A Closeout

至少用：

```text
srd5.1 + tiny test pack A + tiny test pack B
```

證明 multi-pack / cross-pack / same-index different-source / invalid-pack behavior，並維持完整 P0/P1 regression green。

# M01-B — PHB Character Origins & Background Expansion

## 目標

補足第一輪真人創角最直接缺少的 PHB 內容：

- PHB 13 個核心 Background。
- PHB 文件中 supplied 的 5 個官方變體 Background。
- PHB 非 SRD subraces。
- Variant Human。

M01-B 完成後立即進行第一輪真人創角 Gate。

## B1. PHB Background completeness

每個 Background至少完整承載：

- skill proficiencies。
- tool proficiencies / choices。
- language grants / choices。
- starting equipment / quantity / nested choice。
- Background Feature。
- optional Personality Traits。
- optional Ideals。
- optional Bonds。
- optional Flaws。
- variant identity / relation（如來源有）。

不能只做到「下拉看得到 Background 名稱」。

## B2. Roleplay tables

Personality / Ideal / Bond / Flaw：

- 可提供建議選項。
- 可手動填。
- 可完全不填。
- 不屬 Structural Validation。
- 不得阻止 Confirm。

## B3. PHB missing subraces

至少導入 supplied source列出的：

- Wood Elf。
- Drow。
- Mountain Dwarf。
- Stout Halfling。
- Forest Gnome。

其母種族沿用既有 SRD identity；subrace只存自己的差異 grants。

必須正確反映：

- ability bonus。
- speed adjustment。
- proficiency。
- racial feature。
- racial spell。
- level gate。

## B4. Variant Human

Variant Human **必須在 B 完成**，而且不得假裝成 subrace，也不得提前使用 M01-E 才引入的 `race-variant` 機制。

正式 Character identity：

```text
race_ref = phb2014:race:variant-human
subrace_ref = None
```

Content data 可以保存：

```text
variant_of = srd5.1:race:human
```

但 `variant_of` **只代表 provenance / 關聯 metadata，不具有任何 mechanical inheritance 語意**。Compiler 不得因 `variant_of` 自動載入普通 Human 的 mechanical grants，也不得先套標準 Human ability package再做替換。

因此 Variant Human 必須是一個 mechanically complete Race package：它自己的 entry / explicit refs 必須足以決定所有實際 grants 與 choices。若要重用共同 trait，可以使用明確的 reusable feature/trait references；不能靠 `variant_of` 偷做繼承。

M01-B **不新增**：

```text
race-variant StableKind
CharacterBuild.race_variant_ref
BuilderDraft.race_variant_selection
```

這三者全部留到 M01-E，因為 SCAG Half-Elf descent 才是真正「保留 base race、針對部分 grant 做 replacement」的規則形狀。

Builder必須支援：

- 兩個不同 Ability，各 +1。
- 一個 Skill proficiency。
- 一個合法 Feat。
- Feat prerequisite走 P1 existing structural validation。
- Numeric Override與 prerequisite互動沿 P1規則。

這裡刻意接受兩種相近名稱使用不同機制：

- **Variant Human**：完整 Race package，整包取代普通 Human racial package。
- **SCAG Half-Elf descent**：M01-E 的 `race-variant`，保留 Half-Elf base package，只替換指定 grant。

不要為了名稱都叫 Variant 而強行統一成同一資料模型。

## B5. Racial spells

Drow / Forest Gnome等 racial spells必須保留 source identity。

不得：

- 混成 class spellbook。
- 混成 daily prepared list。
- 把一次／長休 racial spell錯當 normal spell slot。

## B6. Background Equipment

沿用 P1 `starting_equipment_choices` / equipment compiler。

Create Confirm只初始化 initial Inventory一次；Level Up不得再次從 Background重建 Inventory。

## B7. Builder UX

Origin step至少做到：

- Race / Subrace / Background searchable 或以等價 server-driven flow 正確選擇；Variant Human直接作為 `Race` option出現。
- source label可辨識。
- options由 server回傳。
- Draft reload不遺失。
- 回上一步改 Race/Subrace/Background後 stale choices不污染 Build。
- Review能看到 final grants與source。

M01-B 不顯示獨立 Race Variant selector；該 UI / Draft identity直到 M01-E才存在。

## B8. Mandatory First Real Character-Creation Gate

至少真人完整建立：

1. 純 SRD角色。
2. PHB新增 subrace角色。
3. Variant Human。
4. 有 tool/language choice的 PHB Background。
5. martial角色。
6. caster角色。

每隻走：

```text
Draft
→ Origin
→ Abilities
→ Class Progression
→ Spells（如有）
→ Equipment
→ Review
→ Confirm
→ Character Sheet
→ browser reload
```

M01-A/B引入或揭露的 Blocker / Major UX confusion必須在 B closeout前修完。

## B9. 不做

- SCAG Half-Elf replacement：E。
- Dhampir lineage：F。
- Artificer：G/H。
- 正式 Roll System。
- Background自動生成器。

## M01-B Closeout

成功標準：**真人已能用 PHB 級別的 Origin / Background內容量完成合法創角**，而不只是資料檔已存在。

# M01-C — SCAG / GoS Background Expansion

## 目標

在 B 已驗證 Background pipeline後，完整導入：

- SCAG supplied 13 個 Background。
- GoS supplied 4 個 Background。

並驗證不同 source、roleplay table reuse、variant/branch、航海／派系等 flavor不會逼系統建立不必要 subsystem。

## C1. Packs

正式建立／啟用：

```text
data/scag/
data/gos/
```

Background StableKey保留來源。

## C2. Mechanical completeness

每筆至少逐項資料化：

- skill grants。
- tool grants / choices。
- language grants / choices。
- starting equipment。
- quantities / currency metadata（依現有 State能力）。
- Background Feature。
- mechanical branch / choice。

Pure flavor tables不得誤成 blocking choice。

## C3. Roleplay table inheritance

SCAG部分 Background會指向 PHB Soldier / Guild Artisan / Sage等建議表格。

系統必須能表達：

```text
roleplay suggestion reuse
```

但：

```text
roleplay inheritance != mechanical inheritance
```

不能因沿用 PHB roleplay table，就多拿 PHB skills / tools / equipment。

### 無條件 static derived value

有一類 Feat 效果既不是 Build 上的 grant / choice，也不需要 Combat / Roll substrate：它只是讓角色卡上某個既有 derived value 改變，而且**無條件成立**。這類效果不得以「等 P3/P4/P5」為由整條退成 description——它現在就會讓角色卡算錯數字。

K 必須讓下列 derived value 能接受來自 Feat 的結構化修正，且只開放這個白名單：

```text
max_hp
passive Perception
passive Investigation
```

要求：

- 修正值是結構化資料，不是描述文字；來源可追溯到具體 Feat acquisition。
- 依角色等級縮放者（Tough）在 Level Up 後必須自動重算，不需要使用者手動維護。
- 與 Numeric Override 的關係固定為 `base → feat static modifier → Numeric Override`；Override 維持 P0 的絕對值覆寫語意，不因本節改變。
- repeatable Feat 的多次 acquisition 依 K4 各自計入，不被 identity dedupe 吃掉。
- 白名單以外的 derived value 一律不在 K 開放；要新增必須是明確的規格決定，不能由資料驅動自行擴張。

**條件式的 derived 效果不屬於本節。** 需要判斷裝備狀態才成立者（Medium Armor Master 的中甲 DEX 上限與 Stealth、Dual Wielder 的雙持 AC）走 K6 的 `deferred_equipment_conditional`；需要 Combat / Rest substrate 者（Heavy Armor Master、Durable）走既有 deferred 分類。

## K4. Feat repeatability / acquisition identity

**禁止任何 runtime link。** Server / Registry / Builder / Character Sheet 不得 parse、import、fetch 或依路徑讀取這兩份 Markdown。正式 runtime package 不含 `docs/` 時仍必須完整工作。

## L4. Negative racial ability modifiers

```text

Orc    → INT -2
```

L 必須保證：

- normalized racial ability bonus允許負值。
- Standard Array / Point Buy 的 base-score legality先於 racial modifier判定。
- Point Buy 的 minimum 8 **不能錯套到套完種族修正後的 effective score**；合法 base 8 + racial -2 可以得到 6。
- final ability仍遵守既有 Character schema合法範圍。
- Review / Character Sheet / localization presentation顯示 `-2`，不得出現 `+ -2` 等錯誤格式。
- Numeric Override semantics不因 signed racial bonus改變。

## L5. Natural Armor — generic Rules Layer candidate

Lizardfolk supplied rule需要：

```text

```

目前 Armor Class Rules Layer只有：

```text
10 + DEX
worn armor
shield
numeric override
```

因此 Natural Armor 是 L 真正需要新增的 Rules Layer primitive。

要求：

- Natural Armor 以 typed rule / feature metadata表示，不 hardcode `if lizardfolk`。
- 只有規則條件成立時才成為 AC candidate；Lizardfolk 的 candidate要求未穿 body armor。
- 未穿 body armor：在普通 unarmored 與可用 Natural Armor candidates 中依規則選正確結果。
- 穿 body armor：不能把 Natural Armor 與 worn armor疊加。
- Shield 延續既有 shield semantics；不能因 Natural Armor 路徑漏掉或 double apply。
- Numeric Override仍是最終絕對值覆寫。
- 既有 SRD armor / shield / unarmored角色結果不變。

L 不因此建立完整 armor-effect DSL。
