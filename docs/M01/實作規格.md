# M01 — 實作規格

> Phase：**M01 — D&D 5e 2014 Private Content Expansion**  
> 類型：**Modification / Maintenance Phase**  
> 本文件定義 M01 各 Subphase 完成後「什麼必須成立」。具體資料模型、檔案結構、API / module 接線與 migration 決策放在同目錄的 `開發設計方針.md`；自動與人工驗收流程放在 `測試指南.md`。

最後更新：2026-08-30

---

## 1. M01 的定位

M01 不取代 P2，也不改寫既有 P0 → P8 產品 Roadmap。

M01 是插入在 P1 closeout 與 P2 規劃之間的 **Modification / Maintenance Phase**，目的有三個：

1. 把目前只有 SRD 5.1 的角色內容基礎擴充成可承載多來源規則資料的 Content Pack 架構。
2. 把 `docs/暫用規則資訊/` 中已提供的非 SRD D&D 5e 2014 資料，逐步轉成 Builder / Character Sheet / Inventory 真正可使用的正式資料。
3. 在進入 Room / Campaign / Session 前，先讓使用者能用更接近真人跑團的內容量進行實際創角測試，提早找出 Builder UX 與規則表示的缺口。

M01 完成後，正常產品 Roadmap 繼續回到 **P2 — Room / Campaign / Session / Seat**。

---

## 2. M Phase 共通規則

M Phase 與正常 P Phase 使用不同編號軸：

```text
P0 → P1 → P2 → P3 ...
       ↑
      M01
```

M Phase 用於：

- 補資料／補規則內容。
- 強化已完成系統的可擴充性。
- 為已提供的新規則來源增加必要的資料表示能力。
- 做資料 migration / normalization / technical hardening。
- 修正已完成 Phase 在真實使用時暴露出的跨系統缺口。

M Phase **不是**用來偷跑下一個正常產品 Phase。若工作本質是 Room、Combat、Adventure、Timeline 等尚未開工的大型產品系統，仍必須回到對應 P Phase。

所有 M Phase 也遵守與 P Phase 相同的基本要求：

- coding 前先拆 Subphase。
- Subphase 必須可獨立實作、驗證、commit。
- 三份正式文件使用完全一致的 Subphase 名稱與順序。
- 只拆目前這個 M Phase；不得現在預先拆 M02、M03。
- 每個 Subphase 完成時 repository 必須可 build、可 test，既有 P0/P1 regression 不得被破壞。

## 4. M01 共通產品／資料原則

### 4.1 SRD 5.1 不再是唯一內容來源

M01 後，系統仍以 **D&D 5e 2014** 為 ruleset，但 Character Builder 可以同時使用多個已安裝的內容來源。

至少要能共存：

```text
srd5.1
phb2014
scag
vgm
vrgr
tce
gos
```

來源名稱是資料 identity 的一部分，不是純 UI 標籤。

### 4.2 StableKey 必須跨 pack 唯一

正式 reference identity 固定採：

```text
<pack-id>:<kind>:<index>
```

例如：

```text
srd5.1:race:elf
phb2014:subrace:wood-elf
phb2014:race:variant-human
vgm:race:goblin
vrgr:lineage:dhampir
tce:class:artificer
tce:item:all-purpose-tool-plus-1
```

同名內容只要來源不同就可以共存，不得靠 display name 或 bare `index` 覆蓋彼此。

### 4.3 非 SRD pack 不得污染 SRD 原始資料

不得為了方便把 PHB / SCAG / VGM / VRGR / TCE / GoS 資料硬塞進 `data/srd5.1/`，也不得把 SRD entry 改造成「看起來像完整 PHB」。

SRD pack 繼續代表 SRD 5.1；其他來源各自放在自己的 pack。

### 4.4 Builder 仍是 Server authoritative

M01 新內容必須透過 P1 已完成的 Builder domain / compiler / validation 進入正式 Character Build。

不得：

- 在 React hardcode 某個種族或職業規則。
- 為 Variant Human、Half-Elf Variant、Dhampir、Artificer 各寫一套獨立創角流程。
- 讓 frontend 自己算 ability grants、spell slots、selection legality。

必要的新規則 primitive 應加入 server-side 共用模型，再讓資料驅動。

### 4.5 不一次做萬用規則 DSL

M01 可以新增為現有內容確實需要的通用 primitive，例如：

- grant
- choice
- replacement
- conditional / level-gated grant
- progression
- resource

但不得因為未來「可能有更多書」就建立 generic scripting language 或完整 rules DSL。

### 4.6 描述資料與自動化分離

內容被匯入不代表所有文字規則都必須立刻 fully automated。

優先順序：

1. Builder legality / permanent Build 結果正確。
2. Character Sheet 能正確呈現。
3. 已有 Current State 能合理承載的資源與狀態正確。
4. 尚未有對應 Runtime 系統的複雜效果，可先保留 structured metadata + description + manual adjudication。

不得為了「自動化完整 TCE」提前做 P4 Combat、P6 Adventure 或 generic effect engine。

# M01-A — Multi-Source Content Pack Foundation

## 目標

把 P0/P1 的「單一 SRD 5.1 registry」泛化成可同時載入多個 D&D 5e 2014 Content Pack 的基礎，但不在本 Subphase 提前實作 Half-Elf replacement、Dhampir lineage 或 Artificer 特例。

## 完成後必須成立

1. `srd5.1` 仍能原樣載入並通過既有 validation。
2. Registry 可以一次載入多個 pack，且每個 pack 有自己的 manifest / metadata。
3. StableKey 第一段不再硬寫死 `srd5.1`。
4. Character / Builder 所有正式 stable reference 可以指向已載入 pack。
5. Builder 可以列出多 pack 的同 kind 選項。
6. 同名／同 index 不同來源不互相覆蓋。
7. cross-pack reference 可以被驗證。
8. 新 pack 使用 explicit stable-key reference；既有 SRD `/api/2014/...` reference 保持相容，不要求 M01-A 先重寫 1,944 筆 SRD 資料。
9. `CharacterBuild.content_sources` 由實際 Build references / selected content 推導並保存，成為 Build provenance，而不是永遠固定 `("srd5.1",)`。
10. Server 啟動時任一已啟用 pack schema、duplicate key 或 dangling reference 錯誤仍 fail-fast。

## M01-A 明確不做

- 不新增 PHB race/background 正式內容。
- 不新增 `race-variant` / `lineage` 特殊流程。
- 不做 Artificer spellcasting rounding。
- 不做 Magic Item effect engine。
- 不做 Content Pack marketplace、dependency manager、enable/disable UI。

Private project 第一版可以直接載入 repository 中配置的 installed packs。

## 完成條件

除了 M01-A 新測試，P0/P1 full regression 必須維持 green；至少要有一個 tiny fixture pack 驗證 multi-pack、cross-pack ref、duplicate identity 與 bad manifest fail-fast。

# M01-B — PHB Background & Core Race Completion

## 目標

補足第一輪真人創角最直接缺少的 PHB 內容，讓 Character Builder 的 Race / Background 選擇不再只有 SRD 的有限集合。

本 Subphase 是 **第一次真人創角測試 Gate**。

## 資料範圍

### PHB Background

以 `背景_PHB.md` 為資料來源，補入 PHB core backgrounds 與文件中包含的正式 variants。

每個 Background 至少要能承載並在 Builder 正確套用：

- skill proficiencies
- tool proficiencies
- language grants / choices
- starting equipment
- background feature
- personality traits
- ideals
- bonds
- flaws

Personality / Ideal / Bond / Flaw 是 optional roleplay assistance，不得變成 Confirm blocking requirement；使用者可以選表格建議、手動輸入或完全不填。

### PHB 非 SRD Race / Subrace

以 `種族_PHB_非SRD內容.md` 為資料來源，至少納入文件列出的：

- Wood Elf
- Drow
- Mountain Dwarf
- Stout Halfling
- Forest Gnome
- Variant Human

其 inherited base-race grants、ability bonus、speed、proficiencies、spell grants、level-gated traits 必須在 Build / Sheet 中正確反映。

## Variant Human 是 M01-B 必做

Variant Human **不得延後到 M01-E**。

第一版把它作為可直接選擇的完整 race option，不需要為此先建立通用 race replacement system。

Variant Human 必須支援：

- 兩個不同 Ability，各 +1。
- 任選一個 Skill proficiency。
- 任選一個合法 Feat。
- Feat prerequisite 仍由既有 Structural Validation enforce。
- 選擇結果編譯進正式 Build，reload 後完全一致。

## Background 完成不是「有文字」就算完成

背景資料必須真正走過既有 P1 系統：

```text
Background selection
→ structural choices
→ starting equipment choices
→ resolved grants
→ Review
→ Confirm
→ immutable Build + initial Current State
```

不能只把 Background name / description 加入下拉選單。

## First Real Character-Creation Gate

M01-B closeout 前必須由真人使用瀏覽器完整建立角色，至少覆蓋：

1. 一隻純 SRD 角色，確認 regression。
2. 一隻 PHB 新增 subrace 角色。
3. 一隻 Variant Human，實際選 +1/+1、Skill、Feat。
4. 一隻使用有 tool / language choice 的 PHB Background 角色。
5. 一隻 martial 角色。
6. 一隻 caster 角色。

真人測試必須走：

```text
New Draft
→ Race / Subrace / Background
→ Abilities / Choices
→ Class progression
→ Spells（如有）
→ Equipment
→ Review
→ Confirm
→ Character Sheet
→ browser reload
```

若真人測試發現的問題屬於 M01-A/B 引入或揭露的 Builder UX / content correctness 缺口，**直接在 M01-B closeout 修完**，不另外開 P Phase。

只有發現需要大型新產品系統時，才另行規劃。

# M01-C — SCAG / GoS Background Expansion

## 目標

在 M01-B 已驗證 Background pipeline 後，將 `背景_SCAG.md` 與 `背景_GoS.md` 的背景資料納入正式 Content Pack。

- SCAG / GoS backgrounds 可在 Builder 與 PHB / SRD backgrounds 同時搜尋、選擇。
- source badge / provenance 足以辨識來源。
- skill / tool / language / equipment / feature / roleplay suggestions 正確。
- background variant 若只是 grant / choice 差異，使用 M01-B 已有通用能力處理。
- 若某個 variant 真正需要 replacement primitive，最小必要能力可以在本 Subphase加入，但不得為 Half-Elf race variant 提前建立專用系統；該項仍屬 M01-E。

## 完成條件

至少各建立一隻使用 SCAG background 與 GoS background 的角色，Confirm / reload 後 Build 與 Inventory 正確。

# M01-D — VGM Race Expansion

## 目標

把 `地精_VGM.md`、`大地精_VGM.md`、`阿斯莫_VGM.md` 轉成正式 VGM content。

## 資料範圍

至少包含 supplied documents 中的：

- Goblin
- Hobgoblin
- Aasimar

UI 與資料 identity 以 canonical English name + 中文顯示資訊並存為原則，避免 Goblin / Gnome 中文譯名造成 identity 混淆；stable key 永遠使用明確英文 index。

## 完成後必須成立

- 三者可正常作為 Race 建立角色。
- ability bonuses、size、speed、languages、darkvision / proficiencies / racial features 等 Build grants 正確。
- 有使用次數／rest recharge 的 racial feature 至少必須有可辨識的 rule metadata；若 P1 Current State 已能自然承載 resource，可接入 resource，否則先以 feature + description / future runtime metadata 表示，不為此提前建立 Combat Engine。
- level-dependent racial spell / feature 若 supplied data 有需求，必須能在 high-level create / level-up 得到正確 feature access。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## 目標

正式支援 SCAG Half-Elf ancestry variants，並建立第一個真正需要的 **grant replacement** 通用能力。

## 核心規則

Half-Elf Variant 的本質不是另一個完全獨立 Race，也不是普通 Subrace：

```text
Base Half-Elf grants
+ ancestry identity
+ optional replacement of Skill Versatility
```

例如選擇某些 ancestry option 時：

```text
remove: Skill Versatility
add: Fleet of Foot / Mask of the Wild / Drow Magic / ...
```

## 完成後必須成立

- Base Race 仍引用既有 Half-Elf stable key。
- Variant selection 有自己的 stable identity 與 Build provenance。
- replacement 必須由 server compiler 明確執行，不能只在 UI 隱藏 Skill Versatility。
- 被 replacement 移除的 grant 不得仍殘留在 Build proficiencies / feature refs。
- 未選 replacement 時仍可合法保留 Skill Versatility。
- nested / branch choice 可重用 P1 已有 Builder choice infrastructure；不要建立第二套 variant wizard。
- replacement primitive 必須是資料驅動且至少可被未來相同型態規則重用，但不要擴張成任意 scripting DSL。

# M01-F — VRGR Lineage & Dhampir

## 目標

加入 VRGR Dhampir，並把「Lineage 取代原 Race、但保留部分 Ancestral Legacy」建模成正式 Character Build 概念。

## Lineage 與 Race 不可混成同一概念

M01-F 必須能區分：

```text
Race / ancestral origin
Lineage
Ancestral Legacy retained traits
```

Dhampir 不應只假裝成 `subrace`。

## 必須支援的使用情境

### 新角色直接建立 Dhampir

若沒有既有 ancestral race，可依 supplied rules 選擇初始 Ancestral Legacy 能力，例如對應 skill proficiencies。

### Existing Character 轉成 Dhampir

利用 P1-G 已有 immutable Build Version / Build Edit / Correction 能力：

```text
Old Build Version
→ Lineage Build Edit
→ preserve allowed ancestral legacy
→ validate
→ New immutable Build Version
```

不得覆寫舊 Version。

## 完成後必須成立

- Character Build 可持久化 lineage identity。
- 可保存 ancestral origin / retained legacy 的 provenance。
- Dhampir ability score choice、size、speed、darkvision、no-breathing、Spider Climb、Vampiric Bite 等 supplied rule data 有正式表示。
- Ancestral Legacy 只保留規則允許的部分，不得把原 race 所有 feature 原封不動疊加。
- transformed character 的 Current State 依既有 Build reconciliation 原則延續；M01-F 不因 lineage change 重建 Inventory / HP / Conditions。

# M01-G — TCE Artificer Core

## 目標

讓 Artificer 成為可以正常 Create、High-Level Create、Multiclass、Subclass、Level Up 的正式 Class。

M01-G 先完成「角色建立與成長正確」，不要求一次自動化所有 Infusion 與戰鬥效果。

## 必須涵蓋

- d8 Hit Die。
- starting / multiclass proficiency grants。
- saving throws。
- class skill choices。
- starting equipment。
- level 1–20 progression。
- subclass timing。
- supplied TCE specialists：Alchemist、Armorer、Artillerist、Battle Smith。
- cantrip / spell access progression。
- prepared spellcasting。
- subclass granted / always-prepared spells（若 supplied rules 有）。
- multiclass spell-slot contribution 的 Artificer 特例。

## Artificer multiclass rounding 是 blocking correctness

Artificer 對 normal multiclass spell slot level 的 contribution 必須是 supplied 2014/TCE 規則：

```text
Artificer class level / 2
rounded UP
```

不得沿用 Paladin / Ranger 的一般 half-caster floor 行為。

Prepared spell formula 與 slot contribution 是兩個不同規則，不得混成一個 rounding flag。

## 完成條件

至少驗證：

- Artificer 1 Create。
- Artificer 3 + subclass。
- High-level Artificer Create。
- Artificer + full caster multiclass slot calculation。
- Artificer + another half caster boundary cases。
- Existing Artificer Level Up。

# M01-H — TCE Artificer Advanced Rules & Infusions

## 目標

在 Artificer Core 可正確創角後，再補 Artificer 特有且需要額外 Build / State 表示的進階能力。

## 優先範圍

- Infusions Known progression。
- infused items capacity。
- infusion selection prerequisites / level gates。
- subclass-specific persistent Build choices。
- Tool Expertise 等永久 feature progression。
- Flash of Genius 等有限次數 feature 的 resource metadata。
- Magic Item Adept / Savant / Master 對 attunement capacity 的影響。
- Spell-Storing Item 的角色資料表示。
- Soul of Artifice 的規則 metadata。

## Build / Current State 邊界

原則：

- 「會哪些 Infusions」屬 Build。
- 「目前哪些物品被 infused」屬 Current State / Inventory runtime。
- 使用次數屬 Current State resource。
- 戰鬥中的 Reaction timing、attack resolution 等若需要 P4 才有正式系統，M01-H 只保存 feature/resource 與可操作的既有 state，不提前建立 Combat Engine。

## 完成條件

Artificer Character Sheet / Review 必須能讓玩家知道自己：

- 已取得哪些核心 features。
- 可選／已知哪些 infusions。
- infusion capacity 是多少。
- 目前可追蹤的相關 resource 狀態。

複雜且尚無 Runtime substrate 的效果必須明確標示為 manual / descriptive，不可假裝已 fully automated。

# M01-I — TCE Magic Items

## 目標

把 `魔法物品_TCE.md` 中 supplied TCE magic items 轉為正式 `tce` content，並讓 Character Inventory 能正確表示 possession / equipped / attuned 等核心狀態。

## 完成後必須成立

每個 item 至少可保存／顯示：

- stable identity
- name
- source
- rarity
- item category / type（資料有提供時）
- attunement requirement
- attunement class / condition restriction（資料有提供時）
- description / structured effect metadata

Inventory 至少要能表示：

```text
possessed / carried
equipped
attuned
quantity
```

若角色 attunement capacity 有變化（例如 Artificer），Character Sheet 應可顯示 current / capacity 並做 structural warning / validation；不建立大型 magic-item management subsystem。

## Effect automation 邊界

M01-I 不要求 84 件物品全部變成 executable script。

第一版允許：

```text
structured common field
+ known simple modifier when existing rules layer already supports it
+ description / manual adjudication fallback
```

不得為少數複雜物品建立 generic effect scripting DSL。

把 M01-A～M01-I 的資料、Builder、Character、Inventory 與 regression 收成一個可以交給下一個 Phase 使用的穩定基線。

## 必須驗證的完整流程

至少包含：

### Multi-pack Creation

```text
PHB race/subrace
+ SCAG/GoS/PHB background
+ SRD class
→ Review
→ Confirm
→ Sheet
→ reload
```

### Variant Human

```text
Variant Human
→ +1/+1 distinct abilities
→ skill
→ feat + prerequisite
→ Confirm
```

### Half-Elf Variant

確認 replacement 前後 Build grants 不重複、不殘留。

### Dhampir

- direct Create。
- Existing Character lineage Build Edit → new immutable Version。

### Artificer

- single-class create / high-level / level-up。
- subclass。
- multiclass spell slots rounding。
- advanced feature / infusion representation。

### TCE Magic Item

- add to Inventory。
- equip / attune（適用時）。
- reload persistence。
- Artificer attunement capacity interaction。

## Regression Gate

M01-J closeout 必須保證：

- P0 Character Sheet regression green。
- P1 Create / High-level / Multiclass / Spellcasting / Level Up / Version History regression green。
- existing SRD-only characters 不需要 migration 成新的 content identity。
- existing Character JSONB Build / Current State 可正常讀取。
- server restart 後 multi-pack Build / State / Inventory 仍一致。
- frontend build / typecheck / unit tests green。
- backend tests / migrations green。
- real-backend Playwright M01 flows green。

## 6. M01 關門標準

M01 只有在以下全部成立後才算 closeout：

1. Multi-source Content Pack architecture 已成為正式基礎，而不是只為一兩個 hardcoded source 開洞。
2. M01-B 真人創角 Gate 已實際執行，發現的 M01-A/B blocker 已修完。
