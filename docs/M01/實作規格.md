# M01 — 實作規格

> Phase：**M01 — Multi-Source Character Content Expansion**  
> 類型：**M Phase（Modification / Maintenance Phase）**  
> 本文件定義 **M01-A～M01-J 每個 Subphase 完成後什麼必須為真**。具體資料格式、schema、模組、API、migration 與接線放在 `開發設計方針.md`；自動與人工驗收方式放在 `測試指南.md`。

最後更新：2026-08-30

---

## 1. M01 定位

P0 / P1 已完成 Character Core、SRD 5.1 Content Foundation、Character Builder、Level Up、immutable Build Versions 與 Current State。現在的主要問題不是「創角流程不存在」，而是 **SRD 5.1 的角色內容量不足，而且 Content Registry / StableKey 仍以單一 `srd5.1` 為前提**。

M01 是第一個 **M Phase**，目的為：

1. 建立正式 Multi-Source Content Pack 能力。
2. 讓 Character / Builder 可引用 SRD 以外的 D&D 5e 2014 來源。
3. 將 `docs/暫用規則資訊/` 中本 Phase 明確列入的內容轉成正式機器可讀資料。
4. 優先補齊會直接影響真人創角體驗的 PHB Background、PHB 非 SRD race/subrace/variant。
5. 在 M01-B 關門後立刻進行第一輪真人創角測試，並把該輪發現的 M01-A/B 問題在 closeout 前修完。
6. 後續再處理 VGM race、SCAG Half-Elf variant、VRGR Dhampir lineage、TCE Artificer 與 TCE magic items。
7. 不因這次資料擴充提前設計 P2 Room / Campaign / Session / Seat。

M01 完成後，正常產品 Roadmap 仍回到 P2。

---

## 2. M Phase 全專案規則

M Phase 使用 `M01`、`M02`… 命名，適用於：

- 補資料、補設定、補內容來源。
- 修改／加強已完成系統。
- 既有資料結構 migration 或相容性強化。
- 為實際使用補上必要能力，但該能力不構成下一個產品 Phase。

M Phase 與 P Phase 一樣：

- coding 前必須先拆 Subphase。
- Subphase 必須可獨立實作、驗證、commit。
- 三份 Phase 文件的 Subphase 名稱與順序必須完全一致。
- 只設計目前正在準備實作的 M Phase，不提前拆下一個 M Phase。
- M Phase 不改寫正常 P Phase 的編號與順序。

## 3. M01 資料來源與正式資料原則

### 3.1 `docs/暫用規則資訊/` 的角色

`docs/暫用規則資訊/` 是 **人類整理／導入參考來源**，不是 runtime data source。

正式程式不得在 runtime：

- parse Markdown 當規則資料。
- 依文件段落文字判斷規則。
- 從 Markdown 即時生成 Builder choice。

本 Phase 完成的內容必須進入正式 `data/<pack>/` content pack，並經 Content Registry validation 後才供 Character Builder / Rules Layer 使用。

### 3.2 單一正式來源

某項規則一旦轉成正式 content data：

- **程式執行以 `data/<pack>/` 為唯一正式來源。**
- Markdown 可以保留 provenance / reference，但不與 JSON 形成雙主來源。
- Phase 文件不重抄完整規則數值；規則數值由正式資料檔與其來源文件承擔。

### 3.3 Pack 邊界

M01 預期會使用以下 pack identity：

```text
srd5.1
phb2014
scag
vgm
vrgr
tce
gos
```

來源名稱不得因 UI 中文翻譯不同而改變 stable identity。

## 5. M01 全局完成定義

M01-J 關門時至少必須成立：

- SRD 與非 SRD content packs 可同時載入。
- StableKey 不再硬編 `srd5.1`。
- CharacterBuild 的 `content_sources` 真正代表該 Build 所使用／允許的內容來源。

- TCE magic item 至少能被正式 registry、inventory 與 attunement metadata 表示；尚未自動化的效果有明確 manual-effect fallback。

# M01-A — Multi-Source Content Pack Foundation

## 目標

把 P0 的「單一 `data/srd5.1/` + hardcoded SRD envelope」改成真正可擴充的 Content Pack foundation，同時保持現有 SRD stable keys 與 P0/P1 Character compatibility。

## 必須支援

### StableKey

StableKey 維持三段 identity：

```text
<pack_id>:<kind>:<index>
```

例如：

```text
srd5.1:race:elf
phb2014:subrace:wood-elf
vgm:race:goblin
vrgr:lineage:dhampir
tce:class:artificer
```

要求：

- `pack_id` 不再固定只能是 `srd5.1`。
- 同一 `<kind>:<index>` 可在不同 pack 中共存。
- 舊 `srd5.1:*` key 不改名，不做破壞性 migration。
- Character schema、Builder schema、reference API、registry lookup 對 pack-aware StableKey 使用同一規則。

### Content Pack

每個 pack 至少有：

- stable pack id。
- ruleset identity。
- source/display metadata。
- content category declarations。
- version/provenance metadata。
- license / usage metadata欄位；M01 不建立商業授權系統。

Registry 能同時載入多 pack，而不是啟動時只能指向一個 manifest。

### Cross-reference

非 SRD pack 的 cross-reference 必須以 StableKey 為正式 identity，不得依賴舊 `/api/2014/...` URL 推導來源。

SRD 舊資料若仍保留 legacy URL，可在 importer / adapter 兼容；新 pack 不得要求仿造 SRD API URL 才能被 registry 接受。

### CharacterBuild `content_sources`

現有欄位必須正式啟用：

- Build 可記錄多來源。
- Builder candidate 的所有 source refs 必須可追溯至啟用來源。
- reload / version history 後來源資訊不得消失。
- 來源清單不可只當 UI metadata；server validation 必須能用它阻擋不允許的 pack reference。

## 不做

M01-A 不做：

- Half-Elf replacement engine。
- Lineage inheritance。
- Artificer 特例。
- magic item effect engine。
- dependency marketplace。
- pack downloader / updater。
- publisher account / signing。

## 完成條件

M01-A 關門時：

1. `srd5.1` 與至少一個測試用非 SRD pack 可以同時 load。
2. 不同 pack 的同 index content 可同時 lookup。
3. P0/P1 既有 SRD tests 全綠。
4. Builder / CharacterBuild 可以保存非 SRD StableKey，不再因 schema regex 被拒絕。
5. invalid pack、unknown key、cross-pack invalid reference 會明確失敗。
6. 新架構沒有把未來複雜規則提前塞進 foundation。

# M01-B — PHB Character Origins & Background Expansion

## 目標

補足第一輪真人創角最直接缺少的內容：

- PHB 非 SRD Background 內容。
- PHB Background variants（依提供來源資料）。
- PHB 非 SRD race/subrace 內容。
- **Variant Human**。

M01-B 是第一個真正的 **真人創角 Gate**。

## Background 必須能表達

正式 PHB Background content 至少要能驅動：

- skill proficiency grants。
- tool proficiency grants / choice。
- language grants / choice。
- starting equipment grants / nested choice（若來源需要）。
- background feature reference。
- variant background 的差異／替換。
- roleplay suggestion data（traits / ideals / bonds / flaws）可供 UI 使用，但不變成必填。

Background 長篇敘述不影響合法性；缺少 flavor text 不應阻止角色 Confirm，只要正式 mechanical data 完整。

## PHB Origin 內容

依 `種族_PHB_非SRD內容.md` 導入本 Phase 列出的 PHB 缺口，包括：

- Wood Elf。
- Drow。
- Mountain Dwarf。
- Stout Halfling。
- Forest Gnome。
- Variant Human。

具體數值與 grant 以正式 content data 為準，本文件不重複作規則來源。

## Variant Human

Variant Human **必須在 M01-B 就正式支援**，不是先當手動 override。

Builder 必須能表達並驗證：

- 選兩個不同 ability，各取得指定永久 bonus。
- 任選一項 skill proficiency。
- 選一個合法 feat。
- 保留 Human 共通的其他基礎 identity / language 等規則。

Feat choice 必須進既有 P1 Feat validation，不另外做「Variant Human 特製 feat selector」。

## Builder UX

M01-B 新資料必須進現有 Character Workshop / Builder，而不是只能靠 API 建立。

至少要求：

- 可搜尋選擇 Background / race / subrace / variant。
- 來源可辨識，但不要求使用者理解 StableKey。
- choice 仍由 server 產生。
- reload draft 後選擇不遺失。
- Review 能看到來源與最終 grants。

## 真人創角 Gate

M01-B 自動測試全綠後，必須進行第一輪真人創角測試。

至少包含：

1. 純 SRD 角色，證明既有流程未壞。
2. PHB 新增 subrace 角色。
3. Variant Human 角色，實際完成 ability + skill + feat 三種 choice。
4. 使用 PHB 新 Background 且包含 tool / language / equipment choice 的角色。
5. 至少一名 martial。
6. 至少一名 caster。
7. 建立 → Confirm → Character Sheet → 關閉／重開 → 資料一致。

真人測試發現、且屬於 M01-A/B 引入或暴露的問題，必須在 M01-B closeout 修掉；不能把明顯創角阻塞問題推到 M01-J。

## 不做

- SCAG Half-Elf replacement：M01-E。
- Dhampir lineage：M01-F。
- Artificer：M01-G/H。
- 正式 Roll System。
- Background 自動生成器。

## 完成條件

M01-B 關門時：

- PHB Background 與本 Subphase PHB origin content 能正式 Create Character。
- Variant Human 正常通過既有 Feat / choice / Build compilation。
- 真人創角 Gate 完成。
- 真人測試所發現的 M01-A/B blocker 已修正。
- Build v1、Current State、Character Sheet reload 正確。

# M01-C — SCAG / GoS Background Expansion

## 目標

在 M01-B 已驗證 Background 基礎能力後，導入已提供的 SCAG / GoS Background，驗證不同 source book 的 background variants、tool/language/equipment 組合可以在同一套 schema 下運作。

## 必須支援

- `scag` 與 `gos` pack 的 Background entries。
- skill / tool / language / equipment grants。
- source-specific background feature。
- 來源文件中存在的 variant / alternative feature 能被清楚表示。
- 與 PHB / SRD 同名或相近 Background 不靠 display name 去重。
- Builder 可同時搜尋多 pack Background。
- CharacterBuild 保存實際 StableKey 與 `content_sources`。

## Variant / Replacement 原則

Background variant 若只是替換特定 feature / grant，可以使用當前 choice / branch 能力表達；若真的需要新的通用 replacement primitive，必須限制在 Background 所需的最小範圍。

不得為了預測 M01-E Half-Elf 而在這裡提前做大型 universal effect graph。

## 完成條件

- SCAG / GoS 提供資料全部有明確導入清單與結果。
- Builder 可以建立至少各一個 SCAG、GoS Background 角色。
- source collision / duplicate display name 不會選錯內容。
- Background grants 與 starting equipment 編譯結果正確。
- P1 starting equipment initialization 仍只在 Create Confirm 發生一次。

# M01-D — VGM Race Expansion

## 目標

導入已提供的 VGM playable race，作為「新增完整 race，而非 PHB subrace」的 Multi-Source 驗證。

本 Subphase 目標內容：

- Goblin。
- Hobgoblin。
- Aasimar（以已提供 VGM 資料為準）。

## 必須支援

每個 race 至少能正式表示：

- ability grants。
- size / speed。
- languages。
- darkvision 等 sensory traits。
- skill / weapon / armor proficiency（若有）。
- feature refs。
- level-dependent racial feature（若來源有）。
- limited-use racial resource（若角色規則需要記錄 capacity）。

## 規則自動化邊界

Create / Build 結構規則要正確；需要 combat runtime 才能真正執行的 feature 不要求 M01-D 實作完整 Combat automation。

例如某 racial feature 的傷害／觸發條件若必須等 P3/P4 Combat 才有執行上下文，M01-D 應：

- 正確保存 feature identity / formula metadata / resource capacity（若現有模型適用）。
- Character Sheet 可辨識。
- 不為了它提前做 Combat Engine。

## 完成條件

- 三個 VGM race 可由 UI 建立。
- Level-dependent grants 在高等 Create / Level Up 時依正確 Character Level 生效。
- limited-use feature 不會被錯當 spell slot。
- VGM race 與未來可能存在的其他版本同名 race 可共存。

# M01-E — SCAG Half-Elf Variant & Grant Replacement

## 目標

正式支援 SCAG Half-Elf ancestry variants，並建立 **最小通用 Grant Replacement 能力**，避免以 `if race == half-elf` 硬編。

## 核心產品行為

基礎 Half-Elf 繼續是原本合法選項。

當使用 SCAG ancestry variant 時，Builder 必須能表示：

```text
Base Half-Elf grants
↓
保留未被替換的 grants
↓
指定可替換 grant
↓
選擇 ancestry branch
↓
取得該 branch 允許的 replacement feature
```

不得：

- 同時保留被放棄的原 grant 與 replacement。
- 讓 replacement 影響無關 grants。
- 把每一個 ancestry 寫成前端條件式。

## Grant Replacement Primitive

最小能力至少需要：

- stable target grant identity。
- replacement group / branch identity。
- mutually exclusive selection。
- replacement provenance。
- compile 後 Build 只保留真正取得的結果。
- Draft reload 後 replacement choice 穩定。

如果既有 P1 `branch` / `nested_choice` 已足夠，優先延伸既有模型，不新造平行 choice engine。

## 完成條件

- 提供文件列出的 Half-Elf ancestry variants 均可建立。
- baseline Half-Elf regression 全綠。
- replacement 只移除指定 grant。
- stale branch selection 不會偷偷殘留到 Build。
- Review 能清楚看出最終取得／放棄內容。

# M01-F — VRGR Lineage & Dhampir

## 目標

加入 **Lineage** 作為與普通 race/subrace 不同的正式角色來源概念，並以 Dhampir 驗證 lineage replacement / ancestral legacy。

## Lineage 不等於 Subrace

Dhampir 不得硬塞成：

```text
race = dhampir
subrace = ...
```

如果來源規則允許角色以 lineage 取代既有 race 特徵，Build 必須有能力保留這個語意。

## Build 必須可追溯

至少需保存：

- active lineage identity。
- lineage source pack。
- ancestral/original origin identity（若適用）。
- 被 lineage 保留的 legacy selections。
- lineage 自己提供的 grants / choices。

## Ancestral Legacy

必須區分至少兩種情境：

1. 初始創角直接選 Dhampir，沒有既有 race 要繼承。
2. 既有角色透過 Build Edit / Correction / versioned workflow 轉成 Dhampir，依規則保留允許的 legacy traits。

保留項目必須是明確 allowlist / selection，不是整包舊 race features 複製後再猜哪些要刪。

## Level / Runtime Feature

Dhampir 的 level-dependent trait 與 limited-use feature 必須可進 Build / resource metadata；需要 Tactical/Combat context 的效果可以 deferred，不提前建立 Combat Engine。

## 完成條件

- 新角色可直接建立 Dhampir。
- 至少一個既有非 Dhampir Character 可透過 versioned Build workflow 轉成 Dhampir並保留合法 Ancestral Legacy。
- 原 Build version 保持 immutable。
- 不合法的 inherited trait 被 server validation 阻擋。
- Character Sheet / History 可看出 lineage change provenance。

# M01-G — TCE Artificer Core

## 目標

讓 Artificer 成為可以正常創建、升級、選 Specialist 並進入既有 Spellcasting / Multiclass framework 的正式 class。

M01-G 專注 **核心 Class progression 正確**，不要求一次自動化所有 Infusion 與高階特殊效果。

## Core progression

必須由正式 TCE class data 表示：

- hit die / HP progression。
- armor / weapon / tool proficiency。
- saving throws。
- skill choices。
- class-level features。
- cantrip / spellcasting progression。
- subclass timing。
- ASI timing。
- class resource capacity（只限核心 create/level-up 需要者）。

## Spellcasting

Artificer 必須進既有 P1 Spellcasting 模型，而不是建立第二套 spell system。

關鍵要求：

- prepared caster identity。
- prepared count formula 可表示 Artificer 規則。
- multiclass slot contribution 支援 Artificer 的 rounding semantics。
- multiclass combined slots 與 Pact Magic 邊界不被破壞。
- spell access / prepared live state 仍維持 Build / State 分離。

不得用 scattered `if class == artificer` 修補每個 slot 計算點；若現有 `half` 表示不足，應升級為可表達 formula + rounding 的通用 representation。

## Specialist / Subclass

本 Subphase 至少要求已提供資料中的 Artificer Specialist 能在正確 class level 選擇並保存 identity。

M01-G 的目標是 subclass selection / base progression 接通；Subclass 內所有複雜 runtime feature 是否自動化，由 M01-H 範圍決定。

## 完成條件

至少通過：

- Lv1 Artificer Create。
- 高等 single-class Artificer Create。
- Artificer Level Up。
- Artificer + full caster multiclass slot calculation。
- Artificer + another half caster edge case。
- Specialist selection timing。
- Prepared spell eligibility / state reload。

# M01-H — TCE Artificer Advanced Features & Infusions

## 目標

在 M01-G 已有合法 Artificer Core 後，補足實際 Character Sheet / Level Up 需要的 Artificer 進階能力，尤其 Infusions、feature resources、attunement capacity exceptions 與可合理結構化的 subclass features。

## Infusion

至少要能表示：

- infusion option identity。
- prerequisite / minimum level（若有）。
- known infusion choices。
- infused-item capacity。
- 同一 infusion 的合法重複／不可重複規則。
- Build 中的永久選擇與 Current State 中的「目前套在哪個 item」分離。

不得把「目前哪件裝備被 infusion」存成 immutable class choice。

## Feature Resources

對 Flash of Genius 等有次數／恢復週期的 feature：

- Build 保存 capacity derivation / feature identity。
- Current State 保存實際 remaining/used。
- Level Up reconciliation 不自動把已消耗資源回滿。

需要完整 Rest engine 才能自動恢復的部分，可保存 refresh metadata，真正的 rest transaction 留既有 Roadmap 對應 Phase。

## Attunement Exception

Artificer 提高 attunement capacity 的 class feature 必須能影響角色的 derived capacity / inventory validation，而不是把某幾件 TCE item 寫死成例外。

## Runtime Automation 邊界

M01-H 不要求把每個 Infusion / Specialist feature 做成 CRPG 式全自動執行器。

可接受：

- 結構規則自動驗證。
- capacity / resource / selection 自動化。
- effect metadata / manual-effect fallback。

不要求：

- 自動放置 turret token。
- 完整 combat targeting。
- 自動處理所有 reaction / damage trigger。

## 完成條件

- Artificer create / level-up 後 infusion known / capacity 正確。
- Current infused item assignment 不污染 immutable Build。
- feature resource level-up reconciliation 正確。
- attunement capacity exception 可被 Inventory/Character derived view 使用。
- 沒有為每個 feature 建立散落 class-name special case。

# M01-I — TCE Magic Items

## 目標

把提供的 TCE magic item 資料正式導入 Content Registry，並讓現有 Inventory 能保存、顯示與驗證最重要的 item metadata。

## Item metadata

至少支援：

- StableKey / name / source。
- item category / type。
- rarity。
- requires attunement。
- attunement restrictions（class 等可結構化條件）。
- charges / resource metadata（資料需要時）。
- passive bonus/effect metadata（能合理結構化者）。
- description / manual-effect information。

## Effect Automation 原則

M01-I **不建立全能 magic item effect engine**。

第一版優先級：

1. item identity 正確。
2. inventory possession 正確。
3. equip / attune state 可表示。
4. attunement requirement / capacity 可驗證。
5. 已有 Rules Layer 能自然支援的 bonus 可接入。
6. 尚未有 runtime primitive 的效果保存 structured/manual metadata，由 DM / Player 執行。

不能因某 item 的效果還沒自動化，就拒絕把該 item 放進 Inventory。

## Artificer 互動
