### 共用 transaction 與 revision

P7 沒有自動存檔，因此不在 Session／Scene／Combat lifecycle 插入存檔 hook，也不要求所有 writer 改走新鎖。鎖只用來讓「手動存檔／還原／匯出」拍到一致的世界切面，分兩條既有路徑：

- **場內（Campaign 有 active Session）**：所有正式事件經 `TableEventRepository.append`，該方法在同一 transaction 確認 Session active 並鎖住該場 `session_table_runtime` 列，本來就逐筆排隊。場內手動存檔也走這條路（見 B.2），與場內寫入自然互斥；P4／P5／P6 場內 writer 不改。
- **場外（沒有 active Session）**：寫入 Snapshot 涵蓋資料的場外操作（P6 世界／context／attachment／override、Monster Instance）、場外手動存檔、Restore、Campaign／Room 匯出，先取得 Campaign guard＝鎖住該 `campaigns` 列。Session Start 既有 `_lock_start_scope` 已鎖同一列，所以 Restore／匯出與開場互斥。取得 guard 後重查 active Session／Combat；狀態已變則回 409 或改走場內路徑，不在錯誤路徑寫入。

Campaign 有 active Session 時，寫入 Snapshot 涵蓋資料的操作必須在該場 `session_table_runtime` 列鎖內完成（多數已經經 `append`）。P7-B 開工時列出所有 Snapshot 涵蓋資料的 writer 作為驗收證據，找出「active Session 中不經事件隊列」的例外；例外只補取同一列鎖並寫管理紀錄，不改既有誰能寫的權限。

Lock order：Room lifecycle guard → Campaign guard（`campaigns` 列，多個 Campaign 依 id 排序）→ `session_table_runtime` 列 → domain entity ids 排序。場內 writer 不取 Campaign guard，直接從 `session_table_runtime` 開始；既有 `append`／Session lifecycle 內部鎖序不變，開工時核對最新程式。現有 repository 若自行開 transaction，增加 internal connection-aware 方法，讓 guard、domain mutation、管理紀錄、capture 在同一 `Connection` 完成；不得先 commit 世界再補存檔，或外層鎖與內層不同 connection 僅做表面互斥。

Room library authoring不是Campaign世界writer，不要求它改取Campaign guard。Capture引用的revision／digest仍須在同Connection取得一致的來源切面，核對M07既有map／template讀取與排序鎖，不能把Campaign guard當作已鎖住Room庫。Portable export的library／placement adapters也必須使用D.2的同一read snapshot，不各開transaction。

Snapshot 對asset／Adventure definition／Room Monster Template／Battle Map（含預配置）／Stage圖片的typed引用以FK `RESTRICT` reference rows表示，沿M07刪除引用保護，不以掃自由文字替代；Room Hard Delete是整包exception，依既有流程連同Snapshot清理。引用manifest記source revision／digest，不因此回捲共享庫或要求所有authoring writer改走Campaign鎖。

庫引用保護針對穩定的模板／map identity；可替換的geometry／placement以map revision與所需歷史內容辨識，不把Snapshot FK直接掛在當前child rows而禁止合法編輯。Portable對歷史embedded IDs亦從其凍結payload建立typed對應，不能假定目前庫仍有同一child row。

新增 Campaign history control row（Campaign FK）：`history_epoch`、`next_position`、`world_revision`、`current_segment_id`。epoch／revision／position 單調遞增，Restore 不復原它們；只在已持有 Campaign guard 的路徑（Session Start、場外寫入、Restore）更新，場內 append 不碰此列。

## P7-A — Campaign Timeline & History Retrieval

### A.1 Schema 與 canonical source

新增：

```text
campaign_history_segments
  id, campaign_id, parent_segment_id?, parent_cutoff_key?, created_at
campaign_session_history
  session_id (PK/FK sessions), campaign_id, segment_id, position
campaign_management_records
  id, campaign_id, segment_id, position, seq, record_rank,
  kind, occurred_at, actor_kind, acting_seat_id?, subject_character_id?,
  visibility, recipient_seat_ids, payload_version, payload
```

Timeline 排序鍵是 `(position, seq, record_rank)`，不用 wall-clock timestamp，也不為每筆場內事件另拿 Campaign 流水號：

- 場內事件：`(該場 position, session_events.seq, 0)`。直接讀既有 `session_events`，不複製 payload、不另寫 index row；既有與未來的 Session event producer 自動進 Timeline，不需逐一接線。
- 場外管理紀錄（場外世界改動、場外存檔、Restore／歸檔）：在 Campaign guard 下取 `next_position`，鍵為 `(新 position, 0, 0)`。
- active Session 期間的例外管理紀錄（見「共用 transaction 與 revision」）：在該場 `session_table_runtime` 列鎖內，鍵為 `(該場 position, 當時 last_event_seq, 遞增 rank≥1)`，不消耗 Session seq。

Session Start 在既有 Campaign 列鎖內寫 `campaign_session_history`（position＝`next_position`，segment＝`current_segment_id`）；Restore 只在沒有 active Session 時執行，所以一個 Session 永遠只屬一個 segment。正式改動與管理紀錄同 transaction；retry 不重複。

Migration 對既有每個 Campaign 建 initial segment，依 `(sessions.created_at, sessions.id)` 一次性分配場次 position；原事件 ID／seq／payload 不動，不 backfill 逐筆事件。unknown event kind 仍保留、用安全的泛用 presentation，不做 destructive payload normalization。

重用 TableEventService 的事件 visibility 與 Combat projector，但必須先修正歷史隱藏名單的來源：按每筆事件所屬的 `combat_id` 取得該場 Combat 的 entry／Monster 隱藏資訊，不能用 Campaign `get_active()`。同頁不同戰鬥須分別解析，page cache 以來源 Combat 為 key；戰鬥結束、另開新戰鬥或 Restore 後，仍不得令舊秘密解除遮蔽。

以 durable event 與 entry／request 的 Server-side 關聯解析來源戰鬥，並保存必要的歷史 visibility facts，不能只依現在的 Monster visibility 推測過去是否公開。缺少可驗證的來源或隱藏資訊時，Player projection 對該事件的 Monster identity 採保守遮蔽，不 fallback 到 active Combat，也不影響合法 DM 讀取。既有資料 migration／backfill 需處理缺少 `combat_id` 的事件與 `roll.*` 關聯。

將共用 projector 與來源解析抽成公開唯讀介面，M05 history／P3 list、wait、Resume／Timeline／AI 歷史 MCP 都調同一實作；P7-A 必須一併修正共用接線，不能只讓新 Timeline 安全而留下舊聊天回捲洩漏。管理 event 的 projection 明確分開，不用 Human Owner 身分假造 `is_current_dm` 去讀所有 Session 秘密。現有缺陷與重現證據見根目錄 `已知問題.md` 的 KI-P5A-001。

### A.2 查詢與 authority

新增 Human `GET /api/rooms/{room_id}/campaigns/{campaign_id}/timeline`，query：`cursor?`、`limit`（預設 50／最大 100）、`query?`（上限 200 字元）、`session_id?`、`kind?`、`character_id?`、`from?`／`to?`、`archive=exclude|include|only`（預設 exclude）。

DTO：`items[]`（record id——場內為 source event id、場外為管理紀錄 id——、Session、kind、occurred_at、可見 summary／details、archive status）、`next_cursor?`、`has_more`。不回傳未過濾 total、raw payload、storage／credential identities。Cursor 是 opaque query continuation，包含固定上界、filter digest、排序鍵；驗 scope 與 filter，不允許猜 cursor 探測其他 Room。

每個來源 Session 重新解 M05 historical scope；控制的 Human Seat 已被改派／archive 時立即失效。P7 campaign endpoint 允許目前可讀歷史、卻沒參加當前場的 Human，不改既有 `/events/history` active actor 契約。沒有合法 scope 回不洩漏存在性的 404。

AI 新 `get_recent_timeline`／`search_campaign_history` 接目前有效 active Session grant（pre-session grant 不擴權）；scope 是 grant 當前綁定 Seat。對每個來源 Session，private events 只按該 Seat，DM-only 還需匹配該場 `dm_seat_id`。不把舊 Human access session 假造為 AI scope；使用共用 `EventReadScope` projection 加 current-grant validator。

搜尋在授權後的 presentation text／結構化可見欄位做比對；不能先搜尋 raw secret payload 再回空 snippet／命中計數。固定 scan budget 與 page limit，稀疏可見結果可回空 items＋continuation，不能掃完整 Campaign 才回覆；SQL 使用參數、建立 `campaign_session_history (campaign_id, segment_id, position)`、`campaign_management_records (campaign_id, segment_id, position, seq, record_rank)` 及必要 kind indexes，沿用 `session_events` 既有 `(session_id, seq)` 索引。V1 不做 vector search／LLM summarization。

歷史搜尋／摘要／details 的來源 Combat 解析與 A.1 相同；查詢跨已結束戰鬥與另一場 active Combat 時，隱藏名單不得混用。完整 Campaign／Room 匯出是 Human Owner 管理資料，可保留秘密；匯入後的 Player 歷史 projection 必須仍能由 remapped 來源 Combat／visibility facts 正確遮蔽，不能把 Owner 匯出權誤當 Player 讀取權。

### A.3 UI 與接續

Timeline 從 Campaign／Session UI 可進入，compact summary 展開詳情；Archived 需明確標記。新增 feature 住 `apps/web/src/features/rooms`，React Query query key 帶 Room／Campaign／filters／authority generation，Take Back／reassignment 清 cache。M05 chat 保持聊天流，不把 Timeline 搜尋結果送進 gameplay reducer。

## P7-B — Campaign Snapshot Capture

### B.1 Schema／payload

新增 `campaign_snapshots`：`id`、`campaign_id`、`segment_id`、`boundary_key`（同 Timeline 排序鍵）、`label?`、`source_session_id?`、`source_event_id?`、`idempotency_key`、`payload_version`、`payload`、`sha256`、`created_at`、`created_by`。`(campaign_id, idempotency_key)` unique；payload immutable；origin metadata 只作 provenance，不是 current authority。沒有 `trigger` 欄位，因為只有手動存檔。

Payload v1 是 typed schema，保存：

- Campaign world entries（含 visibility／DM notes／knowledge relations／archive state）、Adventure overrides、runtime context；
- attached Adventure ids／版本 digest；Stage 另放 historical presentation 區塊，不屬 restore payload；
- Campaign所屬非active Combat Monster Instance狀態、自己的完整rules_snapshot與來源provenance；
- 必要asset／Adventure entry／Room Monster Template／Battle Map與配置的typed引用manifest、revision／digest。

不含 characters／versions／state、Roster、Seat／grant、OAuth、Room settings、Campaign lifecycle、Combat board／pending requests。P6 knowledge relation 恢復只改世界 relation，不寫 Character。因 shared authoring 未回捲，引用 manifest 需驗 digest；若素材／definition 已更動且無舊版本可解析，Restore Preview 拒絕並列出引用，不能聲稱精確還原。個別 deletion 必須尊重 Snapshot 引用，Room Hard Delete 仍是整包 destructive exception。

`monster_templates`已有room_id，不能再當Campaign世界資料保存／回復。Room templates的rules／presentation_json／revision／archived_at，map definitions及monster placements都是excluded authoring。Instance的`rules_snapshot.provenance.template_revision`與`presentation.names/name_is_custom`屬其建立時快照；有完整凍結規則時不因Room模板更新就拿最新版重建或判為缺規則，來源仍驗同Room／存在與必要引用。需要外部歷史版本才能解析的manifest則保留上段Preview拒絕規則。

既有 Stage 是 `app.persistence.rooms.exploration.session_stages`，圖片 bytes 在 `room_stage_images`，不是 Room Asset 的 filesystem bytes。Capture 有來源 Session 時可保存該場 Stage，僅供 Snapshot 歷史呈現；場外 manual capture 沒有來源 Session 時此區塊為空，不自動挑上一場 Stage。Restore 不改任何 `session_stages`，不保存接續 seed，不替下一場建立 Stage；新場沿既有空 Stage 行為。historical Stage 圖片仍須納入 Snapshot 引用及 portable asset adapter，不能只處理 P6 room_assets 而漏掉 P3 bytes。

### B.2 Manual capture

只有 Human `POST .../snapshots`（`label?`、`idempotency_key`），沒有 lifecycle hook。Internal `capture(connection, campaign_id, boundary_key, actor)` 只供完成授權的 manual service 使用，鎖內重查 active Combat，不以前端 disabled 按鈕為保證。

- **場內**：該場Human current DM（含Owner指派的member authority）經 `TableEventRepository.append` 的transaction projection追加DM-only `snapshot.created`事件，capture在同一transaction讀世界；`boundary_key`＝該事件的鍵。這個場內權限不升格為Room管理或場外Restore／portable管理授權。
- **場外**：Room DM／Owner authority 取得 Campaign guard，重查沒有 active Session，capture 並寫一筆場外管理紀錄；`boundary_key`＝該紀錄的鍵。若取得 guard 後發現已開場，回 409，請前端改用場內入口。

同 idempotency key retry 回同一份 Snapshot。`GET .../snapshots` 為 bounded metadata list，`GET .../snapshots/{id}` 只對管理 scope。新增列表／詳情 UI 明示「角色不回復、不可在戰鬥中存檔、存檔永久保留」。

### B.3 Failure

沒有 optional Scene／Adventure 也可存檔。所有可序列化資料在驗證後寫入，失敗整筆 rollback，不留半份存檔或孤兒事件。`snapshot_combat_active` 409；`snapshot_session_state_changed` 409（場外入口遇到已開場）。對外錯誤訊息不含 secret payload。

## P7-C — Campaign Restore & History Archive

### C.1 Preview／Confirm

新增 `POST .../snapshots/{snapshot_id}/restore-preview`，回 `preview_id`、digest、snapshot metadata、world_revision／history_epoch、影響摘要／阻擋原因；預覽紀錄綁 current access session、Campaign、snapshot checksum，短 TTL（15 分鐘）。`POST .../restore` 收 `preview_id`、`expected_world_revision`、`expected_history_epoch`、`idempotency_key`、確認旗標。

兩步皆需 Human Room DM／Owner；Confirm 在 guard 後重新驗有效 Room access、無 active Session／Combat、revision、snapshot checksum、所有引用完整。Preview 不是操作授權。HTTP 409：`restore_session_active`、`restore_combat_active`、`restore_preview_stale`；422：unsupported schema／missing references；越界使用既有 404 policy。

### C.2 原子回復

在一個 transaction：檢查 → 回復 typed world payload → 將存檔後新增世界條目 archive（保留 referenced rows）→ 建 continuation segment（parent＝snapshot segment、cutoff＝snapshot `boundary_key`）→ history_epoch／world_revision 遞增 → 追加 restore management record → invalidate pre-session AI grants／OAuth families → 保存 idempotent result → commit。

所有受影響 entity revision 從當前值遞增，不複製舊 revision；舊 idempotency records 保留作歷史／duplicate detection，來自已 archived generation 的 retry 回 stale conflict，不 replay、不回傳冒充現況的舊成功結果。需要 segment／generation 標籤的既有 world mutation ledger 在同 Subphase migration 補齊。

不修改 Character tables、Campaign lifecycle／Roster／Seat binding（revoke pre-session grant 使用既有 lifecycle revoke 及單調 controller_epoch，不能回復舊 binding）、Session status／participant／table event／Combat rows。Completed Combat 的保存屬歷史，不能成為 active Combat。Snapshot 後 pending request 只保留原已終結 lifecycle 的歷史，不重新排隊。

同樣不修改Room Monster Template／map／monster placement rows或它們的封存狀態、revision；還原Instance狀態使用Snapshot內的凍結規則，不呼叫以最新模板spawn新怪的gameplay factory。Snapshot後新增的Room庫資料也不能當作新增Campaign世界條目archive；其他Campaign共享authoring保持原樣。

### C.3 歷史 lineage

Segment relation 是 internal lineage：目前可用歷史＝current segment 全部＋其 parent 中排序鍵 ≤ cutoff 的紀錄，遞迴到 initial segment。其餘紀錄是 archived；場內事件的 segment 由所屬 Session 的 `campaign_session_history` 決定。不改既有 events、不用 `created_at <= snapshot time` 粗切。

這可處理同一 Session 中途的手動存檔（cutoff 落在該場某個 seq）、多次 Restore、Restore 到不同歷史點；不可只把整個 Session archive。`boundary_key` 永不重新分配；重新 Restore 舊 Snapshot 建新 continuation，不修改舊 segment 或吞掉前次 restore audit。

P3 gameplay cursor 不跨場回退。M05 chat 的 Session read 返回 archived annotation，但 history events 不重送 live reducer；AI recent context／P6 relevant history 預設走 current lineage，查 archived 要明確選項。原有 raw durable event 作診斷與歷史保存，不能被當成當前世界 replay。

Restore 成功前端 invalidate Campaign world／Timeline／Snapshot／Lobby query，顯示保留角色警示；下一次 Session Start 用目前角色狀態與回復世界，Stage 仍從空白開始。沒有 active Session，所以不偽造 Session notifier；新場 event 仍使用原 notifier。

## P7-D — Portable Package Export

### D.1 Portable v1

採 ZIP，固定根 `manifest.json`，資料 JSON 分區與 `assets/<package-local-id>` bytes。Manifest：`schema_version="1"`、`ruleset`、`export_type=adventure|campaign|room`、`created_at`、producer version、entity counts、各檔 `path/size/sha256`、required content-pack stable refs。另保留 Character JSON v1 原格式，不能把 portable envelope 套進既有 Character endpoint。

Schema version／strict typed entity adapters 定義於多人 portable module；`additionalProperties` 拒絕未識別 authority／credential fields。紀錄實際 pack dependency，不把 normalized rules data 或 runtime `docs/` 內容抄成第二份規則真值。

既有 `build_character_export()` 已包含所有 Build Versions、Current State 與 builder provenance；Campaign／Room 直接重用 locked v1 的完整內容，不另造角色版本格式。為符合整包一致切面，擷取邏輯需可使用呼叫者的同一 read Connection，不能在每個角色匯出時各開不同 transaction。Room 的未完成 draft／import source 與未引用 assets 另由多人 adapter 包裝。Adventure original source 選項只影響可選來源，不可移除被正式內容所需的附件。

建立逐型 reference registry：Room、Campaign、Character／Version／Draft、Roster、Seat、Session／participant、event／private recipients、world entry／override／knowledge、Adventure／entry／attachment／import draft/source、Room Monster Template／Instance／Combat／board、Battle Map／geometry／monster placement、Snapshot／segments／records、asset。已存在內嵌payload的typed ID亦須追蹤；禁止靠「所有UUID字串」替換而破壞使用者文字。

M07 adapter欄位與閉包：

| 來源 | 必須追蹤／保留 |
|---|---|
| `monster_templates` | room_id、source_key（provenance）、rules、presentation_json、revision、archived_at；內建stable key是content dependency，不把builtin變自訂row |

Room export收完整庫（含未使用／封存）並以typed identity去重；Campaign／Adventure從自己的root追閉包，納入所需map的全部配置、配置模板、Instance／historical／Snapshot來源與assets，不帶同Room其他Campaign或不相關庫。Snapshot需要的舊內容不可用最新庫填補；typed remap與checksum重算不得抹掉缺版本或Restore阻擋，沿B／C的引用規則。

### D.2 Authority／一致切面

Human routes 住 `app.api.rooms.portable_packages`：`POST /api/rooms/{room_id}/exports`（type／Campaign 或 Adventure id／include_original_sources）；Room／Campaign Owner-only，Adventure Owner／DM。完成後受相同 auth 保護的下載入口。沒有 management MCP definition。

匯出先取得範圍內所有 Campaign guard（依 id 排序），在鎖內查 active Session／Combat，並建立短期 asset pin；DB 使用一致 read snapshot（PostgreSQL repeatable read），在同一讀取點產生完整 typed graph。asset bytes immutable、在下載完成前不可刪除；stream ZIP 不長持 DB connection，先完成 DB materialization／暫存與校驗，再交付。清楚設定檔案／總量上限，超限拒絕，不 silent truncate。

Credential exclusion 採 allowlist DTO。actor access identity remap 成僅供 package audit 的 local author ref，不包含 access token／hash／secret prefix／grant credentials／OAuth state。Snapshot nested payload、event command／result payload、provenance／source metadata 也經各 adapter 檢查，不能只濾頂層。

## P7-E — Previewed Copy Import

### E.1 Staging schema／routes

新增 `portable_import_jobs`：id、target_room_id?、current_requester、export_type、manifest_digest、staging_key、status、preview_json、expires_at、idempotency_key、result_refs；staging 不掛到正式 Room assets。路徑位於 Server 管理 staging root，不回傳給 client。

`POST /api/rooms/{room_id}/imports/preview` 收 Adventure／Campaign package；`POST /api/room-imports/preview` 收 Room package 及新 Room 設定（沿既有 create-room policy，無舊 Owner Key）；`POST .../{job_id}/confirm` 收 preview digest／idempotency key；取消與過期 cleanup 使用同一 job ownership。

target Room 的 job 綁既有 current access session。Room Import 尚無新 Room authority，依現有免帳號 create-room policy 允許準備新副本；Preview 回一次性、僅授權該 job 的 opaque capability，Server 只存 hash，Confirm／取消／重取結果須驗此 capability。它不授予任何既有 Room 權限，也不寫進 package／log；新 Owner authority 只在成功建立新 Room 時簽發。不以 display name 或 source Owner identity 驗 job ownership。

ZIP 驗證不允許 absolute／drive／UNC／`..`／symlink／重複或大小寫碰撞 path；Windows／Linux 同規則。限制壓縮檔／展開總量、單檔、entries 與 compression ratio；每個檔案在 staging streaming 計數並驗 hash，禁止 extract-all 到信任路徑。JSON strict schema／types／reference graph／ruleset／supported version／content pack availability 先驗；非法但「看起來可以忽略」的身份資料不可 silent import。

### E.2 Remap／publication

以 typed `(entity_type, source_id)` → new ID map 重建 graph；同一來源共享 Character／asset 只產一個新 identity。Content stable key 不改，Character export 中 Room-neutral identity 仍依 M03／P2 normalize。Snapshot payload／lineage boundary／event recipient／participant／embedded Combat references 全部 remap 並重新計算 checksum；歷史 position／seq／record_rank 保留原內部排序，new Campaign control 的 `next_position` 從最大值後接續。

同一來源Room模板／map亦各只有一個new ID，placement／geometry建立獨立new IDs並指向mapped parents／custom templates。重建`custom:<uuid>`的reserved typed ref，builtin template_key／source content stable key不改；revision／digest是來源版本資訊，不當作ID remap。target既有Room的Campaign／Adventure import也建立全新閉包，不按source_key／名稱合併或patch既有庫。封存狀態、配置visibility、Instance凍結規則與名稱快照保留，沿M07複製配置／封存使用邊界，不建立active Combat或live queue。

Credentials 全部不匯入；human/AI Seat 均落 `controller_kind=none`，controller_epoch 初始化符合既有 schema；OAuth／AI grants／room access sessions／live pending actions 不建。原 actor provenance 僅作無權限 audit identity，不把同名人物連到現有 user。新 Room 用新 code／password／Owner & DM key，一次性交付沿現有 create-room grant 流程，package 不保存新憑證。

既有 `sessions`／`session_participants` 的 binding check constraint 要求 human／ai 有真實 access／grant FK，不能只把 FK 清空卻保留 human／ai kind。匯入的已結束 Session 與 participant binding 一律 normalize 為 `none`＋null access／grant／generation；原 controller kind／顯示名稱保存在新增 `portable_history_provenance`（entity_type、entity_id、audit_payload），只供歷史呈現。DM Seat、participant Seat／角色、visibility／recipient 關係仍 remap 保留。`session_events.acting_ai_controller_grant_id`／`acting_grant_generation` 清空，寫入者歷史另用無授權 provenance；不建立假的已撤銷 grant 或 access session 來滿足 FK。此 normalization 不修改原 Room／來源歷史，也不放寬既有 binding constraint。

Package producer 不帶 active Session／Combat；Importer 亦拒絕 active runtime，不將它們偷改成 ended 或啟動。已結束 Combat／requests 可作 typed historical evidence 匯入，但沒有 live queue。Confirmed package 內的 archived history 仍帶 lineage 標籤及原 privacy scope。

DB transaction 前把檔案驗完並放進 immutable staged bytes；Confirm reauth、驗 target、digest／TTL／rules refs，重新確認 target 仍存在。取得 publication guard 後 DB 一次建立完整 graph 與新 asset metadata，reference 指向已完整的 bytes；成功 commit 後 job 標完成。失敗 rollback 並追蹤可清理 orphan；crash 後 reconcile 能判定已 commit 或可清除，不由一半 metadata 對外暴露檔案。外部副作用不用偽稱 DB 可 rollback。

UI 依 Preview／Confirm 狀態呈現，成功顯示新 Room／Campaign／Adventure 連結；Room 新 Owner 憑證沿既有顯示規則，不進 log 或歷史。失敗雙語 machine code，不能顯示「匯入成功」後讓使用者補半個 reference graph。
