# M04 — 實作規格

> Phase：**M04 — ChatGPT Web MCP Integration & AI Join Kit**
> 類型：**M Phase（Modification / Maintenance Phase）**
> 插入時點：**P3 關門之後、P4 開工之前。** M04-A 與 M04-B 先於 P4；M04-C 為 P4 前的收尾。
> 本文件定義 **M04-A～M04-C 每個 Subphase 完成後什麼必須為真**。具體 module、endpoint、schema、文字內容與接線放在 `開發設計方針.md`；自動與人工驗收方式放在 `測試指南.md`。

最後更新：2026-09-11

## 1. M04 定位

P3 已交付 `POST /mcp`：AI 以 P3-D 的 scoped AI Join Token 進場，tool catalog 依 Player／DM／pre-session DM 產生，Human UI 與 MCP 共用同一組 application service。P3-F 以 Claude Code 2.1.260 經 HTTPS 跑完整條 DM journey，證明入口可用。

P3 關門當天（2026-09-11）的第一次真實使用暴露了三件事：

1. **使用者的首要目標是讓朋友用 ChatGPT 網頁版直接進桌當 DM 或 Player。** 這條路目前完全不通：網頁版 connector 不能填 static header、需要公開 HTTPS 入口、走 OAuth，而 client 實際送出的 protocol、tool discovery 與 cache 行為對本專案都是未知。
2. **這些未知不是小細節，會決定架構。** 依 reviewer 引述的 OpenAI 文件：custom MCP app 的流程是 authentication → Scan Tools；approved app 使用 frozen tool snapshot，server 之後的 tool 變更不會自動套用，要 Refresh／重新發佈。這直接撞上 P3「tool catalog 依授權 scope（DM／Player／pre-session DM）不同」的設計。不先實測，M04 後續任何入口設計都可能被推翻。
3. **AI 拿到 token 之後不知道該怎麼開始。** token 只在 Lobby 顯示一次，沒有隨附說明；AI 要能讀 repo 才拼得出 client。這是真實缺口，但它必須配合 ChatGPT 的已知契約來做，不能先做。

因此 M04 的順序是：**先用一個極小的獨立 HTTPS 測試 server 對真實 ChatGPT Web 做完整 preflight，再把 Adventure Table 的正式入口做成符合那份實測契約，最後才做 Join Kit 與其他 client 相容。**

M04 不做的事：

- 不改 P3-D 的授權模型（Seat `controller_epoch` SSOT、grant generation snapshot、pre-session TTL、Take Back 規則）。OAuth 只是取得既有 Seat／grant 控制權的另一種交付方式。
- 不讓網站接 LLM API。
- 不提前做 P6 的 Adventure／Campaign context。
- 不做使用者帳號系統；OAuth 的「登入」就是提交 AI Join Token。
- 不把 claude.ai／Codex CLI／Codex Desktop 相容當 closeout 必要條件。

M04 順序：

```text
P3 closeout
→ M04-A — ChatGPT Web MCP Preflight
→ M04-B — Adventure Table ChatGPT Web Integration
→ M04-C — AI Join Kit, Server-hosted Guide & Other Client Compatibility
→ P4
```

## 2. M04 產品行為

### 2.1 ChatGPT Web 是 M04 的必要成功條件

M04 closeout 的定義是：**使用者在 Adventure Table 建好 Seat 並發出憑證後，朋友在 ChatGPT 網頁版加一個 connector、完成一次 OAuth、就能以那個 Seat 的 role 進桌，並完成至少一場 DM 與一場 Player 的真實迴圈。** 這不是可 out-of-scope 的項目。若 preflight 證明 ChatGPT 的方案／權限限制使其不可能，M04 停在 M04-A，記錄阻礙，回使用者拍板，不得以「其他 client 可用」宣稱 M04 完成。

### 2.2 Seat 先於 OAuth，一個 connection 一個固定 Seat

- Seat 必須先在 Adventure Table 的 Lobby／Session 頁建立並發出憑證（P3-D 既有流程）。
- OAuth 只能**取得那張既有 Seat／grant 的控制權**：不建立 Seat、不選 Role、不改 Role、不在同一個 MCP connection 內切換 Seat。
- 一個 ChatGPT connector authorization 對應**恰好一張** grant。要換 Seat 就重新 authorize（或依 M04-A 實測結果決定是否需要另一個 connector）。
- P3-D 的 epoch、revoke、TTL、Take Back 全部沿用；OAuth access token 與 grant 同生共死。

### 2.3 Tool catalog 對 ChatGPT 的呈現由 preflight 決定

P3 的 role-scoped catalog 在 ChatGPT frozen snapshot 下有三種可能結果，M04-A 必須實測出是哪一種，M04-B 依結果設計：

| preflight 結果 | M04-B 對應 |
|---|---|
| 重新 authorize 後 ChatGPT 會重新 scan，catalog 跟著 role 變 | 沿用 P3 role-scoped catalog，不改 |
| 需要使用者手動 Refresh 才更新 | 沿用 role-scoped catalog；kit 與指引明講「換 role 後要 Refresh」 |
| snapshot 凍結、無合理刷新路徑 | 改為對 ChatGPT 暴露**單一 union catalog**，權限仍由 server 在 `tools/call` 階段依 grant role 拒絕；或改為「每個 role 一個 connector URL」。二選一在 M04-B 開工前由使用者拍板 |

不論哪一種，**server 端的 `tools/call` 授權檢查是唯一真值**；catalog 呈現只是 discovery 便利，不是權限邊界。

### 2.4 AI Join Kit 是唯一的 AI 交付物（M04-C）

使用者取得 AI credential 時，畫面上拿到的是一份可複製、可下載的純文字 **AI Join Kit**：URL、token、role、以及「指引在哪」。kit 依 M04-B 定案的入口形態產生（ChatGPT 走 connector + OAuth；Claude Code 走 Bearer；有 shell 的 AI 走 `GET /mcp/guide`）。DM／Player 同一份模板，role 由 token 決定。

### 2.5 指引住 server、與 tool 契約同源（M04-C）

`GET /mcp/guide`（無認證純文字）、加厚的 tool description、`get_session_context.briefing` 三個通道交付同一份內容。指引告訴 AI 怎麼用桌，不提供劇本。

### 2.6 Standalone 不受影響

單機版不掛 `/mcp`、OAuth endpoint 或 `/mcp/guide`。M04 不得讓 `app.standalone`、`app.content.*`、`app.domain.character*` 反向依賴 `app.mcp` 或任何 OAuth module。

## 3. M04 共通硬原則

### 3.1 先實測再設計

M04-B 的任何 OAuth／protocol／catalog 設計決定都必須能指到 M04-A 的 preflight 記錄。沒有實測證據的猜測不得寫成契約。

### 3.2 OAuth 不得新增授權邊界

每個 request 仍走 P3-D：grant → Seat current binding → `controller_epoch == generation` → scope。OAuth token 只是找到 grant 的另一把鑰匙；找到之後的流程與 Bearer AI Join Token 完全相同，不得複製第二份授權邏輯。

### 3.3 Seat 不可在 OAuth 內建立、選擇或切換

見 2.2。這是不可違反的 invariant，M04-B 必須有自動測試證明 OAuth 流程對 `campaign_seats` 零寫入。

### 3.4 kit 與指引不含任何秘密

除 token 本身外，不得含 Room password、Owner Key、DM Key、其他 Seat 的 token、secret DC、DM Notes。`GET /mcp/guide` 無認證，內容必須是「任何人都可以知道」的。

### 3.5 雙語同步交付

M04-B 的 OAuth 授權頁、錯誤訊息，與 M04-C 的指引、briefing、kit、UI copy 都是 user-visible content，同一 Subphase 交付 `zh-TW`／`en`。

### 3.6 指引告訴 AI 怎麼用桌，不替 AI 決定怎麼跑團

守則可以給；劇本、世界觀、NPC 設定不得給，那是 P6。

### 3.7 Preflight 測試 server 不得污染 Adventure Table app

M04-A 的極小 HTTPS server 是獨立程式，不 import `app.*`，不進 app 打包，不共用 DB；它的唯一目的是量測 ChatGPT。

# M04-A — ChatGPT Web MCP Preflight

## 目標

用一個極小、獨立、對外 HTTPS 的 MCP 測試 server，對真實 ChatGPT 網頁版做完整 preflight：OAuth、Scan Tools、一個 read tool、一個 write tool、protocol／metadata／callback 實錄、tool cache／refresh／re-auth 行為。產出可指引 M04-B 設計的實測記錄與架構結論。

## Prerequisite

- **具備完整 MCP write 權限的 ChatGPT workspace。** 依 reviewer 引述的 OpenAI 文件，含 write／modify 的完整 MCP 支援目前是 ChatGPT Business／Enterprise／Edu 的 beta 功能。開工前以當天官方文件再確認一次並記錄；在不具此權限的方案上測到 write 失敗，不得判定為 Adventure Table protocol 問題。
- 一個對外 HTTPS 入口（Tailscale Funnel／Cloudflare Tunnel／等價），沿用 P3-F E1 的形態。

## 完成後必須為真

### A.1 測試 server 存在且獨立

- 位於 repo 內 `tools/m04a-chatgpt-preflight/`，有自己的 dependency 清單與 README，可一行啟動。
- 不 import `app.*`；`test_m03_import_boundary.py` 與 `test_p3e_architecture_boundary.py` 的掃描範圍不含它，但它也不得被任何 app module import。
- 實作 MCP Authorization 所需的最小 server 端：Protected Resource Metadata、Authorization Server Metadata、authorize／token endpoint、dynamic client registration；哪些真的被 ChatGPT 呼叫由記錄回答。
- Authorize 頁是一個最小 HTML 表單：使用者選擇模擬 role（`dm`／`player`）並提交固定測試密碼；這模擬「提交 AI Join Token 取得既有 Seat 控制權」。
- 提供至少：一個 read tool（`get_context`，回 role 與計數）、一個 write tool（`post_note`，把文字寫進 server 記憶體並回 seq）、一個只在 `dm` scope 出現的 tool（`dm_only_ping`）、一個可指定等待秒數的 long-poll tool（`wait_seconds`）。
- 所有 request 的 method、path、header 名稱、`MCP-Protocol-Version`、JSON-RPC method、`Mcp-Session-Id` 有無、`Accept` 是否要求 SSE 全部寫進 JSONL 記錄；`Authorization` 值與 token 值一律遮罩。

### A.2 OAuth 一次成功

在真實 ChatGPT Web 上完成一次完整 authorization，記錄：ChatGPT 呼叫了哪些 metadata endpoint、是否用 dynamic client registration、redirect URI 形態、PKCE 有無、要求的 scope、token endpoint 的 grant type、access token 與 refresh token 的使用方式。

### A.3 Scan Tools 與 protocol 實錄

記錄 ChatGPT 在 Scan Tools 時送出的：`MCP-Protocol-Version`（或缺席）、第一個 JSON-RPC method（`initialize`／`server/discover`／直接 `tools/list`）、是否帶 `Mcp-Session-Id`、是否要求 SSE、`_meta` 內容。這決定 M04-B 是否需要 protocol 相容層。

### A.4 一個 read tool 與一個 write tool 各成功一次

在 ChatGPT 對話中觸發 `get_context` 與 `post_note`，兩者都收到正確結果；記錄 ChatGPT 對 write tool 的確認 UX（是否每次要使用者按確認、能否標記為免確認）。

### A.5 Tool cache／refresh／re-auth 行為

依序執行並記錄每一步 ChatGPT 看到的 tool 清單：

1. 以 `dm` authorize → Scan Tools → 清單應含 `dm_only_ping`。
2. Server 端新增一個 tool（不重新 authorize）→ ChatGPT 是否看到？需要什麼操作才看到？
3. 重新 authorize 為 `player` → ChatGPT 是否重新 scan？`dm_only_ping` 是否消失？需要 Refresh／重新發佈／新 connector 嗎？
4. 撤銷 access token（server 端）→ ChatGPT 下一次呼叫的行為：自動 refresh、要求重新 authorize、或直接錯誤。
5. 兩個不同對話同時使用同一 connector → 是否共用同一個 access token。

### A.6 Long-poll 容忍度

以 `wait_seconds` 分別等 10、30、60 秒，記錄 ChatGPT 端的 timeout 上限。這決定 M04-B 對 `wait_for_event` 的 `timeout` 上限是否要下修。

### A.7 Preflight 記錄與架構結論

`docs/M04/M04-A_PREFLIGHT.md` 含：A.2～A.6 每項的記錄、日期、ChatGPT 方案與可辨識版本、入口形態（不含憑證）、遮罩後的關鍵 request／response 樣本，以及對 M04-B 的明確結論：

- 需要哪些 OAuth endpoint 與 DCR。
- 是否需要 protocol 相容層；若需要，目標版本與必要 method。
- 2.3 表格中 catalog 呈現落在哪一列。
- `wait_for_event` timeout 上限。
- 任何使 ChatGPT Web 不可行的阻礙（若有）。

### A.8 順帶量測（不列驗收）

若當天方便，同一測試 server 對 claude.ai custom connector 與 Claude Desktop 也各量一次 A.3，記錄即可，不影響 M04-A 關門。

## 本 Subphase 不要求

- 不改 Adventure Table 任何 app code。
- 不做正式 OAuth 設計；只記錄與結論。
- 不做 Join Kit／guide。

# M04-B — Adventure Table ChatGPT Web Integration

## 目標

依 M04-A 實測契約，讓 ChatGPT 網頁版以 OAuth 取得既有 Seat／grant 的控制權並進桌；完成真實 ChatGPT Web DM 與 Player 兩場迴圈。

## 完成後必須為真

### B.1 OAuth 入口存在於 web channel

- Adventure Table web channel 提供 M04-A 結論所需的 OAuth endpoint 與 metadata；具體路徑與 schema 在開發設計方針。
- Authorize 頁是雙語的最小表單：**貼上 AI Join Token** 即完成「登入」；不顯示 Room 資訊、不列 Seat 清單、不提供任何選擇。
- Standalone channel 不掛任何 OAuth route。

### B.2 OAuth token 只對應既有 grant

- 每個 access token 在 DB 只留 hash，關聯到恰好一張 `ai_controller_grants` row。
- grant 被 revoke、TTL 到期、Seat epoch 前進、Session End／Abandon 時，對應 access token 同一 transaction 內失效；refresh token（若 M04-A 證明需要）同樣失效。
- 以 access token 進來的 request，在 `authenticate_request` 之後的流程與 Bearer AI Join Token **完全相同**；沒有第二條授權路徑。

### B.3 Seat 不可在 OAuth 內建立、選擇或切換

- OAuth 流程對 `campaign_seats`、`sessions`、`session_participants` 零寫入。
- 同一個 access token 的整個生命週期只綁一張 grant；「換 Seat」唯一方法是拿另一張 grant 的 token 重新 authorize。
- 若 ChatGPT 重複 authorize 同一 connector，舊 access token 立即失效（一個 connection 一個固定 Seat）。

### B.4 Protocol 相容層（僅在 M04-A 證明必要時）

- `2026-07-28` 路徑行為完全不變；P3-E 全部 protocol 測試原樣通過。
- 相容層只做 wire 轉換：`initialize` 若必須回應只回靜態能力；`Mcp-Session-Id` 若必須回傳則是無狀態 opaque 值，server 不以它保存任何 gameplay scope。
- 兩條路徑共用同一份 tool catalog 與 auth 邏輯，有測試證明。

### B.5 Tool catalog 呈現依 M04-A 結論

依 2.3 表格落點實作；若落在第三列，使用者拍板 union catalog 或 per-role URL 後才開工。不論哪種，`tools/call` 階段的 role 檢查是唯一真值，並有測試證明 Player token 呼叫 DM tool 被拒且零副作用。

### B.6 `wait_for_event` timeout 上限依 M04-A 結論

若 ChatGPT 端容忍度低於 60 秒，MCP 入口對 `timeout` 上限下修至實測值；Human UI 的 long-poll 不受影響。

### B.7 對外入口文件

README 部署段新增「讓 ChatGPT 網頁版連進來」：HTTPS 入口形態、只轉發 `/mcp*` 與 OAuth 路徑、不把 Room UI 露出公網；不含憑證。

### B.8 真實 ChatGPT Web DM 與 Player gate

以只拿到 token 的 ChatGPT 網頁版 AI：

- **DM 場**：Lobby 產生 AI DM 憑證 → ChatGPT 加 connector、OAuth 貼 token → `get_session_context` → `start_session` → `post_narration` → `wait_for_event` → Human Player 回應 → AI 再回應 → Owner revoke → AI 下一次呼叫失效。
- **Player 場**：Human DM 開場，Player Seat `Let AI Control` → ChatGPT OAuth → `post_dialogue` → Human DM `request_check` → AI `roll_pending` → Human `Take Back Control` → AI 下一次呼叫失效。

兩場都是 M04 closeout 必要條件。

## 本 Subphase 不要求

- 不做 Join Kit／guide／briefing（M04-C）。
- 不做 claude.ai／Codex 相容。
- 不做多 Room／多 grant 的 connector 管理 UI。
- 不做 refresh token 以外的任何新 persistence。

# M04-C — AI Join Kit, Server-hosted Guide & Other Client Compatibility

## 目標

把「發 token」升級成「發 kit」，讓指引住 server、與 tool 契約同源；kit 依 M04-B 定案的入口形態產生。順帶記錄 claude.ai／Codex CLI／Codex Desktop 的相容狀態，但不作為 gate。

## 完成後必須為真

### C.1 `GET /mcp/guide` 存在且無需認證

- Web channel 提供 `GET /mcp/guide`，`text/plain; charset=utf-8`，200，不需 Bearer，不碰 DB。
- 支援 `zh-TW`／`en`。
- Standalone 不掛。

### C.2 指引內容涵蓋「從零到迴圈」

至少包含：

1. 三種接入方式各一節：ChatGPT 網頁版（connector + OAuth 貼 token，含 M04-A 實測出的 Refresh 注意事項）、有 MCP client 的 AI（Bearer）、有 shell 或可對外連網 code execution 的 AI（`POST /mcp` header 契約 + 最小 client 範例）。
2. 最小 client 範例段開頭明講：**只給有 shell 或可對外連網 code execution 的 AI**；網頁版 chat 的 sandbox 沒有對外網路，不要嘗試，改走 connector。
3. `POST /mcp` 的 header 契約、body `_meta`、不需 `initialize`、不得帶 `Mcp-Session-Id`（若 M04-B 加了相容層，另註明 legacy 路徑）。
4. 一個完整的 `tools/call` 範例與成功／業務錯誤／協定錯誤三種回應。
5. 工具表：名稱、用途、必要參數、適用 role，由 tool 定義同源產生。
6. 進場流程：`get_session_context` → `pre_session` 就 `start_session`、`active_session` 就續場 → cursor 規則 → `wait_for_event` 迴圈。
7. DM 守則與 Player 守則各一節。Player 守則必須正確反映 Player scope：**Player 沒有 `request_check`**；要做 check 時用 `post_action` 描述意圖，等 DM 建立 Check，再以 `roll_pending` 或 `submit_physical_roll` 完成。
8. 401 `ai_token_unauthorized` 的處置：停止並告知使用者，不重試。

不得含 3.4 的任何秘密，不得含 3.6 禁止的劇本內容。

### C.3 tool description 加厚

`tools/list` 每個 description 擴充為用途、何時用、關鍵參數與合法值；仍依 scope 過濾，不洩漏對方 scope 的工具存在。若 M04-B 採 union catalog，description 標明「需要 DM role」而非隱藏。

### C.4 `get_session_context` 回傳 `briefing`

- 兩種 mode 都回傳；依 caller role 產生；含指向 `GET /mcp/guide`。
- `temporary_instruction` 保持獨立欄位。
- Player briefing 不得提及 `request_check`、`post_narration`、`set_stage_text`；DM briefing 不得提及 `quick_roll`、`whisper_dm`。

### C.5 `server/discover.instructions` 指向指引

### C.6 Lobby 與 Session 頁提供 kit

- token 一次性顯示的同一畫面同時提供 kit：純文字區塊、「複製 kit」、「下載 .txt」。
- kit 含 URL、token、role、三種接入方式的一句話指向；ChatGPT 段依 M04-B 定案的 connector URL 與「OAuth 時貼上此 token」寫。
- URL 取自瀏覽器 origin；loopback 時附提醒。
- 既有「只顯示一次」與「複製 token」不變。
- 下載檔名含 role 與日期，不含 token。

### C.7 雙語

C.1～C.6 所有 user-visible 文字同時交付 `zh-TW`／`en`。

### C.8 真實 AI 只憑 kit 能進桌

兩條路徑各至少一次，AI session 沒有讀過本 repo、沒有額外口頭說明：

- **MCP client（Bearer）**：Claude Code 或等價 client。
- **純 HTTP**：一個**確定具備 outbound network 的 code-execution client**（例如 Claude Code 不設定 MCP、或任何有 shell 的 agent）；網頁版 chat 不在此列，它們只驗 connector（已在 M04-B B.8）。

### C.9 其他 client 相容記錄（非 gate）

對 claude.ai custom connector、Codex CLI、Codex Desktop 各嘗試一次 M04-B 的入口，記錄能不能連、卡在哪；寫入 closeout「Compatibility」段。任何一個不通都不阻塞 M04-C 關門。
