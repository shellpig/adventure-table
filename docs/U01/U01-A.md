# U01-A — E2E Database Isolation & Fast Test Foundation

狀態：⬜ Planned

## 1. U01 定位

`U01` 是 **Test / Development Efficiency Optimization** 長期優化軌，用來持續收斂測試速度、開發迴圈成本、CI 效率與相關可靠性問題。

U 類不是正常產品 Phase，也不是 Maintenance / Content Phase：

- 不改寫 `P0 → P1 → ...` 產品 Roadmap。
- `U01` 本身長期保持 open，不設 Full Closeout。
- 每個具體優化項目以 `U01-A`、`U01-B`、`U01-C`… 持續新增。
- 單一優化項目可以完成，但不代表整個 U01 關門。
- U 類工作不能為了「優化」犧牲 correctness、測試隔離或既有產品行為。

本文件只定義 **U01-A**。

---

## 2. 背景與問題

目前本機 Docker E2E 與日常實際使用共用同一個 PostgreSQL database：`adventure_table`。

Playwright global setup 在每次完整 E2E 開始前，會對該 database 執行 destructive reset：

```sql
TRUNCATE TABLE rooms, characters, ai_oauth_clients RESTART IDENTITY CASCADE;
```

目前已有 `ADVENTURE_TABLE_E2E_ALLOW_DESTRUCTIVE_RESET=1` 作為人工保險絲，但它只是在執行前要求顯式 opt-in，**並沒有真正隔離 E2E 資料與實際使用資料**。

因此只要本機 E2E 指向平常使用中的 DB，測試就會清掉真實 Character / Room / Campaign / Session / AI grant / OAuth 等資料。

同時，現有完整 E2E 已偏慢；這次隔離不能以「再啟一整套 PostgreSQL、再多一套昂貴初始化流程」換安全。後續 U01 還要持續把 E2E 執行時間往下壓。

---

## 3. U01-A 目標

U01-A 完成後必須同時滿足：

1. **實際使用 DB 的資料不受 E2E 影響。**
   - 日常資料庫維持 `adventure_table`。
   - E2E 使用獨立 database，例如 `adventure_table_e2e`。
   - E2E 的 truncate、seed、migration、測試資料建立與刪除只發生在 E2E database。

2. **不額外建立第二個 PostgreSQL container。**
   - 正式／日常 DB 與 E2E DB 共用同一個 PostgreSQL container / process。
   - 透過 PostgreSQL database boundary 隔離資料。
   - 不為 U01-A 增加第二套 PostgreSQL healthcheck、volume、image pull 或 container startup 成本。

3. **隔離不得讓完整 E2E 固定成本變高。**
   - 新增 E2E database 的建立／確認應是低成本操作。
   - 不能每次測試都因資料隔離而重新建立 PostgreSQL container 或 volume。
   - 若已有 E2E database，後續 run 應直接 reset + seed + test。

4. **destructive reset 必須有 database-level hard guard。**
   - `ADVENTURE_TABLE_E2E_ALLOW_DESTRUCTIVE_RESET=1` 保留。
   - reset 前必須驗證目前 target database 是明確的 E2E database。
   - 若 `current_database()` 不是 `adventure_table_e2e`（或正式定案的唯一 E2E DB 名稱），立即 fail，絕不執行 truncate。
   - 不可只靠操作者記得切環境變數。

5. **為後續 E2E 加速鋪路。**
   - U01-A 不要求一次解完所有 E2E 慢點。
   - 但新的隔離設計不得綁死「每次 run 必須 full rebuild」或其他不必要成本。
   - 後續可由 U01-B／U01-C 等項目處理 Docker rebuild、Playwright helper、重複 seed／fixture、suite partition 等速度問題。

## 4. 目標架構

採用 **單一 PostgreSQL container + 兩個 PostgreSQL database**：

```text
PostgreSQL container
├── adventure_table
│   └── 日常 / 實際使用資料
│
└── adventure_table_e2e
    └── Playwright / destructive test data
```

### 4.1 日常使用

日常 `server` 的 `DATABASE_URL` 繼續指向：

```text
postgresql+psycopg://...@db:5432/adventure_table
```

E2E 不得 truncate、drop、seed 或 migrate 這個 database 作為測試初始化手段。

### 4.2 E2E

E2E backend 必須明確指向：

```text
postgresql+psycopg://...@db:5432/adventure_table_e2e
```

完整 E2E 的資料生命週期為：

```text
ensure adventure_table_e2e exists
→ migrate E2E DB to current heads
→ verify current_database() == adventure_table_e2e
→ destructive reset E2E DB
→ deterministic seed / baseline Room
→ Playwright
```

下一次 run 不需要重建 PostgreSQL；直接重用同一個 E2E database，再 reset 即可。

## 5. Server / Web 隔離原則

U01-A 的核心目標是資料安全，因此 **DB 必須隔離**。

日常 server/web 與 E2E server/web 是否使用不同 service 名稱、不同 host port 或獨立 compose profile，可依實作時最小成本決定，但需滿足兩件事：

1. 跑 E2E 不得讓日常 server 重新連到 `adventure_table_e2e`。
2. 跑 E2E 不得把日常 `adventure_table` 當成 destructive test target。

若為避免干擾正在使用中的網站而新增 E2E server/web service，應優先共用既有 image / Docker build cache，不得因此複製 PostgreSQL stack。

U01-A 不要求為「看起來完全獨立」而建立第二套完整 Compose project；資料安全與速度優先。

---

## 6. Destructive reset hard guard

目前單純的：

```text
ADVENTURE_TABLE_E2E_ALLOW_DESTRUCTIVE_RESET=1
```

不足以當作資料隔離。

U01-A 後 destructive reset 至少需要雙重條件：

```text
ADVENTURE_TABLE_E2E_ALLOW_DESTRUCTIVE_RESET == 1
AND
current_database() == adventure_table_e2e
```

任何一項不成立都必須 fail closed。

database identity check 與 truncate 應落在同一個 PostgreSQL execution path，避免「先檢查 A、實際 truncate 卻送到 B」的接線錯誤。

驗收時必須刻意把 reset 指向 `adventure_table`，確認 script 拒絕 destructive operation。

---

## 7. Migration / initialization

E2E database 必須使用與 web runtime 相同的 Alembic web migration heads，不允許用 `metadata.create_all()` 取代正式 migration chain 作為主要 E2E schema 初始化方式。

需要處理兩種情況：

### 第一次建立

```text
adventure_table_e2e 不存在
→ create database
→ alembic upgrade heads
→ run tests
```

### 後續執行

```text
adventure_table_e2e 已存在
→ alembic upgrade heads
→ reset data
→ run tests
```

`CREATE DATABASE` 只應在缺少 E2E database 時發生，不應成為每次 E2E 的固定成本。

---

## 8. 效能約束

U01-A 不是單純「安全優先，速度以後再說」。隔離方案本身就必須避免製造新的慢點。

### 必須避免

- 每次 E2E 新開第二個 PostgreSQL container。
- 每次 E2E 建立／刪除 PostgreSQL volume。
- 每次 E2E drop + recreate database，若 reset 已足夠。
- 為資料隔離額外做完整 image rebuild。
- 將 E2E 改成需要更多人工前置步驟。

### 應維持

使用者入口仍應保持單一命令，例如：

```text
npm run test:e2e:docker
```

該命令自行確保 E2E DB 存在、schema 已更新、target 正確、資料已 reset。

使用者不應在每次 run 前手動切 DB、手動 create database、手動 migrate 或手動 restore 日常資料。

---

## 9. U01-A 驗收

U01-A 至少需要以下證據：

### A. 真實資料隔離

1. 在 `adventure_table` 建立可辨識 sentinel data。
2. 記錄其 identity / count。
3. 執行完整 E2E reset + suite。
4. 再查 `adventure_table`。
5. sentinel 與原資料必須仍存在且內容不變。

### B. E2E destructive reset 正常

1. 在 `adventure_table_e2e` 建立垃圾測試資料。
2. 執行 E2E setup。
3. 確認垃圾資料被 reset。
4. baseline fixture / Room 正常重建。

### C. Wrong-DB guard

刻意讓 destructive reset target 指向 `adventure_table`：

- command 必須 non-zero fail。
- log 必須清楚指出拒絕原因與實際 database name。
- `adventure_table` 任何資料不得被修改。

### D. Migration parity

- `adventure_table_e2e` 經 Alembic `upgrade heads` 後可執行完整 E2E。
- 新 migration 加入後，既有 E2E DB 可直接 upgrade，不要求 drop database。

### E. 速度不倒退

記錄 U01-A 前後至少一組本機完整 E2E wall-clock baseline。

U01-A 的隔離機制本身不得造成可觀測的固定時間倒退；若同時做了其他速度改善，應分開記錄，避免把隔離成本藏在總體改善內。

---

## 10. 非 U01-A 範圍

以下是 U01 長期可處理，但不要求塞進 U01-A：

- 移除或縮小 `test:e2e:docker` 每次無條件 `--build` 的成本。
- 讓 dev / E2E server 以 bind mount 或更精準的 image invalidation 避免 stale code。
- Profile Playwright 最慢 specs。
- 改善 Builder E2E 中反覆全頁掃描造成的 O(n²) helper。
- 共用昂貴 Character / Room fixtures，減少重複 UI 建立資料。
- 安全增加 Playwright parallelism。
- CI shard / suite partition / selective E2E。
- 降低第二輪 xge-less subset 的 restart 成本。

這些項目可依量測結果新增為 `U01-B`、`U01-C`…，不需要等 U01 整體關門。

---

## 11. 開工實作原則

U01-A 實作時應先以「最小變更完成硬隔離」為目標：

1. 建立／ensure `adventure_table_e2e`。
2. 讓 E2E backend 固定使用該 DB。
3. 將 destructive reset 改為 E2E DB，並加入 `current_database()` hard guard。
4. 確保日常 `adventure_table` 不受影響。
5. 量測完整 E2E 前後時間，確認隔離沒有讓測試固定成本變高。

完成 U01-A 不代表 U01 關門；下一個優化項目依量測結果續編。
