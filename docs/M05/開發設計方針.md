# M05 — 開發設計方針

> Phase：**M05 — Session History Continuity & Owner End for AI DM Sessions**
> 本文件是 M05-A～M05-B 的**具體實作契約**：module、endpoint、DTO、資料流與接線。「完成後什麼必須為真」在 `實作規格.md`；驗收方式在 `測試指南.md`。
> Subphase 名稱與順序與另外兩份文件一字不差。

最後更新：2026-09-20

## 1. 設計目標

1. **不新增授權路徑，也不擴大既有 gameplay actor。** Owner End 與 Owner Abandon 是同一個 `SessionService` 分支結構、同一個 `_finalize_with_event`。歷史讀取使用**專用的 `HistoricalSessionReadScope`**（只能讀已結束 Session 的事件與定位前一場），**不**改 `resolve_human_actor`／`_human_actor_from_connection`／`actor_binding_is_current`；`TableActorContext` 的所有 consumer（Combat、Exploration、Roll、Stage、Pending、MCP）行為與 M05 前完全相同。（2026-09-20 review round 1：原本改共用 resolver 的方案會讓持舊場 `dm_seat_id` 的讀者經 `/sessions/{舊場}/combat/detail` 取得目前 active Combat 的 DM audience，已砍。）
2. **一個讀取入口、一個 seq 空間一個 Session。** 不做 Campaign-scoped 合併 seq；前端以「前一場定位 → 該場 per-Session history page」串接，舊 Session 事件住獨立資料結構，不進本場 `eventStream`。
3. **舊 Session 唯讀由型別保證，不只靠 append gate。** `HistoricalSessionReadScope` 不是 `TableActorContext`，任何接受 `TableActorContext` 的 service／route 都無法拿它當 actor；`TableEventRepository.append` 對非 active Session 的拒絕維持不變，是第二道防線。
4. **MCP 不變。** `get_session_context`、`wait_for_event`、tool catalog 零改動；AI 讀跨 Session 歷史留 P7。
5. **Standalone 邊界不動。** 所有改動在 `app.domain.rooms.*`、`app.persistence.rooms.*`、`app.api.rooms.*` 與 `apps/web/src/features/rooms/*`。

## 3. M05-A — Owner End for AI DM Sessions

### 3.1 `SessionService.end_session`（`app/domain/rooms/sessions.py`）

在既有 `end_session(room_id, campaign_id, session_id, context)` 中，於 `_require_active` 之後、`_resolve_human_actor` 之前加 Owner 分支：

```python
stored = self._require_active(room_id, campaign_id, session_id)
if (
    context.authority is RoomAccessAuthority.OWNER
    and stored.dm_controller_kind == "ai"
):
    return self._finalize_with_event(
        room_id=room_id,
        campaign_id=campaign_id,
        session_id=session_id,
        status=SessionStatus.ENDED,
        actor=None,
        owner_access_session_id=context.access_session_id,
    )
actor = self._resolve_human_actor(...)
return self.end_session_actor(room_id, campaign_id, session_id, actor)
```

- `_require_active` 現已回傳 `StoredSession`，直接使用其 `dm_controller_kind`。
- `dm_controller_kind == "human"` 時不進 Owner 分支；Owner 若同時是本場 DM 會由 `_resolve_human_actor` → `end_session_actor` 正常通過，否則 `_resolve_human_actor` 拋 `DMControllerMismatchError`（既有行為）。
- `_finalize_with_event` 零改動：`actor=None` → `expected_actor_binding=None`、`execution_mode="system"`、payload `{"status": "ended", "owner_access_session_id": ...}`；`finalize_in_transaction` 既有邏輯撤銷 AI grant、Seat controller 回 `none`＋`epoch+1`、刪 lease。
- `end_session_actor`（MCP AI DM 自己 End 的路徑）不變。

### 3.2 API

`POST /sessions/{session_id}/end` route 零改動；錯誤碼沿用 `_map_session_error`：

| 情境 | 回應 |
|---|---|
| Owner，AI DM active Session | 200 `SessionSnapshot(status=ended)` |
| Owner 非本場 DM，Human DM active Session | 403 `dm_controller_mismatch` |
| `dm`／`member` 非本場 DM，任何 active Session | 403 `dm_controller_mismatch` |
| 非 active Session | 409 `session_not_active` |

### 3.3 Web（`RoomSessionPage.tsx`）

- 新增 `const isAiDmSession = snapshot.dm_controller_kind === 'ai'`、`const canOwnerEnd = snapshot.status === 'active' && isOwner && isAiDmSession && !isCurrentDm`。
- End 按鈕顯示條件由 `isCurrentDm` 改為 `isCurrentDm || canOwnerEnd`；`canOwnerEnd` 時點擊先 `window.confirm(copy.ownerEndAiDmConfirm)` 再 `endSession(...)`。
- 提示：`snapshot.status === 'active' && isOwner && !isCurrentDm` 時，AI DM 顯示 `copy.ownerEndAiDmHint`，Human DM 顯示既有 `copy.ownerAbandonHint`（文案改為只講 Human DM 情況）。
- `api/sessions.ts` `endSession()` 零改動。

## 4. M05-B — Cross-Session Chat History Paging

### 4.1 Persistence：前一場定位（`app/persistence/rooms/sessions.py`）

```python
def previous_for_campaign(self, *, campaign_id: UUID, session_id: UUID) -> StoredSession | None
```

- 以 `session_id` 取得基準 `(started_at, id)`；回傳同 `campaign_id`、`(started_at, id) < 基準` 且排序最大的一筆（任何 status）；無則 `None`。
- 基準 Session 不存在或不屬於該 Campaign → `None`（由 domain 轉 404）。
- 一個 `select ... order by started_at desc, id desc limit 1`；沿用 `_session(row)` 組 `StoredSession`。

### 4.2 Persistence：歷史讀取 scope（`app/persistence/rooms/table_runtime.py`）

**既有 `_human_actor_from_connection`、`_ai_actor_from_connection`、`resolve_human_actor`、`actor_binding_is_current` 一字不改。** 新增一個只讀查詢：

```python
@dataclass(frozen=True)
class StoredHistoryReadScope:
    room_id: UUID
    campaign_id: UUID
    session_id: UUID
    session_status: str            # active / ended / abandoned
    access_session_id: UUID
    controlled_seat_ids: tuple[UUID, ...]
    is_dm: bool                    # session.dm_seat_id in controlled_seat_ids

def history_read_scope(
    self, *, room_id: UUID, campaign_id: UUID, session_id: UUID, access_session_id: UUID,
) -> StoredHistoryReadScope | None
```

- `_session_scope_row` 驗 Session 屬於該 Room／Campaign，否則 `None`。
- `room_access_sessions` 驗同 Room、未 revoke，否則 `None`。
- `controlled_seat_ids` ＝ 該 Campaign 中 `archived_at IS NULL`、`controller_kind == "human"`、`controller_access_session_id == access_session_id` 的 Seat（依 `created_at, id` 排序）。為空 → `None`。**不看 `session_participants`**：Seat 的歷史跟 Seat 走。
- `is_dm` ＝ `session_row["dm_seat_id"] in controlled_seat_ids`。
- 回傳含 `session_status`，由 domain 決定哪些操作接受哪些 status。

設計要點：

- **單位是 Seat。** 讀者對 Campaign 歷史的 scope＝目前以 Human controller 控制的、未 archive 的 Campaign Seat。被 archive 的 Seat 不算；Seat 被 reassign 給別人後原讀者立即失去該 Seat 的 scope（每次請求重算，無快取）。
- **DM 層跟 `dm_seat_id`。** 只有目前控制該場 `dm_seat_id` 的讀者拿到 `is_dm=True`。
- **AI 沒有 history scope。** 本方法只接受 Human `access_session_id`；MCP 不接線。

### 4.2a Domain：`HistoricalSessionReadScope`（`app/domain/rooms/table_events.py`）

```python
class HistoricalSessionReadScope(StrictModel):
    room_id: UUID
    campaign_id: UUID
    session_id: UUID
    session_status: str
    access_session_id: UUID
    controlled_seat_ids: tuple[UUID, ...]
    is_dm: bool

class TableEventService:
    def resolve_history_scope(self, *, room_id, campaign_id, session_id, context: RoomAccessContext) -> HistoricalSessionReadScope
        # context.room_id != room_id 或 repository 回 None → TableEventNotFoundError（→ 404 session_not_found）

    def list_history_before(self, scope: HistoricalSessionReadScope, *, before_seq: int, limit: int) -> TableEventPage
        # scope.session_status == "active" → TableEventNotFoundError（active Session 一律走既有 actor 路徑）
        # 每次呼叫以 scope.access_session_id 重新呼叫 repository.history_read_scope() 並與 scope 比對（等價於 require_actor_current），Seat 變動即失效
        # 其餘與 list_before 相同：分塊回掃、_visible／_present 過濾、after_seq／cursor 語意一致
```

- `_visible`／`_present` 目前只用 `is_current_dm` 與 `controlled_seat_ids`。把這兩個 static method 的參數型別改成一個最小 Protocol（`class EventReadScope(Protocol): is_current_dm: bool; controlled_seat_ids: tuple[UUID, ...]`），`TableActorContext` 與 `HistoricalSessionReadScope`（以 `is_current_dm` property 映射 `is_dm`）都符合；過濾邏輯本體零改動。
- `list_history_before` 與 `list_before` 共用同一個回掃函式（抽出私有 `_scan_before(scope, before_seq, limit)`），避免兩份 pagination 邏輯。
- **`HistoricalSessionReadScope` 不是 `TableActorContext`**：不能傳進 `SessionService`、Combat、Exploration、Roll、Stage、Pending 任一 service；靜態上不可能用它寫入或讀 gameplay view。

### 4.3 Domain（`app/domain/rooms/sessions.py`）

```python
class SessionHistoryLink(StrictModel):
    session_id: UUID                          # 基準 Session
    previous_session: SessionSnapshot | None  # 含 participants，供前端解析舊場角色名
    previous_last_event_seq: int = Field(ge=0)

def previous_session(self, room_id, campaign_id, session_id, context: RoomAccessContext) -> SessionHistoryLink
```

- 讀取權限：`event_service.resolve_history_scope(room_id, campaign_id, session_id=基準, context)`；基準 Session **任何 status 都可**（本場通常是 active）。無 scope（不控制任何 Human、未 archive 的 Campaign Seat；或 Session 不屬於該 Campaign／Room）→ `TableEventNotFoundError` → **404 `session_not_found`**，與 `/events/history` 無 scope 的語意一致。**不**用 `_resolve_human_actor`——那會把「控制 P1 但 P1 沒參加本場」的合法歷史讀者誤擋成 403。
- `repository.previous_for_campaign(...)`；有結果時以 `event_service.repository.current_runtime(...)` 取 `last_event_seq`（無 runtime row 時為 0）。
- 不新增事件、不寫 DB。

### 4.4 API（`app/api/rooms/sessions.py`）

```text
GET /api/rooms/{room_id}/campaigns/{campaign_id}/sessions/{session_id}/previous
→ 200 SessionHistoryLink
→ 404 session_not_found（跨 Campaign／Room、不存在，或呼叫者沒有 history scope）
```

舊 Session 事件讀取沿用既有 `GET .../sessions/{previous_id}/events/history?before=&limit=`，`before = previous_last_event_seq + 1` 取最新一頁。`table_events.py` 的 `list_table_event_history` 改為：

```python
scope = service.resolve_history_scope(...)          # 404 if none
if scope.session_status == "active":
    actor = _resolve_actor(...)                      # 既有路徑，零改動
    return service.list_before(actor, ...)
return service.list_history_before(scope, before_seq=before, limit=limit)
```

- active Session：行為與 M05 前完全相同（history scope 只用來判 status，不影響結果）。
- 非 active Session：只走 history scope；既有 `resolve_human_actor` 對已結束 Session 的 participant-based 解析不再被此 route 使用（它仍供 idempotent replay 等既有用途，零改動）。
- `GET /events`、`/runtime`、`/events/wait` 與所有 gameplay route（combat／exploration／rolls／stage／pending／MCP）零改動：對已結束 Session 的行為與 M05 前相同，**history scope 不會讓任何人在這些 route 上多看到或多做到任何事**。

### 4.5 Web：資料結構（`sessionEventStream.ts`）

```ts
export type OlderSessionHistory = {
  session: SessionSnapshot
  lastEventSeq: number
  historyFloorSeq: number      // 該場 page.after_seq；0 = 該場已載到 Start
  events: TableEvent[]         // 只放 chat-visible 事件即可，但保留原 TableEvent
}

export type SessionHistoryChain = {
  older: OlderSessionHistory[] // 由新到舊；older[0] 是本場的前一場
  exhausted: boolean           // true = 已到 Campaign 第一場 Start
}
```

- `hasOlderHistory(stream, chain)`：`stream.historyFloorSeq > 0`，或 `chain.older` 最末一場 `historyFloorSeq > 0`，或 `!chain.exhausted`。
- `applyOlderSessionPage(chain, sessionId, page)`：對應那場 `mergeEvents`、`historyFloorSeq = min(...)`；不同 session_id 忽略。
- 本場 `SessionEventStreamState` 零改動；`mergeResumeStream`／`applySessionEventPage` 不碰 chain。

### 4.6 Web：載入流程（`RoomSessionPage.tsx` `loadOlderEvents`）

```text
if stream.historyFloorSeq > 0:
    既有：listSessionHistory(current, floor+1)
elif chain.older 非空 且 older[last].historyFloorSeq > 0:
    listSessionHistory(older[last].session.id, older[last].historyFloorSeq + 1)
    → applyOlderSessionPage
else:
    base = chain.older.length ? older[last].session.id : sessionId
    link = getPreviousSession(base)
    if link.previous_session === null: chain.exhausted = true
    else:
        page = listSessionHistory(previous.id, previous_last_event_seq + 1)
        push { session: previous, lastEventSeq, historyFloorSeq: page.after_seq, events: page.events }
```

- 每次點擊只做一步（一頁），避免一次拉多場。「跨場的那一步」是一次點擊發兩個 request：`GET /previous` ＋ 該前一場最新的 `GET /events/history`；不是 previous 與 history 各點一次。
- 前一場 `previous_last_event_seq == 0`（空場）：history 回空頁、`after_seq == 0`，仍 push 一個 `events: []` 的 `OlderSessionHistory` 並顯示分隔線；下一次點擊繼續往前一場。連續多個空場依此一場一場走。
- Session route 變更或 Resume 全量重載時，chain 重設為 `{ older: [], exhausted: false }`。
- `historyLoading` 沿用；prepend anchor 沿用 a62d3253 的 `previousHeight` 機制，chain 變動也要觸發同一 anchor（把 `chain` 併入該 effect 的依賴或改以「渲染的訊息總數」為 key）。

### 4.7 Web：渲染（`SessionTableSurface.tsx`）

- 新 props：`olderSessions: OlderSessionHistory[]`、`historyExhausted: boolean`。
- 聊天串渲染順序：`[...olderSessions].reverse()` 逐場 → 每場先分隔線、再該場 `events.filter(isSessionChatEvent)` → 本場 `chatEvents`。
- 分隔線（`<div role="separator" data-session-divider={session.id}>`）內容：`copy.sessionDividerLabel(status, dmKind)` ＋ `started_at`／`ended_at` 本地時間。
- 舊場訊息的角色名：先查該場 `session.participants` 的 `active_character_id`，再退回 `seatLabel(seatId)`（Campaign Seat 仍存在）。
- 舊場事件 `key` 用 `${event.session_id}:${event.seq}`（現有寫法已含 session_id，跨場不撞）。
- 控制項：`hasOlderHistory` 為 true 顯示既有按鈕；`historyExhausted && !hasOlderHistory` 顯示 `copy.historyStart` 文字。
- `combatLogEvents`、Stage、Combat、Roll Request、Pending Action 只吃本場 `events`，不讀 `olderSessions`。

## 5. 跨 Phase 相容檢查

- **P3-D authority**：`TableActorContext` 結構不變；`require_actor_current`、`controller_epoch`、grant generation 檢查不變；Owner End 走 Room authority，不建 AI bypass。
- **P3-A 事件**：`TableEventVisibility` 四態與 `_visible`／`_present` 邏輯零改動（只放寬參數型別到 Protocol）；`resolve_human_actor`／`_human_actor_from_connection`／`actor_binding_is_current` 零改動，idempotent replay 與所有 gameplay route 對已結束 Session 的行為與 M05 前相同。
- **P4 Combat**：`project_combat_event_payload` 的 audience 由 `is_current_dm` 決定，M05-B 的 DM 判定跟 `dm_seat_id`，Player 讀 AI DM 舊場不會拿到 DM audience。Combat 是 Campaign-root，`get_active_combat_detail` 只認 `TableActorContext`；history scope 不是 actor，無法經舊場 URL 讀目前 active Combat。
- **M04 MCP**：tool catalog、`get_session_context`、OAuth 零改動。
- **M03 Standalone**：不新增多人 module／table／route 名稱空間；`test_m03_import_boundary.py` 不需擴充（無新 package）。
- **P6／P7 交棒**：P7 `search_campaign_history()`／Timeline 讀取以 4.1 的前一場定位＋per-Session history page 為底層，不重做；P6 Campaign Runtime 不受影響。
