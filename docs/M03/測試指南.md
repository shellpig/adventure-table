## 1. 測試總則

- **每條 Subphase 驗收契約都要有可定位的測試證據**。每項 `X.n` 對應至少一條 pytest / Vitest / Playwright test 或人工程序，於 closeout 文件中列出檔名 + test 名稱。
- **同 turn 內把型別 / 編譯 / 該 Subphase test 修綠**。中途留錯是 M03 期間禁止的狀態。
- **零副作用的拒絕**。任何拒絕匯入 / 拒絕 startup / 拒絕 export 的 test，都要驗前後狀態不被污染（DB rows 不變、files 不變、環境變數不被污染）。
- **雙語同步驗收**。所有新加入 UI 於 `zh-TW` / `en` 兩語各跑一次同一條 flow；只驗一語不算完成。
- **不重跑 passing suite**。M03 期間**不做**「順便跑一次 M02 全套」，除非 M03 的改動確實碰到 M02 的 code path 或路徑常數。
- **CI 綠燈是必要條件，不是充分條件**。人工程序（launcher 冷啟動、Windows 上跑 build 產物、匯入缺 pack 的角色）於對應 subphase 必跑。

# B. Character JSON Schema & Export

## B.1 Pydantic model round trip

`apps/server/tests/test_m03b_json_schema.py`：

- 針對每份 `apps/server/tests/data/m03/fixture_*.json`，載入 → validate → serialize → 二次 validate，斷言 idempotent。
- 斷言 `schema_status == "unstable"`。
- 斷言不允許未來 `schema_status` 值於 validation 通過（正例 / 反例對照）。

## B.2 Content ref walker unit test

`apps/server/tests/test_m03b_content_ref_walker.py`：

- 對每份 fixture，斷言 walker 回傳的 refs 集合等於預期集合（預期集合手動列出）。
- 斷言 walker 對 build_payload 未覆蓋的路徑會炸掉（不是沉默漏收）——加一份 fixture 帶假的新路徑，斷言 walker fail 或以特定 error 提醒開發者更新。
- 斷言相同 build_payload 呼叫多次結果一致。

## B.3 Export payload builder

`apps/server/tests/test_m03b_export_payload.py`：

- 對 P1-F 已知 fixture（Fighter 5 / Wizard 5）呼叫 `build_export_payload` → 斷言：
  - envelope `content_requirements` 只列 build_payload 實際引用的 pack。
  - envelope `stable_key_refs_summary` 是整數且與 walker 結果一致。
  - payload `versions` 為完整 chain。
  - payload 不含 `archived_at` / `id` / `current_version_id`。
  - `versions` 依 `version_no` 遞增。

## B.4 Export endpoint

`apps/server/tests/test_m03b_export_api.py`：

- `GET /api/characters/{id}/export` → 200 + `Content-Disposition: attachment`。
- 檔名 sanitize test：角色名含空白 / 中文 / 特殊字元皆產生合法檔名。
- 已 archive 角色可匯出，header 標示 archived。
- 不存在 UUID → 404。
- 匯出前後 DB 狀態未變（rows / updated_at 不動）。

## B.5 Frontend export button E2E

`apps/web/e2e/m03b-character-export.spec.ts`：

- Workshop 卡片按匯出 → 觸發 file download → 斷言檔案為合法 JSON。
- Character Sheet 頭部匯出按鈕 → 同上。
- `zh-TW` / `en` 兩 locale 各跑一次。

## B.6 Localization

# C. Character JSON Import via Builder Draft

## C.1 Import pipeline unit test

`apps/server/tests/test_m03c_import_pipeline.py`：

- `preview_import` 對每份 fixture：
  - 全部 pack 都 enabled 時 → `landing_mode="character"`，`unresolved_refs=[]`。
  - Disable `xge` 時，`fixture_xge_dependent.json` → `landing_mode="draft"`，unresolved_refs 含所有 `xge:*` refs。
  - Disable `phb2014` 時，`fixture_multiclass_mixed.json` → landing_mode="draft"，unresolved_refs 精確列出缺項。
- `commit_import_as_character`：
  - 產生新 UUID，chain 完整 append，`current_version_id` 指向最高。
  - `character_states.state_payload == payload.current_state.state_payload`。
  - `character_import_records` 有新 row，`landing_mode="character"`。
- `commit_import_as_draft`：
  - 建立 fresh Draft，起點為最新 version 的 build_payload。
  - 未解析 choice 於 draft 中呈現為未填。
  - `character_import_records.draft_id` 指向新 draft，`character_id=NULL`。

## C.2 Rejection tests

`apps/server/tests/test_m03c_import_rejections.py`：

每個 rejection code 一條 test：

- `invalid_envelope_shape`：缺 `envelope.ruleset` → 400 + code。
- `invalid_payload_shape`：缺 `payload.character.name`。
- `unsupported_schema_status`：`"future_value"`。
- `unsupported_ruleset`：`"pathfinder2e"`。
- `version_chain_gap`：`versions=[1,3]`。
- `version_chain_out_of_order`：`versions=[2,1]`。
- `current_state_version_missing`：state 對應 version_no 不在 chain。
- `base_version_reference_invalid`：`base_version_no=99` 而 chain 最高 2。

每個 rejection 都斷言：

- 回應 400、含 code、含 `params`（若適用）。
- DB 狀態零副作用：`characters` / `character_versions` / `character_states` / `character_import_records` 無新 row。

## C.3 Duplicate hint

`apps/server/tests/test_m03c_duplicate_hint.py`：

- 相同 `source_character_id` 已有一筆 import record → dry-run 回應含 `duplicate_hint`。
- 沒有時 `duplicate_hint=None`。
- 匯入不被 duplicate_hint 阻擋；commit 後 records 累積。

## C.4 Endpoint

`apps/server/tests/test_m03c_import_api.py`：

- `POST /api/characters/import?dry_run=true` → 200 + ImportResult，`committed=false`。
- `POST /api/characters/import` (JSON body) → 201 + ImportResult。
- `POST /api/characters/import` (multipart file) → 201。
- `POST` 檔案超過合理大小（例：> 5 MB）→ 拒絕。
- Malformed JSON → 400 `invalid_envelope_shape`。

## C.5 Alembic migration `0007`

- 於既有 test infra 上跑 upgrade + downgrade + upgrade（Postgres）。
- SQLite 部分於 M03-D 才把 gate 立起來；C 期間 SQLite 可 fail，不阻擋 C landing，但需於 M03-D 修復。

## C.6 Frontend import dialog E2E

`apps/web/e2e/m03c-character-import.spec.ts`：

- 匯入 `fixture_low_level_srd.json`（檔案選擇路徑）→ dry-run 顯示 4 個 resolved / 0 unresolved / mode=character → 繼續 → 導向 Sheet。
- 匯入 `fixture_low_level_srd.json`（貼上路徑）→ 同上。
- 匯入 `fixture_xge_dependent.json` 且本機 `xge` disabled → dry-run 顯示 mode=draft 與 unresolved 清單 → 繼續 → 導向 Draft，Draft 中未填 choice 呈現正確狀態。
- 匯入同一份 export 二次 → dry-run 顯示 `duplicate_hint` 提示。
- 匯入 JSON schema 錯的檔 → dialog 顯示 rejection message 對應 code。
- `zh-TW` / `en` 兩 locale 各跑主流程一次。

## C.7 Localization

- duplicate_hint 模板兩語完整。

# D. SQLite Migration Chain Gate

## D.1 Migration up/down/idempotent

`apps/server/tests/test_m03d_migration_sqlite.py`：

- Fixture 建立 tmp SQLite 檔。
- `alembic upgrade head`：斷言無例外，結束後 tables 完整。
- `alembic downgrade base`：斷言無例外，結束後 tables 空。
- `alembic upgrade head` 二次：無例外。

## D.2 Schema 一致性

`apps/server/tests/test_m03d_schema_parity.py`：

- 以 `alembic upgrade head` 產生 schema A。
- 以 `metadata.create_all(engine)` 產生 schema B（另一 tmp SQLite）。
- 使用 SQLAlchemy `inspect` 對照兩者的 tables / columns / types / nullable / indexes / unique constraints。
- 差異必須為零；若某個差異已在 migration comment 中被標為 SQLite-only 讓步，於本 test 白名單明列。

## D.3 Postgres 未回歸

- 現有 Postgres migration test 全綠。
- Docker Compose start + migration + smoke 全綠。

## D.4 `psycopg` extras

`apps/server/tests/test_m03d_dependency_extras.py`：

- 讀 `pyproject.toml`：`psycopg[binary]` 不在 `[project.dependencies]`，在 `[project.optional-dependencies].web`。
- CI workflow 檔（`.github/workflows/*.yml`）中網頁版相關 job 安裝 `.[web,dev]`。

# G. Full M03 Integration & Closeout

## G.1 End-to-end round-trip 手動 flow

於 M03 期間的最新網頁版 + 最新單機版 `.zip` 上執行以下四條流程，每條保留 evidence（截圖 / 錄影 / test log）：

### G.1.a W → S 完整

1. 網頁版建立一個 Lv5 Multiclass 角色（Fighter 3 / Cleric 2，Life Domain，含 starting equipment、prepared spells、live HP 有變動、Inventory 有加物）。
2. Character Sheet 匯出 → 檔案 `A.json`。
3. 於單機版 Workshop 匯入 `A.json`。
4. Dry-run 顯示全部 resolved、`landing_mode="character"`。
5. 繼續匯入 → Sheet 開啟後與原網頁版 Sheet 對照：
   - HP / 資源 / conditions / prepared / inventory 一致。
   - Version History 顯示 1..N 完整。

### G.1.b S → W 完整

1. 單機版建立 Lv3 Ranger with Hunter subclass。
2. 匯出 → `B.json`。
3. 網頁版匯入。
4. 對照兩邊 Sheet 一致。

### G.1.c W → S 缺 pack

1. 網頁版建立引用 `xge` 的角色（Gloom Stalker Ranger）。
2. 匯出 → `C.json`。
3. **於一個 `xge` 未 enable 的單機版**匯入 `C.json`（可透過 `ADVENTURE_TABLE_CONTENT_ROOT` 指向去掉 `xge` 的臨時目錄，或事先建立不啟用 `xge` 的 build 版本）。
4. Dry-run 顯示 `landing_mode="draft"` 且 unresolved 清單含 subclass ref。
5. 繼續 → 導向 Draft。
6. 使用者於 Draft 中改選一個可用的 Ranger subclass。
7. Confirm → 產生 Version 1 → Sheet 開啟正常。

### G.1.d 重複匯入

1. 同一份 `A.json` 於單機版匯入第二次。
2. Dry-run 顯示 `duplicate_hint`。
3. 繼續 → 兩個角色並存於 Workshop。
