> Phase：**M03 — Standalone Character Builder Distribution**
> 類型：**M Phase（Modification / Maintenance Phase）**
> 插入時點：**M01 Full Closeout 之後、P2 開工之前。**
> 本文件定義 **M03-A～M03-G 每個 Subphase 完成後什麼必須為真**。具體資料格式、schema、module、API、migration、打包腳本與接線放在 `開發設計方針.md`；自動與人工驗收方式放在 `測試指南.md`。

## 1. M03 定位

P0 / P1 已完成 Character Core、Character Builder、Level Up、Version History 與 Character Sheet；M01 進一步建立 Multi-Source Content Pack 與 PHB / SCAG / GoS / VGM / VRGR / TCE / XGE 大部分 character-relevant content；M02 建立 `zh-TW` / `en` 雙語永久基礎。

在進入 P2 — Room / Campaign / Session / Seat 之前，M03 把「目前已完成的角色相關功能」包成一個**可下載、離線執行的單機創角版本**出貨，並補上網頁版尚未存在的**角色 JSON 匯出／匯入**能力，讓網頁版與單機版之間、以及不同人的單機版之間可以互通角色資料。

M03 要解決的是：

1. `規格企劃.md` 第五章〈Character Workshop〉已允許「未加入 Room 前也能創角色，沒有帳號時可 browser-local + JSON」，但這條保證目前只存在於規格，沒有出貨。
2. 網頁版目前**沒有角色 JSON 匯出／匯入端點**，朋友間無法傳遞角色。
3. `app/content/registry.py` 的 `REPOSITORY_ROOT` 寫死了 repo 目錄結構，凍結打包後找不到 `data/`。
4. `psycopg[binary]` 是無條件相依，任何凍結打包都會帶進 5–10 MB 用不到的相依。
5. 目前 codebase 只有角色這一層，還沒有 Room 可以滲進來，這是把「單機版永遠只做創角、不做多人」界線釘死的最便宜時機。
6. P2 之後角色資料模型仍會變動，但**必須守住「角色可以脫離 Room 存在」的 schema 保證**，否則單機版死亡。M03 是先把這條界線用 import boundary test 與 CI build 具現化，讓 P2 開工時已經有一個會失敗的 build 當守門員。

M03 不改寫正常 P0 → P1 → P2 Roadmap，也不推遲 P2：

```text
M01-A
→ M01-B
→ M01-C
→ 暫停 M01
→ M02-A～M02-H
→ M02 closeout
→ 回到 M01-D
→ M01-E～M01-K
→ M01 Full Closeout
→ M03-A～M03-G
→ M03 closeout
→ P2
```

## 2. M03 產品行為

### 2.1 兩個 entry point，同一份 codebase

不做第二份 repo，也不用 feature flag 散落在各處。

```text
線上版 entry (apps/server/app/main.py)
  → 全部 router，含 P2 之後的 Room / Session / Seat
  → 由 docker-compose / production 部署驅動
  → 資料庫：PostgreSQL

單機版 entry (apps/server/app/standalone.py，M03-E 新增)
  → 只掛 content / character / builder 相關 router
  → 由 PyInstaller 打包成單一可執行檔驅動
  → 資料庫：本機 SQLite 檔
  → 執行時自動開瀏覽器，關閉時收掉 process
```

同一份 domain code、同一份 rules、同一份前端 build（見 2.2），差別只在掛哪些 router 與資料庫選擇。單機版包裡不會出現半殘的多人 UI。

### 2.2 單機版可見範圍

單機版對使用者顯露的功能上限即**目前已完成的角色相關功能**：

- Landing / Character Workshop
- Character Builder（含 Multi-Source Content Pack、Multiclass、Subclass、ASI / Feat、Spellcasting、Starting Equipment）
- Character Sheet
- Level Up 與 Version History
- Character Archive / Permanent Delete
- `zh-TW` / `en` 語言切換
- Character JSON Import / Export（M03-B / M03-C 新增）

**不包含、也永遠不會包含**本質上就是多人的東西：Room、Campaign、Session、Seat、Combat、Timeline、AI Actor、DM 工具、帳號系統。這是定義，不是缺陷。

單機版前端 SPA 的 build 產物與線上版相同（同一 `apps/web` build），M03 不做第二份前端 build。因為前端路由是手寫 `pathname` 比對而非 router library，Room / Session 相關頁面在 M03 出貨時本來就不存在，SPA build 天然不含這些路由。P2 之後線上版增加的頁面，單機版 SPA build 會一併攜帶，但單機版 entry 不掛對應 router，所以那些頁面在單機版打不開；這是 M03-E / M03-F 的守門機制決定的行為，不是缺陷。

### 2.3 角色 JSON 交換

**單機版第一版就要有出有進，同一 JSON 格式在網頁版與單機版之間互通。**

- 網頁版與單機版都提供 `POST /api/characters/import` 與 `GET /api/characters/{id}/export`。
- 使用者可從 Character Workshop 或 Character Sheet 匯出。
- 使用者可從 Character Workshop 匯入。
- 匯入入口同時支援檔案選擇與貼上 JSON。
- 匯出檔為單一 JSON，內含完整 version chain 1..N、current state、envelope metadata。
- 匯入時角色 identity 一律重新產生（新 UUID）；envelope 記錄來源 identity 供重複偵測提示，但不做合併。
- 匯入時若角色 build_payload 引用的 StableKey 在本機 registry 有任一個解析不到，**匯入落地為 Builder Draft**，讓使用者在 Builder 中補完缺口，Confirm 才成為正式 Character。
- 匯入前必須先顯示可解析數與未解析數，由使用者判斷是否繼續，**不設固定門檻**。

### 2.4 版本相容性

**M03 出貨時 JSON schema 尚未鎖定。**

- 每個 M03 期間的單機版釋出說明必須明文標示：「這個版本的匯出檔不保證未來版本讀得進去」。
- 從 M03 到 P2 上線之間，允許新版本改變 JSON schema 語意，舊版 JSON 可以失效。
- **P2 上線時鎖定 JSON schema**：從該版本開始，schema 只能加欄位不能改欄位語意；舊版 JSON 一律必須匯得進來。
- 鎖定不是 M03 承諾，而是 P2 承諾；本 phase 只負責讓 P2 有東西可以鎖。

### 2.5 SQLite 是保存庫，不是快取

- 單機版本機資料庫檔為 SQLite，位於執行檔旁邊，預設檔名 `adventure-table.sqlite3`。
- 該檔可被環境變數 `ADVENTURE_TABLE_DATABASE_PATH` 覆寫（例：讓使用者把資料檔放到 OneDrive 目錄）。
- **啟動時把資料檔的絕對路徑印在 launcher stdout 與瀏覽器 landing 提示區**，讓「解壓到新資料夾發現角色不見了」的解法只是複製舊資料夾裡的 `.sqlite3`。
- 啟動時執行 `alembic upgrade head`，與網頁版共用同一條 migration 鏈。
- 開發期間允許最終手段：某個 M01 / M02 / M03 期間的 migration 真的無法在 SQLite 上跑，允許使用者刪 SQLite 檔重來；JSON 匯出是安全帶而不是主要升級手段。P2 lock 之後才承擔「絕不刪 DB」的責任。

### 2.6 平台範圍

M03 第一版**只出 Windows x64**。

理由：

- PyInstaller 不能跨平台編譯，多一個平台就是多一個 CI runner 與要驗的產物。
- macOS 未簽章 app 被 Gatekeeper 直接擋，簽章需 Apple 開發者帳號；朋友間私用不划算。
- 使用者本人與其朋友主要在 Windows。

但 launcher 與 build 腳本必須寫成**平台中性**（不寫死 `C:\`、不假設路徑分隔符、統一用 `pathlib`）。之後要加 Linux build 就只是 CI matrix 多一列，不是重寫。

### 2.7 打包產物

**使用者不自己在本機打包。** 打包由兩條路徑產生：

- **開發期間**：`scripts/build-standalone.cmd` 在使用者本機 iteration。
- **釋出**：`windows-latest` CI job 在 tag push 時自動 build，產出 `.zip` 上傳成 GitHub Release artifact。

朋友拿到的東西是一個 `.zip`：

- 解壓即得一個資料夾（例：`adventure-table-standalone/`）。
- 資料夾內含 `adventure-table.exe`（或 `.cmd` wrapper）、`data/` 內容包、`_internal/` PyInstaller 相依。
- 雙擊執行 → launcher 起 uvicorn → 開瀏覽器 → 使用 → 關閉瀏覽器或 launcher 就結束 process。

## 3. M03 共通硬原則

### 3.1 網頁版行為不得回歸

M03 是**加功能**與**加封裝**，不改既有功能。

- Landing / Workshop / Builder / Sheet / Level Up / Version History / Archive / Locale 切換行為在 M03 期間一行不得改。
- Content Registry 載入結果、Builder Choice DTO、Rules Layer derive、Character JSON payload 於 `zh-TW` / `en` 下的 presentation 與 M02-H closeout 觀察一致。
- M01 / M02 期間的自動化測試在 M03 每個 Subphase 完成後全綠。

### 3.2 角色可以脫離 Room / Campaign / Session / Seat 存在

這是 M03 的政治承諾，也是 P2 的 schema 約束。

- `characters` 表不得長出 `room_id` / `campaign_id` / `session_id` 欄位；未來 P2 的 Campaign 歸屬走 Party Roster join table。
- Character Campaign Status（`active` / `inactive` / `retired` / `dead`）住在未來 roster row，不是 character row。
- `app/content`、`app/domain/character*`、`app/persistence/characters`、`app/persistence/builder_drafts` 與 `app/api/character*` 不得 import 任何 room / session / seat 模組。
- 權限檢查於 route 外層 wrapper / dependency 加入，不寫進 character domain 內部。
- 上述四條由 M03-F 建立的 **import boundary test** 與 **standalone build gate** 於 CI 強制。

### 3.3 匯入不得產生假資料

網頁版與單機版的匯入端點必須守住 P1 立場：**正式 Build 不可以是假資料**。

- 若匯入的 build_payload 引用了本機解析不到的 StableKey，一律落地為 Builder Draft，讓使用者在 Builder 中補完後 Confirm 建立正式 Character。
- Rules Layer 不新增「容忍缺失 ref」的降級模式；`ContentNotFoundError` 語意不改。
- 因此 Character Sheet 永遠不會出現「數值錯的角色」；未 Confirm 的匯入結果以 Draft 形式呈現，Sheet 不會渲染。

### 3.4 匯入 / 匯出邏輯 server-authoritative

- Import / export 是 server-side 契約，前端不重建 build_payload 結構、不重建 refs 收集邏輯。
- 前端只負責檔案選擇 / 貼上 JSON / 呼叫 API / 顯示回應中的可解析與未解析清單。
- 未來 AI actor（透過 MCP / Site Tools）匯入角色時，共用同一 server-side pipeline，不做兩套邏輯。

### 3.5 單機版可見範圍靠 router 掛載決定，不靠前端隱藏

- 單機版 entry 不掛未來 Room / Session router，前端呼叫對應 endpoint 直接得到 404。
- 前端不新增 `if (standalone) hide(...)` 之類的分支，避免兩套 UI。
- 使用者在單機版偶然 URL 打錯進入 Room 相關路由時，看到的是 SPA 的 not-found 頁面，不是半殘的多人 UI。

### 3.6 Localization 交付對稱

- Import / Export UI（Workshop / Sheet 的按鈕、匯入 dialog、預覽數字文字、error 訊息）於 M03-B / M03-C / M03-G 完成當下必須同步交付 `zh-TW` / `en` 兩語，缺任一視同該 Subphase regression。這是 M02-H 建立的永久 supported-locale 交付守則。

### 3.7 Standalone 打包成本不得回流到網頁版

- 為單機版所做的 refactor（例：Content Root abstraction、psycopg optional extra、資料檔路徑抽象）不得讓網頁版功能行為改變。
- 環境變數缺省時的路徑解析 fallback 必須等同於當前 repo-relative 行為。
- 網頁版 Docker image 不變、Docker Compose 不變、Alembic 於 Postgres 上的行為不變。

## 4. M03 Subphase 順序

```text
M03-A — Content Root Path Abstraction
→ M03-B — Character JSON Schema & Export
→ M03-C — Character JSON Import via Builder Draft
→ M03-D — SQLite Migration Chain Gate
→ M03-E — Standalone Packaging & Launcher
→ M03-F — Windows CI Build & Import Boundary Test
→ M03-G — Full M03 Integration & Closeout
```

每個 Subphase 必須能獨立實作、驗證並 commit；完成時應處於可執行、可測試、沒有已知編譯／型別／該 Subphase 測試錯誤的狀態。

M03-B 完成後，**網頁版即已具備角色 JSON 匯出能力**，這是可獨立驗證的產品增量。M03-C 完成後，網頁版即已具備完整 round-trip 匯入能力。M03-E 之前，尚未有可下載的單機版產物，但角色交換已可行。這個順序讓 JSON 交換的價值早出，也讓打包相關卡關（PyInstaller / SmartScreen 誤判）不會綁住產品增量。

# M03-A — Content Root Path Abstraction

## 目標

把目前 `app/content/registry.py` 寫死的 `REPOSITORY_ROOT = Path(__file__).resolve().parents[4]` 與所有由它推導的路徑（`CONTENT_PACKS_ROOT`、`RULES_PATH`、`data/localization/*`）改成經一組**可覆寫的解析器**取得，讓凍結打包後與環境變數注入場景也能正確定位。

## 完成後必須為真

### A.1 解析順序固定

Content root 解析順序：

1. 明確環境變數 `ADVENTURE_TABLE_CONTENT_ROOT`（若非空且指向存在目錄）。
2. Bundle 路徑：若程序執行於 PyInstaller 凍結環境（`sys.frozen`），使用 `sys._MEIPASS` 或執行檔目錄下的 `data/`。
3. Repo 相對路徑：現況邏輯（`Path(__file__).resolve().parents[4] / "data"`），開發模式使用。

### A.2 現行網頁版行為不變

- 未設 `ADVENTURE_TABLE_CONTENT_ROOT` 且非凍結環境下，解析結果與 M02-H closeout 觀察完全一致。
- `load_default_content_registry()` 載入的 pack 集合、entry 集合、locale overlay 集合、rules JSON 皆不變。
- Docker Compose 環境、pytest 環境、Playwright 環境不需要設定新環境變數即可跑起來。

### A.3 應用啟動不再於 import time 依賴 filesystem 位置

- Registry 載入仍可發生於 `app/main.py` import time，但**路徑解析必須以函式形式**（`resolve_content_root()` 之類）取得，允許在 PyInstaller launcher 起 uvicorn 前就設定環境變數。
- 若解析後的 content root 不存在或 pack 無法載入，啟動時以清楚的錯誤訊息失敗，並包含實際解析出的路徑。

### A.4 集中一處

- 現在被 `REPOSITORY_ROOT` 影響的路徑（至少 `apps/server/app/content/registry.py:21-22` 與 `apps/server/app/domain/character_builder/rules.py:12`）改為引用同一個解析函式，不散落多份 `parents[4]` 常數。

## 本 Subphase 不要求

- 不在此建立 standalone entry point 或 launcher。
- 不新增 JSON 匯出／匯入。
- 不修改 Alembic migration。
- 不引入 SQLite runtime 相關程式碼。

# M03-B — Character JSON Schema & Export

## 目標

在網頁版與（未來的）單機版都提供 `GET /api/characters/{id}/export`，讓使用者從 Character Workshop 或 Character Sheet 下載一份**內含完整 version chain 1..N、current state 與 envelope metadata** 的 JSON 檔。同時定義 M03 期間的 JSON schema，schema 版本標為 `unstable`。

## 完成後必須為真

### B.1 匯出端點

- `GET /api/characters/{id}/export` 回傳 `application/json`，`Content-Disposition: attachment` 給合理檔名（含角色名 sanitized 版本與 export 時間戳）。
- 端點只讀，不改變任何 server 狀態。
- 端點為 server-authoritative；前端不重建 payload 結構。
- 端點對已 archive 角色仍可匯出，回應 header 中標示 archived 狀態（但 payload 中不帶 `archived_at`，見 B.3）。

### B.2 Envelope

Envelope 至少包含以下欄位：

- `schema_version`：M03 期間定為 `"unstable"`；P2 lock 之後改為正式 semver。
- `schema_status`：`"unstable"` 或 `"locked"`；M03 期間一律 `"unstable"`。
- `ruleset`：來自 `characters.ruleset`，M03 期間為 `"dnd5e-2014"`。
- `content_requirements`：本角色 build_payload 引用到的**所有 pack 版本清單**（例：`[{"pack": "srd5.1", "version": "1.0.0"}, {"pack": "phb2014", "version": "..."}]`）。**清單來自實際 build_payload 走訪，不是來自載入時所有 enabled pack。**
- `stable_key_refs_summary`：本角色 build_payload 引用到的 StableKey 總數（診斷用整數，內容細節不進 envelope）。
- `source_character_id`：原始 `characters.id`（UUID）。
- `source_export_id`：本次 export 產生的唯一 UUID，讓匯入端可判斷「同一份 export 匯了兩次」。
- `source_app`：`{"name": "adventure-table", "channel": "web" | "standalone", "commit": ...}`。
- `exported_at`：ISO 8601 UTC 時間戳。

### B.3 Payload

Payload 包含：

- `character`：`characters` row 的 `name`、`ruleset`（不含 `id`、`current_version_id`、`archived_at`、`created_at`、`updated_at`）。
- `versions`：**完整 version chain 1..N**，依 `version_no` 遞增。每個 version 帶 `version_no`、`version_kind`、`base_version_no`（若有）、`change_note`、`build_payload`、`created_at`。
- `current_state`：`character_states.state_payload`。

**不含**：

- Builder Draft（單機版與網頁版皆然）。
- `archived_at`（匯入時一律成為啟用中的角色，見 C.5）。
- server-only 欄位（`id` / `current_version_id` / `updated_at` 等），因匯入端會重新產生。

### B.4 前端匯出入口

- Character Workshop 的角色卡片、Character Sheet 均新增匯出按鈕。
- 按下觸發瀏覽器 file download，不需要匯出 dialog。
- `zh-TW` / `en` 雙語 UI 同步交付。

### B.5 不變性

- Character Sheet / Version History / Level Up / Builder / Locale 切換等既有功能行為與 M02-H closeout 一致。
- `characters.py` 端點 signature 除新增 `/export` 外一律不變。

## 本 Subphase 不要求

- 不做匯入。
- 不做網頁版 JSON schema lock。
- 不修改 `content_requirements` 的細節：只列 pack 版本，不列 StableKey 名單。
- 不做匯出的排程 / 批次匯出。

# M03-C — Character JSON Import via Builder Draft

## 目標

在網頁版與（未來的）單機版都提供 `POST /api/characters/import`，讓使用者從匯入 dialog 選檔或貼上 JSON，把角色匯入為 Builder Draft（若引用有缺）或直接 append 為新角色（若全部解析得到，見 C.4 決策）。同時建立**單一 build_payload StableKey ref 收集器**，供本 phase 與未來 P7 共用。

## 完成後必須為真

### C.1 匯入端點

- `POST /api/characters/import` 接收 `application/json` body（envelope + payload），也接收 `multipart/form-data` 檔案上傳。
- 端點為 server-authoritative；前端不重建 payload 結構、不重建 refs 收集邏輯。
- 端點原子性：拒絕（見 C.7）不留任何殘留狀態。
- 端點對已存在角色的匯入一律以新 UUID 落地（見 C.5）。

### C.2 StableKey ref 收集器

- 建立 `collect_content_refs(build_payload)`，走訪整份 build_payload 蒐集所有 StableKey 引用。
- 收集器覆蓋範圍需涵蓋 M01-K 完成後 build_payload 中所有 pack-sourced content：race / subrace / lineage / background / class / subclass / feature choice / spell / feat / infusion / maneuver / fighting style / starting equipment 等。
- 收集器獨立於匯入流程可測，供未來 P7、外部工具重用。

### C.3 解析預檢

匯入分兩階段：

1. **Preview 階段**：`POST /api/characters/import?dry_run=true`，執行 envelope 檢查與 refs 收集 + 解析嘗試，回應：
   - `resolved_count`：可解析 ref 數。
   - `unresolved_refs`：未解析的完整 StableKey 清單（前端顯示前 N 筆，其餘折疊）。
   - `landing_mode`：`"character"`（全部解析到）或 `"draft"`（任一未解析）。
   - `character_preview`：擬顯示的角色名、level、class summary（僅供 UI 顯示，未寫入 DB）。
2. **Commit 階段**：`POST /api/characters/import`（不帶 `dry_run`），實際落地。

前端 UI 一律先呼叫 dry-run，顯示可解析 / 未解析數字與 landing_mode 給使用者確認後才 commit。**沒有預設門檻**，是否繼續由使用者決定。

### C.4 落地邏輯

- **`landing_mode == "character"`**：直接 append 為新角色。
  - 新 UUID → `characters` row。
  - Full version chain → `character_versions` 依序 append。
  - `current_state` → `character_states`。
  - `current_version_id` 指向最高 `version_no`。
- **`landing_mode == "draft"`**：落地為 Builder Draft。
  - 只匯入**最新一個 version 的 build_payload** 作為 Draft 起點；歷史版本不進 Draft（見 C.6）。
  - 未解析的 refs 對應的 choice 在 Draft 中呈現為「待選」，使用者於 Builder UI 中重新選擇。
  - Draft 完成 Confirm 後成為 Version 1；歷史版本鏈條無法還原（M03 期間可接受的犧牲，見 C.6）。
  - Current state 不進 Draft。

### C.5 Identity 與重複偵測

- 匯入一律以**新 UUID** 落地，`characters.id` 全新。
- Envelope 的 `source_character_id` 與 `source_export_id` 存進**匯入端 metadata 表**（`character_import_records`，見開發設計方針），供匯入前重複偵測。
- Dry-run 回應包含 `duplicate_hint`：若匯入端已存在同 `source_character_id` 的過去匯入紀錄，回應中列出「你已經從相同來源匯入過 M 次，最近一次為 …」，前端據此提示但不阻擋。
- 匯入後**不合併**、不覆寫既有角色。
- `archived_at` 不帶入；匯入結果一律為啟用中的角色。

### C.6 歷史版本處理

- `landing_mode == "character"`：完整 1..N 皆保留，歷史 version 內含解析得到的 refs。
- `landing_mode == "draft"`：**只有最新 version 的 build_payload 進 Draft**，1..N-1 於本次匯入丟棄；envelope 中的舊版 refs 未解析情況已在 dry-run 呈現，使用者已知情。
- 這是 M03 期間可接受的犧牲：完整鏈條保留需 Rules Layer 容忍缺失 ref，違反 3.3 硬原則；「補完後從 Version 1 重新開始」對朋友間私用可接受。

### C.7 拒絕條件

匯入直接拒絕（原子拒絕、零副作用）的情況：

- JSON parse 失敗、envelope 缺必要欄位、`schema_status` 未來出現不相容值。
- `ruleset` 不是本 registry 支援的 ruleset。
- Envelope 或 payload 缺 `character.name` / `versions` / `current_state` / 至少一個 version。
- Version chain 非連續（`version_no` 缺號、順序錯亂）。
- `current_state` 對應的 `version_no` 不在 chain 中。
- 內部一致性錯誤（例：`base_version_no` 指向不存在的 version）。

**未解析 refs 不是拒絕條件**；未解析 → Draft 落地。

### C.8 前端匯入入口

- Character Workshop 的空狀態與角色列表區均新增「匯入角色」按鈕。
- 匯入 dialog **同時提供檔案選擇按鈕與 textarea 貼上 JSON**；兩者共用同一 preview 呼叫。
- Dry-run 回應以清楚的視覺呈現：`X 個可解析、Y 個未解析、landing_mode 為 …`；未解析清單可展開。
- 使用者按下「繼續匯入」才發送 commit 請求。
- 匯入成功後導向新落地的 Character Sheet（`landing_mode == "character"`）或新 Draft（`landing_mode == "draft"`）。
- `zh-TW` / `en` 雙語 UI 同步交付。

### C.9 不變性

- Character Sheet / Version History / Level Up / Builder / Locale 切換等既有功能行為與 M02-H closeout 一致。
- 既有 Builder Draft 語意不變（M03 不改 Draft schema，只是新增一種建立來源）。

## 本 Subphase 不要求

- 不做 Campaign / Party Roster 匯入。
- 不做 batch 匯入。
- 不做 undo import。
- 不做 diff 顯示（「這份匯入與你既有角色 X 的差異」）。

## 目標

## 本 Subphase 不要求

# M03-E — Standalone Packaging & Launcher

## 目標

用 PyInstaller 把單機版打包為可下載、離線執行的 Windows x64 產物；launcher 負責啟動 uvicorn、跑 alembic upgrade、開瀏覽器、顯示資料檔路徑、提供結束方式。

## 完成後必須為真

### E.1 單機版 entry point

- 新增 `apps/server/app/standalone.py`，內含 `FastAPI` 應用只掛以下 router：`reference_router`、`content_presentation_router`、`characters_router`、`character_builder_router`。
- **不掛**任何未來 Room / Session / Seat / Combat / Timeline / AI Actor router。
- Standalone entry 亦負責掛前端 SPA 靜態檔（同源 `/api/...` + `/` SPA），不需要 CORS。
- Standalone entry 於 startup 呼叫 `alembic upgrade head`（SQLite target），失敗時以清楚錯誤訊息中止並保留 launcher stdout。

### E.2 Launcher

- 新增 `apps/server/app/launcher.py`（可執行入口，PyInstaller 打包 target）。
- 職責：
  1. 決定資料檔路徑（見 E.3），設定 `ADVENTURE_TABLE_DATABASE_PATH`。
  2. 決定 content root（見 E.4），設定 `ADVENTURE_TABLE_CONTENT_ROOT`。
  3. 選擇一個空閒的 localhost port（從固定範圍例如 8000～8100 選第一個可用）。
  4. 啟動 uvicorn。
  5. 等待 server ready，自動開啟預設瀏覽器至 `http://127.0.0.1:<port>/`。
  6. 在 launcher stdout / console window 顯示：資料檔絕對路徑、content root 絕對路徑、監聽 port、結束方式提示。
  7. Ctrl+C / 關閉 console 視窗時，收掉 uvicorn 子執行緒 / 子 process。

### E.3 資料檔路徑

- 預設：**執行檔所在資料夾下**的 `adventure-table.sqlite3`（不是 `%LOCALAPPDATA%`，不是使用者家目錄）。
- 可覆寫：`ADVENTURE_TABLE_DATABASE_PATH` 環境變數（絕對或相對路徑）。
- 覆寫路徑無效時（非法 / 無寫入權），launcher 以清楚錯誤中止並顯示解析出的路徑。
- 啟動時把最終解析的絕對路徑印在 stdout。

### E.4 Content root

- 沿用 M03-A 的解析順序。
- 打包時將 `data/` 目錄整體放入 bundle，PyInstaller spec 明確列入。
- Bundle 內的 `data/` 包含所有 enabled pack、localization overlay 與 rules JSON。

### E.5 PyInstaller spec

- 新增 `apps/server/pyinstaller/standalone.spec`。
- One-folder build（不是 one-file，冷啟動較快、抗防毒誤判較好）。
- 產物根目錄結構至少：
  ```
  adventure-table-standalone/
    adventure-table.exe          # launcher
    _internal/                   # PyInstaller runtime
    data/                        # content root
    LICENSE.txt                  # 專案 license + SRD 5.1 attribution
    README-standalone.txt        # 資料檔位置 / 匯出入口 / 已知限制
  ```
- Spec 不依賴 repo 相對路徑於 runtime。

### E.6 Build 腳本

- 新增 `scripts/build-standalone.cmd`（Windows）與對應 `scripts/build-standalone.sh`（僅供 CI，因 PyInstaller 不能跨平台編譯，正式產物必於 Windows runner 產生）。
- 腳本內容：
  1. 建立臨時 venv。
  2. 安裝 `apps/server` 主相依與 PyInstaller，**不裝 `web` extra**。
  3. Build 前端（`npm run build`）。
  4. 複製 SPA 產物到 launcher 掛載處。
  5. 執行 PyInstaller spec。
  6. 將 `data/`、`LICENSE.txt`、`README-standalone.txt` 複製進產物資料夾。
  7. 打包為 `.zip`。
- 腳本冪等：可重複執行不留污染。

### E.7 前端 build 一致性

- Standalone entry 掛的前端 SPA build **與網頁版相同**（同一 `npm run build` 產物）。
- 不新增 feature flag、不新增 build-time 分支。
- P2 之後線上版新增的頁面會一併攜帶進單機版 SPA，但單機版 entry 不掛對應 router → 使用者呼叫時 404，SPA 顯示 not-found。

### E.8 啟動可觀察行為

- 雙擊 `adventure-table.exe` 到瀏覽器打開時間 < 10 秒（乾淨啟動、無防毒干預情況下）。
- Console window 保持開啟，顯示所有啟動訊息與後續 request log（M03 期間可接受簡易 stdout；未來優化為隱藏 console + tray icon 由使用者提議後才做）。

## 本 Subphase 不要求

- 不做 code signing。
- 不做 Windows installer（`.msi` / `.exe` installer）。
- 不做自動更新機制。
- 不隱藏 console window。
- 不建立 system tray icon。
- 不做 macOS / Linux build。
