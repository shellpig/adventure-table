## 1. M03 定位

P0 / P1 已完成 Character Core、Character Builder、Level Up、Version History 與 Character Sheet；M01 進一步建立 Multi-Source Content Pack 與 PHB / SCAG / GoS / VGM / VRGR / TCE / XGE 大部分 character-relevant content；M02 建立 `zh-TW` / `en` 雙語永久基礎。

在進入 P2 — Room / Campaign / Session / Seat 之前，M03 把「目前已完成的角色相關功能」包成一個**可下載、離線執行的單機創角版本**出貨，並補上網頁版尚未存在的**角色 JSON 匯出／匯入**能力，讓網頁版與單機版之間、以及不同人的單機版之間可以互通角色資料。

M03 要解決的是：

1. `規格企劃.md` 第五章〈Character Workshop〉已允許「未加入 Room 前也能創角色，沒有帳號時可 browser-local + JSON」，但這條保證目前只存在於規格，沒有出貨。
2. 網頁版目前**沒有角色 JSON 匯出／匯入端點**，朋友間無法傳遞角色。
3. `app/content/registry.py` 的 `REPOSITORY_ROOT` 寫死了 repo 目錄結構，凍結打包後找不到 `data/`；同一個常數也已被 `app/api/dependencies.py` 引用，改動範圍不只兩處。
4. `psycopg[binary]` 是無條件相依，任何凍結打包都會帶進 5–10 MB 用不到的相依。
5. 目前 codebase 只有角色這一層，還沒有 Room 可以滲進來，這是把「單機版永遠只做創角、不做多人」界線釘死的最便宜時機。
6. P2 之後角色資料模型仍會變動，但**必須守住「角色可以脫離 Room 存在」的 schema 保證**，否則單機版死亡。M03 是先把這條界線用 import boundary test 與 CI build 具現化，讓 P2 開工時已經有一個會失敗的 build 當守門員。

M03 不改寫正常 P0 → P1 → P2 Roadmap，也不推遲 P2：

```text
M01-A
→ M01-B
→ M01-C
→ 暫停 M01
→ M02-A～M02-H
→ M02 closeout
→ 回到 M01-D
→ M01-E～M01-K（K 之後可能仍有其他 M01 Subphase）
→ M01 Full Closeout
→ M03-A～M03-G
→ M03 closeout
→ P2
```

## 2. M03 產品行為

### 2.1 兩個 entry point，同一份 codebase

不做第二份 repo，也不用 feature flag 散落在各處。

```text
線上版 entry (apps/server/app/main.py)
  → 全部 router，含 P2 之後的 Room / Session / Seat
  → 由 docker-compose / production 部署驅動
  → 資料庫：PostgreSQL

單機版 entry (apps/server/app/standalone.py，M03-E 新增)
  → 只掛 content / character / builder / meta 相關 router
  → 不 import app.main
  → 由 PyInstaller 打包成單一可執行檔驅動
  → 資料庫：本機 SQLite 檔
  → 執行時自動開瀏覽器，關閉 launcher（Ctrl+C 或關 console）時收掉 process
```

同一份 domain code、同一份 rules、同一份前端 build，差別在：

- 掛哪些 router；
- 資料庫選擇；
- `GET /api/meta/capabilities` 回傳的 capability 值。

單機版包裡不會出現半殘的多人 UI，靠 capability contract（見 2.2）而不是靠前端 build 時剔除路由。

### 2.2 前端 capability contract

`GET /api/meta/capabilities` 是**兩個 entry point 共同掛載的 neutral endpoint**，回傳當前 entry 所具備的 capability 表：

```json
{
  "channel": "web" | "standalone",
  "capabilities": {
    "character_builder": true,
    "character_import_export": true,
    "room": false,
    "campaign": false,
    "session": false,
    ...
  }
}
```

- 前端 SPA 於 bootstrap 讀一次；`Navigation` / `Landing` 依此決定顯示哪些入口。
- 對應 capability 為 `false` 的 route 於 SPA 中不 render 入口按鈕；若使用者手動打開 URL，SPA 顯示對應的 `capability_disabled` 頁面。
- Capability 與 backend router 掛載一致：`room=false` 的 entry 不會掛 `/api/rooms/*` router，讓兩端保持一致的行為。
- 這**不是** feature flag：前端 codebase 沒有 `if (standalone) hide(...)` 分支；差別集中在 capability 表這一份宣告。

### 2.3 單機版可見範圍

單機版 capability 表對使用者顯露的功能上限即**目前已完成的角色相關功能**：

- Landing / Character Workshop
- Character Builder（含 Multi-Source Content Pack、Multiclass、Subclass、ASI / Feat、Spellcasting、Starting Equipment）
- Character Sheet
- Level Up 與 Version History
- Character Archive / Permanent Delete
- `zh-TW` / `en` 語言切換
- Character JSON Import / Export（M03-B / M03-C 新增，`character_import_export=true`）

**不包含、也永遠不會包含**本質上就是多人的東西：Room、Campaign、Session、Seat、Combat、Timeline、AI Actor、DM 工具、帳號系統。這是定義，不是缺陷。

單機版前端 SPA 的 build 產物與線上版相同（同一 `apps/web` build）。P2 之後線上版新增的頁面會一併攜帶進單機版 SPA，但單機版 capability 表對應功能為 `false`，SPA 不 render 入口，backend 不掛 router；這是雙重機制決定的行為，不是缺陷。

### 2.4 角色 JSON 交換

**單機版第一版就要有出有進，同一 JSON 格式在網頁版與單機版之間互通。**

- 網頁版與單機版都提供 `POST /api/characters/import` 與 `GET /api/characters/{id}/export`。
- 使用者可從 Character Workshop 或 Character Sheet 匯出。
- 使用者可從 Character Workshop 匯入。
- 匯入 API **只接受 JSON body**；endpoint 手動讀 raw body、size gate、`json.loads` 與明確 `CharacterExport.model_validate`（不依賴 FastAPI typed body 的預設 422 `validation_failed`，見 3.5 與開發設計方針 §5.1）。前端檔案選擇於瀏覽器端 `File.text()` 讀出後以 JSON body POST（不使用 multipart，也不新增 `python-multipart` 相依）。
- 匯入入口同時支援檔案選擇與貼上 JSON。
- 匯出檔為單一 JSON，內含完整 version chain 1..N、current state、每個 version 的 `builder_provenance`（見 2.5）、envelope metadata。
- 匯入時角色 identity 一律重新產生（新 UUID）；envelope 記錄來源 identity 供重複偵測提示，但不做合併。
- 匯入時若 build refs 或 state refs 引用的 StableKey 在本機 registry 有任一個解析不到，**匯入落地為 Builder Draft**（前提是最新 version 帶有非 null 且可 validate 的 `builder_provenance`，見 2.5），讓使用者在 Builder 中補完缺口，Confirm 才成為正式 Character。
- **只有 build refs 缺** 時 `landing_mode="draft"`；**Current State 引用的 ref 有缺** 時 `landing_mode="draft_with_history_loss"`，UI 明示「補完後會產生新的 Version 1，本次匯入的 Current State 與完整 Version History 都會放棄」，使用者按繼續才落地。
- 匯入前必須先顯示可解析數與未解析數（以 origin=build/state 分組）與 landing_mode，由使用者判斷是否繼續，**不設固定門檻**。

### 2.5 Builder Provenance 隨 version 匯出，也接回 Level Up / Build Edit

從 M03-B 開始，`character_versions` 表新增 nullable 欄位 `builder_provenance`（JSON）。Confirm 時把 Builder Draft 當時的 payload 快照寫入該欄位；legacy version（M03-B migration 之前 Confirm 的角色）該欄位為 `NULL`。

**匯出**：每個 version 攜帶其 `builder_provenance` 快照（可能為 `null`）。

**匯入且全 refs 解析成功**：直接 append 為新角色。

**匯入且有 build refs 未解析**：
- 若最新 version 的 `builder_provenance` 存在且通過 `BuilderDraftPayload.model_validate()`，取該 provenance 作為 CREATE Draft 起點，未解析 ref 對應的 choice 清為未填，`landing_mode="draft"`。
- 若最新 version 的 `builder_provenance` 為 `null` 或無法 validate，拒絕匯入並回傳 code `draft_reconstruction_unavailable` / `invalid_builder_provenance`，不假裝能修。

**Versioned draft seeding SSOT**：M03-B 之後，Level Up / Build Edit / Correction 於載入 versioned draft seed 時，**優先讀 `character_versions.builder_provenance`**；缺才走 `character_build_drafts` 對應舊 draft row；再缺才走 `legacy_payload_from_build()`。這條 fallback chain 讓匯入落地的角色也能安全走後續 Level Up，不會退回 legacy reconstruction。

`legacy_payload_from_build()` 不作為匯入路徑上的反推手段；該函式本身需要 registry 完整，缺 pack 情境根本走不到終點。

### 2.6 版本相容性

**M03 出貨時 JSON schema 尚未鎖定。**

- 每個 M03 期間的單機版釋出說明必須明文標示：「這個版本的匯出檔不保證未來版本讀得進去」。
- 從 M03 到 P2 上線之間，允許新版本改變 JSON schema 語意，舊版 JSON 可以失效。
- **P2 上線時鎖定 JSON schema**：從該版本開始，schema 只能加欄位不能改欄位語意；舊版 JSON 一律必須匯得進來。
- 鎖定不是 M03 承諾，而是 P2 承諾；本 phase 只負責讓 P2 有東西可以鎖。

### 2.7 SQLite 是保存庫，不是快取

- 單機版本機資料庫檔為 SQLite，位於執行檔旁邊，預設檔名 `adventure-table.sqlite3`。
- 該檔可被環境變數 `ADVENTURE_TABLE_DATABASE_PATH` 覆寫（例：讓使用者把資料檔放到 OneDrive 目錄）。
- **Database URL SSOT**：新增 `paths.resolve_database_url()`。若 `ADVENTURE_TABLE_DATABASE_PATH` 有值 → 回傳 `sqlite+pysqlite:///<abs path>`；否則回傳 `settings.database_url`（保留 Docker `DATABASE_URL` 語意不變）。**`app/api/dependencies.py:get_database_engine`、`alembic/env.py` 與 launcher 都必須走這條 resolver**；沒有其他讀取 `settings.database_url` 的路徑。
- **啟動時把資料檔的絕對路徑印在 launcher stdout**，並在 SPA landing 提示區顯示，讓「解壓到新資料夾發現角色不見了」的解法只是複製舊資料夾裡的 `.sqlite3`。
- Launcher 於啟動 uvicorn **之前** 執行 `alembic upgrade head`，與網頁版共用同一條 migration 鏈；`app.standalone` startup **不**再次呼叫 alembic。
- 所有 SQLite engine 啟用 `PRAGMA foreign_keys=ON`，讓 `ON DELETE SET NULL` 等外鍵語意生效。
- 開發期間允許最終手段：某個 M01 / M02 / M03 期間的 migration 真的無法在 SQLite 上跑，允許使用者刪 SQLite 檔重來；JSON 匯出是安全帶而不是主要升級手段。P2 lock 之後才承擔「絕不刪 DB」的責任。

### 2.8 Enabled content pack SSOT

- 現況：`app/content/registry.py` 內定義 `DEFAULT_CONTENT_PACKS = ("srd5.1",)`；`app/content/__init__.py` 於 import 時直接 monkey-patch `_registry.DEFAULT_CONTENT_PACKS = (...)` 塞入完整 9 pack 清單（`srd5.1` / `phb2014` / `scag` / `gos` / `vgm` / `vrgr` / `tce` / `xge` / `mtf`）。這條 monkey-patch 是目前完整 pack 清單的實際來源。
- M03-A 必須**同時清掉這兩個位置**：`registry.py` 內的 `DEFAULT_CONTENT_PACKS` 常數，與 `content/__init__.py` 對它的 monkey-patch。改為由 `Settings.enabled_content_packs` 提供，可經環境變數 / 測試 fixture 覆寫。
- **Web entry 預設**：完整 9 pack 清單（M03-A start baseline；若 M01-K 後又新增 pack，缺省值隨之更新）。
- **Standalone entry 預設**：與 Web 相同的完整 pack 集合。
- **環境變數覆寫**：`ADVENTURE_TABLE_ENABLED_CONTENT_PACKS=srd5.1,phb2014`。pydantic-settings 把 `tuple[str, ...]` 視為 complex type，`EnvSettingsSource` 會在任何 validator 之前先對環境變數值做 JSON decode，comma string 因此以 `SettingsError` 失敗（已於 pydantic-settings 2.15.0 實測）。欄位必須標成 `Annotated[tuple[str, ...], NoDecode]` 關掉該欄的自動 decode，再由 `field_validator("enabled_content_packs", mode="before")` 明確 split。
- **測試 / 匯入模擬缺 pack**：透過 settings 注入 subset（例：不含 `xge`），**不**靠刪除仍 enabled 的 pack 目錄——刪目錄會直接讓 registry startup 失敗。

### 2.9 平台範圍

M03 第一版**只出 Windows x64**。

理由：

- PyInstaller 不能跨平台編譯，多一個平台就是多一個 CI runner 與要驗的產物。
- macOS 未簽章 app 被 Gatekeeper 直接擋，簽章需 Apple 開發者帳號；朋友間私用不划算。
- 使用者本人與其朋友主要在 Windows。

但 launcher 與 build 腳本必須寫成**平台中性**（不寫死 `C:\`、不假設路徑分隔符、統一用 `pathlib`）。之後要加 Linux build 就只是 CI matrix 多一列，不是重寫。

### 2.10 打包產物與資料根

**使用者不自己在本機打包。** 打包由兩條路徑產生：

- **開發期間**：`scripts/build-standalone.cmd` 在使用者本機 iteration。
- **釋出**：`windows-latest` CI job 在 tag push 時自動 build，產出 `.zip` 上傳成 GitHub Release artifact。

朋友拿到的東西是一個 `.zip`：

- 解壓即得一個資料夾（例：`adventure-table-standalone/`）。
- 資料夾內含 `adventure-table.exe`（PyInstaller launcher）、`_internal/` PyInstaller 相依、`data/`（content pack 與 rules）、`web/`（前端 SPA build）、`LICENSE.txt`、`README-standalone.txt`。
- 雙擊執行 → launcher 起 uvicorn → 開瀏覽器 → 使用 → 關閉 console 或 Ctrl+C 就結束 process。

**資料根位置決策**：

- `data/` 與 `web/` 於 release 產物中放在**執行檔同層目錄**（`<exe_dir>/data`、`<exe_dir>/web`），**不**打包進 PyInstaller bundle。
- Resolver frozen mode **優先** `<exe_dir>/data`（見 M03-A）。
- 好處：使用者能直接看見資料夾；未來需要 mod pack / 手動 patch 也直觀；避免 bundle 與 exe_dir 兩份資源產生 canonical root 歧義。

## 3. M03 共通硬原則

### 3.1 網頁版行為不得回歸

M03 是**加功能**與**加封裝**，不改既有功能。

- Landing / Workshop / Builder / Sheet / Level Up / Version History / Archive / Locale 切換行為在 M03 期間一行不得改。
- Content Registry 載入結果、Builder Choice DTO、Rules Layer derive、Character JSON payload 於 `zh-TW` / `en` 下的 presentation 與 M02-H closeout 觀察一致（M03 開工時基線更新為 M03-A start baseline；見 2.8）。
- M01 / M02 期間的自動化測試在 M03 每個 Subphase 完成後全綠。

### 3.2 角色可以脫離 Room / Campaign / Session / Seat 存在

這是 M03 的政治承諾，也是 P2 的 schema 約束。

- `characters` 表不得長出 `room_id` / `campaign_id` / `session_id` 欄位；未來 P2 的 Campaign 歸屬走 Party Roster join table。
- Character Campaign Status（`active` / `inactive` / `retired` / `dead`）住在未來 roster row，不是 character row。
- `app/content`、`app/domain/character*`、`app/persistence/characters`、`app/persistence/builder_drafts` 與 `app/api/character*`、`app/api/reference`、`app/api/content_presentation` 不得 import 任何 room / session / seat 模組。
- `app/standalone` 不得 import `app/main`；共用邏輯（exception handler、meta router 等）住 neutral module。
- 權限檢查於 route 外層 wrapper / dependency 加入，不寫進 character domain 內部。
- 上述五條由 M03-F 建立的 **import boundary test** 與 **standalone build gate** 於 CI 強制。

### 3.3 匯入必須走 domain validation，不得產生假資料

網頁版與單機版的匯入端點必須守住 P1 立場：**正式 Build 不可以是假資料**。

- 每個 version 的 `build_payload` 必經 `CharacterBuild.model_validate()`；不通過即拒絕（`invalid_build_shape`）。
- `version_kind` 於 JSON schema 上是 strict enum（與 persistence 對齊，非 `str`）；不通過即拒絕（`invalid_version_kind`）。
- 每個非 null `builder_provenance` 必經 `BuilderDraftPayload.model_validate()`；不通過即拒絕（`invalid_builder_provenance`）。
- 全 refs 可解析時，於 commit 之前逐 version 執行 `validate_build_references(build, registry)`；不通過即拒絕（`build_references_invalid`）。
- Current State 必經 `CharacterState.model_validate()`，並對 `current_version_no` 對應的 build 執行 `validate_state_against_build(state, build, registry)`；不通過即拒絕（`state_shape_invalid` / `state_inconsistent_with_build`）。
- **Ruleset 三重 cross-check**：`envelope.ruleset == character.ruleset == 每個 CharacterBuild.ruleset`；任何不一致 → 拒絕 `ruleset_mismatch`。
- **Version lineage 完整性**：`parent_version_no` 不得 self-reference；`parent_version_no` 必須 < 自身 `version_no`；`superseded_by_version_no` 必須 > 自身 `version_no`；chain 上不得有環。任何違反 → `version_lineage_direction_invalid` / `version_lineage_cycle` / `version_lineage_self_reference`。
- 若匯入的 build / state 引用了本機解析不到的 StableKey，一律落地為 Builder Draft，讓使用者在 Builder 中補完後 Confirm 建立正式 Character；Draft 起點來自最新 version 的 `builder_provenance`。
- Rules Layer 不新增「容忍缺失 ref」的降級模式；`ContentNotFoundError` 語意不改。
- 因此 Character Sheet 永遠不會出現「數值錯的角色」；未 Confirm 的匯入結果以 Draft 形式呈現，Sheet 不會渲染。

### 3.3.1 State-only 缺 ref 的 UX 明示

- 當 build refs 全解析、僅 Current State refs 有未解析時，`landing_mode="draft_with_history_loss"`。
- Dialog 明示：「本次匯入的 Current State 與完整 Version History 都無法保留；補完後會產生新的 Version 1。要繼續嗎？」
- 使用者確認後才落地為 CREATE Draft；未確認前不 mutate DB。
- 這是 M03 期間可接受的犧牲；替代路線（Rules Layer 容忍 state 缺失 ref）會違反 3.3 前段硬原則。

### 3.4 Ref walker 涵蓋 build + state

- 匯入時的解析預檢對 **每個 version 的 `build_payload`** 與 **`current_state.state_payload`** 各跑一次 ref 收集。
- Landing_mode 判定由 union（build_refs ∪ state_refs）決定：任一未解析即 `draft`。
- 未解析清單以 `{origin: "build" | "state", version_no?, stable_key, kind, pack, index}` 呈現，讓 UI 能標示「不見的引用來自 Version 3 的 build 還是 current state 的 inventory」。

### 3.5 匯入 / 匯出邏輯 server-authoritative

- Import / export 是 server-side 契約，前端不重建 build_payload 結構、不重建 refs 收集邏輯。
- 前端只負責檔案選擇 / 貼上 JSON / 呼叫 API / 顯示回應中的可解析與未解析清單。
- 未來 AI actor（透過 MCP / Site Tools）匯入角色時，共用同一 server-side pipeline，不做兩套邏輯。

### 3.6 單機版可見範圍靠 capability contract 與 router 掛載雙重決定

- 前端 SPA 於 boot 讀 `/api/meta/capabilities`；capability `false` 的功能不 render 入口。
- Backend `app.standalone` 不掛未來 Room / Session router；前端誤打對應 URL 時，capability 表已標示不支援，SPA 顯示 `capability_disabled` 頁面，backend 也回 404。
- 前端沒有 `if (channel === "standalone") ...` 散落分支；分流只集中在 nav manifest 讀 capability 表這一處。

### 3.7 Localization 交付對稱

- Import / Export UI（Workshop / Sheet 的按鈕、匯入 dialog、預覽數字文字、error 訊息、`capability_disabled` 頁面文字、README-standalone）於 M03-B / M03-C / M03-E / M03-G 完成當下必須同步交付 `zh-TW` / `en` 兩語，缺任一視同該 Subphase regression。這是 M02-H 建立的永久 supported-locale 交付守則。

### 3.8 Standalone 打包成本不得回流到網頁版

- 為單機版所做的 refactor（例：Content Root abstraction、psycopg optional extra、enabled pack SSOT、資料檔路徑抽象、capability endpoint、SPA fallback、SQLite FK PRAGMA）不得讓網頁版功能行為改變。
- 環境變數缺省時的路徑解析 fallback 必須等同於當前 repo-relative 行為。
- 網頁版 Docker image 不變、Docker Compose 不變、Alembic 於 Postgres 上的行為不變、meta capability 表對網頁 entry 回傳 P2 所需的所有 `true`（本 phase 只保證單機端為 `false`）。

# M03-A — Content Root Path Abstraction & Enabled-Pack SSOT

## 目標

把目前 `app/content/registry.py` 寫死的 `REPOSITORY_ROOT`、`CONTENT_PACKS_ROOT`、`DEFAULT_CONTENT_ROOT`、`DEFAULT_SRD_CONTENT_ROOT`，`app/domain/character_builder/rules.py` 的 `RULES_PATH`，以及 `app/api/dependencies.py` 引用的 `CONTENT_PACKS_ROOT`（用於 localization loader）等所有路徑常數改成經一組**可覆寫的解析器**取得，並把 enabled pack 清單從 `DEFAULT_CONTENT_PACKS` 常數改為 `Settings.enabled_content_packs`。

## 完成後必須為真

### A.1 解析順序固定

Content root 解析順序：

1. 明確環境變數 `ADVENTURE_TABLE_CONTENT_ROOT`（若非空且指向存在目錄）。
2. Frozen mode（`sys.frozen`）：`<executable directory>/data`。
3. Frozen mode fallback：`sys._MEIPASS / "data"`（僅在 exe_dir 未含 `data/` 時退回，供 dev iteration 或早期 spec 遺留使用）。
4. Repo 相對路徑：現況邏輯（自 `app/paths.py` 起算 `parents[3] / "data"`），開發模式使用。

Rules JSON、localization root 一律從 content root 推導；不獨立於別處硬編。

### A.2 現行網頁版行為不變

- 未設 `ADVENTURE_TABLE_CONTENT_ROOT` 且非凍結環境下，解析結果與 M02-H closeout 觀察完全一致。
- 未設 `ADVENTURE_TABLE_ENABLED_CONTENT_PACKS` 時，`Settings.enabled_content_packs` fallback 為「M03-A start baseline 完整 pack 集合」。
- `load_default_content_registry()` 載入的 pack 集合、entry 集合、locale overlay 集合、rules JSON 皆不變。
- Docker Compose 環境、pytest 環境、Playwright 環境不需要設定新環境變數即可跑起來。
- `app/api/dependencies.py` 對 localization loader 的呼叫仍成立，走同一 resolver。

### A.3 應用啟動不再於 import time 依賴 filesystem 位置

- Registry 載入仍可發生於 `app/main.py` / `app/standalone.py` import time，但**路徑解析必須以函式形式**（`resolve_content_root()` 等）取得，允許 PyInstaller launcher 起 uvicorn 前就設定環境變數。
- 若解析後的 content root 不存在或 pack 無法載入，啟動時以清楚的錯誤訊息失敗，並包含實際解析出的路徑與解析階段（`env` / `frozen-exe-dir` / `frozen-meipass` / `repo-relative`）。

### A.4 Repo-wide sweep

於本 subphase 內完成以下清理，一次到位：

- 移除 `app/content/registry.py` 內 `REPOSITORY_ROOT`、`CONTENT_PACKS_ROOT`、`DEFAULT_CONTENT_ROOT`、`DEFAULT_SRD_CONTENT_ROOT` 常數；改為 `resolve_content_root()` / `resolve_srd_content_root()` 等函式呼叫。
- **移除 `app/content/__init__.py` 對 `_registry.DEFAULT_CONTENT_PACKS` 的 monkey-patch**；完整 pack 清單改由 `Settings.enabled_content_packs` 提供。此檔目前的 `install_m01l_content_models()` / `install_m01m_content_models()` 等 side effects 保留。
- 移除 `app/domain/character_builder/rules.py` 的 `RULES_PATH` 常數；改為 `resolve_rules_path()`。
- 修改 `app/api/dependencies.py` 對 `CONTENT_PACKS_ROOT` 的 import 與 `get_database_engine` 對 `settings.database_url` 的直接讀取，改為呼叫 `resolve_content_root()` 與 `resolve_database_url()`。
- 修改 `alembic/env.py` 兩處對 `settings.database_url` 的直接讀取，改為 `resolve_database_url()`；migration URL 因此隨 `ADVENTURE_TABLE_DATABASE_PATH` 切換為 SQLite 時 launcher 也能跑 upgrade。
- 掃 repo 內所有 `Path(__file__).resolve().parents[N]` 用於路徑推導的位置，若指向 repo root，全面統一為呼叫 resolver。
- 新增靜態 test（M03-A 測試指南 A.5）：禁止上述常數被重新引入 module scope；禁止 `module.CONSTANT = ...` 形式對已移除常數的 legacy monkey-patch；禁止 `from app.content.registry import CONTENT_PACKS_ROOT` 等 legacy import。

### A.5 Enabled pack SSOT

- 新增 `Settings.enabled_content_packs: Annotated[tuple[str, ...], NoDecode]`，可經 `ADVENTURE_TABLE_ENABLED_CONTENT_PACKS`（逗號分隔字串）覆寫。`NoDecode` 是必要的：沒有它，`EnvSettingsSource` 會先把該欄當 complex type 做 JSON decode 而以 `SettingsError` 失敗，`field_validator` 根本收不到字串。關掉自動 decode 後，再由 `field_validator("enabled_content_packs", mode="before")` 明確把 comma string 切為 tuple、同時接受 list/tuple。
- 缺省值：`("srd5.1", "phb2014", "scag", "gos", "vgm", "vrgr", "tce", "xge", "mtf")`（M03-A start baseline；若 M01-K 之後新增 pack，缺省值同步更新）。
- `load_default_content_registry()` 讀 `settings.enabled_content_packs`，不再依賴 `DEFAULT_CONTENT_PACKS` 常數或 `content/__init__.py` 的 monkey-patch。
- 對於 web / standalone / pytest / Playwright，settings 缺省時皆取上述完整清單。
- 測試 fixture 可注入 subset（例：`enabled_content_packs=("srd5.1", "phb2014")`）以模擬缺 pack 情境，**不**靠刪目錄。

### A.5.1 Subset registry 的 unresolved 語意（M01-A 契約收窄）

Subset 載入要成立，就必須放寬 registry load 時的 dangling reference 檢查——`phb2014` 會引用 `scag` / `tce`，只 enable 部分 pack 時舊規則必定失敗。但放寬只能放到「**已安裝但本次未啟用**」為止：

- **Installed but disabled**：目標 pack 的目錄存在於 content root、但不在 `enabled_content_packs` 內 → ref 保持 unresolved，registry 正常載入。這是 M03-C import preview 要分類的情況，不是內容損壞。
- **Not installed**：StableKey 的 source 段指向一個 content root 裡根本不存在的 pack（打錯字、引用未出貨的 pack）→ 仍然 raise `ContentValidationError`，訊息維持 `dangling reference`。
- **Enabled but missing entry**：目標 pack 已啟用、entry 卻不存在 → 仍然 raise。這是原本就有的內容損壞。
- 同一判準必須套用在三個地方，不得只改 registry：`ContentRegistry._validate_cross_references()`、`builder_content_validation` 的 `_require_key()` / `_validate_spell_relation()`、`background_roleplay` 的 inheritance resolver。kind 不符（例如 background 欄位填了 race key）永遠 raise，不受 disabled 放行影響。
- `ContentRegistry` 因此需要同時記住 `enabled_pack_ids` 與 `installed_pack_ids`；後者於 `from_root()` 由 content root 目錄掃描得出。

> 這條**收窄了 M01-A 原本的「跨 pack 依賴必須被 enable，否則 registry load 失敗」**。原契約的兩半只有一半能保留：subset 載入是 M03-A 的硬需求，所以「未 enable 就失敗」讓位；「source 打錯字要炸」則完整保留，M01-J / M01-L / M01-M 依賴的 registry load 身分守門不因 M03 而失效。`tests/test_m01a_content_packs.py` 內原本的 `test_cross_pack_dependency_must_be_enabled` 已改寫成兩條測試分別守住上述兩半。

### A.6 Settings 環境變數相容性

- **不改** 現有 `Settings` 的 `env_file=".env"` 與缺省行為；不啟用 `env_prefix="ADVENTURE_TABLE_"`。原因：Docker Compose 目前傳 `DATABASE_URL`（沒有 `ADVENTURE_TABLE_` 前綴），啟用 prefix 會直接 break 網頁版部署。
- 新欄位（`content_root` / `database_path` / `spa_root` / `enabled_content_packs`）以 `Field(validation_alias=AliasChoices("ADVENTURE_TABLE_CONTENT_ROOT", ...))` 明列環境變數名，逐個欄位掛 alias。
- `database_url` 欄位維持既有 `DATABASE_URL` 語意，不觸動。

## 本 Subphase 不要求

- 不建立 standalone entry point 或 launcher。
- 不新增 JSON 匯出／匯入。
- 不修改 Alembic migration。
- 不引入 SQLite runtime 相關程式碼。
- 不新增 `/api/meta/capabilities` router。

# M03-B — Character JSON Schema, Export & Builder Provenance

## 目標

在網頁版與（未來的）單機版都提供 `GET /api/characters/{id}/export`，讓使用者從 Character Workshop 或 Character Sheet 下載一份**內含完整 version chain 1..N、current state、每個 version 的 `builder_provenance` 與 envelope metadata** 的 JSON 檔。同時新增 `character_versions.builder_provenance` 欄位，讓後續 M03-C 於缺 pack 情境能重建 CREATE Draft。

## 完成後必須為真

### B.1 Migration：`character_versions.builder_provenance`

- 新增一支 Alembic migration，於 `character_versions` 加 `builder_provenance JSONB NULL`（Postgres）／`JSON NULL`（SQLite 走 `with_variant`）。
- 現有 version rows 該欄位為 `NULL`。
- Postgres 上 up/down 綠燈；SQLite 上綠燈延至 M03-D 統一保證，M03-B 期間 SQLite 上可 fail。
- Migration 檔名不寫死編號，實作者依當時 Alembic head 的下一個 revision 命名（例：`<next>_m03b_builder_provenance.py`）。

### B.2 Confirm 寫入 `builder_provenance`

- Builder Draft Confirm 建立 Version 1 時，寫入當時 draft payload 的 snapshot（`BuilderDraftPayload.model_dump()`）。
- Level Up Confirm 建立 Version N+1 時，寫入當時 versioned draft payload 的 snapshot。
- Correction 建立 Version 產生 `superseded_by_version_id` 時，寫入該 correction draft 的 snapshot。
- Snapshot **不**包含使用者 session 資訊、revision counter、UI-only fields；僅包含 Draft 產出 Confirm 所需的 `BuilderDraftPayload` shape data。
- Legacy version（migration 之前 Confirm）該欄位保持 `NULL`。

### B.2.1 Versioned draft seeding SSOT

- 修改 `apps/server/app/domain/character_builder/versions.py` 內載入 versioned draft seed 的路徑（現行第 344 行附近 `source_payload` 決定邏輯）。
- 新 fallback 順序：
  1. `character_versions.builder_provenance`（非 null 且通過 `BuilderDraftPayload.model_validate()`）。
  2. `character_build_drafts` 對應 base_version 的舊 draft row。
  3. `legacy_payload_from_build(character, registry)`。
- Level Up / Build Edit / Correction 於載入 seed 時走此順序；同一函式服務所有分支，不重複條件判斷。
- 這條 SSOT 讓匯入落地的角色（沒有對應 legacy draft rows）也能安全走後續 Level Up；`legacy_payload_from_build` 保留但降級為最後 fallback。

### B.3 匯出端點

- `GET /api/characters/{id}/export` 回傳 `application/json`，`Content-Disposition: attachment` 給合理檔名（含角色名 sanitized 版本與 export 時間戳）。
- 端點只讀，不改變任何 server 狀態。
- 端點為 server-authoritative；前端不重建 payload 結構。
- 端點對已 archive 角色仍可匯出，回應 header 中標示 archived 狀態（但 payload 中不帶 `archived_at`，見 B.5）。

### B.4 Envelope

Envelope 至少包含以下欄位：

- `schema_version`：M03 期間定為 `"unstable"`；P2 lock 之後改為正式 semver。
- `schema_status`：`"unstable"` 或 `"locked"`；M03 期間一律 `"unstable"`。
- `ruleset`：來自 `characters.ruleset`，M03 期間為 `"dnd5e-2014"`。
- `content_requirements`：本角色 build_payload + state_payload 引用到的**所有 pack 版本清單**（例：`[{"pack": "srd5.1", "version": "1.0.0"}, {"pack": "phb2014", "version": "..."}]`）。清單來自實際 refs 走訪，`version` 由匯出當下 registry 中對應 pack 的 manifest version 提供。
- `stable_key_refs_summary`：本角色 build_refs + state_refs 總數（診斷用整數，內容細節不進 envelope）。
- `source_character_id`：原始 `characters.id`（UUID）。
- `source_export_id`：本次 export 產生的唯一 UUID，讓匯入端可判斷「同一份 export 匯了兩次」。
- `source_app`：`{"name": "adventure-table", "channel": "web" | "standalone", "commit": ...}`。
- `exported_at`：ISO 8601 UTC 時間戳。

### B.5 Payload

Payload 包含：

- `character`：`characters` row 的 `name`、`ruleset`（不含 `id`、`current_version_id`、`archived_at`、`created_at`、`updated_at`）。
- `current_version_no`：整數，指向 `versions` 中對應「當前 Character 顯示的那個 version」的 `version_no`；**不假定** = max。
- `versions`：**完整 version chain**，依 `version_no` 遞增。每個 version 帶：
  - `version_no`
  - `version_kind`（strict enum，對齊 persistence 現行 `version_kind` 值集合，非任意 `str`）
  - `parent_version_no`（nullable，將原本 `parent_version_id` 映射為 chain 內的 `version_no`；匯入時再 map 回新 UUID）
  - `superseded_by_version_no`（nullable，correction lineage）
  - `change_note`
  - `build_payload`
  - `builder_provenance`（nullable，見 B.2；legacy version 為 `null`）
  - `created_at`
- `current_state`：`character_states.state_payload`，視為綁定 `current_version_no`。

**不含**：

- Builder Draft（單機版與網頁版皆然）。
- `archived_at`（匯入時一律成為啟用中的角色，見 C.5）。
- server-only 欄位（`id` / `current_version_id` / `updated_at` 等），因匯入端會重新產生。

### B.6 前端匯出入口

- Character Workshop 的角色卡片、Character Sheet 均新增匯出按鈕。
- 按下觸發瀏覽器 file download，不需要匯出 dialog。
- `zh-TW` / `en` 雙語 UI 同步交付。

### B.7 不變性

- Character Sheet / Version History / Level Up / Builder / Locale 切換等既有功能行為與 M02-H closeout 觀察一致（M03 開工時基線更新為 M03-A start baseline）。
- `characters.py` 端點 signature 除新增 `/export` 外一律不變。
- 網頁版與（尚未打包的）單機版本 phase 不新增其他 endpoint。

- 不做匯入。
- 不做網頁版 JSON schema lock。
- 不做 `/api/meta/capabilities`（延至 M03-E）。

# M03-C — Character JSON Import via Builder Draft

## 目標

在網頁版與（未來的）單機版都提供 `POST /api/characters/import`（JSON body），讓使用者從匯入 dialog 選檔或貼上 JSON，把角色匯入為 Builder Draft（若引用有缺且有 `builder_provenance`）或直接 append 為新角色（若全部解析得到且通過 domain validation）。同時建立**單一 build + state ref 收集器**與 **domain-validator import pipeline**，供本 phase 與未來 P7 共用。

## 完成後必須為真

### C.1 匯入端點

- `POST /api/characters/import` 接收 `application/json` body（envelope + payload）；**不接受** multipart。
- 端點**手動讀 raw body**（`await request.body()`），依序執行：size gate（超過 5 MB → 413）→ `json.loads`（失敗 → 400 `invalid_envelope_shape`）→ `CharacterExport.model_validate`（失敗 → 依 error location 對應 400 `invalid_envelope_shape` 或 400 `invalid_payload_shape`）→ 後續 pipeline。不使用 FastAPI 的 typed body pydantic 綁定，避免 `RequestValidationError` 走全域 422 `validation_failed` 覆蓋這批 machine code。
- 端點為 server-authoritative；前端不重建 payload 結構、不重建 refs 收集邏輯。
- 端點原子性：拒絕（見 C.7）不留任何殘留狀態。
- 端點對已存在角色的匯入一律以新 UUID 落地（見 C.5）。

### C.2 Ref 收集器：build + state

- 建立 `collect_build_refs(build_payload) -> Iterable[ContentRef]`。
- 建立 `collect_state_refs(state_payload) -> Iterable[ContentRef]`。
- Build walker 覆蓋範圍需涵蓋 M01 Full Closeout 後 `CharacterBuild` 中所有 pack-sourced content：race / subrace / lineage / background / class / subclass / feature choice / spell / feat / infusion / maneuver / fighting style / starting equipment 等。
- State walker 至少涵蓋：
  - `conditions[].condition_ref`
  - `prepared_spells[].spell_key`
  - `inventory_state.inventory_entries[].item_ref`（或現行 InventoryEntry 結構等效欄位）
  - `active_infusions[].infusion_ref`
  - `spell_storing_item.spell_ref`
  - Starting equipment（如已納入 state 快照）
- Walker 明列可能出現的 StableKey path，不用 reflection / 全 dict 遞迴；發現 build_payload / state_payload 帶未列出的 StableKey 形狀時，walker 需 fail-fast 以逼開發者更新，而不是沉默漏收。
- Walker 獨立於匯入流程可測；純函式，不呼叫 registry。

### C.3 解析預檢

匯入分兩階段：

1. **Preview 階段**：`POST /api/characters/import?dry_run=true`，執行以下依序：
   1. Raw body / size gate / JSON parse / `CharacterExport.model_validate`（C.1）。
   2. Envelope shape / ruleset / schema_status 檢查（不通過即 400，見 C.7）。
   3. Version chain 一致性檢查（`version_no` 連續、`current_version_no` 存在於 chain、`parent_version_no` / `superseded_by_version_no` 指向 chain 內、`current_state` 對應 `current_version_no`）。
   4. Version lineage 完整性檢查：self-reference、direction、cycle（見 3.3）。
   5. 每個 version 的 `build_payload` 過 `CharacterBuild.model_validate()`（不通過即 400 `invalid_build_shape`）。
   6. 每個非 null `builder_provenance` 過 `BuilderDraftPayload.model_validate()`（不通過即 400 `invalid_builder_provenance`）。
   7. `current_state.state_payload` 過 `CharacterState.model_validate()`（不通過即 400 `state_shape_invalid`）。
   8. Ruleset 三重 cross-check（envelope / character / 各 build）：不一致 → 400 `ruleset_mismatch`。
   9. 收集 build_refs（每個 version）與 state_refs。
   10. 對每個 ref 呼叫 `registry.get_optional`；分類 resolved / unresolved。
   11. 判定 landing_mode：
       - unresolved 為空 → 逐 version 執行 `validate_build_references(build, registry)`；對 current_version 對應的 build 執行 `validate_state_against_build(state, build, registry)`；全部通過 → `landing_mode="character"`；任一不通過 → 400（`build_references_invalid` / `state_inconsistent_with_build`）。
       - build refs 有未解析 → 取 `versions[current_version_no].builder_provenance`；為 `null` → 400 `draft_reconstruction_unavailable`；有效 → `landing_mode="draft"`。
       - build refs 全解、僅 state refs 有未解析 → 同上取 provenance；有效 → `landing_mode="draft_with_history_loss"`（UI 明示 history / state 將放棄，見 3.3.1）；provenance null → 400 `draft_reconstruction_unavailable`。
   12. 組 `duplicate_hint`（見 C.5）。
   13. 組 `character_preview`（角色名、最高等級、class 摘要）。
2. **Commit 階段**：`POST /api/characters/import`（不帶 `dry_run`），實際落地；再走一次上述檢查，通過後 commit。

前端 UI 一律先呼叫 dry-run，顯示可解析 / 未解析數字與 landing_mode 給使用者確認後才 commit。**沒有預設門檻**，是否繼續由使用者決定。

### C.4 落地邏輯

- **`landing_mode == "character"`**：
  - 新 UUID → `characters` row。
  - Full version chain → `character_versions` **兩階段** append：第一 pass 每個 version INSERT 時 `parent_version_id=NULL`、`superseded_by_version_id=NULL`；第二 pass 依 `version_no → 新 UUID` dict 執行 UPDATE 填入 lineage 欄位。這條路徑與現行 correction 落地一致，避免 FK 於 INSERT 時指向尚未存在的 row。`builder_provenance` 逐 row 保留原 JSON。
  - `current_state` → `character_states`，綁定 `current_version_no` 對應的新 version UUID。
  - `characters.current_version_id` 指向 `current_version_no` 對應的新 UUID。
  - `character_import_records` 新增一列，`landing_mode="character"`。
- **`landing_mode == "draft"`** 或 **`landing_mode == "draft_with_history_loss"`**：
  - 從 `versions[current_version_no].builder_provenance` 建立 fresh CREATE Draft（不綁 `base_version_id`，因為沒有既有 Character）。
  - Draft 中每個未解析 build ref 對應的 choice 被清空為未填；使用者於 Builder UI 中重新選擇。
  - Draft 建好之後，`character_import_records` 新增一列，`landing_mode` 對應（`"draft"` 或 `"draft_with_history_loss"`），`draft_id=<new draft id>`。
  - Current state 不進 Draft；Draft 沒有 live state 的概念，Confirm 產生 Version 1 時走一般 initial state 建立流程。
  - 使用者於 Draft 中補完後 Confirm，走既有 P1-F create flow → 新角色的 Version 1。歷史版本鏈條無法還原；envelope 中的舊 version 資訊於本次匯入放棄（3.3 硬原則已接受）。`draft_with_history_loss` 情境已於 preview 明示，使用者知情。

### C.5 Identity 與重複偵測

- 匯入一律以**新 UUID** 落地，`characters.id` / `character_versions.id` 全新。
- Envelope 的 `source_character_id` 與 `source_export_id` 存進 `character_import_records`（見 C.8），供匯入前重複偵測。
- Dry-run 回應包含 `duplicate_hint`：若匯入端已存在同 `source_character_id` 的過去匯入紀錄，回應中列出「你已從相同來源匯入過 M 次，最近一次為 …」，前端據此提示但不阻擋。
- 匯入後**不合併**、不覆寫既有角色。
- `archived_at` 不帶入；匯入結果一律為啟用中的角色。

### C.6 歷史版本處理

- `landing_mode == "character"`：完整 chain 保留，含 correction lineage（`superseded_by`）。
- `landing_mode == "draft"`：只有 `current_version_no` 的 `builder_provenance` 進 Draft；其他 version 於本次匯入放棄。這是 M03 期間可接受的犧牲，用來避免違反 3.3 硬原則。

### C.7 拒絕條件

匯入直接拒絕（原子拒絕、零副作用）的情況：

- `invalid_envelope_shape`：raw body JSON parse 失敗、envelope 缺必要欄位、或 `CharacterExport.model_validate` 於 envelope 段失敗。
- `invalid_payload_shape`：payload 缺 `character.name` / `versions` / `current_state` / 至少一個 version / `current_version_no`；`CharacterExport.model_validate` 於 payload 段失敗。
- `unsupported_schema_status`：`schema_status` 出現不相容值（special case，見 C.7.1）。
- `unsupported_ruleset`：`ruleset` 不是本 registry 支援的 ruleset。
- `ruleset_mismatch`：`envelope.ruleset` / `character.ruleset` / 各 `CharacterBuild.ruleset` 不一致。
- `version_chain_gap`：`version_no` 非連續。
- `version_chain_out_of_order`：順序錯亂。
- `current_state_version_missing`：`current_version_no` 不在 chain 中。
- `version_lineage_invalid`：`parent_version_no` / `superseded_by_version_no` 指向 chain 之外的 version。
- `version_lineage_self_reference`：`parent_version_no == self.version_no`。
- `version_lineage_direction_invalid`：`parent_version_no >= self.version_no` 或 `superseded_by_version_no <= self.version_no`。
- `version_lineage_cycle`：parent chain 或 superseded chain 有環。
- `invalid_version_kind`：`version_kind` 不是允許的 enum 值（special case，見 C.7.1）。
- `invalid_build_shape`：`CharacterBuild.model_validate` 失敗。
- `invalid_builder_provenance`：某個非 null `builder_provenance` 不通過 `BuilderDraftPayload.model_validate`。
- `state_shape_invalid`：`CharacterState.model_validate` 失敗。
- `build_references_invalid`：全 refs 可解析但 `validate_build_references` 失敗。
- `state_inconsistent_with_build`：`validate_state_against_build` 失敗。
- `draft_reconstruction_unavailable`：未解析 refs 存在且 current version 無 `builder_provenance`（或 provenance null）。
- `payload_too_large`：raw body > 5 MB → 413。

**未解析 refs 本身不是拒絕條件**；有 provenance 則落地為 Draft（或 draft_with_history_loss），無 provenance 則以 `draft_reconstruction_unavailable` 拒絕。

### C.7.1 Pydantic 階段的 code 映射

`schema_status` 是 `Literal["unstable", "locked"]`、`version_kind` 是 strict enum，兩者都在 `CharacterExport.model_validate()` 就失敗，**到不了任何語意檢查步驟**。若不特別處理，它們會被歸成泛用的 `invalid_envelope_shape` / `invalid_payload_shape`，而 C.7 又要求 `unsupported_schema_status` 與 `invalid_version_kind` 兩個專屬 code，兩條驗收無法同時成立。

因此 import endpoint 捕捉 `CharacterExport.model_validate()` 的 `ValidationError` 後，**必須**依每筆 error 的 `loc` 做以下映射：

| `loc` 命中 | code |
|---|---|
| `schema_status` | `unsupported_schema_status` |
| `version_kind` | `invalid_version_kind` |
| `schema_version` | `invalid_envelope_shape` |
| 其餘 envelope 欄位 | `invalid_envelope_shape` |
| 其餘 payload 欄位 | `invalid_payload_shape` |

決定性規則（兩條都必須成立，否則同一份輸入可能回不同 code）：

- **special case 優先於泛用 shape code**：同一個 `ValidationError` 同時含 special-case 與其他欄位錯誤時，回 special-case code。
- **多個 special case 同時命中時，取 `loc` 排序最前者**，不依賴 pydantic 的 error 順序。

對應地，envelope **語意**檢查階段只負責 ruleset（`unsupported_ruleset` / `ruleset_mismatch`）；`schema_status` 不在該階段判定。

### C.8 Import records

新增 `character_import_records` 表（migration 隨本 subphase 提交，檔名編號依當時 Alembic head 的下一個 revision，不寫死 `0007`）：

- `id UUID PK`
- `character_id UUID NULL FK → characters.id ON DELETE SET NULL`
- `draft_id UUID NULL FK → character_build_drafts.id ON DELETE SET NULL`
- `source_character_id UUID NOT NULL`
- `source_export_id UUID NOT NULL`
- `landing_mode VARCHAR(32) NOT NULL`（`"character"` | `"draft"` | `"draft_with_history_loss"`）
- `imported_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- Index on `source_character_id`；index on `source_export_id`。
- `CheckConstraint`：`character_id IS NULL OR draft_id IS NULL`（**至多一欄非 NULL**）。
  - **不可**寫成 XOR（`(character_id IS NULL) != (draft_id IS NULL)`）：兩個 FK 都是 `ON DELETE SET NULL`，而 import record 在目標 character / draft 被永久刪除後仍須保留。原本 `character_id` 非 NULL 的列在 character 被 permanent delete 後會變成兩欄皆 NULL，XOR 當場違反，刪除操作會被 constraint 擋掉。
  - 「建立當下恰好一欄非 NULL」由 service / domain 層在 insert 時保證，不由 DB constraint 表達。
  - **兩欄皆 NULL 是合法的終態**，語意為「這筆匯入的落地目標已被刪除，記錄保留供 dedupe 提示」。不是資料損毀，不得在後續 Phase 被「修正」回 XOR。
- **SQLite 上 FK 語意由 M03-D 建立的 `PRAGMA foreign_keys=ON` 保證**；本 subphase 內 SQLite 側 FK 可暫時不成立，於 M03-D 綠燈時同步驗證。

### C.9 前端匯入入口

- Character Workshop 的空狀態與角色列表區均新增「匯入角色」按鈕。
- 匯入 dialog **同時提供檔案選擇按鈕與 textarea 貼上 JSON**；檔案選擇於瀏覽器端 `File.text()` 讀出後與貼上 JSON 走同一 preview 呼叫（皆為 JSON body）。
- Dry-run 回應以清楚的視覺呈現：`X 個可解析、Y 個未解析、landing_mode 為 …`；未解析清單可展開，並標示每個 unresolved ref 的 origin（`build` / `state`）與所在 version_no（若適用）。
- `landing_mode="draft_with_history_loss"` 時，dialog 顯示明確 warning banner：「Current State 與完整 Version History 都不會保留；補完後會產生新的 Version 1。」（見 3.3.1）。使用者需二次確認才發送 commit。
- 使用者按下「繼續匯入」才發送 commit 請求。
- 匯入成功後導向新落地的 Character Sheet（`landing_mode == "character"`）或新 Draft（`draft` / `draft_with_history_loss`）。
- `zh-TW` / `en` 雙語 UI 同步交付。

### C.10 不變性

- Character Sheet / Version History / Level Up / Builder / Locale 切換等既有功能行為與 M02-H closeout 觀察（M03-A start baseline）一致。
- 既有 Builder Draft 語意不變（M03 不改 Draft schema，只是新增一種建立來源）。

## 本 Subphase 不要求

- 不做 Campaign / Party Roster 匯入。
- 不做 batch 匯入。
- 不做 undo import。
- 不做 diff 顯示（「這份匯入與你既有角色 X 的差異」）。
- 不做 SQLite migration gate（延至 M03-D）。

# M03-D — SQLite Migration Chain Gate & FK PRAGMA

## 目標

把「整條 Alembic migration 鏈可以在 SQLite 上 `upgrade head` 到完整 schema、外鍵語意在 SQLite 上被啟用」從假設變成 CI-enforced 事實。M03 靠這條路徑升級單機版使用者的本機資料庫；沒有這道 gate，2.7 節的保存庫承諾無法兌現。

## 完成後必須為真

### D.1 SQLite migration 綠燈

- CI 在乾淨的空 SQLite 檔上執行 `alembic upgrade head` 全綠。
- 涵蓋所有現存 migration（M03-D 撰寫當下為 0001～現行 head，含 M03-B、M03-C 新增的 migration）。
- 每個 migration 的 `downgrade()` 於 SQLite 上亦可執行；若某個 migration 明顯無法 downgrade，需在 migration 中以清楚語意標示，並取得使用者拍板。
- `alembic downgrade base` 之後，**除 `alembic_version` 外**無其他 table 殘留，且 `alembic_version` row 數為 0。`alembic_version` 由 Alembic 自身管理，downgrade 不會 drop 它——「tables 全空」不是本契約的字面要求。

### D.2 Schema 一致性

- SQLite 上 `alembic upgrade head` 之後的 schema 與 `metadata.create_all()` 之後的 schema 於**表列、欄位型別、null 屬性、索引、unique 約束**上一致。
- **比對時自兩側排除 `alembic_version`**：migration 路徑會建立它、`metadata.create_all()` 不會。這是結構性的預期差異，不列入「零差異」的計算，也不算下一條的表達力讓步。
- 若 SQLite 對某類 DDL 表達力有限（例：某類 alter column），差異需明列，並確認不影響 runtime 讀寫。

### D.3 SQLite FK PRAGMA

- 於 SQLite engine 建立時透過 SQLAlchemy `event.listens_for(Engine, "connect")` 或等效 hook，對每條新連線執行 `PRAGMA foreign_keys=ON`。
- 適用範圍：`app/db.py` 建 SQLite engine 的所有位置，含 launcher 呼叫的 `run_migrations`。
- 回歸測試：`character_import_records.character_id` / `.draft_id` 對應的 `ON DELETE SET NULL` 於 SQLite 上實際生效（刪除 character 後 record 對應欄位為 NULL）。

### D.4 Postgres 行為不變

- CI 同一批 test 於 Postgres 上仍全綠。
- 網頁版 Docker Compose 啟動、pytest suite、Playwright suite 於 M03-D 結束時皆綠。

### D.5 psycopg 相依可選

- `psycopg[binary]` 從 `pyproject.toml` 的無條件相依中移出，改放於 optional extra（例：`web` extra）。
- 網頁版 Docker image / Docker Compose / CI 網頁測試皆改為安裝 `.[web]` 或等價 extra。
- Standalone 打包環境不安裝 `web` extra，`psycopg` 不進 PyInstaller bundle。

## 本 Subphase 不要求

- 不引入 standalone launcher。
- 不修改任何角色 JSON 匯出／匯入邏輯。
- 不改變 Postgres migration 行為。

# M03-E — Standalone Packaging & Launcher

## 目標

用 PyInstaller 把單機版打包為可下載、離線執行的 Windows x64 產物；launcher 負責啟動 uvicorn、跑 alembic upgrade、開瀏覽器、顯示資料檔路徑、提供結束方式。同時建立 `/api/meta/capabilities` neutral endpoint、SPA fallback route、以及 `app.standalone` 對 `app.main` 的完全隔離。

## 完成後必須為真

### E.0 Minimal frozen smoke gate

**這條先於 E.7 的完整 spec 完成，是 M03-E 內部的順序要求。**

PyInstaller + Alembic + Uvicorn 這一疊的風險不在架構，而在**只有真的 freeze 成 exe 才知道漏了哪個 dynamic import / resource / 路徑**：`_MEIPASS` 下的 alembic `ScriptDirectory`、`uvicorn.Config("app.standalone:app", ...)` 的字串式 import、hiddenimports 缺漏，unit test 一個都測不到。若等 E.1～E.10 全部堆完才第一次 freeze，這些失敗會一次爆出且難以歸因到單一層。

因此必須先有一個**最小 frozen 產物**通過：

- 內容只需 launcher + alembic resources + `app.standalone`，不需要 `web/`、不需要 build 腳本、不需要 CI、不需要 `.zip`。
- 於乾淨資料夾雙擊（或 CLI 執行）該 exe，必須：
  1. 在 exe 同層建立 `adventure-table.sqlite3`；
  2. alembic upgrade 至 head 成功（`alembic_version` 等於當時 head revision）；
  3. `GET /api/meta/capabilities` 回 200 且 `channel="standalone"`；
  4. 全程 stdout 不含任何 PostgreSQL 連線嘗試或 psycopg 相關錯誤。
- 允許以 CLI 啟動代替雙擊；**不允許**以非 frozen 的 `python -m app.launcher` 代替——那正是本 gate 要抓的差異。
- 本 gate 通過前，不進行 E.7 完整 spec、E.8 build 腳本與 E.9 前端整合。
- 通過後，最小 spec 併入 E.7 的正式 spec，不保留兩份。

### E.1 Neutral shared modules

- 新增 `app/api/error_handlers.py`，提供 `register_exception_handlers(app: FastAPI)`；`app.main` 與 `app.standalone` 各自 import 並呼叫，互不依賴。
- 新增 `app/api/meta.py`，提供 **factory** `create_meta_router(channel: Literal["web", "standalone"]) -> APIRouter`。每次呼叫產生新的 `APIRouter` instance；**不使用 module-scope global router**，避免跨 entry import 時同一路由被註冊兩次、handler 取錯 channel。
- 新增 `app/api/spa.py`（或於 standalone 內定義），提供 SPA history fallback 的 catch-all route。Catch-all 必須**明確排除 `/api/` prefix**：未知 `/api/*` 保持 404，不 fallback 至 `index.html`。
- `app.standalone` **不得** import `app.main`；共用邏輯只走以上 neutral module。

### E.2 單機版 entry point

- 新增 `apps/server/app/standalone.py`，內含 `FastAPI(docs_url=None, redoc_url=None, openapi_url=None)`（disable API docs；朋友間出貨不需要 OpenAPI 頁面），只掛以下 router：
  - `reference_router`
  - `content_presentation_router`
  - `characters_router`
  - `character_builder_router`
  - `create_meta_router("standalone")` 產出的 router
- **不掛**任何未來 Room / Session / Seat / Combat / Timeline / AI Actor router。
- 呼叫 `register_exception_handlers(app)`。
- 掛前端 SPA 靜態檔（`StaticFiles`）於 `/assets/*` 等資源路徑。
- 掛 SPA history fallback：路徑不以 `/api/` 起頭 且對應 static file 不存在時，回應 `index.html`；路徑以 `/api/` 起頭則交回 FastAPI 預設 404，不 fallback。
- Startup **不呼叫** alembic upgrade（由 launcher 於 uvicorn 啟動前執行）。
- **啟動硬守衛**：app 組裝時檢查 `resolve_database_url()`，非 SQLite URL 即以明確錯誤中止，訊息含實際解析到的 URL 與該檢查哪個環境變數。單機版永遠不得對 PostgreSQL 發出連線嘗試。此守衛必須能在**不 freeze、不進 CI** 的情況下由 unit test 觸發。

### E.3 Capability endpoint

- `GET /api/meta/capabilities` 回傳：
  ```json
  {
    "channel": "web" | "standalone",
    "capabilities": {
      "character_builder": true,
      "character_import_export": true,
      "room": false,             // standalone 一律 false；web P2 之前也為 false，P2 之後由 web entry 覆寫為 true
      "campaign": false,
      "session": false,
      "seat": false,
      "combat": false,
      "timeline": false,
      "ai_actor": false
    }
  }
  ```
- 值由 entry point 於載入時決定：`app.main` 覆寫可支援的 capability；`app.standalone` 一律回上表。
- Endpoint 未來擴充 capability 時**只新增 key、不改變舊 key 語意**。

### E.4 Launcher

- 新增 `apps/server/app/launcher.py`（可執行入口，PyInstaller 打包 target）。
- 職責：
  1. **在任何其他動作之前**決定資料檔路徑（見 E.5）並寫入 `ADVENTURE_TABLE_DATABASE_PATH`（外部已設時尊重覆寫），接著驗證該路徑可建立、可寫入。此步驟必須早於 migration 與 app import；路徑決策不得依賴「呼叫者已設好環境變數」。
  2. 決定 content root（見 E.6），設定 `ADVENTURE_TABLE_CONTENT_ROOT`。
  3. **建立 Alembic Config 手動指向 bundle 內的 `alembic.ini`**（見 E.7 對 alembic resources 打包的要求），呼叫 `alembic.command.upgrade(config, "head")`。DB URL 透過 `resolve_database_url()` 取得（SQLite）；`PRAGMA foreign_keys=ON` 由 M03-D 的 hook 生效。失敗時以清楚錯誤訊息中止並保留 launcher stdout。
  4. 選擇一個空閒的 localhost port（從固定範圍例如 8000～8100 選第一個可用）。
  5. 啟動 uvicorn 載入 `app.standalone:app`。
  6. 等待 server ready，自動開啟預設瀏覽器至 `http://127.0.0.1:<port>/`。
  7. 在 launcher stdout / console window 顯示：資料檔絕對路徑、content root 絕對路徑、監聽 port、結束方式提示。
  8. Ctrl+C / 關閉 console 視窗時，收掉 uvicorn 子執行緒 / 子 process。
- **關閉瀏覽器分頁不會停 server**；這是刻意行為，不新增 shutdown/heartbeat 機制。README-standalone 明列。

### E.5 資料檔路徑

- 預設：**執行檔所在資料夾下**的 `adventure-table.sqlite3`（不是 `%LOCALAPPDATA%`，不是使用者家目錄）。非 frozen 直接跑 launcher（dev）時為 `<cwd>/adventure-table.sqlite3`。
- 可覆寫：`ADVENTURE_TABLE_DATABASE_PATH` 環境變數（絕對或相對路徑）。
- **解析順序為硬契約**：env → `settings.database_path` → frozen 時 `<exe_dir>/adventure-table.sqlite3` → launcher dev 執行時 `<cwd>/adventure-table.sqlite3`。**單機版任何情況下都不得 fallback 到 `settings.database_url`**（其預設為 PostgreSQL，且 bundle 刻意 exclude `psycopg`，落到該分支的症狀會是 driver 缺失堆疊而非可辨識的設定錯誤）。
- 覆寫路徑無效時（非法 / 無寫入權），launcher 以清楚錯誤中止並顯示解析出的路徑。
- 啟動時把最終解析的**絕對路徑**印在 stdout；不得印佔位字串。

### E.6 Content root / SPA root

- 沿用 M03-A 的解析順序；frozen mode 優先 `<exe_dir>/data`。
- SPA root 對應 resolver：`resolve_spa_root()`。順序**與 content root 一致**：`ADVENTURE_TABLE_SPA_ROOT` env var → `<exe_dir>/web` →（frozen fallback `_MEIPASS/web`）→ dev 時 `None`。env var 為第一順位覆寫。
- Build 腳本把 `data/` 與 `web/` 目錄整體放在**執行檔同層目錄**，PyInstaller bundle **不**內嵌第二份。
- Bundle 內的 `data/` / `web/` 若不存在 or 為空，是正常狀態；resolver 於 frozen mode 找不到 exe_dir 才 fallback `_MEIPASS`。
- 這消除「bundle 一份、exe_dir 一份」canonical root 歧義。

### E.7 PyInstaller spec

- 新增 `apps/server/pyinstaller/standalone.spec`。
- One-folder build（不是 one-file，冷啟動較快、抗防毒誤判較好）。
- Spec **不** 內嵌 `data/` 或 `web/` 為 `datas`；這兩個資料夾由 build 腳本複製到產物根目錄。
- Spec **必須** 內嵌 alembic resources 為 `datas`：`alembic/alembic.ini`、`alembic/env.py`、`alembic/script.py.mako`（若有）、`alembic/versions/*.py`。alembic 靠 `ScriptDirectory` 走檔案系統載入 migration，`hiddenimports` 沒辦法取代這條路徑。Launcher 據此建 `Config(str(_MEIPASS/'alembic'/'alembic.ini'))` 並 set `sqlalchemy.url = resolve_database_url()`。
- 產物根目錄結構：
  ```
  adventure-table-standalone/
    adventure-table.exe          # launcher
    _internal/                   # PyInstaller runtime（含 bundled alembic/ 資源）
    data/                        # content root（build 腳本複製）
    web/                         # 前端 SPA build（build 腳本複製）
    LICENSE.txt                  # 專案 license + SRD 5.1 attribution
    README-standalone.txt        # 資料檔位置 / 匯出入口 / 已知限制
  ```
- `hiddenimports` 明列 alembic migration module 名稱（動態 import 需要）與 pydantic 內建 codecs。
- `console=True`（保留 console window）。
- `excludes` 明列 `psycopg`。

### E.8 Build 腳本

- 新增 `scripts/build-standalone.cmd`（Windows；正式產物必於 Windows runner 產生）。
- 於 CI Windows runner 上呼叫。
- 腳本內容：
  1. 建立臨時 venv。
  2. 安裝 `apps/server` 主相依 + `standalone` extra；**不裝 `web` extra**。
  3. Build 前端（`npm ci` + `npm run build`）。
  4. 執行 PyInstaller spec 產出 `dist/adventure-table-standalone/`。
  5. 複製 `data/` → 產物 `data/`。
  6. 複製 `apps/web/dist/` → 產物 `web/`。
  7. 複製 `LICENSE.txt`、`README-standalone.<locale>.txt`。
  8. 打包為 `.zip`。
- 腳本冪等：可重複執行不留污染。
- 支援 `--version <tag>` 寫入 launcher 的 build id。

### E.9 前端 build 一致性

- Standalone entry 掛的前端 SPA build **與網頁版相同**（同一 `npm run build` 產物）。
- 不新增 feature flag、不新增 build-time 分支。
- 前端 SPA 於 boot 讀 `/api/meta/capabilities`；capability 為 `false` 的頁面 nav 入口不 render，使用者手打對應 URL 時 SPA 顯示 `capability_disabled` 頁面。

### E.10 啟動可觀察行為

- 雙擊 `adventure-table.exe` 到瀏覽器打開時間 < 10 秒（乾淨啟動、無防毒干預情況下）。
- Console window 保持開啟，顯示所有啟動訊息與後續 request log。
- Landing SPA 提示區顯示資料檔絕對路徑，讓使用者不看 console 也知道位置。

## 本 Subphase 不要求

- 不做 code signing。
- 不做 Windows installer（`.msi` / `.exe` installer）。
- 不做自動更新機制。
- 不隱藏 console window。
- 不建立 system tray icon。
- 不做 macOS / Linux build。
- 不做 shutdown/heartbeat（關閉分頁不停 server 是刻意的）。

# M03-G — Full M03 Integration & Closeout

## 目標

把 M03-A～M03-F 建立的所有 pieces 串成一次真實的 end-to-end 體驗，確認網頁版 → 單機版、單機版 → 網頁版、缺 pack 情境、Draft 補洞情境、legacy 角色拒絕情境都跑得通；並把 M03 的產品行為、已知限制與後續 P2 依賴的界線正式關門。

## 完成後必須為真

### G.1 End-to-end round trip

以下路徑至少完整跑過一輪並保留證據：

1. **W → S 完整**：網頁版建立一個 Lv5 Multiclass 角色（含 subclass 選擇、starting equipment、prepared spell、live inventory 有變動）→ 匯出 JSON → 於單機版匯入 → dry-run 全部解析（build + state）→ commit → Character Sheet 呈現與網頁版一致，Version History 完整。
2. **S → W 完整**：單機版建立一個 Lv3 角色 → 匯出 → 網頁版匯入 → 相同結果。
3. **W → S 缺 pack**：網頁版建立一個引用 `xge` 內容的角色 → 匯出 → 於一個 `enabled_content_packs` 未含 `xge` 的單機版設定匯入 → dry-run 顯示未解析數與 origin → landing_mode = draft → 使用者於 Builder 中改選 → Confirm 成為 Version 1。
4. **State-only 缺 ref**：Build 全部可解析、但 Current State 的 inventory 帶一個 pack subset 中缺失的 item → dry-run 顯示 `landing_mode=draft_with_history_loss`（因 state ref 未解析）→ 走 Draft 補洞。
5. **重複匯入偵測**：同一份 export 於同一台單機版匯入第二次 → dry-run 顯示 `duplicate_hint` → 使用者仍可繼續 → 兩個角色並存。
6. **Legacy character 缺 pack 拒絕**：一個 legacy 角色（`builder_provenance = NULL`）匯出 → 於缺對應 pack 的環境嘗試匯入 → 400 `draft_reconstruction_unavailable`；DB 無殘留。
