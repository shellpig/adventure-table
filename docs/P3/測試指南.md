# P3 — 測試指南

> Phase：**P3 — Exploration + Roll + AI**  
> 本文件定義 P3-A～P3-F 的自動／人工驗收與 closeout evidence。產品完成條件以 `實作規格.md` 為準；具體架構、schema、API、MCP與transaction contract以 `開發設計方針.md` 為準。

最後更新：2026-09-08

## 1. P3 Subphase 順序

三份 P3 文件固定使用：

```text
P3-A — Session Table Runtime & Event Stream
P3-B — Exploration, Chat & Actions
P3-C — Roll, Check & PendingAction
P3-D — AI Controller, Scoped Token & Handoff
P3-E — AI Tool Surface & Event Delivery
P3-F — Full P3 Integration & Closeout
```

每個 Subphase 的 code與對應tests同一小階段完成；先做focused local驗證與static review，review完成後才依 `AGENTS.md` gate使用GitHub Actions。不要把permission / secret filtering / restart / concurrency全部留到P3-F第一次驗。

## 2. P3 測試核心風險

P3最危險的regression包括：

- Player / AI Player收到DM-only或secret DC。
- Whisper DM被其他Seat讀到。
- 猜event sequence / UUID繞過audience filter。
- reconnect後pending roll消失或被重roll。
- retry造成同一formal RollRequest兩個結果。
- Character State已改但event沒commit，或反過來。
- P2 Human-only caller contract被複製到P3新service，AI永遠無法走正式授權。
- AI為通過P2函式被偽造成Human `RoomAccessContext` / Room authority。
- DM proxy被錯做成「切換Player Controller」，或audit只剩subject Player看不出真正acting DM。
- DM proxy走DM Direct Edit bypass而不是Player rules，導致可繞過資源／roll規則。
- `/search` 自動roll或自選Skill，違反DM裁定；`/check` 讓Player自行建立secret DC / formal result。
- Player Human → AI → Human後舊token還能操作。
- Temporary Handoff Instruction被寫進Character/Campaign永久資料，或Take Back後仍被下一個AI看到。
- Session End / Abandon後session-scoped AI token仍可read/wait/write。
- AI DM pre-session token未原子綁定Session，可被拿去操作其他Session。
- P2 controller binding CHECK沒有DB invariant綁grant/generation。
- event同步只靠process-local queue，server restart就斷歷史。
- `wait_for_event` 用sync long-poll佔滿worker或等待期間持有DB connection。
- Session頁為了即時更新高頻重抓P2 Resume，放大N+1。
- MCP adapter直接繞過Human UI共用service。
- MCP SDK仍用 2025-era `initialize` / `Mcp-Session-Id` path，卻被誤認為已驗 `2026-07-28`。
- MCP request 的 `MCP-Protocol-Version` / `_meta` / `Mcp-Method` / `Mcp-Name` 不一致，gateway與body看到不同operation。
- external MCP bearer token經 plain HTTP 離開 loopback，或選定client實際無法注入 static Authorization header，導致 external gate到最後才發現不能跑。
- P3 PostgreSQL job只設 `P3_POSTGRES_URL`，使既有 P2/M03 PostgreSQL tests因 env 缺失靜默 skip，形成假綠。
- workflow YAML被改壞但沒有 contract test釘住 workflow name / branch / env / explicit regression files。
- `app.mcp.*` 不在既有 M03 forbidden regex，Standalone protected import graph意外 reach MCP package卻仍綠。
- P3誤做半套 `resolve_action()`，提前形成P6/P7不完整contract。
- standalone因P3新module/table/MCP route被污染。
- P3 event log被誤當成P7完整Timeline，形成難以演進的contract。

P3 minimum gate：

```text
scope isolation
+ audience secrecy
+ durable ordered events
+ non-blocking event wait
+ acting-vs-subject audit
+ DM proxy permission/rules parity
+ slash command behavior
+ atomic gameplay writes
+ roll idempotency
+ typed Human/AI actor authorization
+ controller generation / session token scope / revocation
+ Temporary Handoff Instruction lifecycle
+ controller binding DB invariants
+ real PostgreSQL concurrency
+ no-silent-skip PostgreSQL regressions
+ workflow contract tests
+ real browser UX
+ modern MCP 2026-07-28 wire compliance
+ HTTPS/TLS real external MCP client
+ restart recovery
+ standalone independence including app.mcp
```

## 3. 執行環境與指令原則

### Backend

Windows / PowerShell 5.1 不使用 `&&`。需要 `alembic.ini` / relative path的Backend Python指令，cwd在 `apps/server`，interpreter使用repo root `.venv`。

```powershell
Set-Location .\apps\server
..\..\.venv\Scripts\python.exe -m pytest
```

Focused：

```powershell
Set-Location .\apps\server
..\..\.venv\Scripts\python.exe -m pytest tests\test_p3a_table_events.py -q
```

### PostgreSQL focused tests

P3建立自己的環境變數：

```text
P3_POSTGRES_URL
```

但 P3 CI **不能只設這一個名字**。既有 P2 PostgreSQL suites直接讀 `P2_POSTGRES_URL`，M03 migration suite讀 `M03C_POSTGRES_URL`（或 fallback P2）；若缺 env 它們會 skip。P3 `postgres-migrations` job必須把同一 dedicated test DB 同時提供為：

```text
DATABASE_URL=<dedicated test db>
P3_POSTGRES_URL=<same dedicated test db>
P2_POSTGRES_URL=<same dedicated test db>
M03C_POSTGRES_URL=<same dedicated test db>
```

本機要跑完整 P3 + legacy PostgreSQL regression時也比照設定：

```powershell
docker compose up -d db
docker compose exec -T db psql -U adventure -d postgres -c "DROP DATABASE IF EXISTS adventure_table_p3_test;"
docker compose exec -T db psql -U adventure -d postgres -c "CREATE DATABASE adventure_table_p3_test;"
Set-Location .\apps\server
$env:P3_POSTGRES_URL = "postgresql+psycopg://adventure:adventure@localhost:5432/adventure_table_p3_test"
$env:P2_POSTGRES_URL = $env:P3_POSTGRES_URL
$env:M03C_POSTGRES_URL = $env:P3_POSTGRES_URL
$env:DATABASE_URL = $env:P3_POSTGRES_URL
..\..\.venv\Scripts\python.exe -m pytest <P3 PostgreSQL focused tests + required P2/M03 PostgreSQL regressions> -q
```

不要drop開發中的真實資料庫。migration/concurrency證據不能由SQLite取代。Closeout必須能證明 required legacy PostgreSQL tests **實際執行而非 skip**。

### Frontend unit / build

```powershell
Set-Location .\apps\web
npm test -- --run
npm run build
```

### E2E

依既有 `KI-ENV-001`，完整Playwright走Docker/Linux web service。

P2-F已知限制：`test:e2e:docker`只rebuild web。P3在第一次新增backend-dependent E2E時必須把這個operational trap收斂掉：

- 優先修改script讓它一起build server；或
- 建立P3 wrapper command，明確build server + web後再跑。

不得讓P3 closeout evidence可能靜默測到舊backend image。

P3-F具名 workflow 固定為：

```text
.github/workflows/p3-e2e.yml
Display name: P3 Full-Stack E2E
```

至少支援 `workflow_dispatch`，在同一 run 中 clean full-stack、**rebuild server + web**、等 health/readiness、跑完整 P3 Playwright、failure印 logs、always upload Playwright report/test-results、always teardown。可以沿用 P2 workflow structure，但名稱與 artifact必須能區分 P3 evidence。

### MCP client smoke

P3-E起分兩層：

1. protocol-level automated client：對真 `/mcp` 驗 `2026-07-28` modern wire contract，不把 legacy initialize handshake當通過。
2. closeout external-client smoke：至少一個實際外部AI host/client經 **HTTPS/TLS** MCP URL連線 Adventure Table，且已驗證能設定 P3 static Bearer credential。

repo docker-compose 的 loopback plain HTTP可以作 automated protocol substrate，但不能算 external bearer closeout evidence。只call Python handler function或 custom mock client也不算正式MCP evidence。

- assert `name: P3 Non-E2E`。
- assert允許的 branch / `workflow_dispatch` policy；不得意外加入 pre-review `pull_request` auto-run，除非專案流程日後明確改變。
- assert PostgreSQL service與四個 URL env都存在。
- assert required P3 + P2 + M03 real-Postgres test files被明列。
- assert Windows standalone gate / build / smoke仍存在。

P3-F加入 `p3-e2e.yml` 時，同一 contract test（或獨立 P3 E2E contract test）再 assert：

- `name: P3 Full-Stack E2E`。
- `workflow_dispatch`。
- clean stack + full `docker compose ... --build`／等價 server+web rebuild。
- Playwright command、logs-on-failure、artifact upload、teardown。

Actions執行順序遵守使用者既定開發流程：該小階段code + tests完成 → static review完成 → 才跑non-E2E Actions。

- branch / exact code SHA。
- local commands與pass/fail/skip。
- Actions workflow + run id + exact SHA。

- P3 E2E workflow + run id + artifact。
- external MCP client名稱、版本、auth配置方式、HTTPS/TLS入口形態與測試日期。

- RollRequest status / visibility。

### Layer B — Persistence / migration

驗：

- P3 web-branch Alembic revisions。

- multi-browser Human DM + Players。

### Layer G — MCP protocol / external AI

Modern `2026-07-28` automated wire gate至少驗：

- `/mcp`只在web channel存在。
- request沒有 legacy `initialize` prerequisite；不使用 `Mcp-Session-Id`。
- `MCP-Protocol-Version: 2026-07-28` 與 body `_meta.io.modelcontextprotocol/protocolVersion`一致。
- 每個 request 有符合 body method 的 `Mcp-Method`；named operations有正確 `Mcp-Name`；缺失或 header/body mismatch被拒絕。
- `server/discover` 可成功，但後續合法 request **不依賴先 discover**；Server保持stateless protocol authorization。
- `server/discover`、`tools/list` 與其他規格定義的 cacheable result在 raw wire有 `ttlMs` / `cacheScope`。
- invalid / revoked / wrong-seat / wrong-session token被拒絕。
- tool schema與structured error。
- get context audience。
- wait cursor。
- Player AI context可得有效Temporary Instruction、失效後不可得。
- action / roll共用canonical state。
- `resolve_action` **不在 P3 tool catalog**。
- real external client經 HTTPS/TLS完成journey，且該client版本已實測可設定 static Bearer/header auth。

### Layer H — Standalone regression

驗：

- frozen build成功。
- SQLite無P3 tables。
- import graph無P3 modules。
- `app.mcp.*` 被 `test_m03_import_boundary.py` 明確視為 forbidden multiplayer dependency；新增 negative fixture要能證明 protected Character/Standalone import reach `app.mcp.tools`／等價 module 時測試會失敗。
- `/mcp` / P3 routes不存在或capability disabled。
- `ai_actor=false`；P3不得打開 `combat` / `timeline`。
- Character Create / Import / Sheet / Level Up / Export仍正常。

## P3-A — Session Table Runtime & Event Stream

### Automated gate

最低案例：

1. event seq由1起單調增加，同Session無duplicate。
2. 兩個transaction並發append，真PostgreSQL得到不同且連續／可排序seq。
3. public event所有合法participant可見。
4. DM_ONLY只current DM可見；Owner但不是current DM不可見。
5. ACTOR_AND_DM只有相關actor/subject controller + DM依contract可見。
6. SEAT_PRIVATE只recipient Seat + DM（依contract）。
7. Room A caller拿Room B Session id → not found/scope reject，不洩漏existence。
8. `after_seq`只回後續；limit/cursor正確。
9. duplicate idempotency key不產生第二event。
10. wait HTTP endpoint是 `async def`／等價非同步路徑；不得以sync endpoint + `sleep`/blocking loop佔住AnyIO worker。
11. wait timeout正常回empty，不報500。
12. wait進入idle狀態後沒有長期checked-out DB connection / active transaction；可用pool instrumentation、test hook或等價證據驗證。
13. 在受限DB pool / worker資源下同時建立16～32個或明顯高於pool容量的idle waiter，另一個一般DB-backed Session/event request必須在wait timeout前完成。
14. wait期間新增event會wake；即使故意miss process-local notify，DB cursor recheck仍能補到event。
15. client cancellation / timeout後waiter registration與資源回到baseline。
16. process restart後last seq / runtime revision保持。
17. Ended Session不接受新gameplay event write，但既有event可依history policy讀取。
18. initial Resume後增量event不用再call完整Resume；前端mock/spy或API contract證明。
19. P3-A修正／避開P2 Resume N+1後有query-count或repository batch test，避免heartbeat級別放大。
20. `recipient_seat_ids` 若在 SQL 直接做 JSONB/ARRAY membership，migration有對應 membership index且有 `EXPLAIN`／focused query-plan evidence；若採 bounded `(session_id, seq)` window後 application projection，測試必須證明 window有硬limit / query bound，而不是無界seq scan。
21. standalone schema / import boundary新增P3命名後仍綠。

### Static review checklist

- 是否有任何audience filter只在frontend。
- 是否用 `max(seq)+1` 無鎖配置seq。
- 是否process-local queue成為唯一truth。
- 是否P3 event payload複製整份Character snapshot。
- 是否event endpoint可以傳flag要求DM資料。
- private recipient query是否採無界JSON/array scan；若不用membership index，是否真的有 bounded seq window證據。
- wait endpoint是否仍是sync `def`。
- await notifier期間是否還持有DB dependency / ORM Session / transaction。
- 是否把整個30–60秒wait offload到sync worker thread。
- disconnect/cancellation是否真的cleanup。

### Subphase closeout evidence

- focused backend。
- PostgreSQL concurrent event test。
- private-recipient query/index strategy evidence。
- event wait async/no-DB-hold/starvation resource test。
- frontend cursor reducer tests。
- `P3 Non-E2E` exact SHA綠。
- P3 workflow contract test綠。
- standalone boundary綠。

## P3-C — Roll, Check & PendingAction

### Domain / backend cases

#### Normal formal roll

- DM request Investigation。
- target controller或current DM proxy roll。
- Server保存raw d20、modifier、total。
- request `pending -> resolved`。

#### Advantage / Disadvantage

- raw two d20皆保存。
- kept die由Server計。
- modifier來自canonical subject Character rules。

#### Group Check

- 一個RollGroup多requests。
- 每個Seat各自完成或由current DM proxy完成。
- group projection顯示Waiting/Rolled。
- 不自動宣稱fiction success/failure。

#### Secret Check

- Player能看到「需要擲」所需資訊。
- secret DC不在Player JSON。
- dm-only result不在Player JSON / event stream。
- DM projection完整。

#### Physical formal dice

- submit raw die成功。
- Server重算total。
- 只傳total被schema拒絕。

#### Quick Dice

- 可roll / log。
- pending formal request狀態完全不變。

#### Duplicate completion

同一RollRequest兩個並發completion：

- 一個結果commit。
- DB只有一個formal result。
- retry取得same result或stable conflict。
- 不得重新RNG。

### `/check` cases

1. Player `/check search the sigil`只建立Check intent /呈現給DM，不直接建立帶secret DC的formal result。
2. Player不能藉command自行指定「DC 1 therefore success」或把Quick Dice配對pending request。
3. current DM `/check` 走同一 `RequestCheckService` 可合法建立RollRequest。
4. `/check` 與Toolbar / Player Action上的Request Check最後進同一domain service。

### DM proxy roll cases

```text
RollRequest target=Mira
Mira controller offline/unresponsive
→ current DM proxy Roll
→ RNG/modifier使用Mira canonical Character rules
→ result acting=DM, subject=Mira
→ Mira controller unchanged
```

另驗：

- DM proxy physical roll提交raw die仍由Server計modifier。
- 非current DM不能proxy完成request。
- current DM不能用自己的Ability/Proficiency替代subject Character。

### PendingAction cases

- legal transition全覆蓋。
- illegal reverse transition拒絕。
- waiting_for_roll綁request。
- roll resolve後action可繼續resolve。
- cancel與resolve concurrency有真PostgreSQL證據。

### Character state atomicity / actor boundary

至少：

```text
Human Player self action
→ legal Character Current State change
→ table event

current DM proxy Player action
→ legal subject Character Current State change
→ event retains acting DM + subject
```

故障注入／transaction rollback證明不能只成功一半；proxy不改Controller。

### Real-backend journey C1

```text
Player Action: check the door
→ DM Request Check
→ Player sees pending request
→ current controller or DM proxy rolls
→ DM sees raw/result/DC
→ Player sees allowed result only
→ reload
→ request remains resolved, no second roll
```

### Static review checklist

- client能不能自填proficiency / total。
- AI/tool能不能直接提交「natural 20」當Server roll。
- formal roll有沒有unique result constraint。
- secret DC是否只是TypeScript optional但backend其實全回。
- DM proxy是否使用subject Character規則，而不是DM角色規則。
- Character write是否又直接呼叫只能吃Human `RoomAccessContext` 的P2入口。

### End/revoke atomicity

故障注入至少驗：

- revoke step失敗 → Session不能只留下ended/abandoned狀態。

- lease release / pending close失敗 → 不留下「token仍有效但Session半關閉」或相反狀態。

具體transaction順序可不同，但observable result必須all-or-nothing。

### Handoff concurrency

真PostgreSQL：

- two Let AI Control同時。
- Let AI Control vs Take Back。
- old token write transaction vs revoke。
- repeated Take Back idempotency / stable conflict。
- End/Abandon vs AI action/wait。
- duplicate AI DM Start / pre-session grant bind。

不得留下兩個active generation或grant跨Session重綁。

## P3-E — AI Tool Surface & Event Delivery

### Protocol automated tests

以真HTTP MCP endpoint，**pin `2026-07-28` modern era**；測項不是舊版 handshake negotiation：

1. Server接受合法 `2026-07-28` request，不要求先送 `initialize` / `notifications/initialized`；response/request flow不建立 `Mcp-Session-Id` correctness依賴。
2. `MCP-Protocol-Version: 2026-07-28` 與 request body `_meta.io.modelcontextprotocol/protocolVersion` 一致；缺失／不一致得到 protocol-level reject，不能silent fallback到legacy。
3. `Mcp-Method` 必須與 JSON-RPC method一致；`tools/call`、`resources/read`、`prompts/get` 等 named operation 的 `Mcp-Name` 必須與body name一致；缺失/mismatch reject。
4. `server/discover` 成功並提供 modern capability/cache metadata；但 client不先discover直接送合法 `tools/list` / `tools/call` 仍可工作，證明 discover不是handshake state。
5. `server/discover`、`tools/list`、`prompts/list`、`resources/list` / `resources/read` 中本專案實際支援的 cacheable response在 raw wire有規格要求的 `ttlMs` / `cacheScope`，值符合server policy；不能只看SDK已normalize後的object。
6. tools list穩定且只含P3正式工具。
7. no token / invalid / revoked / wrong-session token拒絕。
8. Player token呼DM-only tool得到structured permission error。
9. structured result schema可被client SDK解析。
10. `get_session_context` Player projection無secret，含有效Temporary Instruction（若有）。
11. Take Back / End後同token context call被拒絕，不可再讀instruction。
12. `post_action`後Human browser/event API看到同一canonical action。
13. Human DM Request Check後AI Player `get_pending_events`看到pending。
14. AI `roll_pending`完成後Human UI看到同一result。
15. `wait_for_event` timeout成功empty。
16. MCP wait使用P3-A同一async/no-DB-hold service；不得另包sync blocking wait。
17. wait中server無process-local history依賴；disconnect後cursor補回。
18. revoked token對所有tool由共同auth resolver拒絕。
19. standalone endpoint不可用。
20. **tool catalog不得包含 `resolve_action`**；若出現視為P3越界。

如果使用官方/第三方 SDK，另加 negative test或wire capture證明 SDK 已明確 opt in 到 `2026-07-28`，不是 SDK default legacy mode碰巧可call成功。

### Shared-service proof

至少用spy / dependency injection / architecture test證明：

- Web action route與MCP action tool呼同一application service。
- Web roll route與MCP roll tool呼同一Roll service。
- Human route與AI MCP最後都resolve成typed `TableActorContext`進同一permission layer。
- MCP module不得import persistence repository作direct mutation。
- AI DM細粒度 Narration / Request Check / Current State tool不得偷包成同名half `resolve_action()`。

### External MCP human gate E1

P3-E closeout必做一次真實external client，而且 remote URL必須是 **HTTPS/TLS**：

```text
0. Record external client name/version and prove it can configure static Bearer/header auth.
1. Expose Adventure Table /mcp through TLS tunnel / reverse proxy / HTTPS ingress.
2. Human Player Let AI Control + Temporary Instruction.
3. External MCP client connects to the HTTPS URL with the scoped AI Join Token.
4. get_session_context sees instruction.
5. Human DM在browser送Narration或Request Check。
6. AI wait/get pending event收到。
7. AI post_action。
8. AI完成formal roll。
9. Human browser看到同一action/result。
10. Take Back或End Session。
11. external client下一個call被拒絕。
```

Closeout記錄：client名稱、版本、static Bearer/header設定方式、HTTPS入口（tunnel/reverse proxy/正式ingress）、測試日期。**不得**用 plain HTTP docker-compose URL當 external gate；不得使用只為測試寫的自製 client來取代「真 external AI host/client」。若預定client無法安全設定 static token，P3-E在此 gate前就是 blocker，先調整client或auth design。

### AI DM gate E2

- DM context可見DM資料，Player secret不外洩。
- AI DM可Request Check / Narration。
- AI DM可用一般DM proxy path代理Player Seat時，acting/subject audit正確（若MCP surface暴露對應操作）。
