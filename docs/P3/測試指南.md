## 2. P3 測試核心風險

P3最危險的regression包括：

- Player / AI Player收到DM-only或secret DC。
- Whisper DM被其他Seat讀到。
- 猜event sequence / UUID繞過audience filter。
- reconnect後pending roll消失或被重roll。
- retry造成同一formal RollRequest兩個結果。
- Character State已改但event沒commit，或反過來。
- P2 Human-only caller contract被複製到P3新service，AI永遠無法走正式授權。
- AI為通過P2函式被偽造成Human `RoomAccessContext` / Room authority。
- DM proxy被錯做成「切換Player Controller」，或audit只剩subject Player看不出真正acting DM。
- DM proxy走DM Direct Edit bypass而不是Player rules，導致可繞過資源／roll規則。
- `/search` 自動roll或自選Skill，違反DM裁定；`/check` 讓Player自行建立secret DC / formal result。
- Player Human → AI → Human後舊token還能操作。
- Temporary Handoff Instruction被寫進Character/Campaign永久資料，或Take Back後仍被下一個AI看到。
- Session End / Abandon後session-scoped AI token仍可read/wait/write。
- AI DM pre-session token未原子綁定Session，可被拿去操作其他Session。
- P2 controller binding CHECK沒有DB invariant綁grant/generation。
- event同步只靠process-local queue，server restart就斷歷史。
- `wait_for_event` 用sync long-poll佔滿worker或等待期間持有DB connection。
- Session頁為了即時更新高頻重抓P2 Resume，放大N+1。
- MCP adapter直接繞過Human UI共用service。
- P3誤做半套 `resolve_action()`，提前形成P6/P7不完整contract。
- standalone因P3新module/table/MCP route被污染。
- P3 event log被誤當成P7完整Timeline，形成難以演進的contract。

P3 minimum gate：

```text
scope isolation
+ audience secrecy
+ durable ordered events
+ non-blocking event wait
+ acting-vs-subject audit
+ DM proxy permission/rules parity
+ slash command behavior
+ atomic gameplay writes
+ roll idempotency
+ typed Human/AI actor authorization
+ controller generation / session token scope / revocation
+ Temporary Handoff Instruction lifecycle
+ controller binding DB invariants
+ real PostgreSQL concurrency
+ real browser UX
+ real external MCP client
+ restart recovery
+ standalone independence
```

## 5. Test layers

### Layer A — Domain / pure policy

驗：

- event audience projection。
- `TableActorContext` Human / AI typed identity與role permission。
- `TableActionContext` acting actor / subject Seat / execution mode。
- current-DM policy可接受合法Human或AI actor，但Owner escape hatch不等於DM actor。
- current DM proxy任意合法Player Seat；非current DM不可proxy。
- DM proxy不改controller。
- PendingAction transition。
- RollRequest status / visibility。
- advantage / disadvantage / flat adjustment計算。
- controller generation + session scope validation。
- Temporary Handoff Instruction active/inactive lifecycle。

### Layer B — Persistence / migration

驗：

- P3 web-branch Alembic revisions。
- fresh PostgreSQL `upgrade heads`。
- P2 final DB → P3 heads upgrade。
- P3-D不修改歷史 `0013_p2d_campaign_seats.py` / `0014_p2e_sessions.py`。
- `ck_campaign_seats_controller_binding` / `ck_sessions_dm_controller_binding` / `ck_session_participants_controller_binding` 新revision正確drop + add。
- Human binding：access session有值、AI grant/generation皆NULL。
- AI binding：access session為NULL、grant/generation皆有值。
- None binding：兩種identity皆NULL。
- 缺grant / 缺generation / mixed binding由DB constraint拒絕。
- Session fixed DM AI grant/generation與Participant join snapshot restart後仍可還原。
- session-scoped grant有明確 `session_id` / 等價不可跨Session綁定。
- pre-session AI DM grant可在Start transaction綁定一次，不能重綁另一Session。
- Temporary Instruction持久於同一grant generation但不進Character/Campaign永久資料。
- standalone `character@head`完全無P3 tables。
- event seq unique / monotonic。
- message+event / roll+event atomicity。
- restart persistence。
- Room Hard Delete清P3 Room-scoped rows/assets。

### Layer C — API integration

驗：

- Session / Seat / Room path scope。
- audience filtering。
- Stage upload/read auth。
- Chat / Action / Whisper。
- DM proxy Dialogue / Action / Roll / Current State。
- `/action /check /search /whisper /ooc` parser/route行為。

- handoff / token revoke。
- Temporary Instruction讀取與失效。

- Human / AI caller都只透過共同actor resolver進gameplay service。

### Layer D — Concurrency / resource

真 PostgreSQL至少驗：

- concurrent event append不重seq。
- duplicate formal roll completion。
- roll resolve vs cancel。
- PendingAction resolve vs cancel。
- Player write vs DM proxy同一subject的競態走同一UoW/invariant。
- Human→AI與Take Back同時競態。
- two token rotations / two Let AI Control。
- old token write racing with revoke。

- Start Session AI DM grant bind vs duplicate Start/rebind。

- multiple idle event waiters不長期佔用DB connections；一般DB-backed request仍可完成。

## P3-A — Session Table Runtime & Event Stream

### Automated gate

最低案例：

1. event seq由1起單調增加，同Session無duplicate。
2. 兩個transaction並發append，真PostgreSQL得到不同且連續／可排序seq。
3. public event所有合法participant可見。
4. DM_ONLY只current DM可見；Owner但不是current DM不可見。
5. ACTOR_AND_DM只有相關actor/subject controller + DM依contract可見。
6. SEAT_PRIVATE只recipient Seat + DM（依contract）。
7. Room A caller拿Room B Session id → not found/scope reject，不洩漏existence。
8. `after_seq`只回後續；limit/cursor正確。
9. duplicate idempotency key不產生第二event。
10. wait HTTP endpoint是 `async def`／等價非同步路徑；不得以sync endpoint + `sleep`/blocking loop佔住AnyIO worker。
11. wait timeout正常回empty，不報500。
12. wait進入idle狀態後沒有長期checked-out DB connection / active transaction；可用pool instrumentation、test hook或等價證據驗證。
13. 在受限DB pool / worker資源下同時建立16～32個或明顯高於pool容量的idle waiter，另一個一般DB-backed Session/event request必須在wait timeout前完成。
14. wait期間新增event會wake；即使故意miss process-local notify，DB cursor recheck仍能補到event。
15. client cancellation / timeout後waiter registration與資源回到baseline。
16. process restart後last seq / runtime revision保持。
17. Ended Session不接受新gameplay event write，但既有event可依history policy讀取。
18. initial Resume後增量event不用再call完整Resume；前端mock/spy或API contract證明。
19. P3-A修正／避開P2 Resume N+1後有query-count或repository batch test，避免heartbeat級別放大。
20. standalone schema / import boundary新增P3命名後仍綠。

### Static review checklist

- 是否有任何audience filter只在frontend。
- 是否用 `max(seq)+1` 無鎖配置seq。
- 是否process-local queue成為唯一truth。
- 是否P3 event payload複製整份Character snapshot。
- 是否event endpoint可以傳flag要求DM資料。
- wait endpoint是否仍是sync `def`。
- await notifier期間是否還持有DB dependency / ORM Session / transaction。
- 是否把整個30–60秒wait offload到sync worker thread。
- disconnect/cancellation是否真的cleanup。

### Subphase closeout evidence

- focused backend。
- PostgreSQL concurrent event test。
- event wait async/no-DB-hold/starvation resource test。
- frontend cursor reducer tests。
- `P3 Non-E2E` exact SHA綠。
- standalone boundary綠。

## P3-C — Roll, Check & PendingAction

### Domain / backend cases

#### Normal formal roll

- DM request Investigation。
- target controller或current DM proxy roll。
- Server保存raw d20、modifier、total。
- request `pending -> resolved`。

#### Advantage / Disadvantage

- raw two d20皆保存。
- kept die由Server計。
- modifier來自canonical subject Character rules。

#### Group Check

- 一個RollGroup多requests。
- 每個Seat各自完成或由current DM proxy完成。
- group projection顯示Waiting/Rolled。
- 不自動宣稱fiction success/failure。

#### Secret Check

- Player能看到「需要擲」所需資訊。
- secret DC不在Player JSON。
- dm-only result不在Player JSON / event stream。
- DM projection完整。

#### Physical formal dice

- submit raw die成功。
- Server重算total。
- 只傳total被schema拒絕。

#### Quick Dice

- 可roll / log。
- pending formal request狀態完全不變。

#### Duplicate completion

同一RollRequest兩個並發completion：

- 一個結果commit。
- DB只有一個formal result。
- retry取得same result或stable conflict。
- 不得重新RNG。

### `/check` cases

1. Player `/check search the sigil`只建立Check intent /呈現給DM，不直接建立帶secret DC的formal result。
2. Player不能藉command自行指定「DC 1 therefore success」或把Quick Dice配對pending request。
3. current DM `/check` 走同一 `RequestCheckService` 可合法建立RollRequest。
4. `/check` 與Toolbar / Player Action上的Request Check最後進同一domain service。

### DM proxy roll cases

```text
RollRequest target=Mira
Mira controller offline/unresponsive
→ current DM proxy Roll
→ RNG/modifier使用Mira canonical Character rules
→ result acting=DM, subject=Mira
→ Mira controller unchanged
```

另驗：

- DM proxy physical roll提交raw die仍由Server計modifier。
- 非current DM不能proxy完成request。
- current DM不能用自己的Ability/Proficiency替代subject Character。

### PendingAction cases

- legal transition全覆蓋。
- illegal reverse transition拒絕。
- waiting_for_roll綁request。
- roll resolve後action可繼續resolve。
- cancel與resolve concurrency有真PostgreSQL證據。

### Character state atomicity / actor boundary

至少：

```text
Human Player self action
→ legal Character Current State change
→ table event

current DM proxy Player action
→ legal subject Character Current State change
→ event retains acting DM + subject
```

故障注入／transaction rollback證明不能只成功一半；proxy不改Controller。

### Real-backend journey C1

```text
Player Action: check the door
→ DM Request Check
→ Player sees pending request
→ current controller or DM proxy rolls
→ DM sees raw/result/DC
→ Player sees allowed result only
→ reload
→ request remains resolved, no second roll
```

### Static review checklist

- client能不能自填proficiency / total。
- AI/tool能不能直接提交「natural 20」當Server roll。
- formal roll有沒有unique result constraint。
- secret DC是否只是TypeScript optional但backend其實全回。
- DM proxy是否使用subject Character規則，而不是DM角色規則。
- Character write是否又直接呼叫只能吃Human `RoomAccessContext` 的P2入口。

## P3-D — AI Controller, Scoped Token & Handoff

### Migration / backward compatibility gate

1. P2 final Web DB → P3-D heads migration成功；既有Human Seat / Session / Participant rows仍合法。
2. 新revision對三條具名binding CHECK做drop + add，不修改 `0013` / `0014` 歷史migration。
3. Seat AI current binding必須同時有grant id + generation；只寫 `controller_kind='ai'` 但兩者NULL會被DB拒絕。
4. Session AI DM fixed snapshot必須有grant id + generation；Participant AI join snapshot同理。
5. Human row若混入AI grant/generation、AI row若混入Human access session、None row若帶任何identity都被DB拒絕。
6. restart / reload後fixed AI DM identity與participant snapshot不靠in-memory map還原。
7. session-bound grant不可重綁到另一Session。

### Existing P2 caller regression

改 `TableActorContext` / current-DM policy後，至少重跑並更新：

- `test_p2e_live_character_scope.py`。
- `test_p2e_session_lifecycle.py`。
- `test_p2e_late_join.py`。
- `test_p2e_session_api.py`。
- `test_p2e_persistence_contract.py` / controller persistence相關tests。
- P2-D Seat controller policy / persistence regressions。

Human DM Start / Late Join / End / Abandon、Human Player live Character write既有行為不得退化。

### Token security / scope cases

1. plaintext token只create/rotate response出現一次。
2. DB row / log不含plaintext。
3. random wrong secret拒絕。
4. Room/Campaign/Seat mismatch拒絕。
5. revoked generation拒絕。
6. wrong `session_id` / ended Session scope拒絕。
7. token不能取得Owner endpoint。
8. AI Player token不能取得DM tool/action。
9. AI token resolve後產生typed `TableActorContext`；不得產生假的Human access session / Room authority。

### Temporary Handoff Instruction cases

1. `Let AI Control` instruction省略成功（nullable）。
2. 有instruction時AI第一次context可取得原文。
3. server restart / AI reconnect後同一有效generation仍可取得。
4. instruction不出現在public event、其他Player context、Character JSON、Character Biography/Roleplay Guidance、Campaign permanent facts。
5. Take Back後舊AI token被拒絕，Human UI active instruction清除。
6. 下一次 Let AI Control不自動沿用舊instruction。
7. Session End / Abandon後instruction不再可由任何舊grant context取得。

### Player handoff journey D1

```text
Human controls Mira
→ Let AI Control with "Protect the wizard; save last 2nd-level slot"
→ token generated once
→ AI context contains instruction
→ AI acts as Mira
→ AI disconnect/reconnect
→ instruction still available
→ Take Back Control
→ Human can act again
→ old token rejected everywhere
→ instruction inactive
→ Mira id / state / active character unchanged except committed actions
```

### AI DM Start / lifecycle journey D2

```text
Owner creates active Campaign / DM Seat
→ Owner sets DM Seat AI
→ mint pre-session AI DM token (session_id=NULL)
→ AI auth/join
→ AI calls Session Start
→ Start transaction binds grant to new Session
→ fixed DM controller = that AI grant generation
→ AI authorizes Late Join
→ AI can End as fixed current DM
→ End atomically revokes all Session AI grants
→ same token cannot read/wait/write ended Session
→ same token cannot operate next Session
```

另驗：

- active Session時rotate DM grant被拒絕，避免暗中handoff。
- fixed AI DM可Abandon是「current DM actor」權限，不是Owner權限。
- Owner可Abandon不會讓Owner通過current-DM-only Stage / Request Check / End / Late Join / proxy path。
- AI DM disconnect/offline時Session stays active，grant不因presence timeout被自動revoke。

### Owner Abandon journey D3

```text
AI DM starts Session
→ one AI Player Seat also active
→ Owner Abandon via Human Owner escape hatch
→ Session abandoned
→ DM + Player session-scoped AI grants all revoked
→ old tokens read/wait/write rejected
→ Character Current State remains as committed
→ leases released
```

### End/revoke atomicity

故障注入至少驗：

- revoke step失敗 → Session不能只留下ended/abandoned狀態。
- final event失敗 → lifecycle transaction rollback。
- lease release / pending close失敗 → 不留下「token仍有效但Session半關閉」或相反狀態。

具體transaction順序可不同，但observable result必須all-or-nothing。

### Handoff concurrency

真PostgreSQL：

- two Let AI Control同時。
- Let AI Control vs Take Back。
- old token write transaction vs revoke。
- repeated Take Back idempotency / stable conflict。
- End/Abandon vs AI action/wait。
- duplicate AI DM Start / pre-session grant bind。

不得留下兩個active generation或grant跨Session重綁。

### Static review checklist

- 是否token plaintext入DB。
- 是否只驗token hash、不驗current generation / session scope。
- 是否AI DM因role=dm順便拿Room Owner service。
- 是否Human/AI controller id混用同一無type欄位。
- 是否為了相容P2而替AI偽造 `RoomAccessContext` / `RoomAccessAuthority`。
- `start_session` / `_is_current_dm` / `late_join` / `end_session` / current-DM `abandon` / live-character authorization是否真的全部進actor-aware policy。
- persistence `start_from_lobby` / late-join current-DM comparison是否仍硬性要求Human access session。
- pre-session AI DM grant是否只bind一次。
- End/Abandon是否只best-effort revoke而非同一UoW。
- Temporary Instruction是否污染Character/Campaign permanent state。

## P3-E — AI Tool Surface & Event Delivery

### Protocol automated tests

以真HTTP MCP endpoint：

1. supported MCP protocol negotiation / discovery成功。
2. tools list穩定且只含P3正式工具。
3. no token / invalid / revoked / wrong-session token拒絕。
4. Player token呼DM-only tool得到structured permission error。
5. structured result schema可被client SDK解析。
6. `get_session_context` Player projection無secret，含有效Temporary Instruction（若有）。
7. Take Back / End後同token context call被拒絕，不可再讀instruction。
8. `post_action`後Human browser/event API看到同一canonical action。
9. Human DM Request Check後AI Player `get_pending_events`看到pending。
10. AI `roll_pending`完成後Human UI看到同一result。
11. `wait_for_event` timeout成功empty。
12. MCP wait使用P3-A同一async/no-DB-hold service；不得另包sync blocking wait。
13. wait中server無process-local history依賴；disconnect後cursor補回。
14. revoked token對所有tool由共同auth resolver拒絕。
15. standalone endpoint不可用。
16. **tool catalog不得包含 `resolve_action`**；若出現視為P3越界。

### Shared-service proof

至少用spy / dependency injection / architecture test證明：

- Web action route與MCP action tool呼同一application service。
- Web roll route與MCP roll tool呼同一Roll service。
- Human route與AI MCP最後都resolve成typed `TableActorContext`進同一permission layer。
- MCP module不得import persistence repository作direct mutation。
- AI DM細粒度 Narration / Request Check / Current State tool不得偷包成同名half `resolve_action()`。

### External MCP human gate E1

P3-E closeout必做一次真實external client：

```text
1. Human Player Let AI Control + Temporary Instruction.
2. 外部MCP client連Adventure Table。
3. get_session_context sees instruction.
4. Human DM在browser送Narration或Request Check。
5. AI wait/get pending event收到。
6. AI post_action。
7. AI完成formal roll。
8. Human browser看到同一action/result。
9. Take Back或End Session。
10. 外部client下一個call被拒絕。
```

可用ChatGPT / Claude / Codex或其他支援正式MCP protocol的真實host；closeout記錄client名稱與測試日期。不要求特定廠牌。

### AI DM gate E2

- DM context可見DM資料，Player secret不外洩。
- AI DM可Request Check / Narration。
- AI DM可用一般DM proxy path代理Player Seat時，acting/subject audit正確（若MCP surface暴露對應操作）。
- AI DM不能Room Hard Delete / rotate Owner credentials。
- AI DM不能修改Player Character Build。
- AI DM沒有 `resolve_action()`；P3 closeout不得把多個細粒度tool包裝後宣稱P6能力已完成。

## 6. Static review gate before final Actions

P3-F跑最終Actions前，static review至少逐項回答：

1. Human / MCP是否存在兩套permission/rules。
2. Human / AI是否真的以typed actor identity進同一gameplay authorization，而非AI偽造Human access context。
3. acting actor與subject Seat是否被混成一個identity；DM proxy audit是否完整。
4. DM proxy是否誤改Seat Controller或繞過Player rules成Direct Edit。
5. 五個slash command是否都有owner；`/search`是否偷自動roll、`/check`是否繞過DM。
6. P2 Session lifecycle / live Character scope有哪些簽名被actor abstraction改動，對應P2 regression是否同步更新。
7. P2三條controller binding CHECK是否由新migration正確演進，歷史0013/0014是否保持不變。
8. AI grant綁Session的時機是否明確；pre-session DM grant是否只能bind一次。
9. End/Abandon是否原子revoke全部session-scoped AI grants，而非best effort cleanup。
10. Temporary Instruction是否只存在handoff lifecycle、失效後不可讀、不污染Character/Campaign資料。
11. DM-only / private資料是否任何endpoint先全量回傳。
12. token secret是否可能進log、DB、exception。
13. current controller generation / session scope是否每個AI request都重驗。
14. formal roll能否duplicate commit。
15. Character State + event是否atomic。
16. event seq是否DB-safe。
17. event wait是否async；等待期間是否零長期DB checkout / sync worker hold；並發waiter是否會starve一般request。
18. Session Resume是否被高頻poll。
