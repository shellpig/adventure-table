## 2. 開工時真實 codebase 與永久依賴方向

P3 開工時多人核心已存在於 `app.domain.rooms` / `app.persistence.rooms` / `app.api.rooms` 一帶，重要既有契約包括：

- `SessionService` / Session lifecycle。
- `SessionResumeService`。
- Campaign / Seat / controller / participant snapshot。
- `active_character_session_leases`。
- active Session期間 Character / Builder write scope。
- `build_capabilities()` 與 frontend `protectedCapabilityForPath()`。

P3 的依賴方向固定：

```text
Human Web UI ─┐
              ├─> P3 application/domain services ─> P2 Session / Character services
MCP Adapter ──┘

Persistence <─ application/domain services

Character Core ─X→ P3 multiplayer runtime
Standalone    ─X→ P3 multiplayer runtime
MCP Adapter   ─X→ raw repository mutation
```

最重要的架構原則：

> **Human UI 與 AI Tool 只是在入口不同；permission、roll、event、state mutation必須共用同一層 application/domain service。**

不得建立 `ai_*` 版本的 roll engine、character-state updater或secret filter。

### 2.1 P2 caller identity 的真實限制

P2 雖然 schema 已接受 `controller_kind='ai'` 這個 enum shape，但目前真正能進 Session gameplay authorization 的 caller 是 **Human-only**。開工時必須把這個事實視為正式 migration 前提，而不是假設 AI 只要有 token 就能沿用現有入口：

- `apps/server/app/api/rooms/session_scope.py::require_live_character_write()` 接受 `RoomAccessContext`，依 `access_session_id` 判斷，Player path並且明確要求 `player_controller_kind == "human"`。
- `apps/server/app/domain/rooms/sessions.py::SessionService._is_current_dm()` 明確要求 `dm_controller_kind == "human"` + Human `RoomAccessAuthority`。
- `SessionService.start_session()` / persistence `start_from_lobby()` 傳遞並查驗 `caller_access_session_id` + `caller_authority`。
- `late_join` persistence同樣以 Human access session識別 current DM。

因此 P3 的新 service **不得再把 `RoomAccessContext` 當桌內 actor 的永久 abstraction**。Human Room authority仍保留，但 gameplay caller要收斂成後述 `TableActorContext`。P3-C 可先只交付 Human controller的實際 journey；P3-C 新 service本身不能 hardcode Human-only identity，P3-D 才把 AI grant resolver正式接上同一層。

## 4. Alembic 與 persistence track

P3 全部 multiplayer schema都落在 P2 建立的 **`web` Alembic branch**。

```text
character@head
  └─ shared Character migrations only

web@head
  └─ P2 Room/Campaign/Seat/Session
      └─ P3 table runtime / events / rolls / AI grants
```

規則不變：

- Web upgrade：`alembic upgrade heads`。
- Standalone：只 `character@head`。
- P3 Web revision可以 `depends_on` 新的 Character revision，但 Character branch永遠不能依賴 Web revision。
- 禁止 merge Character / Web Alembic heads。
- **不得回頭修改已存在的 `0013_p2d_campaign_seats.py` / `0014_p2e_sessions.py`。** P3 對 P2 controller binding 的演進必須放在新的 web revision，用具名 constraint drop + add完成可升級 migration。

P3 migration tests要在真 PostgreSQL驗 fresh + P2 legacy upgrade，不能只有 SQLite `metadata.create_all`。

## 5. P3-A — Session Table Runtime & Event Stream

### 5.1 canonical tables

P3-A 建議新增最小兩個核心 persistence concept：

```text
session_table_runtime
session_events
```

`session_table_runtime` 一場 Session最多一列：

```text
session_id                PK/FK -> sessions
revision                  bigint, monotonic
last_event_seq            bigint, monotonic
created_at
updated_at
```

不要先塞 Stage / Roll / AI全部欄位；各 Subphase的 canonical table各自持有真實資料。`session_table_runtime`只提供共用 revision / cursor coordination。

`session_events` 是 **P3 transport/event substrate，不是 P7 Timeline UI model**：

```text
id                        UUID PK
session_id                FK
seq                       bigint
kind                      stable string / enum
actor_seat_id             nullable FK
actor_character_id        nullable FK
visibility                enum
recipient_seat_ids        JSON/array, default []
payload                   JSON object
created_at
idempotency_key           nullable
```

DB constraint：

```text
UNIQUE(session_id, seq)
UNIQUE(session_id, idempotency_key) WHERE idempotency_key IS NOT NULL
```

sequence配置必須是 transaction-safe。可用 runtime row `SELECT ... FOR UPDATE` increment，或 PostgreSQL-compatible等價做法；不能 `max(seq)+1` 無鎖計算。

### 5.2 event payload規則

Event payload只放**該 event重播／呈現需要的 immutable fact**，不複製整份 Character / Session snapshot。

例如：

```json
{
  "kind": "chat.character",
  "message_id": "...",
  "text": "I check the door."
}
```

而不是把整隻 Character Sheet塞進每個 event。

P3 event payload從第一天就要有 schema/version discipline：

- `kind` stable。
- payload decoder default-deny unknown required field形狀。
- additive欄位可以向後相容。
- 不把 localized display text當 canonical business data。

### 5.3 audience model

P3 event visibility固定由 Server產生 caller projection。最低 enum：

```text
public
DM_ONLY
ACTOR_AND_DM
SEAT_PRIVATE
```

`SEAT_PRIVATE` 可帶 `recipient_seat_ids`。讀取時規則：

- public：Session合法 participant / current DM可讀。
- DM_ONLY：只有 fixed current DM Controller。
- ACTOR_AND_DM：actor Seat controller + current DM。
- SEAT_PRIVATE：指定 Seat controller + current DM（若產品行為要求）。

不得讓 caller query傳 `include_dm_only=true` 自己選 audience。

### 5.4 event query / wait API

Human Web 與 MCP共用 application service：

```text
TableEventService.current_cursor(session_id, caller)
TableEventService.list_after(session_id, caller, after_seq, limit)
TableEventService.wait_after(session_id, caller, after_seq, timeout)
```

HTTP建議：

```text
GET /api/rooms/{roomId}/campaigns/{campaignId}/sessions/{sessionId}/events?after=<seq>&limit=<n>
GET /api/rooms/{roomId}/campaigns/{campaignId}/sessions/{sessionId}/events/wait?after=<seq>&timeout=<seconds>
```

`wait` 的 correctness contract不是單純「可以 long-poll」；現有 Web backend 主要是同步 SQLAlchemy / sync FastAPI route，因此 **wait HTTP endpoint 必須是 `async def`／等價非同步 request path，且等待期間不得持有 SQLAlchemy connection、ORM Session、transaction或把整段 timeout佔在 sync worker thread裡。**

固定 lifecycle：

```text
async wait request
→ 短 DB read：authorize + read cursor / immediate events
→ 關閉 DB connection / transaction
→ await process-local notifier / AnyIO-asyncio primitive
→ wake / timeout / cancellation
→ 短 DB re-read：list_after(cursor)
→ response
```

若 repository仍是 sync SQLAlchemy，短 DB 操作可用既有 dependency / thread offload執行；**只能 offload短 query，不能把 30–60 秒等待本身丟進 threadpool**。

Durability以DB為真，不可只靠 process-local queue。Process-local notifier只降低 latency；任何 lost wakeup、process restart或多 worker miss都必須能靠DB cursor補回。

Resource invariant：

- idle waiter數量增加時，DB pool checkout數不應跟 waiter一比一長期增加。
- idle waiter不得長期佔有 AnyIO sync worker。
- client disconnect / cancellation / timeout要能釋放 waiter registration。
- 一般 DB-backed Session / event request在多個 idle waiter存在時仍可完成，不得等到 wait timeout後才獲得資源。

P3 不需要 WebSocket 作為 correctness requirement。未來可換 transport，但 domain event cursor contract不變。

### 5.5 Resume integration

P2 `SessionResumeService`保留「組合 canonical truth」原則。P3擴充時建議建立：

```text
SessionTableResumeDTO
```

由既有 Resume + P3 current runtime projection組成，而不是把 P2 DTO變成第二份 persistence snapshot。

初次載入至少回：

- P2 active session / participant / active character summary。
- P3 current stage projection（P3-B後）。
- pending action / roll summary（P3-C後）。
- caller-visible event cursor與最近必要 event。

P2已知 N+1問題在 P3-A 必須處理：

- active character summary batch load；或
- 只在初次進頁取得，incremental feed不重抓；
- heartbeat不能觸發完整 Session Resume N+1。

### 5.6 End / Abandon

Session End / Abandon：

- 停止接受新的 gameplay write。
- 保留已 commit P3 tables / events。
- release P2 active character lease照原 contract。
- 不 reset Character Current State。
- pending item若產品上不能再完成，server在 transition transaction中標記 cancelled/closed，但**不能刪歷史 row**。

## 6. P3-B — Exploration, Chat & Actions

### 6.1 canonical message / stage tables

建議新增：

```text
session_messages
session_stage_state
room_stage_assets
```

`session_messages` canonical欄位：

```text
id
session_id
actor_seat_id nullable
actor_character_id nullable
kind = character_dialogue | narration | action | ooc | whisper_dm
text
visibility
created_at
```

Message insert與對應 `session_events` append必須同 transaction commit；不能出現DB有訊息但event沒送，或event出現但message row不存在。

`session_stage_state`：

```text
session_id PK
text nullable
image_asset_id nullable
revision
updated_by_seat_id
updated_at
```

Stage更新採 optimistic revision / compare-and-swap或等價 stale-write guard，避免DM兩個browser tab後送的舊內容蓋掉新內容而無提示。

### 6.2 最小 Stage asset

P3沒有 Asset Library，所以圖片 persistence刻意簡單。建議 `room_stage_assets`：

```text
id
room_id
mime_type
byte_size
sha256
content BYTEA
created_by_controller_ref
created_at
```

私人朋友使用、P3只支援 Stage image時，DB `BYTEA`可換取最簡單的一致 transaction / backup / Room Hard Delete語意；若實作時已有正式 blob storage abstraction，可沿用，但不可因此建立完整 Asset domain。

最低限制由設計鎖定並測試，例如：

- allowlist：PNG / JPEG / WebP。
- 最大單檔：10 MiB。
- server以 magic bytes / decoder驗證，不信任 client MIME alone。
- 不接受 SVG / HTML 作P3 Stage upload，避免 script / active content風險。

圖片讀取 endpoint本身也要 Room authorization，不得因URL可猜而public。

### 6.3 exploration permission

`TableActionService`使用 P3 共用 caller context：

```text
TableActorContext
  actor_kind = human | ai

  human identity:
    access_session_id

  ai identity:
    ai_controller_grant_id
    controller_generation

  resolved common truth:
    room_id
    campaign_id
    session_id
    seat_id
    role
    active_character_id nullable
```

Human adapter可額外保有 `RoomAccessAuthority` 供 Room-management endpoint使用；**該 authority不是 AI actor欄位，也不能為了讓AI DM通過既有函式而偽造。**

所有 Human / AI exploration action都先通過同一 context resolver / permission layer。

權限：

- current DM Controller：Narration、Stage set/clear、一般public message、Whisper回覆。
- Player controller：自己Seat的Character Dialogue / Action / OOC / Whisper DM。
- Spectator：P3預設read-only；若未來要chat另開產品決策，不在P3默默放寬。
- Owner / DM Key holder但不是current DM Controller：不能靠Room authority改active table gameplay state。

### 6.4 Web UI

Session page在P3-B後變成桌面shell：

```text
┌─────────────────────────────────────────────┐
│ Player Cards                                │
├──────────────────────────────┬──────────────┤
│ MAIN STAGE                   │ Chat         │
│ image/text                   │ Dice (P3-C)  │
│                              │ Log          │
├──────────────────────────────┴──────────────┤
│ Exploration Input / Quick Action Bar        │
└─────────────────────────────────────────────┘
```

Main Stage與右側panel divider可調整；layout preference只需client preference，不進game state。

Stage與Chat必須語意分離：

- Stage = current world presentation。
- Chat = dialogue / narration / action stream。

Slash command只在frontend/parser把輸入轉成同一typed API request，不建立第二種endpoint。

## 7. P3-C — Roll, Check & PendingAction

### 7.1 tables

建議新增：

```text
roll_groups
roll_requests
roll_results
pending_actions
action_windows            # optional but若實作就依本節
```

`roll_groups`：一個DM request / group check的集合。

`roll_requests`最低欄位：

```text
id
session_id
roll_group_id nullable
target_seat_id
target_character_id nullable
request_type
ability_ref nullable
skill_ref nullable
dc nullable
modifier_mode = normal | advantage | disadvantage
flat_adjustment
visibility
status = pending | resolved | cancelled
requested_by_seat_id
created_at
resolved_at nullable
version
```

`dc` 是 secret-bearing field；API projection依caller決定是否輸出，不是frontend `display:none`。

`roll_results`：

```text
id
roll_request_id nullable   # quick dice為null
session_id
roller_seat_id
source = server | physical | quick
formula
raw_dice
kept_dice
base_modifier
flat_adjustment
total
visibility
created_at
```

formal request加唯一 constraint：一個 `roll_request_id` 最多一個 committed result。

### 7.2 RNG

Server formal roll使用 Python `secrets.SystemRandom` / OS CSPRNG或等價不可預測來源，不使用client `Math.random()`。

Roll engine輸出完整 audit shape：

```text
raw dice
adv/disadv kept die
derived modifier
explicit ±N
total
```

規則資料從 Character / Rules canonical data計算；API client不能傳「我的 proficiency bonus=99」覆蓋 Server derivation。

### 7.3 physical formal roll

Physical dice submit endpoint只接受：

- pending `roll_request_id`；
- raw die value(s)；
- 必要時明示由哪顆被保留可由Server根據adv/disadv自行計算；

Server重新計 modifier / total。Client不得只提交 final total。

### 7.4 idempotency / concurrency

Formal roll completion最危險的是 retry後多roll一次。所有 completion request必須有：

- request row lock / atomic compare `pending -> resolved`；
- optional idempotency key；
- unique `roll_request_id` result。

Race結果：只有一個commit成功；後來者取得既有resolved result或stable conflict，不能產生第二結果。

### 7.5 PendingAction

`pending_actions`：

```text
id
session_id
actor_seat_id
actor_character_id nullable
text / typed intent payload
status
roll_request_id nullable
window_id nullable
version
created_at
updated_at
```

transition至少：

```text
pending -> processing
pending/processing -> waiting_for_roll
waiting_for_roll -> processing/resolved
pending/processing/waiting_for_roll -> cancelled
processing -> resolved
```

非法逆轉用stable error code，不靠UI禁止。

若實作 `ActionWindow`：

- 只是一次「大家現在要做什麼」的collection container。
- 不生成exploration turn order。
- DM可close window並自行決定fiction order。

### 7.6 Character state mutation

P3不建立第二套 Character write API。正式table action若要扣HP / 改Temp HP / condition / resource：

```text
TableActionService
→ resolve TableActorContext
→ actor-aware live-character authorization adapter
→ existing Character State mutation service
→ append table event in same transaction boundary if persistence layer permits
```

P3-C closeout實際只需要 Human controller path，但這層 service / UoW從建立時就必須接受 typed actor context，不能直接要求 `RoomAccessContext.access_session_id`。P3-D 會把既有 P2 `live_character_write_scope()` / `require_live_character_write()` 的 Human-only入口演進成 actor-aware authorization，再讓AI grant走同一條路。

如果既有 Character service與P3 repository不能自然共用同一DB transaction，P3-C必須明確建立application unit-of-work；不能接受「先改HP，第二個request再寫log」的best effort雙步驟。

這個 atomic commit boundary不是P7完整 `GameTransaction` product；P7之後可以把它一般化。

## 8. P3-D — AI Controller, Scoped Token & Handoff

### 8.1 TableActorContext 與既有授權入口 migration

P2 existing Seat / Session controller identity需演進為可明確區分：

```text
none
human(access_session_id)
ai(ai_controller_grant_id, generation)
```

P3 gameplay caller的正式 application context：

```text
TableActorContext
  actor_kind = human | ai

  human:
    access_session_id

  ai:
    ai_controller_grant_id
    generation

  resolved:
    room_id
    campaign_id
    session_id
    seat_id
    role
    active_character_id nullable
```

`RoomAccessAuthority`仍屬 Human Room-management context；AI DM的DM能力來自被Owner事前配置的 DM Seat + valid grant，不得建立假的 `authority='dm'/'owner'` 來騙過P2函式。

P3-D 必須把以下既有入口改成接受／resolve typed actor，而不是只在MCP adapter旁路：

- `apps/server/app/api/rooms/session_scope.py::require_live_character_write()` 與包住它的 live Character write scope。
- `apps/server/app/domain/rooms/sessions.py::SessionService.start_session()`。
- `SessionService._is_current_dm()`／等價 current-DM policy。
- `SessionService.late_join()`。
- `SessionService.end_session()`。
- `SessionService.abandon_session()` 的 **current DM controller分支**；Owner escape hatch仍走 Human Room Owner authority。
- persistence `start_from_lobby()`。
- persistence `late_join_from_lobby()`／任何 current-DM access-session comparison。

不得用「AI token驗過，所以隨便找一個 Human access session id代入」的相容層。

既有 P2 Human 行為必須保持向後相容；P3-D 改 caller abstraction時同步更新/保留 P2 regression，至少涵蓋 live character scope、Session Start/End/Abandon、Late Join、API authorization與controller persistence。

### 8.2 controller persistence / P2 CHECK constraint migration

P2 schema 已把 Human access-session binding與 `controller_kind` 分欄，但目前三個 binding CHECK 的語意都是：Human必須有 access session；AI / None只能是 access session NULL。這只能表示「kind是AI」，**不能表示究竟是哪個grant / generation控制**。

P3-D 在新的 web Alembic revision新增 AI binding columns，最低包含：

```text
campaign_seats
  ai_controller_grant_id nullable
  controller_generation nullable

sessions
  dm_controller_ai_grant_id nullable
  dm_controller_generation nullable

session_participants
  controller_ai_grant_id_at_join nullable
  controller_generation_at_join nullable
```

命名可依實作 convention微調，但語意不能缺。Session欄位是 fixed DM controller snapshot；Participant欄位是 join-time controller snapshot；Seat欄位是 current controller binding。

新的 migration **不得修改 `0013_p2d_campaign_seats.py` / `0014_p2e_sessions.py` 歷史檔**，而是對下列既有具名 constraint做 drop + add：

```text
ck_campaign_seats_controller_binding
ck_sessions_dm_controller_binding
ck_session_participants_controller_binding
```

新的 CHECK 語意固定：

```text
human:
  human access_session_id IS NOT NULL
  ai grant id IS NULL
  ai generation IS NULL

ai:
  human access_session_id IS NULL
  ai grant id IS NOT NULL
  ai generation IS NOT NULL

none:
  human access_session_id IS NULL
  ai grant id IS NULL
  ai generation IS NULL
```

既有 `controller_kind IN ('human','ai','none')` 類 enum constraint保留。

P3-D persistence / migration tests至少要證明：P2 final DB可升級、既有Human rows保持有效、AI row若缺 grant/generation會被DB拒絕、None row若偷帶binding也被拒絕、Session/Participant snapshot可在reload/restart後還原 fixed identity。

### 8.3 AI controller grant model

建議新增：

```text
ai_controller_grants
```

最低欄位：

```text
id
room_id
campaign_id
seat_id
role
secret_hash
secret_prefix / display hint
generation
status = active | revoked
created_at
revoked_at nullable
last_seen_at nullable
```

Token plaintext只在create/rotate response返回一次。Persistence不可存plaintext。

Seat current binding、Session fixed DM snapshot與Participant join snapshot都 reference grant identity + generation；不要用 `controller_id` 同欄位混塞 Human access session UUID與AI token hash。

### 8.4 token format

採至少128 bits entropy的opaque bearer secret，例如：

```text
at_ai_<public-id>_<random-secret>
```

Server用public id定位grant，再constant-time驗hash。不要讓整張 `ai_controller_grants` 做全表hash scan。

Room / Campaign / Seat / role全部從grant row取得，不相信tool request自行宣稱。

### 8.5 Player Human → AI / AI → Human

`Let AI Control` transaction：

1. lock Seat controller row / equivalent。
2. verify caller是目前Human controller。
3. verify active Session participant / Active Character仍一致。
4. ensure沒有不可安全切換的in-flight commit；已commit transaction不回滾。
5. revoke previous AI generation（若有）。
6. mint new grant + increment generation。
7. switch Seat controller to AI grant。
8. append controller-changed event（audience依產品需求；至少DM與該Seat可知）。
9. commit。

`Take Back Control`：

- 由該Seat原Human access session /合法Human controller發起。
- lock同一controller state。
- revoke AI grant / generation。
- switch回Human。
- commit後舊token任何request都得到stable `ai_token_revoked` / `controller_changed` 類error。

Authorization每次request都驗目前generation，不能只驗token本身未過期。

### 8.6 AI DM Start / Session lifecycle

P2的「Owner事前assign Human DM Controller」需在P3-D做**向後相容擴充**，不是破壞：

Human DM path仍成立；新增AI path：

```text
Owner configures DM Seat as AI
→ create scoped AI DM grant
→ external AI authenticates / joins
→ AI DM calls Start Session
→ Session snapshots ai_controller_grant_id + generation as fixed DM Controller
```

Start policy共同條件：

- DM Seat assignment必須由Owner事前完成。
- caller必須就是被assign的controller identity。
- Human DM仍需其既有Room authority條件；AI DM不取得Owner key，但grant明確有DM gameplay scope。
- Start後DM controller identity immutable。

AI DM token rotate / replace只允許**Session尚未開始**。Active Session期間不能用rotate達成DM handoff。

`End Session`由 fixed current DM actor執行，因此 Human DM / AI DM都可依同一 policy End。

`Abandon Session`維持兩條合法路徑：

```text
fixed current DM actor (human or ai)
OR
Human Room Owner escape hatch
```

AI DM不因為能Abandon就取得Owner authority；Owner也不因為能Abandon就成為current DM。

Late Join同樣由 fixed current DM actor授權，不能再硬綁 Human access session id。

### 8.7 connection / presence

AI Connection與controller ownership分開。

AI request / wait event成功可更新 `last_seen_at`，但：

- `last_seen_at`過期只代表Offline。
- 不revoke token。
- 不End Session。
- 不把DM controller改成None。

P3不假設Server可主動喚醒外部AI conversation。

## 9. P3-E — AI Tool Surface & Event Delivery

### 9.1 protocol baseline

P3 remote MCP以 **MCP specification `2026-07-28`** 為設計基準。該版已把protocol core改成stateless request/response，Streamable HTTP每個request自我描述；這正好符合Adventure Table「authorization不能依賴transport session」的需求。

官方參考：

```text
https://modelcontextprotocol.io/
https://blog.modelcontextprotocol.io/posts/2026-07-28/
```

實作可使用當時Tier-1官方SDK的Python或TS server adapter，但核心P3 service不可被某個SDK type污染。

### 9.2 MCP endpoint

建議：

```text
POST /mcp
```

或由framework要求的等價Streamable HTTP entry。

MCP request authentication在HTTP boundary完成：

```text
Authorization: Bearer <AI Join Token>
```

這是Adventure Table私人MVP的app-level scoped credential；P3不因此建立完整OAuth account system。

每個request：

```text
Bearer token
→ resolve AIControllerGrant
→ verify active generation / Seat scope
→ build TableActorContext
→ call shared application service
```

不得把上一個MCP request的scope留在global / thread-local再沿用。

### 9.3 tool naming

Tool應該是高階table action，不是CRUD table mapping。最低集合可採：

```text
get_session_context
get_character_context
post_dialogue
post_action
post_ooc
whisper_dm
set_stage_text              # DM only; image可先要求existing asset id
request_check               # DM only
roll_pending
submit_physical_roll
quick_roll
update_character_state      # policy-controlled Current State action
get_pending_events
wait_for_event
```

Tool name可依SDK convention微調，但P3-E closeout要能完成相同能力。

禁止：

```text
execute_sql
get_table_row
patch_character_json
set_roll_total
read_dm_only_as_player
impersonate_seat
```

### 9.4 structured response

所有tool回：

```json
{
  "ok": true,
  "data": {...},
  "cursor": 42
}
```

或SDK等價structured content。

Error至少：

```json
{
  "ok": false,
  "error": {
    "code": "roll_request_already_resolved",
    "message_key": "...",
    "details": {...safe fields...}
  }
}
```

AI control flow判斷 `code`，不是解析localized `message`。

### 9.5 get_session_context

回 caller projection，不是整個DB dump：

Player AI：

- Session identity。
- current Stage public projection。
- public recent events。
- own Seat / Active Character summary + allowed Current State。
- own pending requests/actions。
- other Player必要public card summary。

AI DM：

- DM-visible table state。
- all public / DM-only pending check info。
- participant summaries。

P6前沒有Adventure Runtime，所以P3-E不得假裝提供完整world/NPC knowledge。

### 9.6 event wait

`wait_for_event(timeout)` wrapper只呼叫P3-A `TableEventService.wait_after`。

- request帶last cursor。
- timeout建議上限30–60秒，避免無界resource hold。
- timeout回 `events=[]` + same/new cursor，屬成功。
- process restart / transport disconnect後client改呼 `get_pending_events(after_cursor)`補洞。
- **MCP adapter不得另寫 sync sleep / blocking repository loop；實際 HTTP wait一律沿用 §5.4 的 async/no-DB-hold lifecycle。**

Modern MCP本身是stateless；P3 gameplay durability全由Adventure Table DB / cursor承擔，不依賴MCP protocol session。

### 9.7 Site Tools / future agent

P3只需要一條production-like MCP真正可用。未來Site Tools或persistent API agent：

```text
new transport adapter
→ same TableActorContext resolver
→ same application services
```

不得複製rules / permission。

## 12. Transaction boundary / Unit of Work

P3從「單資料CRUD」進入「一次桌上行動同時改多個canonical object + event」，必須正式有application transaction boundary。

至少以下必須 atomic：

- message row + event append。
- Stage state update + event append。
- roll request resolve + result + event append + pending action transition。
- Character Current State mutation + corresponding gameplay event。
- controller handoff + token revoke/mint + controller changed event。
- Session End / Abandon + pending close + final event + P2 lease release。

可以使用現有SQLAlchemy Session / repository UoW；不要求在P3命名成完整 `GameTransaction` persistence entity。

禁止 application service內先commit一次、再呼另一service第二次commit來模擬atomic。

## 13. Security boundary

P3新增三種特別高風險資料：secret roll、private chat、AI bearer token。

永久規則：

1. audience filter在Server projection。
2. token plaintext不落DB / log。
3. request logging對 `Authorization` header做redaction。
4. MCP tool args若含私密文字，不在exception telemetry全文輸出。
5. Stage upload檔案驗magic bytes、大小、allowlist。
6. cross-Room / Seat / Session scope每個write/read都從canonical relation重驗，不相信client path ids彼此一致。
7. AI DM沒有Owner destructive endpoint；即使知道Room id也不能靠MCP碰Room Hard Delete / key rotation。
8. AI Player看不到其他Player whisper / dm-only result。
9. revoked / stale generation token在所有tool共用auth resolver被拒絕，不逐tool手寫。
10. Human / AI actor不得共用一個無type的controller UUID欄位或用偽造Human access-session完成AI authorization。

## 14. Performance / polling

P3桌面開始有高頻同步，不能沿用P2「每heartbeat抓完整Resume」作遊戲event transport。

最低要求：

- 初始Resume一次。
- 後續cursor增量。
- message / event query有合理limit與index `(session_id, seq)`。
- pending roll / action current projection可batch query。
- `SessionResumeService` Active Character summary避免per-character full load的N+1。
- Lobby heartbeat與Session event feed分離。
- event wait等待期間零長期DB checkout；waiter數量不能直接消耗DB pool容量。
- event wait不得把整段timeout佔住sync worker thread；短sync DB query與async等待要分離。

P3不要求Redis / Kafka / websocket broker。朋友桌規模下 PostgreSQL + process-local wake notification + DB truth即可；但correctness不能依賴單process memory。
