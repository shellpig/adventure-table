# M06 — 實作規格

> Phase：**M06 — AI Long-Session Hosting Efficiency**
> 類型：**M Phase（Modification / Maintenance Phase）**
> 插入時點：**P6 關門並合併回 `main` 之後、P5-A 開工之前。** 三個 Subphase 各自關門；M06-C 關門後進 P5-A。
> 本文件定義 **M06-A～M06-C 每個 Subphase 完成後什麼必須為真**。具體 module、DTO、migration 與接線放在 `開發設計方針.md`；自動與人工驗收方式放在 `測試指南.md`。

最後更新：2026-09-25

## 1. M06 定位

2026-09-24～25 P6-G G4 期間，網頁版 AI agent（ChatGPT Web、Claude 網頁版）以 MCP 擔任 AI DM 連續主持多場 Session。Claude 在主持後回饋、指揮者核對程式後確認三件事：

1. **自己的寫入會把 `wait_for_event` 提早喚醒。** `TableEventService.wait_after` 只要 cursor 之後有任何可見事件就返回，不分是誰寫的。AI DM 每次 `world_update_entry`、`set_stage_text`、`post_narration`、`request_check` 之後，`wait_for_event` 立刻帶回自己剛寫的 echo 事件，但寫入工具的回傳早已包含完整結果。每次都多一趟 round-trip，並把沒有新資訊的內容塞進 AI context；長時間主持時成本持續累積。
2. **`wait_for_event` 的實際等待上限與契約不符。** M04-C 把 `WaitEventsInput.timeout` 上限改為 120 秒（M04-A 實測值），AI 指引也寫「每次最多 120 秒、連續 5 次約 10 分鐘」；但 `wait_after` 內部仍把 timeout 截到 60 秒。AI 實際約 5 分鐘無事件就停止，比指引承諾的短一半。
3. **`roll.resolved` 對 AI 的 payload 偏大。** AI 判斷需要的是總值、天然骰與（DM 才有的）DC 與成敗；`raw_dice`、`base_modifier`、`flat_adjustment`、`source` 等每筆都送，長時間累積佔 context。

`規格企劃.md`「AI Event / Reconnect」要求 AI 能以 `get_pending_events()`／`wait_for_event(timeout)` 持續參與並在重連後重建狀態。M06 維持這個結構：**即時等待走精簡路徑，補帳路徑保留完整事件**。

M06 不做的事：

- 不改 durable event 的儲存內容與人類 UI 看到的事件；精簡只發生在 MCP `wait_for_event` 的回傳。
- 不改 `get_pending_events`、`get_session_context` 的內容；重連、新對話、換 controller 時仍能完整補帳。
- 不改 P3-D 授權模型、可見性與秘密過濾；DC 仍只給 DM。
- 不改 briefing 的長度上限（`BRIEFING_MAX_CHARS`）；新說明放 tool description 與 guide。
- 不新增網站端 LLM 呼叫、不新增 AI 專屬 authority bypass。
- 不動 `app.standalone`、`app.content.*`、`app.domain.character*`。

M06 順序：

```text
P6 closeout → main
→ M06-A — wait_for_event Timeout Cap Alignment
→ M06-B — Own-Write Echo Suppression in wait_for_event
→ M06-C — Compact Roll Result Projection for MCP wait
→ P5-A
```

## 2. M06 共通硬原則

### 2.1 cursor 永遠前進，不漏 seq

被精簡或略過的事件，其 seq 仍計入回傳的 `cursor`。AI 只要照 cursor 往前，就不會重複收到、也不會卡在被略過的事件上。

### 2.2 「自己」以 controller 身分判斷，不只看 Seat

同一個 DM Seat 可能換 controller（Take Back、換另一個 AI、新 grant generation）。只有**寫入當下的 AI grant 與 generation 都等於目前呼叫者**的事件才算「自己的寫入」；Seat 相同但 controller 不同的事件照常送達。

### 2.3 只略過純 echo

只有「寫入工具回傳已包含完整結果」的事件種類可以被略過。會觸發系統後續狀態、或結果由其他 actor 決定的事件（Combat 事件、擲骰結果、pending action、controller 變更）一律照送。

### 2.4 補帳路徑完整

`get_pending_events` 永遠回傳完整、未精簡的可見事件。AI 重連、開新對話或懷疑漏資訊時，以它補帳。

### 2.5 秘密靠 Server 過濾

精簡投影在既有可見性與 Combat 敵方投影之後才套用，不得因精簡而多送任何欄位；DC 與成敗只進 DM 投影。

### 2.6 雙語同步交付

tool description、guide 等 AI 會讀到的新文字，`en`／`zh-TW` 同步交付。

# M06-A — wait_for_event Timeout Cap Alignment

## 目標

MCP `wait_for_event` 的實際等待上限與契約、指引一致。

## 完成後必須為真

### A.1 MCP 等待可達 120 秒

AI 以 `timeout=120` 呼叫 `wait_for_event` 且期間沒有新事件時，server 實際等待約 120 秒才回傳空頁，不再在 60 秒時提早返回。

### A.2 上限只有一個來源

MCP 等待上限只由 `WAIT_EVENT_MAX_TIMEOUT_SECONDS` 決定；輸入驗證、service 截斷與 guide／briefing 顯示的數字一致。

### A.3 人類 long-poll 不變

Human UI 的 `/events/wait` 仍維持自己的 60 秒上限與既有行為。

## 本 Subphase 不要求

- 不改「連續 5 次無事件就停」的指引規則。
- 不改預設 timeout。

# M06-B — Own-Write Echo Suppression in wait_for_event

## 目標

`wait_for_event` 預設不因呼叫者自己的純 echo 寫入而醒來或回傳它們，但 cursor 照常前進；補帳路徑不受影響。

## 完成後必須為真

### B.1 自己的 echo 不喚醒

AI 以某 grant／generation 寫入白名單種類的事件後呼叫 `wait_for_event`：若之後只有這些自己的 echo，wait 繼續等待直到出現其他可見事件或 timeout；回傳的 `cursor` 已越過這些 echo。

### B.2 其他人的事件照常喚醒

Player（真人或 AI）的 dialogue／action、擲骰結果、Combat 事件、以及同 Seat 但不同 controller 寫入的事件，都照常喚醒並回傳。

### B.3 非白名單事件照送

即使是自己觸發，Combat 事件、`roll.resolved`、pending action、controller 變更等非白名單種類照常回傳。

### B.4 可以要求完整

AI 以 `include_own=true` 呼叫 `wait_for_event` 時，行為與 M06 前相同（自己的 echo 照常喚醒與回傳）。

### B.5 補帳路徑與人類 UI 不變

`get_pending_events`、`get_session_context`、Human UI 的 event list／long-poll／Resume 回傳與 M06 前相同，包含自己的寫入。

### B.6 身分判斷跨 controller 正確

同一 Seat 由另一個 grant 或新 generation 接手後，前一任 controller 寫入的事件對新 controller 不算「自己」；真人寫入的事件對任何 AI 都不算「自己」。

### B.7 AI 會讀到的說明

`wait_for_event` 的 tool description 與 guide（`en`／`zh-TW`）說明：預設略過自己的 echo、cursor 仍前進、需要完整事件時用 `include_own=true` 或 `get_pending_events`，重連或新對話先以 `get_session_context`／`get_pending_events` 補帳。

## 本 Subphase 不要求

- 不精簡事件 payload（M06-C）。
- 不回填既有事件的 controller 身分；M06-B 之前寫入的事件一律不算「自己」。
- 不把白名單擴到 Combat 或 P5 Tactical 事件；後續 Phase 需要時，另以同一機制加入並補測試。

# M06-C — Compact Roll Result Projection for MCP wait

## 目標

MCP `wait_for_event` 回傳的 `roll.resolved` 改用精簡投影，保留 AI 判斷需要的欄位；DM 多拿到 DC 與成敗。

## 完成後必須為真

### C.1 精簡欄位

`wait_for_event` 回傳的 `roll.resolved` payload 只含：`roll_request_id`、`total`、`formula`、`natural`（單顆 d20 保留骰的點數，其他情況為 null）、`visibility`。不含 `raw_dice`、`kept_dice`、`base_modifier`、`flat_adjustment`、`source`。

### C.2 DM 投影

目前 DM 另外拿到 `dc` 與 `outcome`（有 DC 時為 `success`／`failure`，`auto_fail` 為 `failure`；無 DC 時為 null）。

### C.3 Player 投影

Player（真人或 AI）的精簡投影不含 `dc` 與 `outcome`。

### C.4 天然骰判斷不失真

優勢／劣勢、天然 20、天然 1 的判斷結果與完整 payload 一致。

### C.5 其他路徑不變

`get_pending_events`、Human UI 與 durable event 內容與 M06 前相同；精簡與 `include_own` 無關，`wait_for_event` 一律使用精簡投影。Combat 內擲骰的既有敵方投影規則照舊先套用。

## 本 Subphase 不要求

- 不精簡其他事件種類。
- 不改變擲骰或成敗的計算規則。

## 4. 與既有契約的關係

- **M04**：`wait_for_event` 的 120 秒上限沿用 M04-A 實測與 M04-C 契約；M06-A 修的是 M04-C 漏改的 service 截斷。
- **P3-A／P3-D**：durable event、cursor、可見性與 controller epoch 為單一事實來源；M06 只在 MCP 回傳端加過濾與投影。
- **P4／P5**：Combat 事件不列入 M06-B 白名單；P5 Tactical 事件同樣照送，除非 P5 以同一機制明確加入並補測試。
- **P6**：`world.*` echo 列入白名單；世界狀態的補帳仍由 `get_session_context`／`get_campaign_context` 提供。
