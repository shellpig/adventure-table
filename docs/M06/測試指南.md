# M06 — 測試指南

> Phase：**M06 — AI Long-Session Hosting Efficiency**
> 本文件定義 **M06-A～M06-C 每個 Subphase 的自動／人工驗收流程與測試證據要求**。驗收意圖見 `實作規格.md`；實作契約見 `開發設計方針.md`。

最後更新：2026-09-25

---

## 1. 測試總則

- **每條驗收契約都要有可定位的測試證據。** 每項 `X.n` 對應至少一條 pytest，closeout 列出檔名與 test 名稱。
- **P3-A／P3-D／P4／M04／P6 既有測試是回歸底線且不改斷言。** 特別是 `tests/test_p3a_*.py`（cursor／可見性）、`tests/test_p3e_*.py`（MCP 協定與 token lifecycle）、`tests/test_m04b_wait_timeout_cap.py`、`tests/test_p6*_mcp_*.py`。若既有測試需要改才綠，視為設計偏離，回頭修實作；唯一例外是 M06-C 明確改變的 `wait_for_event` 回傳中 `roll.resolved` payload，若既有測試鎖了其完整欄位，改斷言並在 closeout 列出。
- **Human 路徑零改變。** 每個 Subphase 都要有一條以 Human actor 打 `/events`、`/events/wait` 的測試，斷言回傳與 M06 前相同（含自己的寫入、完整 roll payload）。
- **秘密過濾是自動測試。** DC、`outcome`、敵方精確 HP 不得出現在 Player 的 `wait_for_event` 回傳。
- **雙語同步驗收。** tool description 與 guide 新句子以 pytest 斷言 `en`／`zh-TW` 都存在。
- **Standalone 邊界**：`tests/test_m03_import_boundary.py`、`tests/test_m03d_schema_parity.py` 三個 Subphase 都必須通過。
- 等待類測試用可控時鐘或縮短的 timeout，不讓全套 pytest 因實際等待 120 秒而變慢；A.1 以注入的 `max_timeout` 與 fake notifier 證明截斷值，不做真 120 秒 sleep。

### 1.1 M06 的 E2E 範圍對照

| Subphase | diff 性質 | Subphase 關門要跑的 E2E |
|---|---|---|
| **M06-A** | backend-only（service 截斷） | 無；AGENTS backend-only 規則 |
| **M06-B** | backend＋web track migration；MCP 輸入新增欄位；不動 `apps/web`、不動送給前端的 DTO | `p3e-mcp-browser-integration.spec.ts`（MCP journey 與 Human UI 共存） |
| **M06-C** | backend-only（MCP 回傳投影） | `p3e-mcp-browser-integration.spec.ts` |

M06-C 關門即 M06 全 Phase 關門；合併回 `main` 前依 AGENTS 跑全套 Docker E2E（`npm run test:e2e:docker`）。

## 2. 共通測試資料與觀察值

### 2.1 Fixture

- 沿用 P3-D／P3-E 的 AI DM pre-session grant → Start 建立 **AI DM active Session**，另有一個 Player Seat（真人 access session）與一個 AI Player Seat（另一 grant）。
- **換 controller fixture**：同一 DM Seat 先由 grant G1 寫入，再 Take Back 並發新 grant G2（generation 前進）。
- **舊事件 fixture**：以 migration 前格式（兩個新欄位為 NULL）寫入的事件列。
- **擲骰 fixture**：有 DC 的 skill check（成功與失敗各一）、`auto_fail` 檢定、無 DC 檢定、優勢（`2d20kh1`）與劣勢（`2d20kl1`）各一、天然 20 與天然 1 各一、Combat 內 Monster 攻擊擲骰一筆。

### 2.2 觀察值

- `cursor` 單調前進；被略過的 seq 不再出現在後續 `wait_for_event`。
- `get_pending_events(after_seq=x)` 回傳的事件集合 ⊇ 同範圍 `wait_for_event` 回傳的事件集合。
- `TableEvent` 序列化結果不含 `acting_ai_controller_grant_id`、`acting_grant_generation`。

# M06-A — wait_for_event Timeout Cap Alignment

測試檔：`tests/test_m06a_wait_timeout_cap.py`。

## A.1 MCP 等待可達上限

以 fake notifier 記錄 `wait(handle, timeout)` 收到的值：MCP `wait_for_event(timeout=120)` 傳入 120；`timeout=90` 傳入 90。

## A.2 上限只有一個來源

- `WaitEventsInput` 的 `timeout` 上限、`ai_guidance.WAIT_TIMEOUT_SECONDS`、`AIToolApplicationService` 傳給 `wait_after` 的 `max_timeout` 都等於 `WAIT_EVENT_MAX_TIMEOUT_SECONDS`。
- guide 與 briefing 顯示的秒數等於該常數。

## A.3 人類 long-poll 不變

Human `/events/wait?timeout=60` 以 fake notifier 觀察為 60；`timeout=61` 仍被 Query 驗證拒絕（422）。

## A.4 回歸

`test_m04b_wait_timeout_cap.py`、`test_m04c_briefing.py`、`test_m04c_mcp_guide.py`、`test_p3e_*.py` 全綠且不改斷言；backend 全套 pytest。

# M06-B — Own-Write Echo Suppression in wait_for_event

測試檔：`tests/test_m06b_own_echo_suppression.py`（含 migration 蓋章與 service 行為）。

## B.1 自己的 echo 不喚醒

AI DM 依序 `set_stage_text`、`post_narration`、`world_create_entry`、`world_set_current_context`、非戰鬥 `request_check`，接著 `wait_for_event(after_seq=寫入前 cursor, timeout=短)`：回傳 `events == []`、`cursor` 等於最後一筆 echo 的 seq。之後 Player 發一句 dialogue，再 wait：只回傳該 dialogue。

## B.2 其他人的事件照常喚醒

真人 Player dialogue、AI Player（另一 grant）dialogue、Player 擲出的 `roll.resolved` 都會喚醒 AI DM 的 wait 並回傳。

## B.3 非白名單事件照送

AI DM 自己開始 Quick Combat、推進回合：`combat.*` 事件與戰鬥中的 `roll.requested` 照常回傳。

## B.4 可以要求完整

同 B.1 流程改 `include_own=true`：回傳全部 echo，內容與 M06 前相同。

## B.5 補帳路徑與人類 UI 不變

同一範圍 `get_pending_events` 回傳全部 echo；Human `/events`、`/events/wait` 回傳包含 AI DM 寫入的事件。

## B.6 身分判斷跨 controller 正確

- 換 controller fixture：G1 寫入的 echo 對 G2 的 wait 照常回傳。
- 真人 DM 寫入的事件對任何 AI 都照常回傳。
- 舊事件 fixture（欄位 NULL）一律照常回傳。
- 蓋章欄位：AI 經 binding 寫入的事件列帶正確 grant／generation；真人與系統事件為 NULL。

## B.7 白名單前提

對 `OWN_ECHO_EVENT_KINDS` 每個由 MCP tool 產生的種類，參數化斷言：寫入工具回傳內容包含事件 payload 的全部鍵值資訊（id、revision、文字等）。新增白名單種類時必須加一列。

## B.8 AI 會讀到的說明

`wait_for_event` tool description 與 guide 的 `en`／`zh-TW` 都含「略過自己的寫入」「cursor 前進」「`include_own`」「`get_pending_events` 補帳」對應句。

## B.9 秘密與 DTO

- Player 的 wait 不因 M06-B 多拿到任何 `dm_only` 或 `seat_private` 事件。
- `TableEvent` JSON 不含兩個新欄位（REST 與 MCP 都測）。

## B.10 Migration 與回歸

- `alembic upgrade heads` 與 downgrade 一步可逆；真 PostgreSQL（`P4_POSTGRES_URL`）下 upgrade 後既有事件可讀。
- `test_m03_import_boundary.py`、`test_m03d_schema_parity.py`；backend 全套 pytest；E2E 見 1.1。

# M06-C — Compact Roll Result Projection for MCP wait

測試檔：`tests/test_m06c_compact_roll_projection.py`。

## C.1 精簡欄位

AI DM 與 AI Player 的 `wait_for_event` 收到的 `roll.resolved` 只含規格列出的鍵；不含 `raw_dice`、`kept_dice`、`base_modifier`、`flat_adjustment`、`source`。

## C.2 DM 投影

擲骰 fixture：有 DC 成功→`outcome=success`；失敗→`failure`；`auto_fail`→`failure`；無 DC→`dc=None`、`outcome=None`。`dc` 等於 roll request 的 DC。

## C.3 Player 投影

同一批擲骰，AI Player 的 wait 回傳不含 `dc` 與 `outcome` 鍵。

## C.4 天然骰判斷不失真

`1d20`、`2d20kh1`、`2d20kl1` 的 `natural` 等於完整 payload `kept_dice[0]`；天然 20／1 正確；非 d20 公式與敵方投影已隱藏骰值時 `natural is None`。

## C.5 其他路徑不變

- 同範圍 `get_pending_events` 的 `roll.resolved` payload 與 M06 前完整相同。
- Human `/events` 的 payload 完整。
- Combat 內 Monster 擲骰：Player 視角先套敵方投影，精簡後不多出任何欄位。
- 一頁多筆 `roll.resolved` 只觸發一次 roll request 查詢（以 repository spy 斷言）。

## C.6 回歸

`test_p3e_*.py`、`test_p4e_*.py`（MCP 戰鬥）、`test_p6*_mcp_*.py`；backend 全套 pytest；E2E 見 1.1。
