> Phase：**P2 — Room / Campaign / Session / Seat**  
> 本文件定義 P2-A～P2-F 的自動／人工驗收與 closeout evidence。產品完成條件以 `實作規格.md` 為準；具體架構與 migration / API contract以 `開發設計方針.md` 為準。

最後更新：2026-09-06

## 1. P2 Subphase 順序

三份 P2 文件固定使用：

```text
P2-A — Room Foundation & Web Entry
P2-B — Room Character Workspace
P2-C — Campaign & Party Roster
P2-D — Seat, Controller & Lobby
P2-E — Session Lifecycle & Late Join
P2-F — Full P2 Integration & Closeout
```

每個 Subphase 的測試新增要跟該段 code一起完成；不要把「Room scope / permission / migration」全部留到 P2-F才第一次驗。

---

## 2. P2 測試核心原則

P2 從單機 Character 系統進入多人 namespace，最危險的 regression不只是功能壞掉，而是：

- Room A 能摸到 Room B 資料。
- Web global endpoint繞過 Room scope。
- standalone因 shared code被多人 domain污染。
- standalone SQLite跑到 Web migrations。
- Character / Draft成功建立但 Room association失敗，留下 orphan。
- Campaign偷偷複製 Character State，兩份狀態開始 diverge。
- 同 Character被兩個 active Session同時使用。
- Session End意外 heal / reset Character State。
- Owner / DM Key / Seat Role / current DM Controller混成一種權限。
- Alembic Character / Web branches未來因 dependency merge而把 standalone拖進 multiplayer ancestry。

因此 P2 的 minimum gate不是「頁面打得開」，而是：

```text
Scope isolation
+ persistence atomicity
+ migration correctness
+ concurrency invariant
+ controller authority
+ standalone independence
+ real-backend UX
```

## 3. 執行環境與指令原則

### Backend

Windows / PowerShell 下不要使用 `&&` 串 command。Backend Python 指令若依賴 `alembic.ini` / relative path，cwd在 `apps/server`，interpreter使用 repo root `.venv`。

例如從 repo root：

```powershell
Set-Location .\apps\server
..\..\.venv\Scripts\python.exe -m pytest
```

Focused test同理：

```powershell
Set-Location .\apps\server
..\..\.venv\Scripts\python.exe -m pytest tests\test_p2a_rooms.py -q
```

### Frontend unit / build

```powershell
Set-Location .\apps\web
npm test -- --run
npm run build
```

### E2E

依 `KI-ENV-001`，完整 Playwright一律走 Docker/Linux web service：

```powershell
Set-Location .\apps\web

```

不要在 Windows 上改用 Playwright-managed Vite來「暫時過測試」。

### Actions

GitHub Actions只代表其 workflow實際覆蓋的 gate；不得因 M03 standalone workflow綠燈就宣稱 P2 backend / web / permission / E2E全綠。

每個 closeout要記錄：

- exact commit SHA。
- local / CI command。
- pass / fail / skip數。
- intentional skip對應已知問題。

## 4. Test layers

### Layer A — Domain / pure policy

驗：

- RoomAccessAuthority。
- Campaign status / Roster status transition。
- Seat role / Controller validation。
- Session Active Character freeze。
- eligibility（active/inactive vs retired/dead）。
- permission policy helpers。
- Character JSON legacy → v1 normalization。

### Layer B — Persistence / migration

驗：

- Alembic branch graph / ancestry / cross-branch dependency。
- fresh Web DB `upgrade heads`。
- legacy 0008 Web DB upgrade。
- standalone SQLite `character@head`。
- FK / unique / transaction atomicity。
- restart persistence。
- Room Hard Delete orphan check。

### Layer C — API integration

驗：

- Room access credential。
- cross-Room resource isolation。
- room-scoped Character / Builder wrappers。
- Campaign / Roster / Seat / Session lifecycle。
- stable error codes。
- Room authority與 Session Controller的 authorization matrix。

### Layer D — Concurrency

P2 首次有真正多人 race condition，需要明確測：

- Room access token revoke vs write。
- two Room association attempts same Character。
- simultaneous Draft Confirm replay。
- two Sessions同時 lease同 Character。
- Session End vs Late Join。

不能只用 sequential API test推論 concurrency安全。

### Layer E — Frontend unit / routing

驗：

- Web / Standalone capability route split。
- Web Room-first landing。
- RoomContext不掉失。
- Back navigation回正確 Room。
- P2-B後 global `/characters` Web path不洩漏 global list。
- locale copy。

### Layer F — Real-backend Playwright

驗真正 browser + FastAPI + PostgreSQL：

```text
Room
→ Character
→ Campaign
→ Lobby
→ Session
```

以及多 Room隔離、reload、restart後仍成立。

### Layer G — Standalone frozen regression

至少：

- import-boundary static graph。
- standalone app routes。
- character-only Alembic branch。
- SQLite schema table allowlist / forbidden multiplayer tables。
- frozen build / smoke。
- Character JSON Web ↔ Standalone roundtrip。

## 5. Alembic branch gate（P2-A 起永久）

### 5.1 Graph shape

Automated test直接檢 Alembic ScriptDirectory：

- `0008_m03c_import_records`是 branch point。
- 有 `character` branch head。
- 有 `web` branch head。
- `character@head` ancestry不包含任何 Web / Room migration。
- Web `heads`包含 shared Character + web multiplayer兩支。

不要只 grep檔名。

### 5.2 Cross-branch dependency

建立 migration graph fixture / structural assertion：

- Web revision可以 `depends_on`某個 Character revision。
- Character revision不得 `depends_on` Web revision。
- 不允許 Character / Web merge revision把兩條 ancestry合一。
- 在 Web revision依賴較新的 Character revision時，`upgrade heads`仍 deterministic成功。
- `upgrade character@head`仍完全不執行 Web revision。

### 5.3 Fresh Web PostgreSQL

Empty PostgreSQL：

```text
alembic upgrade heads
```

驗：

- 所有 shared Character tables存在。
- 該 Subphase已完成的 Web tables存在。
- Alembic heads正確。
- app `/ready` green。

### 5.4 Legacy Web upgrade

建立 fixture DB停在：

```text
0008_m03c_import_records
```

seed：

- Character。
- Current State。
- multiple Character Versions。
- open Create Draft。
- versioned Builder Draft。
- Character Import record。

再：

```text
upgrade heads
```

驗既有 payload byte/semantic等價；P2-B再驗 Room claim workflow。

### 5.5 Standalone SQLite

Fresh SQLite與 legacy M03 SQLite都跑：

```text
upgrade character@head
```

驗：

- Character tables正常。
- Alembic current在 shared Character branch所需 revisions。
- `rooms` / `campaigns` / `campaign_seats` / `sessions` / P2 association tables**不存在**。
- standalone可以 create / reload Character。

### 5.6 Actual command wiring gate

P2-A code review / automated static test檢查 active operational paths：

- `docker-compose.yml` Web server migration target不是 stale `upgrade head`。
- README 現行 Web migration指令使用 `upgrade heads`。
- standalone launcher使用 `character@head`。
- CI / Actions / active helper scripts若有 Web Alembic command，也使用 `heads`。

歷史 closeout / archive文件可以保留當時的 `head`證據，不列為 stale operational command。

### 5.7 Wrong target negative test

加入測試證明如果 standalone誤跑 `heads`，test會偵測 multiplayer tables；launcher test則鎖死實際 target為 `character@head`。

目的不是故意讓 production做錯，而是確保 gate能抓到未來 regression。

## 6. P2-A — Room Foundation & Web Entry

### 6.1 Backend focused tests

#### Room create

- name / password valid → room建立。
- code unique。
- owner / dm raw key只在 create response出現，不進 DB raw value。
- password使用 salt + slow KDF，不等於 plaintext / plain SHA。
- RoomAccess token high entropy且 DB只存 hash。

#### Enter Room

- correct password → `member`。
- password + correct DM key → `dm`。
- password + correct Owner key → `owner`。
- wrong password拒絕。
- wrong elevated key不得被誤判成成功 elevated login。
- revoked RoomAccess token拒絕。
- Room A token不能拿去 Room B。

#### Secret rotation

如果 P2-A實作 rotate：

- old DM / Owner key失效。
- affected access sessions按 contract revoke。
- raw key不進 log / response list endpoint。

### 6.2 Capability tests

Web：

```text
channel=web
room=true
```

Standalone：

```text
channel=standalone
room=false
campaign=false
seat=false
session=false
```

Standalone不得 mount `/api/rooms`。

### 6.3 Web landing / incremental compatibility

P2-A Web capability：

- `/` 顯示 Enter Room / Create Room。
- 首頁不顯示 Character Workshop。

Standalone capability：

- `/` 顯示 Character Workshop。
- 不顯示 Enter / Create Room。

P2-A 為避免單一 Subphase讓既有 Web Character功能失效，direct legacy `/characters` / Character APIs 可以暫時存在；但要有 test證明首頁不導流，也要列成 P2-B 必須清掉的 transitional surface。

P2-B closeout後再把 direct Web global route改成 room-required / redirect negative gate。

不要靠 build-time separate SPA測；同一 frontend build切 capability。

### 6.4 Character JSON v1 tests

#### v1 export

assert：

```text
schema_version == "1"
schema_status == "locked"
export_type == "character"
```

以及不含：

```text
room_id / room_code / campaign_id / seat_id / session_id
```

#### legacy M03 import

保存一份由最後 M03 contract產出的 realistic `unstable` fixture：

- multiple versions。
- builder_provenance。
- current state。
- content requirements。

P2 parser：

```text
legacy unstable
→ normalize
→ preview
→ import
→ export
```

最後輸出 v1，Character semantics不變。

#### v1 roundtrip

v1 export → import as new identity → export；除了 source identity / timestamps等預期變化，Build / State / Version chain semantics等價。

### 6.5 Import boundary

`test_m03_import_boundary.py`：

- protected Character / standalone graph不 reach `app.*.rooms`。
- negative fixture `app.api.rooms.characters`一定被抓。
- `app.domain.rooms.sessions`一定被抓。
- harmless `app.content.roommate`不誤判。

## 7. P2-B — Room Character Workspace

### 7.1 Association constraints

Persistence test：

- Character A attach Room A成功。
- 再 attach Room B → unique violation被 domain轉成 stable error；transaction rollback。
- Draft同理。
- delete Character可 cascade / explicit cleanup association。
- delete Draft cleanup association。

### 7.2 Create Draft atomicity

Fault-injection test：

```text
create neutral draft
→ insert room_builder_drafts故意 fail
```

整個 transaction rollback；不能留下 unscoped Draft。

反向 fault也要測：association不能存在但 Draft不存在。

### 7.3 Confirm atomicity

Room Draft Confirm：

- create Character / Version 1 / State。
- create `room_characters` link。
- mark Draft confirmed。

全部在一 transaction。

在 link insert前注入 failure → Character / Version / State / confirmed marker全部 rollback。

Repeated Confirm：

- 回同一 Character。
- 不新增第二 Room link。
- version count不增加。

### 7.4 Versioned Draft inheritance

Room A Character：

- Level Up Draft → Room A。
- Build Edit Draft → Room A。
- Correction Draft → Room A。

API沒有 target Room欄位可把它搬到 B。

### 7.5 Cross-Room API matrix

用 Room A token + Room B resource id逐項驗：

- list/get Character。
- sheet。
- patch state。
- export。
- archive / restore。
- permanent delete。
- versions。
- create Level Up draft。
- list Character drafts。
- get/patch/validate/review/confirm/cancel Draft。

每條都必須 fail，不得只測 GET。

### 7.6 Global Web route negative gate

P2-B後 Web app：

- `/api/characters` 不提供 global list / mutation bypass。
- `/api/character-builder/drafts` 不提供 global list / mutation bypass。
- frontend `/characters` 不顯示 global Workshop。

Standalone對應 endpoints仍 green。

### 7.7 Legacy claim

至少兩種 upgrade fixture：

#### Case A — P2-B 時沒有 Room

- 0008 legacy Characters/Drafts。
- upgrade P2。
- Create first Room。
- auto claim。
- Room list看到全部預期資料。
- unscoped count = 0。

#### Case B — P2-A 已建立 Room

- Room A / Room B已存在。
- legacy unscoped data存在。
- Server不得自行猜 Room。
- non-owner看不到 global identities。
- Owner在 Room B explicit claim。
- 全部 unscoped data進 Room B。
- Room A看不到。

### 7.8 Import target Room

Web Room A import：

- direct full Character landing → new Character link Room A。
- missing build refs → repair Draft link Room A。
- `draft_with_history_loss` → target Room association仍正確。
- duplicate import → new Character id，仍 Room A。
- Room B不受影響。

### 7.9 Archive / permanent delete authority

- member / DM可做 reversible archive / restore（無 active Session lease時）。
- permanent individual delete：member deny、DM deny、Owner allow only when archived + no history reference。
- active lease時 archive deny。
- history referenced時 permanent delete deny。

### 7.10 Room Hard Delete

seed：

- active / archived Characters。
- open / confirmed Drafts。
- multiple Versions。
- Current State。
- import records。

Hard Delete Room後 query所有 P2 association / Character core tables，沒有屬於該 Room的 orphan。

其他 Room資料完全不動。

## 8. P2-C — Campaign & Party Roster

### 8.1 Campaign lifecycle authority

Table-driven：

- Owner create / archive / select active Campaign → allow。
- member → deny。
- DM key本身 → deny Campaign lifecycle。
- Owner hard delete draft-with-no-history → allow。
- 有 Session history後 destructive delete拒絕，改 archive / completed。
- set Room active_campaign只接受 same-Room Campaign。
- Room B Campaign id不能設給 Room A。

### 8.2 Roster

DM / Owner：

- add same-Room Character。
- duplicate add idempotent或 stable conflict（實作擇一但測試鎖定）。
- cross-Room Character拒絕。
- status active/inactive/retired/dead persistence。
- missing Session不會因某角色沒出席改 status。

Member：所有 Roster mutation deny。

### 8.3 Same Character / Multi-Campaign State

建立：

```text
Room A
├─ Campaign A roster → Mira
└─ Campaign B roster → Mira
```

在 Campaign A context修改 Mira Current HP後，在 Campaign B context讀同一 Character Sheet：看到相同 Current HP。

再改 Inventory / prepared spell / resource至少各一個代表，證明不是只碰 HP巧合。

DB assert：沒有第二份 campaign state payload。

### 8.4 Character archive interaction

- active Session lease無時可 archive。
- archived Character roster history仍可 query。
- archived Character不可成為新 Session selection。
- restore後若 roster status合法，可再選。
- history referenced archived Character不可 permanent individual delete。

## 9. P2-D — Seat, Controller & Lobby

### 9.1 Seat validation

- DM seat不綁 active Character。
- Spectator不綁 active Character。
- Player Seat可以選 active / inactive Roster Character。
- retired / dead拒絕。
- Room archived Character拒絕。
- cross-Campaign / cross-Room Character拒絕。
- 同 Lobby兩 Seat不能選同 Character。

### 9.2 Human一人多角

同一 RoomAccessSession：

```text
Seat 1 → Mira
Seat 2 → Luna
```

合法。

反向：

```text
Seat 1 → Mira + Luna
```

資料模型做不到／API拒絕。

### 9.3 Controller shape

- human需合法 same-Room access session。
- none不帶 controller id。
- ai domain value可 parse / persist（若設計允許），但 P2 API不得簽發 AI token或回傳「connected AI」。

### 9.4 Presence

Fake clock測 heartbeat：

- recent heartbeat → Connected。
- timeout → Offline。
- Offline不自動刪 Seat、不改 Controller。
- reconnect same access session恢復。

不要用 sleep造成 flaky test。

### 9.5 Permission matrix

至少 table-driven測：

```text
member / dm / owner
×
room settings / campaign lifecycle / roster / seat / character workspace
```

鎖定：

- Owner：Room/Campaign lifecycle。
- DM / Owner：Roster / Lobby / Seat configuration。
- member：Room Character Workspace + assigned Human Player Seat。
- permanent Character delete：Owner only。

每個 deny都測 server response，不只檢 frontend button hidden。

## 10. P2-E — Session Lifecycle & Late Join

### 10.1 Start Session happy path

Seed：

- Room。
- active Campaign。
- DM Seat。
- Player Seat 1 → Mira。
- Player Seat 2 → Borin。
- Serena roster active但沒 seat。

**該 DM Seat的 Human controller** Start：

- session status active。
- participant count正確。
- Mira / Borin active_character snapshot正確。
- Serena沒被自動塞進 Session。
- character leases建立。
- Current State原樣。

### 10.2 Start authority negative matrix

同一 Lobby：

- Room member但不是 DM Seat controller → deny。
- 持有 DM authority但不是本次 DM Seat controller → deny。
- Owner但不是 DM Seat controller → deny。
- Human DM Seat controller + DM authority → allow，並固定為 current DM Controller。

### 10.3 不強制 Ready / Online

- Player seat controller Offline仍可 Start（DM決定）。
- 空 Player Seat不阻塞 Start。
- Roster Character未出席不阻塞。
- 不存在 Ready flag gate。

### 10.4 DM fixed

- DM controller start後保存。
- DM heartbeat Offline → Session仍 active。
- same controller reconnect可繼續。
- Owner不是該 DM controller時呼叫 End Session → deny。
- 另一個 DM key holder呼叫 End Session → deny。
- 另一 DM access session不能 takeover同 Session。
- Owner可 Abandon stuck Session。
- current DM Controller也可 Abandon。

### 10.5 Active Character freeze

Session active後：

- update campaign seat selection不改 session participant snapshot。
- API嘗試換 participant character → `session_active_character_locked`。
- Player死亡／roster status變更不會自動換新角色。

### 10.6 Lease concurrency

這是 P2 必須有的真正 concurrent DB test。

兩個 transaction同時：

```text
Session A start → Mira
Session B start → Mira
```

只能一個 commit成功。

失敗側：

- 回 stable `character_already_in_active_session`。
- 不留下 half-created session / participant / partial leases。

至少 PostgreSQL執行；不要只在 SQLite mock concurrency。

### 10.7 Same Campaign second active Session

同一 Campaign已有 active Session時第二次 Start拒絕，即使選不同 Characters。

Ended / abandoned後才可開下一 Session。

### 10.8 Late Join authority / validation

Active Session：

- current DM Controller late join Luna from same Roster成功。
- Owner但非 current DM → deny Late Join。
- 其他 DM authority但非 current DM → deny。
- retired/dead失敗。
- archived失敗。
- Room B Character失敗。
- 已被另一 active Session lease失敗。
- 加入後 participant / lease persistence正確。

### 10.9 End Session state preservation

Start前 snapshot一個 rich Character State：

- current HP / temp HP。
- conditions。
- prepared spells。
- spell slots / resources。
- hit dice。
- inventory。
- artificer state / feature modes（若 fixture適用）。

Session內先做合法 state改動；記住 end前 exact state。

current DM Controller End Session後：

```text
state_after_end == state_immediately_before_end
```

不能只 assert HP。

Leases已釋放；Session participant/history仍存在。

### 10.10 Abandon

Owner或 current DM Controller abandon：

- status abandoned。
- leases release。
- Current State不變。
- 不建立 replacement DM。

### 10.11 Restart persistence

Server restart後：

- active Session仍 active。
- participant assignments仍固定。
- current DM Controller identity仍固定。
- leases仍對應。
- Room access token若未 revoke仍可重新建立 context。
- ended Session不會重建 lease。

## 11. Web live Character write-scope tests

P2-B/E 完成後，特別驗現有 Character State API不被 Room wrapper漏掉。

### No active Session

Room member可依 Room協作規則使用 Room Character Workshop / Sheet。

### Active Session

Mira已 lease給 Seat A / Human A：

- Human A patch Mira state → allow。
- Human B member patch Mira → deny。
- current Session DM Controller patch Mira → allow。
- 另一個 DM key holder patch Mira → deny。
- Owner但非 current DM / Mira Seat controller → deny。
- Room B caller → resource not found / deny。

Borin若未在 active Session：依 Room一般協作規則處理。

Versioned Builder對 active Character也做同樣 Seat/current-DM scope guard，避免一般 member、另一 DM或 Owner用 Build Edit繞過 active table控制權。

## 14. Standalone regression matrix（每個會碰 shared boundary 的 P2 Subphase）

### Static

- `test_m03_import_boundary.py`。
- `app.standalone`不 import `app.*.rooms`。
- core Character modules不 import rooms。
- Character Alembic ancestry不含 Web revisions。

### Runtime app

Standalone capability：

```text
character_builder=true
character_import_export=true
room=false
campaign=false
seat=false
session=false
```

### SQLite schema

不得存在：

```text
rooms
room_access_sessions
room_characters
room_builder_drafts
campaigns
campaign_roster_entries
campaign_seats
sessions
session_participants
active_character_session_leases
```

### Character workflow

至少：

```text
Create → Confirm → Sheet
Level Up → Confirm → Version History
Export → Import → Sheet
```

## 15. Security / privacy negative matrix

P2 沒有 DM secrets world data yet，但 namespace與access credential已是 security boundary。

至少：

1. Room A token + Room B id。
2. revoked token。
3. random token。
4. member呼叫 Owner action。
5. DM呼叫 Owner-only Campaign lifecycle action。
6. member改別人 active Seat Character state。
7. non-current-DM End Session。
8. Owner但非 current DM Controller Start / Late Join / End Session。
9. 另一 DM key holder但非 current DM Controller寫本場 Character。
10. DM試圖 Hard Delete Room。
11. URL UUID guessing。

Response不得洩漏：

- Room password hash / salt。
- Owner / DM key hash。
- RoomAccess token hash。
- 另一 Room Character name / draft payload。

## 17. Human smoke

P2 人工 smoke只驗 automation難以判斷的 UX，不人工重做全部 permission matrix。

建議代表流程：

1. Web首頁確認沒有 Character Workshop，Create Room / Enter Room清楚。
2. 建 Room A，記下 Room code / Owner / DM credential presentation是否容易理解、不誤把 key當一般 password。
3. Room A → Characters，創一隻角色，刻意中途離開再回來，Draft位置清楚。
4. Confirm後 Sheet / Version History 的 Back不會掉出 Room。
5. 建 Room B，視覺上不會看到 Room A Characters / Drafts。
6. Room B import一隻 JSON角色，確認「這是 B 的 new copy」容易理解。
7. Owner建 Campaign；DM管理 Roster / Lobby，authority差異不讓人困惑。
8. Lobby建立 DM + 2 Player Seats；一個 browser identity控制兩 Seat的 UX仍可理解。
9. 由 DM Seat Controller Start Session、late join、End Session；不強迫 Ready。
10. Owner但不是 current DM時，UI不應讓人誤以為可以接管／End；Abandon入口需清楚是重手段。
11. End後回 Character Sheet確認 HP / resources沒有莫名 reset。
12. Standalone啟動確認仍直接進 Character Workshop，看不到 Room / Campaign字樣。
13. 切 `zh-TW` / `en` 各巡一次 P2主要頁面，檢查 overflow / raw key。

若 human smoke發現 UX confusion但不影響資料 correctness，可在 P2-F closeout列為 polish；若容易讓使用者誤刪 Room、進錯 Room、以為 Character跨 Room共用、誤以為 Owner可接管 Session，視為 blocker。
