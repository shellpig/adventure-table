> Phase：**P2 — Room / Campaign / Session / Seat**  
> 本文件定義 P2-A～P2-F 的自動／人工驗收與 closeout evidence。產品完成條件以 `實作規格.md` 為準；具體架構與 migration / API contract以 `開發設計方針.md` 為準。

最後更新：2026-09-06

## 1. P2 Subphase 順序

三份 P2 文件固定使用：

```text
P2-A — Room Foundation & Web Entry
P2-B — Room Character Workspace
P2-C — Campaign & Party Roster
P2-D — Seat, Controller & Lobby
P2-E — Session Lifecycle & Late Join
P2-F — Full P2 Integration & Closeout
```

每個 Subphase 的測試新增要跟該段 code一起完成；不要把「Room scope / permission / migration」全部留到 P2-F才第一次驗。

## 2. P2 測試核心原則

P2 從單機 Character 系統進入多人 namespace，最危險的 regression不只是功能壞掉，而是：

- Room A 能摸到 Room B 資料。
- Web global endpoint繞過 Room scope。
- standalone因 shared code被多人 domain污染。
- standalone SQLite跑到 Web migrations。
- Character / Draft成功建立但 Room association失敗，留下 orphan。
- Campaign偷偷複製 Character State，兩份狀態開始 diverge。
- 同 Character被兩個 active Session同時使用。
- Session End意外 heal / reset Character State。
- Owner / DM Key / Seat Role / current DM Controller混成一種權限。
- Alembic Character / Web branches未來因 dependency merge而把 standalone拖進 multiplayer ancestry。
- branch split後既有 M03 migration tests、M03-E frozen helper、standalone smoke或舊 workflow仍假設整個 repository只有一個 Alembic head。
- global SQLAlchemy `MetaData`因 test import order含 Web tables，讓 Standalone schema parity變 flaky。
- Room-first route改版時，既有 P1 / M01 / M02 Web browser/API regression被大量 skip、改跑 standalone，造成 Web coverage在最需要保護時反而消失。

因此 P2 的 minimum gate不是「頁面打得開」，而是：

```text
Scope isolation
+ persistence atomicity
+ migration correctness
+ concurrency invariant
+ controller authority
+ standalone independence
+ existing Web regression continuity
+ real PostgreSQL evidence
+ real-backend UX
```

## 3. 執行環境與指令原則

### Backend

Windows / PowerShell 下不要使用 `&&` 串 command。Backend Python 指令若依賴 `alembic.ini` / relative path，cwd在 `apps/server`，interpreter使用 repo root `.venv`。

例如從 repo root：

```powershell
Set-Location .\apps\server
..\..\.venv\Scripts\python.exe -m pytest
```

Focused test同理：

```powershell
Set-Location .\apps\server
..\..\.venv\Scripts\python.exe -m pytest tests\test_p2a_rooms.py -q
```

### PostgreSQL focused tests

P2-A 起 PostgreSQL-specific gate使用統一 env var：

```text
P2_POSTGRES_URL
```

CI的 `P2 Non-E2E` workflow提供乾淨 PostgreSQL service並同時設定：

```text
P2_POSTGRES_URL=<test db url>
DATABASE_URL=$P2_POSTGRES_URL
```

本機可從 repo root建立 dedicated test DB；PowerShell 5.1 不使用 `&&`：

```powershell
docker compose up -d db
docker compose exec -T db psql -U adventure -d postgres -c "DROP DATABASE IF EXISTS adventure_table_p2_test;"
docker compose exec -T db psql -U adventure -d postgres -c "CREATE DATABASE adventure_table_p2_test;"
Set-Location .\apps\server
$env:P2_POSTGRES_URL = "postgresql+psycopg://adventure:adventure@localhost:5432/adventure_table_p2_test"
$env:DATABASE_URL = $env:P2_POSTGRES_URL
..\..\.venv\Scripts\python.exe -m pytest <P2 PostgreSQL focused tests> -q
```

需要 clean DB語意的 focused test不得假設開發用 `adventure_table`可隨便 drop；一律使用 dedicated `adventure_table_p2_test`或 CI fresh service。

### Frontend unit / build

```powershell
Set-Location .\apps\web
npm test -- --run
npm run build
```

### E2E

依 `KI-ENV-001`，完整 Playwright一律走 Docker/Linux web service：

```powershell
Set-Location .\apps\web
npm run test:e2e:docker
```

不要在 Windows 上改用 Playwright-managed Vite來「暫時過測試」。

### Actions

P2-A 必須建立專屬：

```text
.github/workflows/p2-non-e2e.yml
Display name: P2 Non-E2E
```

它是 P2 PostgreSQL migration / persistence / concurrency non-E2E evidence的正式 workflow。P2-B～E持續在同 workflow擴充各自 focused tests。

GitHub Actions只代表其 workflow實際覆蓋的 gate；不得因 M03 standalone workflow或舊 M01 workflow綠燈就宣稱 P2 backend / PostgreSQL / permission / E2E全綠。

每個 closeout要記錄：

- exact commit SHA。
- local / CI command。
- workflow name + run id（若用 Actions）。
- pass / fail / skip數。
- intentional skip對應已知問題。

## 4. Test layers

### Layer A — Domain / pure policy

驗：

- RoomAccessAuthority。
- Campaign status / Roster status transition。
- Seat role / Controller validation。
- Session Active Character freeze。
- eligibility（active/inactive vs retired/dead）。
- permission policy helpers。
- Character JSON legacy → v1 normalization。
- Room code normalize / password throttle policy helper（若拆成 pure policy）。

### Layer B — Persistence / migration

驗：

- Alembic branch graph / ancestry / cross-branch dependency。
- fresh Web DB `upgrade heads`。
- legacy 0008 Web DB upgrade。
- standalone SQLite `character@head`。
- existing M03 migration / launcher / smoke tests已改成 multi-head-aware。
- Character schema parity allowlist不受 global MetaData import order影響。
- FK / unique / transaction atomicity。
- restart persistence。
- Seat history archive / FK restrict。
- Room Hard Delete orphan check。

### Layer C — API integration

驗：

- Room access credential。
- Room access throttle / heartbeat。
- cross-Room resource isolation。
- room-scoped Character / Builder wrappers。
- Campaign / Roster / Seat / Session lifecycle。
- stable error codes。
- Owner DM assignment與 Session Controller authorization matrix。
- 既有 `app.main` Character / Builder HTTP regression在 P2-B後仍由 Web room-scoped endpoint承接，不被移去 standalone。

### Layer D — Concurrency

P2 首次有真正多人 race condition，需要明確測：

- Room access token revoke vs write。
- two Room association attempts same Character。
- simultaneous Draft Confirm replay。
- two Sessions同時 lease同 Character。
- Session End vs Late Join。

不能只用 sequential API test推論 concurrency安全。

### Layer E — Frontend unit / routing

驗：

- Web / Standalone capability route split。
- Web Room-first landing。
- RoomContext不掉失。
- Back navigation回正確 Room。
- P2-B後 global `/characters` Web path不洩漏 global list。
- heartbeat lifecycle不在離開 Room後繼續亂送。
- locale copy。
- shared E2E Room bootstrap / Workshop navigation seam能支撐既有 Web character/content specs，不要求每個 spec hardcode Room route。

### Layer F — Real-backend Playwright

驗真正 browser + FastAPI + PostgreSQL：

```text
Room
→ Character
→ Campaign
→ Lobby
→ Session
```

以及多 Room隔離、reload、restart後仍成立。

**Layer F 包含既有 Web Playwright regression suite，不只新增 P2 journey。** P2-A/P2-B改 route時，既有 P1/M01/M02 spec必須透過 Room-aware helper繼續跑 Web channel。

### Layer G — Standalone frozen regression

至少：

- import-boundary static graph。
- standalone app routes。
- character-only Alembic branch。
- SQLite schema Character allowlist / forbidden multiplayer tables。
- frozen build / smoke。
- Character JSON Web ↔ Standalone roundtrip。

Standalone gate是獨立保護，不是既有 Web regression的替代執行環境。

## 5. Alembic branch gate（P2-A 起永久）

### 5.1 Graph shape

Automated test直接檢 Alembic ScriptDirectory：

- `0008_m03c_import_records`是 branch point。
- 有 `character` branch head。
- 有 `web` branch head。
- `character@head` ancestry不包含任何 Web / Room migration。
- Web `heads`包含 shared Character + web multiplayer兩支。

不要只 grep檔名。

### 5.2 Cross-branch dependency

建立 migration graph fixture / structural assertion：

- Web revision可以 `depends_on`某個 Character revision。
- Character revision不得 `depends_on` Web revision。
- 不允許 Character / Web merge revision把兩條 ancestry合一。
- 在 Web revision依賴較新的 Character revision時，`upgrade heads`仍 deterministic成功。
- `upgrade character@head`仍完全不執行 Web revision。

### 5.3 Fresh Web PostgreSQL

Empty PostgreSQL：

```text
alembic upgrade heads
```

驗：

- 所有 shared Character tables存在。
- 該 Subphase已完成的 Web tables存在。
- Alembic revision set / heads正確；不能再假設 `alembic_version`只一列。
- app `/ready` green。

此 gate至少在 `P2 Non-E2E`的 PostgreSQL service執行。

### 5.4 Legacy Web upgrade

建立 fixture DB停在：

```text
0008_m03c_import_records
```

seed：

- Character。
- Current State。
- multiple Character Versions。
- open Create Draft。
- versioned Builder Draft。
- Character Import record。

再：

```text
upgrade heads
```

驗既有 payload byte/semantic等價；P2-B再驗 Room claim workflow。

### 5.5 Standalone SQLite

Fresh SQLite與 legacy M03 SQLite都跑：

```text
upgrade character@head
```

驗：

- Character tables正常。
- Alembic current在 shared Character branch所需 revisions。
- `rooms` / `campaigns` / `campaign_seats` / `sessions` / P2 association tables**不存在**。
- standalone可以 create / reload Character。

### 5.6 Existing migration / launcher / smoke rewiring gate

P2-A 不只掃 operational command，也必須改既有 pytest、frozen helper與 standalone smoke的 single-head contract。

#### `test_m03c_migration.py`

- 原本 `command.upgrade(config, "head")`改成 Web `heads`。
- 原本 `SELECT version_num ... scalar()` / 單一 revision equality不得保留；split後應比較 Alembic revision **set**，並明確包含當時 character + web heads。
- downgrade / upgrade regression仍要驗 `character_import_records`不被 branch split破壞。

#### `test_m03d_migration_sqlite.py`

- 所有 upgrade target改成 `character@head`。
- 原本 `ScriptDirectory.get_current_head()`不得再使用，因 repository已有多 head；應明確 resolve `character@head` revision。
- downgrade base → re-upgrade `character@head`仍要成立。

#### `test_m03d_schema_parity.py`

- migration target改成 `character@head`。
- 不再做「整份 global metadata create_all == standalone migration schema」。
- 依 `開發設計方針.md` §3.8使用 explicit Character table allowlist。
- 同 test process即使事先 import `app.persistence.rooms.tables`，結果也必須相同。

#### `scripts/smoke_standalone.py`

- 不得再以自行 AST 推導 `heads`後要求 `len(heads) == 1`。
- helper必須只 resolve Character branch current head；repository同時存在 Web head是正常狀態。
- frozen SQLite `alembic_version`與 Character branch expected current比對；不能跟 repo-global唯一 head比。

#### `test_m03e_smoke_script.py`

- 不得再 assert `0008_m03c_import_records` 是目前唯一 head。
- 驗 helper在 multiple-head graph仍解析目前 `character@head`。

#### `test_m03e_alembic_bundle_ready.py`

- 不再呼叫 `ScriptDirectory.get_current_head()`。
- bundled Alembic resources明確 resolve `character@head`，再跟 frozen SQLite current比對。

#### `test_m03e_launcher_headless.py`

- 不再呼叫 `ScriptDirectory.get_current_head()`。
- launcher migration結果鎖定 `character@head`。

Static scan範圍至少包含：

```text
apps/server/tests/**
scripts/**
.github/workflows/**
active dev / release helpers
```

判準是**任何 repo-global single-head 假設**，不只是字面 `"head"` target。至少掃：

```text
upgrade(..., "head") / alembic upgrade head
get_current_head()
len(heads) == 1 / expected one Alembic head
自製 AST / filename 唯一-head inference
Web assertion把 alembic_version 永遠讀成單列 scalar
```

逐一分類成 Web `heads` / revision set、Standalone `character@head` / Character revision，或明確的歷史文件文字。歷史 closeout文件文字不算 active contract。

### 5.7 Character schema parity allowlist gate

Parity test至少做兩次等價情境：

1. 只 import neutral Character persistence後執行。
2. 先 import P2 Room tables，再執行同一 parity helper。

兩者都必須：

- `metadata.create_all(..., tables=CHARACTER_SCHEMA_TABLES)`只建立 Character allowlist。
- snapshot與 `character@head` migrated SQLite一致。
- forbidden P2 Web tables不存在。

這直接鎖死 import-order flake。

### 5.8 Actual command / assumption wiring gate

P2-A code review / automated static test檢查 active operational paths：

- `docker-compose.yml` Web server migration target不是 stale `upgrade head`。
- README 現行 Web migration指令使用 `upgrade heads`。
- standalone launcher使用 `character@head`。
- CI / Actions / active helper scripts若有 Web Alembic command，也使用 `heads`。
- `apps/server/tests/**`與`scripts/**`沒有 repo-global `get_current_head()` / `len(heads)==1` / 自製唯一-head inference 留在 active migration / standalone smoke路徑。
- Web migration assertions不再假設 `alembic_version`永遠只有一列；Standalone只比較 Character branch current。

目前已知 P2-A branch split必須檢查的舊 workflow至少：

```text
p0a-foundation.yml
m01f-non-e2e.yml
m01g-non-e2e.yml
m01h-non-e2e.yml
m01i-non-e2e.yml
m01j-non-e2e.yml
m03a-non-e2e.yml
m03b-non-e2e.yml
```

若這些 workflow在目前 main仍執行 migration，就不能因名稱屬舊 Phase而保留 ambiguous `upgrade head`。

歷史 closeout / archive文件可以保留當時的 `head`證據，不列為 stale operational command。

### 5.9 Wrong target negative test

加入測試證明如果 standalone誤跑 `heads`，test會偵測 multiplayer tables；launcher test則鎖死實際 target為 `character@head`。

目的不是故意讓 production做錯，而是確保 gate能抓到未來 regression。

## 6. P2-A — Room Foundation & Web Entry

### 6.0 第一個 implementation checkpoint：封存 M03 unstable fixture

**任何 v1 exporter / parser code修改之前**，先建立並 commit：

```text
apps/server/tests/fixtures/character_export_m03_unstable.json
```

產生規則：

- 必須由尚未修改的最後 M03 exporter/API實際輸出，不可手刻。
- fixture包含 multiple versions、builder provenance、rich Current State、content requirements / representative non-SRD refs。
- assert原始 envelope仍是 `schema_version="unstable"` / `schema_status="unstable"`。
- 先以 focused test讀回這份 fixture，證明它是可被當時 M03 parser接受的真實檔。
- 這一小階段先 commit；review完成後才進下一個「exporter切v1」commit。
- v1上線後不得修改這份 fixture去迎合 parser；它是 backward-compatibility evidence。

### 6.1 Backend focused tests

#### Room create / code

- name / password valid → room建立。
- code由CSPRNG產生，長度固定10，字元只屬 Crockford Base32允許集合，canonical uppercase。
- lowercase輸入可 normalize到同 Room。
- code unique；mock collision時會 retry而不是覆蓋 existing Room。
- code不是user-chosen field。
- owner / dm raw key只在 create response出現，不進 DB raw value。
- password使用 salt + slow KDF，不等於 plaintext / plain SHA。
- RoomAccess token high entropy且 DB只存 hash。

#### Password contract / throttle

- password <6 或 >128 Unicode code points拒絕。
- whitespace不被silent trim成另一個 password。
- wrong password計入 `(room_code, remote_addr)` failure window。
- 5分鐘內第1～10次依正常 invalid credential處理；超過門檻回 429 + `room_access_throttled`。
- fake clock跨過window後可再嘗試。
- successful enter清掉failure window。
- throttle不要用 real sleep。
- 不信任任意 `X-Forwarded-For`改寫client identity（除非測試/部署明確設定 trusted proxy contract）。

#### Enter Room

- correct password → `member`。
- password + correct DM key → `dm`。
- password + correct Owner key → `owner`。
- wrong password拒絕。
- wrong elevated key不得被誤判成成功 elevated login。
- revoked RoomAccess token拒絕。
- Room A token不能拿去 Room B。

#### Secret rotation

如果 P2-A實作 rotate：

- old DM / Owner key失效。
- affected access sessions按 contract revoke。
- raw key不進 log / response list endpoint。

### 6.2 Heartbeat contract

P2-A直接交付 heartbeat endpoint，因此本 Subphase就測：

```text
POST /api/rooms/{room_id}/access/heartbeat
```

- valid token + same Room → 2xx，`last_seen_at`使用server time更新。
- revoked token → deny。
- Room A token打 Room B heartbeat → deny / scope mismatch。
- heartbeat不建立新 RoomAccessSession、不rotate token、不建立 Seat / game event。
- fake clock可精準assert timestamp；不 sleep。

P2-D再測 `last_seen_at`到 Connected/Offline的 projection；不重做第二套 heartbeat。

### 6.3 Capability tests

`apps/server/tests/test_m03e_capabilities.py` 是 P2-A 必改 regression，不是新增 P2 test取代它。

Web：

```text
channel=web
room=true
```

Standalone：

```text
channel=standalone
room=false
campaign=false
seat=false
session=false
```

要求：

- P2-A同 commit把原本 `web.capabilities.room is False` expectation改為 `True`。
- Standalone expectation仍 `room is False`。
- Standalone不得 mount `/api/rooms`。

### 6.4 Web landing / incremental compatibility

P2-A Web capability：

- `/` 顯示 Enter Room / Create Room。
- 首頁不顯示 Character Workshop。

Standalone capability：

- `/` 顯示 Character Workshop。
- 不顯示 Enter / Create Room。

P2-A 為避免單一 Subphase讓既有 Web Character功能失效，direct legacy `/characters` / Character APIs 可以暫時存在；但要有 test證明首頁不導流，也要列成 P2-B 必須清掉的 transitional surface。

P2-B closeout後再把 direct Web global route改成 room-required / redirect negative gate。

不要靠 build-time separate SPA測；同一 frontend build切 capability。

### 6.5 Character JSON v1 tests

#### legacy fixture先存在

在修改 exporter前，先 assert §6.0 committed fixture：

- 是 valid M03 unstable envelope。
- realistic representative payload不為空。
- fixture commit早於 v1 exporter commit（closeout evidence記兩筆SHA）。

#### v1 export

assert：

```text

schema_status == "locked"
export_type == "character"
```

以及不含：

```text

```

#### legacy M03 import

使用§6.0真正封存的 fixture：

```text

→ normalize
→ preview
→ import
→ export
```

最後輸出 v1，Character semantics不變。

#### v1 roundtrip

v1 export → import as new identity → export；除了 source identity / timestamps等預期變化，Build / State / Version chain semantics等價。

### 6.6 Import boundary

`test_m03_import_boundary.py`：

- protected Character / standalone graph不 reach `app.*.rooms`。
- negative fixture `app.api.rooms.characters`一定被抓。
- `app.domain.rooms.sessions`一定被抓。
- harmless `app.content.roommate`不誤判。

### 6.7 Existing Web Playwright Room bootstrap gate

P2-A 必須先為**既有 Web E2E**建立共用 Room bootstrap / navigation seam；不要等 P2-B關掉 `/characters`才一次撞完整 suite。

建議 contract（檔名可按現有 style）：

```text
enterRoom(page, options?)
openCharacterWorkshop(page, roomContext)
```

驗收原則：

1. 測 Character / Builder / M01/M02 rules content 的既有 specs從 P2-A 起不再各自 hardcode `page.goto('/characters')`；先透過 `enterRoom()`取得 isolated Room context，再由 `openCharacterWorkshop()`進 Workshop。
2. P2-A transitional window中，`openCharacterWorkshop()`可以先導向既有 `/characters`；因為 P2-B Room-scoped Character API尚未完成。這不是 bypass，而是讓 route transition集中在 helper。
3. P2-B只改 shared helper / route context一次到 `/rooms/{roomId}/characters`，不逐一再改二十多個 spec。
4. 真正測首頁本身的 specs（例如 app shell / localization landing）直接更新對 `/` 的期待，改驗 Create / Enter Room與 Room-first雙語 copy；不能用 helper跳過首頁後宣稱 landing有測。
5. 每個 spec / worker使用獨立 Room或 deterministic reset，避免平行 suite共享 mutable Room。
6. 既有 suite仍是 **Web channel regression**；不得整批改用 standalone capability、不得因 Room-first migration大量 `skip/fixme`。

P2-A closeout至少要證明：完整既有 Playwright suite在新的 Room-first首頁存在後仍可執行；P2-B closeout再證明同一 suite在 global Web `/characters`收口後仍全程走 Room-scoped Web path。

## 7. P2-B — Room Character Workspace

### 7.1 Association constraints

Persistence test：

- Character A attach Room A成功。
- 再 attach Room B → unique violation被 domain轉成 stable error；transaction rollback。
- Draft同理。
- delete Character可 cascade / explicit cleanup association。
- delete Draft cleanup association。

### 7.2 Create Draft atomicity

Fault-injection test：

```text
create neutral draft
→ insert room_builder_drafts故意 fail
```

整個 transaction rollback；不能留下 unscoped Draft。

反向 fault也要測：association不能存在但 Draft不存在。

### 7.3 Confirm atomicity

Room Draft Confirm：

- create Character / Version 1 / State。
- create `room_characters` link。
- mark Draft confirmed。

全部在一 transaction。

在 link insert前注入 failure → Character / Version / State / confirmed marker全部 rollback。

Repeated Confirm：

- 回同一 Character。
- 不新增第二 Room link。
- version count不增加。

### 7.4 Versioned Draft inheritance

Room A Character：

- Level Up Draft → Room A。
- Build Edit Draft → Room A。
- Correction Draft → Room A。

API沒有 target Room欄位可把它搬到 B。

### 7.5 Cross-Room API matrix

用 Room A token + Room B resource id逐項驗：

- list/get Character。
- sheet。
- patch state。
- export。
- archive / restore。
- permanent delete。
- versions。
- create Level Up draft。
- list Character drafts。
- get/patch/validate/review/confirm/cancel Draft。

每條都必須 fail，不得只測 GET。

### 7.6 Global Web route negative gate

P2-B後 Web app：

- `/api/characters` 不提供 global list / mutation bypass。
- `/api/character-builder/drafts` 不提供 global list / mutation bypass。
- frontend `/characters` 不顯示 global Workshop。

Standalone對應 endpoints仍 green。

### 7.7 Legacy claim

至少兩種 upgrade fixture；**Primary Case 是 P2-A 已被使用、Room 已存在**，zero-Room auto-claim只保留 bootstrap edge coverage。

#### Primary Case — P2-A 已建立 Room

- Room A / Room B已存在。
- legacy unscoped Character / Draft存在。
- Server不得自行猜 Room。
- non-owner看不到 `Legacy Character Data` migration card，也拿不到 global identities。
- Owner進入 Room B 的 `Characters` / Room Character Workshop，看到 owner-only migration card。
- card只顯示仍 unscoped 的 Character / Draft count，不列出跨 Room global identity清單。
- Owner按 `Claim Legacy Character Data` → confirmation modal顯示 target `Room B` 名稱與 Character / Draft count。
- Cancel → 不改任何 association。
- Confirm → 所有仍 unscoped data進 Room B；Room A看不到。
- repeated/concurrent claim要重新計數並安全完成或回 stable conflict；不得搬動已 scoped object。
- claim後 unscoped count = 0，migration card消失。

#### Bootstrap Edge Case — P2-B 時沒有 Room

- 0008 legacy Characters / Drafts。
- upgrade P2。
- server Room count = 0。
- Create first Room。
- auto claim。
- Room list看到全部預期資料。
- unscoped count = 0。

### 7.8 Import target Room

Web Room A import：

- direct full Character landing → new Character link Room A。
- missing build refs → repair Draft link Room A。
- `draft_with_history_loss` → target Room association仍正確。
- duplicate import → new Character id，仍 Room A。
- Room B不受影響。

### 7.9 Archive / permanent delete authority

- member / DM可做 reversible archive / restore（無 active Session lease時）。
- permanent individual delete：member deny、DM deny、Owner allow only when archived + no history reference。
- active lease時 archive deny。
- history referenced時 permanent delete deny。

### 7.10 Room Hard Delete

seed：

- active / archived Characters。
- open / confirmed Drafts。
- multiple Versions。
- Current State。
- import records。

Hard Delete Room後 query所有 P2 association / Character core tables，沒有屬於該 Room的 orphan。

其他 Room資料完全不動。

### 7.11 Existing Web backend Character regression migration

P2-B 收掉 `app.main` 的 global Character routers時，既有 Web HTTP regression必須改成 Room-scoped，**不改綁 standalone app來逃避 authorization / route migration**。

## 8. P2-C — Campaign & Party Roster

### 8.1 Campaign lifecycle authority

Table-driven：

- Owner create / archive / select active Campaign → allow。
- member → deny。
- DM key本身 → deny Campaign lifecycle。
- Owner hard delete draft-with-no-history → allow。
- 有 Session history後 destructive delete拒絕，改 archive / completed。
- set Room active_campaign只接受 same-Room Campaign。
- Room B Campaign id不能設給 Room A。

### 8.2 Roster

DM / Owner：

- add same-Room Character。
- duplicate add idempotent或 stable conflict（實作擇一但測試鎖定）。
- cross-Room Character拒絕。
- status active/inactive/retired/dead persistence。
- missing Session不會因某角色沒出席改 status。

Member：所有 Roster mutation deny。

### 8.3 Same Character / Multi-Campaign State

建立：

```text
Room A
├─ Campaign A roster → Mira
└─ Campaign B roster → Mira
```

再改 Inventory / prepared spell / resource至少各一個代表，證明不是只碰 HP巧合。

DB assert：沒有第二份 campaign state payload。

### 8.4 Character archive interaction

- active Session lease無時可 archive。
- archived Character roster history仍可 query。
- archived Character不可成為新 Session selection。
- restore後若 roster status合法，可再選。
- history referenced archived Character不可 permanent individual delete。

## 9. P2-D — Seat, Controller & Lobby

### 9.1 Seat validation

- DM seat不綁 active Character。
- Spectator不綁 active Character。
- Player Seat可以選 active / inactive Roster Character。
- retired / dead拒絕。
- Room archived Character拒絕。
- cross-Campaign / cross-Room Character拒絕。
- 同 Lobby兩 Seat不能選同 Character。

### 9.2 Seat history lifecycle

先建立未使用 Seat：

- 從未被 Session reference → hard delete allow。

再建立 ended Session reference該 Seat：

- hard delete → `seat_history_referenced` / deny。
- archive → allow。
- archived Seat不出現在新 Lobby / Start selection。
- 舊 Session仍可透過 non-null `seat_id`讀取歷史 Seat。
- `campaign_seats.campaign_id` 使用 CASCADE，但只有無 Session history的 Campaign可 hard delete；`sessions.campaign_id` 使用 RESTRICT，存在 Session history時 DB / service都必須阻止 Campaign hard delete。
- `sessions.dm_seat_id`與`session_participants.seat_id` FK都使用 restrict semantics；一般 Seat delete不能把 historical FK設 null。
- Room Hard Delete仍可在完整 workspace transaction先清 Session history，再移除 Seat / Campaign。

### 9.3 Human一人多角

同一 RoomAccessSession：

```text
Seat 1 → Mira
Seat 2 → Luna
```

合法。

反向：

```text
Seat 1 → Mira + Luna
```

資料模型做不到／API拒絕。

### 9.4 Controller shape

- human需合法 same-Room access session。
- none不帶 controller id。
- ai domain value可 parse / persist（若設計允許），但 P2 API不得簽發 AI token或回傳「connected AI」。

### 9.5 Owner-controlled DM assignment

建立 Owner、DM A、DM B access sessions：

- DM A持DM Key但未被Owner assign到DM Seat → 不可自行綁自己。
- DM A嘗試 reassign DM Seat → deny。
- Owner assign DM A → allow。
- Owner reassign到 DM B（Session尚未開始）→ allow。
- Owner可把自己的 owner access session assign到 DM Seat。
- member不可被直接當成 DM Seat controller，除非先取得合法 `dm` authority；Owner自身例外因 `owner` authority高於 `dm`。

這裡鎖的是**Start前 assignment**；Session開始後由P2-E current DM Controller snapshot鎖死。

### 9.6 Presence

Fake clock測 P2-A heartbeat projection：

- heartbeat後 `now-last_seen_at <= 90s` → Connected。
- 超過90s → Offline。
- 30秒 heartbeat cadence不要求 exact browser timer assertion，但 component / hook不得在離開 Room後持續送錯 Room heartbeat。
- Offline不自動刪 Seat、不改 Controller。
- reconnect same access session + heartbeat恢復。

不要用 sleep造成 flaky test。

### 9.7 Permission matrix

至少 table-driven測：

```text
member / dm / owner
×
room settings / campaign lifecycle / roster / player-seat / dm-seat-assignment / character workspace
```

鎖定：

- Owner：Room/Campaign lifecycle + **DM Seat assignment**。
- DM / Owner：Roster / non-DM Lobby / Seat configuration。
- DM authority不能 self-assign DM Seat。
- member：Room Character Workspace + assigned Human Player Seat。
- permanent Character delete：Owner only。

每個 deny都測 server response，不只檢 frontend button hidden。

## 10. P2-E — Session Lifecycle & Late Join

### 10.1 Start Session happy path

Seed：

- Room。
- active Campaign。
- Owner已把一個合法 `dm` authority Human access session assign到 DM Seat。
- Player Seat 1 → Mira。
- Player Seat 2 → Borin。
- Serena roster active但沒 seat。

**Owner-assigned DM Seat Human controller** Start：

- session status active。
- participant count正確。
- Mira / Borin active_character snapshot正確。
- Serena沒被自動塞進 Session。
- character leases建立。
- Current State原樣。

### 10.2 Start authority negative matrix

同一 Lobby：

- Room member但不是 DM Seat controller → deny。
- 持有 DM authority但未被Owner assign到本次 DM Seat → deny。
- 另一個 DM Key holder → deny。
- Owner但未被 assign到 DM Seat → deny。
- Owner-assigned Human DM Seat controller + `dm` authority → allow。
- Owner把自己 assign到 DM Seat + `owner` authority → allow。

Start成功後固定為 current DM Controller。

### 10.3 不強制 Ready / Online

- Player seat controller Offline仍可 Start（DM決定）。
- 空 Player Seat不阻塞 Start。
- Roster Character未出席不阻塞。
- 不存在 Ready flag gate。

### 10.4 DM fixed

- DM controller start後保存。
- DM heartbeat Offline → Session仍 active。
- same controller reconnect可繼續。
- Owner不是該 DM controller時呼叫 End Session → deny。
- 另一個 DM key holder呼叫 End Session → deny。
- Owner重新指派 Campaign DM Seat不會改既有 Session controller。
- 另一 DM access session不能 takeover同 Session。
- Owner可 Abandon stuck Session。
- current DM Controller也可 Abandon。

### 10.5 Active Character freeze

Session active後：

- update campaign seat selection不改 session participant snapshot。
- API嘗試換 participant character → `session_active_character_locked`。
- Player死亡／roster status變更不會自動換新角色。

### 10.6 Lease concurrency

這是 P2 必須有的真正 concurrent PostgreSQL DB test。

兩個 transaction同時：

```text
Session A start → Mira
Session B start → Mira
```

只能一個 commit成功。

失敗側：

- 回 stable `character_already_in_active_session`。
- 不留下 half-created session / participant / partial leases。

**至少在 `P2 Non-E2E` PostgreSQL service執行**；不要只在 SQLite mock concurrency，也不要用 M03 workflow綠燈代替。

### 10.7 Same Campaign second active Session

同一 Campaign已有 active Session時第二次 Start拒絕，即使選不同 Characters。

Ended / abandoned後才可開下一 Session。

### 10.8 Late Join authority / validation

Active Session：

- current DM Controller late join Luna from same Roster成功。
- Owner但非 current DM → deny Late Join。
- 其他 DM authority但非 current DM → deny。
- retired/dead失敗。
- archived失敗。
- Room B Character失敗。
- 已被另一 active Session lease失敗。
- 加入後 participant / lease persistence正確。

### 10.9 End Session state preservation

Start前 snapshot一個 rich Character State：

- current HP / temp HP。
- conditions。
- prepared spells。
- spell slots / resources。
- hit dice。
- inventory。
- artificer state / feature modes（若 fixture適用）。

Session內先做合法 state改動；記住 end前 exact state。

current DM Controller End Session後：

```text
state_after_end == state_immediately_before_end
```

不能只 assert HP。

Leases已釋放；Session participant/history與non-null historical Seat references仍存在。

### 10.10 Abandon

Owner或 current DM Controller abandon：

- status abandoned。
- leases release。
- Current State不變。
- 不建立 replacement DM。

### 10.11 Restart persistence

Server restart後：

- active Session仍 active。
- participant assignments仍固定。
- current DM Controller identity仍固定。
- leases仍對應。
- Room access token若未 revoke仍可重新建立 context。
- ended Session不會重建 lease。
- archived historical Seat仍可被舊 Session reference。

## 20. P2 後永久保留的 regression

P2 關門後以下不再是「只有 P2才跑」：

1. Multi-Room isolation。
2. Room Character / Draft scope。
3. Roster same-Room invariant。
4. same Character multi-Campaign state sharing。
5. active Session Character lease collision。
6. Owner-controlled DM assignment + fixed DM Controller / Owner不能 takeover。
7. Session End state preservation。
8. Seat history archive / non-null historical FK。
9. Character JSON v1 backward import + immutable M03 unstable fixture。
10. standalone no-multiplayer import graph。
11. standalone character-only migration branch / SQLite schema allowlist。
12. Alembic dependency direction Web → Character only。
13. existing migration / launcher / smoke tests保持multi-head-aware，不回退到任何 repo-global single-head假設。
14. Room access throttle / heartbeat authorization boundary。
15. Legacy unscoped data primary claim UX保持 Owner-only、target-Room scoped，zero-Room auto-claim只作 bootstrap fallback。
16. 既有 P1/M01/M02 Character browser/API regression持續在 Web Room-scoped channel執行；Standalone regression不得取代 Web coverage。
