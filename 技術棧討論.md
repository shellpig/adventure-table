## 一、專案前提

Adventure Table 是一個：

- 輕量、桌上跑團優先的 D&D 5e 2014 VTT。
- Built-in Content 先使用 SRD 5.1。
- Human 與 AI 共用同一套 Game State / Game Actions。
- 外部 AI 透過 MCP / Site Tools 正式加入桌內當 DM 或 Player。
- Server 是唯一真實狀態來源。
- 支援長期 Campaign、Session、Character、Combat、Timeline、Snapshot 等持久狀態。
- 第一版是朋友間私人使用，不以大型 SaaS 或商業平台為目標。
- **網站本身不接 LLM API**：不保存模型 API key、不代付模型費用、不在 backend 自行呼叫 LLM。所有 AI 能力都來自使用者的外部 AI Session，透過 MCP / Site Tools 操作網站。
- **介面以繁體中文為主**；D&D / 系統關鍵字如 Action、Bonus Action、Reaction、Saving Throw、Concentration、Spell Slot、Initiative 等保留英文原文。

因此技術棧優先順序不是「可支援百萬使用者」，而是：

1. **規則層容易寫對、容易測。**
2. **Human UI 與 AI Tool 能共用同一套 backend logic。**
3. **Character / Combat / Campaign state 有可靠 transaction 與 persistence。**
4. **Permission / Visibility 有中央收口，秘密不能靠每個 endpoint 自己記得過濾。**
5. **Auth / scoped AI token 可撤銷、可驗證，不能事後補洞。**
6. **Undo / Snapshot 雖然晚期才做完整功能，但 P0 資料與 Transaction 模型不能把它堵死。**
7. **AI reconnect 後能重新取得真實狀態，不依賴舊 conversation。**
8. **Tactical Map 可以之後加入，但不能污染核心 Rules Engine。**
9. **部署與本機開發要簡單。**
10. **避免第一版過度架構。**

例如 PostgreSQL、Vite、MCP SDK 的版本在真正開工時再核對，不讓討論稿裡的數字永久綁死專案。

## 四、Frontend：React + TypeScript + Vite

### 4.1 React / TypeScript 為什麼保留

Adventure Table 是大量互動 UI：

- Character Sheet
- Character Builder
- Spell selection
- Inventory
- Player Cards
- Chat
- Dice / RollRequest
- Quick Combat
- Tactical Combat
- Map Editor
- DM Tools
- Adventure Import Review

React component model 適合這類重互動且元件重複度高的產品。

TypeScript 有助於：

- API contract 清楚。
- Character / Combat UI 少掉欄位拼錯。
- generated API client 有完整型別。
- AI coding agent 對 TS / React 支援成熟。

### 4.2 為什麼第一輪 review 後改用 Vite

原提案是 Next.js，但目前更推薦 Vite，理由：

- 產品沒有 SEO 需求。
- 高度 client-heavy，主要是登入後 Application。
- 真正 Game Server 已經是 FastAPI。
- 不需要 Server Components / Server Actions 承擔核心價值。
- Vite build 後可直接由 Caddy 提供靜態檔。
- production 少一個 Node server runtime。
- 可以更明確維持「Frontend 是 Client；FastAPI 是唯一 backend」。

Production 可簡化成：

```text
Caddy
├─ static React/Vite build
└─ /api + WebSocket proxy
        ↓
      FastAPI
```

這不是說 Next.js 不可用；只是目前需求下，Vite 的簡單性更有價值。

### 4.3 Frontend 不擁有 Game Truth

前端可以有 draft / local UI state，但以下不能只存在 client：

- HP
- Inventory
- Spell Slots
- Character Build
- Campaign State
- Combat State
- Formal Roll result
- committed Tactical position

Server 才是唯一 truth。

目前建議管理 Server State：

- Character

適合：

- right panel width
- builder current step

不適合承載 Server truth。

## 六、Backend：Python + FastAPI

### 6.1 Python 的真正優勢

第一輪 review 後，不再把「MCP 生態」當成 Python 獨有優勢；MCP 同樣有一級 TypeScript SDK。

目前保留 Python 的主要理由是：

- D&D 5e domain logic 可讀性與測試性。
- Pydantic 很適合大量 reference data / action / DTO validation。
- Character progression、numeric override、structural validation 等規則形狀很適合明確的 Python domain layer。
- pytest 適合大量 headless rules test。
- PDF / DOCX 等普通 document preprocessing 生態成熟。
- 使用者本身熟悉 Python。

典型 domain logic：

```text
calculate_proficiency_bonus()
validate_multiclass()
calculate_spell_slots()
resolve_attack()
apply_condition()
validate_feat_prerequisite()
resolve_rest()
resolve_reaction()
```

### 6.2 FastAPI 的角色

FastAPI 負責：

- HTTP API
- WebSocket endpoint
- Request / Response validation
- OpenAPI generation
- authentication entry point
- Human UI access
- MCP 與 backend service 的共同宿主／整合點之一

它不是 Rules Engine 本身。

推薦分層：

```text
HTTP / WebSocket / MCP Adapter
             ↓
      Actor Context
             ↓
       Authorization
             ↓
     Application Use Case
             ↓
    Domain / Rules Engine
             ↓
 GameTransaction / Repository
             ↓
         Persistence
```

## 七、Permission / Visibility — P0 必須立好的地基

這是第一輪 review 指出的最高優先缺口。

產品硬規則是：

> Secret DC、DM Notes、Hidden Monster、其他角色 private knowledge 等資料，不該看的 actor 根本不能收到。

因此不能使用：

```text
每個 endpoint 自己 query 完整 entity
↓
各自記得 remove_secret_fields()
```

這會隨 endpoint / WebSocket / MCP 增加而必然漏資料。

### 7.1 Authorization 與 Visibility 分開

至少分成：

```text
Authentication
→ 你是誰 / 這個 credential 是誰

Actor Context
→ role / seat / controller / session / scopes

Authorization
→ 你可不可以做這個 action

Visibility Projection
→ 這個結果你可以看到哪些欄位 / entity / event
```

例如：

```text
Full NPC Domain Entity
        ↓
project_for(actor_context)
        ↓
Player-visible NPC DTO
```

DM 可以拿到：

```text
Public data
+ Hidden identity
+ DM Notes
+ Secret knowledge
```

Player 只能拿到：

```text
Public / currently revealed data
```

### 7.2 所有 outbound adapter 共用同一套 projection

以下三種出口都必須經過同一 visibility boundary：

```text
HTTP response
WebSocket event
MCP resource / tool result
```

不能只保護 Web UI，MCP 又回傳 full domain entity。

### 7.3 測試要求

涉及 private data 時，除了 happy path，必須有負向測試：

- Player 收不到 DM-only 欄位。
- AI Player 收不到 secret data。
- 不同 Seat 不能拿到彼此 private knowledge。
- WebSocket event 也不能洩漏。
- MCP result 也不能洩漏。

完整實作細節到 `開發設計方針.md` 再定，但這個 architecture boundary 從 P0 就不能違反。

## 八、Authentication / Credential / AI Token

P2 / P3 才會完整出現 Room / Seat / AI join workflow，但 credential model 會影響 backend boundary，因此 P0 就應保留正確位置。

產品需要：

```text
Room Password
DM Key
Owner Key
AI Join Token
```

第一版不代表要做 OAuth / 大型帳號系統。

### 8.1 AI Join Token 特性

至少要能表達：

```text
token identity
role / seat scope
room / campaign / session scope（視實際設計）
issued_at
optional expires_at
revoked_at / revocation state
```

精確欄位到開發設計時決定，但必須滿足：

- Token 可撤銷。
- Human Take Back 後舊 AI Token 立即失效。
- Server 每次 formal action 都驗證 scope / revocation。
- AI 永遠拿不到 Owner Key。
- Credential 與 Controller connection state 分離。

### 8.2 Auth 與 Permission 不混在一起

```text
Credential valid
```

不代表：

```text
這個 action 一定被允許
```

Token 驗證後仍要進 Authorization / Role / Seat / Scope validation。

## 九、Undo / Snapshot 對 P0 的反向要求

完整 Undo / Snapshot / Restore 功能排在 P7，但 P0 的 Transaction / Persistence 模型不能讓 P7 只能推倒重做。

產品已要求：

```text
Undo Last Transaction
Restore Snapshot
Undo 不是刪歷史，而是建立 Revert transaction
```

因此 P0 開始設計 GameTransaction 時至少要保證未來可以支援：

```text
Transaction A
Transaction B
Transaction C
Undo C
→ Revert Transaction D
```

以及：

```text
Snapshot
→ Restore State
→ 後續 history 保留為 archived / inactive branch semantics
```

### 9.1 P0 不必做完整 Undo UI

P0 需要的是 architecture compatibility，不是把 P7 提前實作。

P0 design review 必須問：

> 現在的 mutation / transaction / persistence 設計，未來能不能實作 revert 與 snapshot restore，而不必重寫所有 domain write path？

具體採用 event sourcing、state diff、before/after snapshot、command log 或其他方法，現在仍可討論；**不要因為 P7 很晚才做，就讓 P0 mutation 變成無法追蹤的一堆任意 SQL update。**

## 十一、Database：PostgreSQL

Adventure Table 有強 relational structure：

```text
Room
Campaign
Session
Seat
Character
CharacterVersion
Combat
Combatant
GameTransaction
TimelineEvent
RollRequest
Item
Adventure
Scene
NPC
```

再加上 Transaction、Concurrent mutation、Referential integrity、Version history、Snapshot、Restore、Permission、Archive lifecycle，因此 PostgreSQL 比 document DB 更自然。

### 11.1 PostgreSQL + JSONB

不代表所有資料都要正規化成數百 table。

Relational core 傾向：

- Room
- Campaign
- Session
- Character
- Seat
- GameTransaction
- Timeline
- Combat
- credential / token identity

JSONB 可考慮：

- Custom content extensions
- Imported provenance metadata
- Partially structured feature payload
- Snapshot payload（是否用 JSONB 仍待設計）
- Rare custom rule extension

### 11.2 避免兩個極端

不要：

```text
每個 feature property 都拆成 table
```

也不要：

```text
整個 Campaign 塞一個超大 JSON blob
```

P0 開發設計時需要更精確定 relational / JSONB boundary。

## 十三、Reference Content 與 Runtime Content 的 Source of Truth

第一輪 review 後，這一點改成明確雙線，而不是模糊寫 Hybrid。

### 13.1 靜態 SRD / Custom Definition

```text
Git file = Source of Truth
DB = derived / indexed copy
```

例如：

```text
data/
├─ srd5.1/
│  ├─ races.json
│  ├─ classes.json
│  ├─ subclasses.json
│  ├─ backgrounds.json
│  ├─ feats.json
│  ├─ skills.json
│  ├─ spells.json
│  ├─ equipment.json
│  ├─ monsters.json
│  ├─ conditions.json
│  ├─ languages.json
│  └─ ...
└─ custom/
```

流程：

```text
File definitions
↓
Validate / Normalize
↓
Idempotent Import
↓
DB derived copy
```

要求：

- Import 必須 idempotent。
- Reference row 不靠 production DB 手工修改。
- 修改 reference content 應回到 Git file。
- DB 可建立索引、FK target、查詢最佳化，但不是原始真值。
- provenance / source version 要可追蹤。

### 13.2 使用者／跑團 Runtime Content

以下相反：

```text
DB = Source of Truth
```

例如：

- Quick Enemy
- Runtime NPC
- Runtime Scene
- Runtime Item
- Campaign Fact
- Save as Template
- Character current state
- Campaign current state

需要可攜時：

```text
DB
→ Export
→ Portable file/package
```

### 13.3 P0 SRD 導入

P0 仍應完成主要 SRD 5.1 reference data 導入，而不是只塞少量 fixture。

但：

> **資料已導入 ≠ mechanics 全部在 P0 自動化。**

Fireball definition 可 P0 完整存在；Tactical AoE geometry 到 P5 才做。

## 十四、MCP

### 14.1 MCP 是正式 Adapter

```text
Human HTTP/WebSocket ─┐
                     ├─→ Same Application Services
External AI / MCP ───┘
```

MCP 不是第二個 backend。

### 14.2 Python 不是因為 MCP 才選

MCP 有成熟的一級 TypeScript SDK，因此「要做 MCP」本身不是選 Python 的理由。

目前若 backend 採 Python，使用 Official MCP Python SDK current stable line 即可。

### 14.3 MCP types 不污染 Domain

```text
MCP protocol types
      ↓ adapter
Application DTO / Use Case
      ↓
Domain
```

Rules Engine 不依賴 MCP-specific object。

### 14.4 網站沒有 LLM

MCP Adapter 提供 tool / resource / event access；它不代表 backend 有模型。

例如 Adventure Import：

```text
External AI
→ 讀取 source / extracted text
→ 呼叫 importer MCP tools
→ 建 Draft / update Draft / answer warning
→ finalize
```

backend 可以做普通 document preprocessing（例如 PDF / DOCX text extraction），但不自行呼叫 LLM parse。

第一版沒有理由先建立獨立「LLM importer worker」。

## 十五、API Contract：OpenAPI → TypeScript 是強制 Pipeline

Python + TypeScript 雙語言的最大長期風險之一是 schema drift。

因此由「建議」升級為實作契約方向：

```text
API DTO / Pydantic
↓
FastAPI OpenAPI
↓
Code Generation
↓
Generated TypeScript client / types
↓
React Frontend
```

**禁止為同一 API DTO 長期手寫另一份 TypeScript mirror interface。**

Domain model 不必等於 API DTO：

```text
Domain Model
→ Visibility-safe API DTO
→ OpenAPI
→ Generated TS
```

CI 應能驗：

```text
generate API client/types
↓
git diff --exit-code
```

如果 backend schema 已改但 generated client 未更新，CI fail。

精確 codegen 工具到開發設計時再選。

## 十六、Realtime / Durable Event / Reconnect

需要 realtime 的場景：

- Chat
- RollRequest
- PendingAction
- Turn changed
- HP changed
- Combat event
- ReactionRequest
- AI / Human controller changed
- Session state changed

WebSocket 是 delivery / invalidation mechanism，不是 truth。

```text
GameAction
↓
Transaction commit
↓
Persistent state / durable event
↓
WebSocket notification
```

掉線後 client / AI 必須能重新 fetch 真實狀態。

### 16.1 Durable event 先用 PostgreSQL

規格要求 AI 可以：

```text
get_pending_events()
wait_for_event(timeout)
```

第一版朋友團規模下，先讓 durable pending event 存 PostgreSQL。

WebSocket / long polling / MCP wait 是 delivery mechanism。

Server restart 不應讓待處理 Reaction / Roll 等重要事件消失。

真的遇到 scale / latency 問題，再評估 Redis / NATS / RabbitMQ。

---

## 十七、i18n / UI Language

產品已定：繁體中文為主要介面，但 D&D / 系統關鍵字保留英文。

P0 前建議先確立最小 i18n boundary，避免字串散落在 component 裡難以整理。

不一定要一開始做多語系切換 UI；至少做到：

- default locale = `zh-TW`。
- 使用集中 message/resource 機制。
- 規則內容與 UI chrome 分離。
- 英文關鍵字可在中文句子中保留，不做強制全翻譯。

具體 library（如 i18next、react-intl 或其他）仍可討論，不需要因為 i18n 就引入重型框架。

## 十八、Tactical Map 技術延後到 P5 前決定

原提案直接選 PixiJS，第一輪 review 後改成 **Deferred Decision**。

原因：

- Tactical Combat 是 P5。
- P0～P4 尚未提供足夠真實互動資料來判斷 renderer / editor library。

- Map Editor 可能更重視 selection、handles、drag、hit detection、shape editing。

P4 Quick Combat 完成後，再依實際需求比較：

- Konva
- PixiJS
- Native Canvas
- SVG / hybrid
- 其他當時成熟方案

評估項目：

```text

Wall / Door editor
Terrain paint
Path preview
AoE preview
Zoom / Pan
Touch
Hit detection
Selection handles
Performance
React integration
```

不論最後選哪個 library：

> Rules Engine 不知道 renderer library 存在；client movement draft 也不是 server true position。

## 二十三、P0 / P1 對底層架構的要求

P0：Character Core + SRD / Rules Foundation。  
P1：Character Builder Complete。

P0 architecture 必須一開始就能支援 P1，不能因 P0 尚未有完整 Builder 而簡化成不可擴充形式。

P0 至少要能表示：

```text
Human
Fighter 5 / Wizard 5
Character Level 10
```

即使該資料在 P0 是 fixture / developer import。

因此：

- Character 不可寫死單一 Class。
- 保存 class level progression order。
- character_level 與 class level 分離。
- Feature 能標記 source。
- Spell 能標記 source class / feature。
- Spell slot 與 spell access 分離。
- Build 與 Current State 分離。
- Character Version 能演進。
- SRD / custom definition 與 runtime character state 分離。
- mutation path 不可堵死未來 Revert Transaction / Snapshot Restore。
- outbound data 不得繞過 Visibility Projection。
- API DTO 必須能經 OpenAPI 生成 TS client，而不是靠兩邊手寫同步。

P1 才要求從 UI 正式完成合法 progression。

## 二十五、目前最大技術風險

### 25.1 Permission / Visibility 漏資料

如果每個 endpoint / MCP tool / WebSocket handler 自己過濾 secret，遲早洩漏。

對策：中央 Actor Context + Authorization + Visibility Projection。

### 25.2 Transaction 模型堵死 Undo / Snapshot

如果 mutation 只是任意 SQL update，P7 會很痛苦。

對策：P0 就要求 mutation 有一致的 GameTransaction boundary，並在設計時驗證未來 revert / snapshot restore 可行。

### 25.3 Auth / Token 事後補

如果 MCP 先只靠「知道一個 URL」就能操作，之後很難補安全邊界。

對策：P0 架構就保留 credential → actor context → scope → authorization。

### 25.4 Rules Engine 資料模型過早寫死

例如假設單一 class、單一 spell slot pool、spell 只有單一來源，P1 Multiclass 立刻重構。

### 25.5 Reference Data 與 Rules Logic 混在一起

不要到處寫：

```python
if class_name == "fighter" and level == 5:
    add_extra_attack()
```

需分清 Content Definition、Structural Rule、Calculation Engine。

### 25.6 Frontend 變第二個 Game State

Client local mutation 不能凌駕 Server truth。

### 25.7 WebSocket 被當 Event Store

Realtime 連線可能掉，重要狀態必須能從 persistence 重建。

### 25.8 AI Adapter 污染 Domain

Rules Engine 不應出現：

```text
if controller == chatgpt
```

Human / AI 差異只在 authentication、adapter、connection、context delivery；Role / gameplay permission 共用。

### 25.9 Adventure Importer 把外部 AI Output 當 Truth

Importer 仍必須走 Draft / Validation / Review / Confirm。

### 25.10 Tactical renderer 過早定案

P5 前資訊不足，不應為 Pixi / Konva 提前扭曲資料與 component 架構。

## 二十七、希望下一輪 Reviewer 特別挑戰的問題

第一輪已大致收斂 Vite、SRD truth、Permission/Visibility 等問題。下一輪更希望挑戰以下項目。

### A. Authorization / Visibility architecture 是否足夠？

請檢查：

- 是否需要 Policy Engine？
- role / seat / controller / knowledge visibility 如何避免散落？
- HTTP / WebSocket / MCP 如何保證同一 projection？
- 什麼資料必須在 query 前就限制，什麼可以 projection 後限制？

### B. GameTransaction 怎樣才能支援 P7，而不過度設計？

候選可能包括：

- before / after snapshot
- semantic operation payload
- domain events
- append-only transaction log
- hybrid

不要因為需要 Undo 就直接推 event sourcing；也不要完全無視未來 revert。

### C. Auth / scoped AI Join Token 最小安全模型

請評估：

- token storage / hashing
- revocation
- expiration 是否必要
- Room / DM / Owner credential 怎麼分
- session scope vs seat scope
- reconnect

目標是朋友私用但不亂來，不是打造企業 IAM。

### D. PostgreSQL relational / JSONB 邊界

特別是：

- Character build
- Feature definition
- Spell definition
- Custom content
- Snapshot
- GameTransaction payload

### E. Python + TypeScript 雙語言成本

目前已決定若採此組合，就必須 OpenAPI codegen。

請再評估有沒有其他隱性同步成本，或是否值得改 TS backend。

### F. i18n 最小方案

只需要以繁中為主、未來可擴充，不希望一開始堆太重的 internationalization framework。

### G. P0 還有沒有其他「晚期功能反向要求早期地基」？

已知：

- P1 Multiclass → P0 Character model
- P2/P3 Auth / Visibility → P0 backend boundary
- P7 Undo / Snapshot → P0 Transaction model
- P5 Tactical → Quick Combat 不依賴 geometry

請找其他類似缺口。
